## 先读这几条

改代码前先认下这几条，它们不是风格偏好，是踩过坑之后定下来的：

1. **所有云端调用走一条单线程串行队列**（`core/jobs.py`）。`requests.Session` 不是线程
   安全的，上游自带节流；自己开线程发请求迟早出乱序或限流。
2. **子线程绝不直接回调 UI**，只把结果塞队列，主线程定时取走执行。
3. **写入用乐观 UI + 版本号**（`core/store.py`），否则"点一下绿了又弹回去"。
4. **设备特判一律按型号**（`core/adapters/<厂商>.py`，键是 `DeviceNode.model` 精确串）。
   **唯一例外是文案**，允许按品类，理由见[枚举文案层](#枚举文案层云端原话--界面短名)。
5. **滚轮只滚页面，不改设备参数**。新控件也必须守，见[交互约定](#交互约定滚轮只滚页面)。
6. **不确定能不能删的东西，先证明"没人要"**（`scripts/pe_imports.py`），见[打包](#打包成-exe-的实现)。
7. **下"做不到 / 只能抓包 / 得换方案"这类结论之前，先翻
   `docs/reference/README.md`**。那是已经花过时间调研的结论索引（四档状态 + 一张
   "还没定论的"清单）。2026-11-11 栽过一次：极客版取码 11-07 就实测通了（云端 RPC，
   不用抓包），做入口时又按"只能抓包"重新研判了一遍，还去问了用户。

## 调研结论存在哪（下结论之前先看）

调研结论不是写在对话里就算数的，必须落到三处，**缺一处就等于没做**：

| 落点 | 写什么 | 例子 |
|---|---|---|
| `docs/reference/<主题>.md` | 数据、实测过程、接口契约、边界、**未验证项** | `mijia-geek-login-code.md` |
| `docs/reference/README.md` | 一行登记：一句话结论 + 状态 + 落地位置 + 关联待办 | 索引表 |
| `TODO.md` | 对应的待办条目（`待研判` / `待排期` / `已落地` / `明确排除`） | 「数据与账号能力」 |

**状态只有四档**，写清楚能省掉下一轮研判：

- **已落地**：代码里有，能指到文件与验证脚本——别重复实现。
- **待排期**：结论已通、功能没做（或只做了探针）——可以直接动手，不用再调研。
- **明确排除**：试过或算过，收益不成立——**不要重开**，除非前提变了。
- **仅参考**：视觉 / 规格 / 行为契约，不产生功能。

两条纪律：

1. **结论变了就改原文档 + 改索引状态**，不要另起一份新文档——同一件事有两份文档时，
   读者只会看到过期的那份（`mijia-geek-login-code.md` 里"暂不实现 / 按型号找 did"
   两处过期表述就是这么来的，2026-11-11 已就地更正）。
2. **"还没定论的"要显式写出来**（索引第五节）。留白最容易被读成"没研究过"，
   于是又从头查一遍。

## 与参考项目的关系

`huanyuejue/MiHome-Windows`（0.5.0 版）是起点参考项目，能力层写得扎实，本项目**沿用了它的三个核心判断**：

1. 所有网络调用进**单线程串行队列**（`requests.Session` 不是线程安全的，且上游自带节流）
2. 子线程**绝不直接回调 UI**，只把结果塞队列，主线程定时取走执行
3. 写入用**乐观 UI + 版本号**，避免"点一下绿了又弹回去"

界面层完全重写。参考项目是"一个规格属性 = 一个控件"堆在同一张面板上，所以每台设备
长得都一样；本项目建了一层**品类 → 卡片形态**映射，并按米家 UED 的分层原则
（高频在卡片、低频进详情、其余折叠）重排了信息。

## 数据从哪来

| 环节 | 来源 | 说明 |
|---|---|---|
| 登录 | `account.xiaomi.com` 扫码 | 凭据写到 `~/.config/mijia-api/auth.json`，与 mijiaAPI CLI 共用 |
| 家庭 / 房间 | `/v2/homeroom/gethome_merged` | 设备列表本身不带房间，只能靠 `roomlist[].dids` 反查 |
| 设备列表 | `/home/home_device_list` + 共享设备 | 云端下发的 `spec_type` 是一切能力的钥匙 |
| 设备能力 | `miot-spec.org` 原始 JSON | 自己解析，保留 `unit` / `format` / `access` / `comment` / `events` |
| 实时状态 | `/miotspec/prop/get` | 批量读，单请求实测可带 300 条 |
| 控制 | `/miotspec/prop/set` / `/miotspec/action` | 写属性用 `value`、执行方法用 `in`；混用会报 `-704220025`（见踩坑清单） |
| 场景 | `GetSimpleSceneList` / `NewRunScene` | 只给"能在智能页手动执行"的那批 |
| App 自动化 | `AppSceneService/GetSceneList` | 触发 / 条件 / 动作 / 启用状态全在，同账号共享；**必须带 `app_version:12` + `get_type:2`**，否则少给手动场景 |
| 设备事件 | `/miotspec/event/get` | 每个 `(did, siid, eiid)` 的**最近一次**发生 + `updateTime` + 参数；body 必须 `{"params":[…]}` |
| 中枢虚拟事件 | 同 `prop/action`：`siid 4 / aiid 1` | 发一个名字就能触发米家里监听它的自动化；`siid 4 / eiid 1` 是它"发生"的事件 |
| 产品图 | `/v2/productconfig/get_icon` | 302 跳转到 CDN，168×168 透明底 |
| 摄像头画面 | 本机 `go2rtc` + `xiaomi://` 源 | 局域网直连；跨网时前面多一层 `core/relay.py` 代理，见下节 |

**后三行是 2026-11-10 的调研成果**（自动化 / 事件 / 虚拟事件，完整实测见
`docs/reference/mijia-automation-events.md`）。要点：米家 App 的自动化在账号里存着，
`GetSceneList` 能读全；"米家发生了一件事"以前只能靠轮询属性猜，现在有 `event/get`
能直接拉（**只保留最近一次**，所以轮询间隔就是事件的分辨率）；中枢网关的「虚拟事件」
就是规格里的 `siid 4` 服务（**spec 版本 3 才有**，`miot-spec.org` 的 `:1` 里没有），
发一次 `action` 实测 253 ms，发出去到云端可见 356 ms。三件事都走云端账号接口，
**不是局域网直连**，与「局域网 miIO 明确排除」那条决定无关。

**我们只有轮询，但"米家没有推送"这句话是错的**，得把区别说清楚：小米云有一套 MQTT 推送
（`cn-ha.mqtt.io.mi.com:8883`，TLS；主题 `device/{did}/up/properties_changed/{siid}/{piid}`、
`device/{did}/up/event_occured/…`、`device/{did}/state/#` 是上下线），米家 App 与官方 HA 集成
用的就是它——所以按一下实体键，App 里基本 1 秒内就变，那不是"1 秒轮询"，是设备把变化推给
云端、云端推给订阅者。App 退到后台就不更新，是系统把那条长连接挂起了，回到前台重连 + 重拉
一次快照，看起来"一打开就是新的"。

**这条通道我们拿不到**，两条都卡死：（1）它的 MQTT 密码是 OAuth 换来的 service token，
client_id 只发给 HA 集成，我们的登录是米家 cookie，没有这条路；（2）那套实现（`XiaoMi/
ha_xiaomi_home`）的许可证写明"仅用于 Home Assistant、非商业"，并且**明确不授权用于开发
APP / Web 服务**——本项目是桌面 App，属于被排除的那类，只学思路、不抄码、不进发行包
（与 README 的致谢口径一致）。

**2026-11-11 补充实测：这条通道其实能通，上面「拿不到」要改一半。** 探针项目在仓库外
（`e:\Code\_mqtt_probe`，**不属于本仓库交付物**，这里只记结论）：

- **可通**：55 台设备、约 1500 条消息、端到端 **< 1 秒**；payload 是纯 JSON，
  `siid / piid / eiid` 与 MIoT 规格一致。
- **订阅必须按设备白名单逐台订阅**：通配符会被 `SUBACK 135 Not authorized` 拒绝。
- **实投 QoS 为 0**（申请 2），不能当可靠队列；`retain` 全为 `false`。
- **拿不到设备上下线**：`state` 主题零消息，这是当前最大的缺口。
- **鉴权**：`expires_in=259200`（3 天）指的是 access_token；refresh_token 单次使用、
  每次刷新强制换发，持续运行就是一条永续滚动链，日常不需要人工授权。官方 HA 集成把
  到期时间记为 `now + expires_in × 0.7` 提前刷新，刷新失败弹持久通知要求重新认证。
- 观察到个别设备异常高频上报：蒸烤箱 `chunmi.oven.x14`（did 828487133）的腔体温度约
  每 0.4 秒一条，单窗占比 93%，订阅时会把通道淹没。
- **许可证那条判断仍然成立**：只学思路、不抄码、不进发行包。程序**本期仍未接入**。

上游能给我们的是 HTTP：`/miotspec/prop/get` 批量读（单请求实测可带 300 条）。所以实时性靠
两件事撑：只轮询卡片上真的会显示的属性（约 130 条，一批发完，一个往返 0.3 秒左右），
以及 3 秒一轮的间隔。**想量"我们这条路到底多快"**，用
`scripts/probe_latency.py`：它按指定间隔读一台设备的全部可读属性，把每次变化的时间、
云端 `updateTime` 距读到的秒数、每轮往返都打出来——按一下实体键就能看到"设备→云端→我们"
整条链路的真实延迟，也是判断"要不要加频率"的直接依据（往返 0.15 秒时 1 秒轮询
技术上可行，代价是请求量三倍且频控没有保证；**2026-11-10 用户已明确不做这类压测**，
所以按保守值设计，不再往 1 秒压）。

**2026-11-11 再次确认：轮询提速不做，维持前台 3 秒 / 托盘 15 秒。** 两条理由：设备上报
是**设备→云的上行**、走设备自己的配额，与客户端→云的属性轮询不是同一配额池，不能拿
"设备上报很快"推论"客户端可以读得更勤"；而且端到端 <1 秒的推送通道已经实测存在（见上），
轮询只是兜底，提速收益接近于零，不值得拿账号去压测。

> **2026-11-12 补一档"只在需要时快"**：常态仍是 3 秒 / 15 秒，但**发过写指令之后的 5 秒**
> 压到 0.5 秒一轮（`BURST_MS` / `BURST_HOLD_MS`），见「发过指令之后的 5 秒」。这不是
> 提速常态，是把频率花在"用户刚点完、正在盯着看结果"那几秒——那几秒之外的几倍频率
> 换不来任何可感知的收益。

**还有一条"技术上存在但我们不做"的路：局域网 miIO 订阅。** 云端设备列表里每台设备都带
32 位 `token` 和 `localip`（`tree.DeviceNode.token` / `localip` 已经在用了，摄像头取流就是
按 localip 直连），miIO 的 UDP 54321 上报是设备主动推，局域网内几十毫秒、不占云端额度。
**2026-11-10 用户决定明确排除**：它要求按品类 / 型号各写一套本地会话（握手、token 校验、
上报解析），而设备库是"每台设备一套"的，这个程序一旦装到别人家里，绝大多数型号都没有对应
实现，等于把"通用客户端"降级成"作者自己那几台设备的客户端"——收益（秒内响应）远小于代价
（永远追不上的型号清单）。落款与理由见 `TODO.md`「已作废 / 已取消（不计入待办）」。
**别再拿它当"以后能提速"的退路**：想更快只有提高 HTTP 轮询频率这一条，而那是频控风险，
不是能力问题。

轮询的**范围**由 `store.poll_refs()` 决定，是"在线设备的卡片属性"的并集：`CardSpec` 的
`controls`（卡片上那个主控件）、`metrics`（卡片上的只读读数）、`gangs`（多键开关的每一
路）、以及型号级 `extra`（只读、不渲染，但要用它判断状态，如挂灯的 `scene-mode`）。
`advanced`（"更多功能"里的属性）**不参与轮询**，打开详情页时才按需读一次。

频率换算：3 秒一轮 = 20 轮/分 = **1200 轮/小时**；`DEFAULT_CHUNK = 300` 之后，130 条属性
**一个请求就能发完**，即约 1200 个批量读/小时（原来是 2400）。三条自保：
上一轮没回来就跳过（`store.polling` 闸门，请求不堆叠）、连续失败指数退避（`1s × 失败
次数`，封顶 30 秒）、看不见的时候降频（见下节）。

> **`DEFAULT_CHUNK` 为什么从 120 提到 300**（2026-11-10 实测）：200 条真实属性各跑 3 次，
> `chunk=120` 走 2 次串行请求 510–620 ms，`chunk=300` 走 1 次 261–357 ms，返回条数一样。
> 分批是**串行**的，每多一批就多付一次往返，所以"批大一点"既省请求也快一倍。代价是
> 整批失败时影响面从"丢一半"变成"丢一整轮"，但失败本来就是网络层问题，调用方一律保留
> 旧值 + 退避，这个代价可以接受。
>
> 米家云端对非官方客户端的频控没有公开保证。这个量级对一个云服务不算高，但它是**持续**
> 的——所以托盘常驻之后必须有降频档，不然关着窗口在托盘里待一整天，等于替用户按了
> 一万多次批量读。**再往下压就不是技术问题是风险问题**，用户已明确不测、不冒这个险。

**请求语言钉死 `zh_CN`。** 不钉的话，中文 Windows 上 `locale.getlocale()` 返回的是一个
显示名（`Chinese (Simplified)_China`），服务端认不出就回退英文，卡片上全变成
"Xiaomi Smart Wall Switch (3 Gang)" 这类厂商默认名。

**目前是单账号。** 凭据只有一份 `auth.json`，换号要退出再扫码。多账号同时在线是可行的
（上游 `mijiaAPI(auth_data_path=...)` 支持自定义路径），方案与隔离细节记在 [TODO](../TODO.md)。

## 规格解析与型号适配

### 型号级适配：只有挂灯会把「无」显示出来

米家显示器挂灯 1S 有**两个**和模式有关的属性，含义不一样：

| 属性 | 可写 | 实际含义 |
|---|---|---|
| `mode`(2,5) | 是 | 用户**上次点过**的预设。手调亮度/色温后它不会变（实测一直停在 5/6/7），拿它当"当前生效模式"会让下拉一直假亮着 |
| `scene-mode`(3,9) | 否 | **真正生效**的预设，会被任何亮度/色温写入清成 0（0 = 无激活项） |

所以读 `scene-mode` 当判据、写仍然走 `mode`。数值 5–9 两边一致，可以直接当枚举值用。

**这件事按型号做，不按品类。** "手调亮度后 `mode` 不变"是这台设备实测出来的行为，
其它灯的 `mode` 会不会跟着变完全没验过；按品类推给所有灯会把别人的选中态弄坏。所以
`schema` 之外单独有一张"型号 → 属性"的表，放在 `mihome/core/adapters/`，**一个厂商一个
文件**：

```
mihome/core/adapters/
  __init__.py   汇总各厂商文件 → MODEL_ADAPTERS，对外只暴露 find_adapter(model)
  base.py       ModelAdapter / TextLayer 结构 + 型号格式校验 + 合并时的重复检查
  categories.py 类别级**文案**覆盖（按 URN 的 category，如 lock）——见下一节
  yeelink.py    yeelink.* 的适配规则
```

一条规则就是一条记录，键是 `DeviceNode.model` 的**精确字符串**：

```python
"yeelink.light.lamp22": ModelAdapter(
    extra=("scene-mode",),          # 额外参与轮询、不在卡片上渲染
    mode_active="scene-mode",       # 模式高亮的判据
    note="mode(2,5) 手调亮度后不变，真实预设看只读的 scene-mode(3,9)",
)
```

按厂商分而不是按品类分，因为查找键就是型号、而型号第一段就是厂商：`yeelink.py` 只管
`yeelink.*`，不会让文件名天天暗示"灯都差不多"。导入期会校验型号格式（必须
「厂商.品类.型号」、不能带前后空格）和重复登记（同一型号写两遍直接报错）——写错了当场
炸，不会拖成"某台设备莫名没有适配"。

新增一个型号 = 在对应厂商文件里加一条，通用逻辑一行不用改。新增一个厂商 = 新建
`<厂商>.py`，再在 `__init__.py` 的 `_MODULES` 里加一行 import 与一项（**不要改成
`pkgutil` 自动发现**：打包成 exe 时静态分析看不到动态导入的模块）。

`build_card(model=...)` 用 `find_adapter()` 命中后把它解析进 `CardSpec.extra`（只读、要轮询）和
`CardSpec.mode_active`（界面判据）。`extra` 由 `store._card_props` 自动并入轮询与寻址，
所以加一个型号适配不用碰 store。属性在 spec 里找不到、或运行时读不到时，两者都是空的，
一切退回默认行为（按 `mode` 自己高亮），不报错也不空高亮。

### 「无」不是一个枚举项，是一段客户端占位文案

往 `value_list` 里塞一个假选项看着省事，但下拉的每一项都能被 `currentIndexChanged` 写出去
——设备不认这个值，它还会被当成枚举值回读回来。所以做法是 `setPlaceholderText("无")` +
`setCurrentIndex(-1)`：框里显示「无」，列表里仍然只有设备给的那几项，用户点任何一项发出的
都是正常写请求。不在枚举里的自定义场景（1–4）和流光（10）同理，显示「其他」。

卡片上的模式胶囊走同一套判据（`CardChips.set_active`）：值为 0 时整排不选中，而不是
硬选某个值。

### 小爱音箱的文字指令：能力在，但 aiid 按型号不同（2026-11-11 落地）

顶栏那条指令条（`ui/speaker_bar.py`）就是这块的界面，底下是 `core/speaker.py`。
设备规格里：

- `wake-up`：**无入参**，只负责唤醒（让音箱进入聆听）。
- `execute-text-directive`：入参是 **`[文本, 是否静默]`** 两个。

**aiid 跨型号不一样**，所以一条 iid 都不许写死，只能按 action 的**名字**查：

| 型号 | `spec_type` | 服务 siid / 文本 aiid | wake-up aiid |
|---|---|---|---|
| 小爱音箱 Pro | `lx06` | 5 / 5 | 3 |
| Xiaomi 智能音箱 Pro | `oh2p` | 7 / 4 | 1 |
| 智能家庭屏 6 | `x6a` | 7 / 4 | 1 |

三处踩过的细节，改这块前先看：

1. **`wake-up` 也跨型号**（3 vs 1）。只按 `execute-text-directive` 查会漏掉它，两个
   action 都只能按名字解析。
2. **`text-content`(piid 1) 与 `silent-execution`(piid 2) 的 `access` 是空数组**。它们
   只作为 action 入参存在，不是可读可写属性 → 能力探测走 `spec.writeable()` /
   `prop_names()` 一个都认不出来，必须看 `ActionSpec.in_piids` 再回服务里按 piid 取名字。
3. **实参顺序不能假设**。`in_piids` 就是实参顺序，但它是数据不是常量：按 piid→名字
   映射后再拼 `in`，否则换个固件版本会把"静默"塞进"文本"里。名字全认不出时退回米家
   的实际顺序 `[文本, 是否静默]`。

服务名在三个型号上都叫 `intelligent-speaker`（URN 第 4 段）。固件改名的退路是：
先搜这个服务，找不到再全服务搜同名 action。

**发出去的时候参数键必须叫 `in`**（`{"did","siid","aiid","in":[文本, false]}`）。
2026-11-11 首次真机实测就是栽在这：`Client.run_action` 沿用了属性那套 `value`，
云端在 action 上只认 `in`，于是"0 个参数 vs 需要 2 个"→ `-704220025`，界面提示
「发送失败」，看着像设备不支持，实际 key 名错。细节见文末踩坑清单。

改完当天真机验收通过：`lx06` 发「现在几点了」`code 0`、203 ms（静默一次），
随后用户在界面上发同一条，**音箱收到并开口回复**——默认非静默路径也通。
所以这条链路只剩"唤醒"（`wake-up`）没在真机上按过一次，文字指令本身已无未知。

**文本清洗**（`speaker.clean`）不是可选步骤：米家 App 的自定义指令只允许中文、英文与
四种中文标点，我们按白名单清洗并**把剔除的字符报给用户**（toast），不静默吞掉。
数字刻意放行——「音量调到 20」离了数字说不通，剔掉会静默改掉语义。200 字符的上限在
`textChanged` 里收口：`setMaxLength` 到点会**静默**截断，用户看不出为什么少了一段；
重载 Python 的 `QLineEdit.insert()` 也拦不住——键盘输入与 `paste()` 走的是
QWidgetLineControl 的内部路径，绕不到 Python 层。

界面侧的三个约定：

- **指令条与警告条占同一条横带**（`ALERT_MARGIN_X/TOP` + `AlertBar.H`）。警告条是不进
  布局的浮层，出现时会正好压住指令条——这是 2026-11-11 定下的预期，别去调解层级。
  左右边距取 28（不是原来的 24），为了和 `WallView` 的 28px 内容边距对齐。
- **目标音箱离线时只禁输入框，不禁左侧选择器**。禁选择器会让用户卡在离线设备上，
  连切走都做不到；名字直接标「（离线）」说明原因。
- **提示条复用 `tooltip.TipBubble`**：新增了 `show_toast(text, anchor, ms)` 走"给位置 +
  定时自己收"的用法，不再依赖鼠标 hover。`TipManager.show_toast` 是它的入口。
- **一次性提示有两条路，别混用**（`tooltip.toast` / `tooltip.toast_top`）：
  - `toast(anchor, ...)` 锚在控件下方，是"这个控件刚才做了什么"的回声（指令条发送
    反馈走这条）。它**程序失焦即收**（`TipBubble._on_app_state`）——它是 `Qt.ToolTip`
    顶层窗口，**会盖在别的程序上面**：用户切走了，这条提示就没有读者了。
  - `toast_top(anchor, ..., kind=)` 落在**屏幕上沿往下 18%、横向居中**，是"刚才那件事
    的结果"（极客版取码走这条）。它**钉住不收**（`_pinned`）、13px + 左侧圆点定色
    （成功薄荷绿 / 失败警告红，边框跟着染）。用户点完按钮浏览器立刻抢焦点，锚在卡片
    上的提示只活在那 0.2 秒里，等于没有。
  - **钉住期间是独占的**：`TipManager._enter` 不再 `_dismiss()`、`_on_timeout` 不弹悬停
    提示、滚轮/点击/`WindowDeactivate` 也不收。这条是实测出来的——`processEvents()`
    里一个排队中的 `Enter` 就能把刚弹出来的通知踢掉，而代码里没人"叫它隐藏"。
  - 程序失焦也看不见的那次教训留下的规矩没变：**提示要么跟着读者走，要么别挡路**。
- **选音箱是一块横向设备面板，不是菜单**（`_Panel`，2026-11-11 按参考图改）：产品图
  56px + 名字横排，像启动器一样一眼认得出是哪台；文字菜单十行里认设备太慢。图标从
  44px 放大到 56px（用户反馈"小得像一排徽标"）：产品图才是认设备的主线索。一排方块
  **等宽**（按最长的名字统一），各自按名字算会出现 111/88/111 这种参差，图标间距忽宽
  忽窄。它是带 `Qt.Popup` 的独立顶层窗口，必须自己透明（`WA_TranslucentBackground` +
  去边框 + 去系统阴影），否则圆角外面还有一块方底——和 `ui/menu.py` 顶部那段是同一个坑。
  **它不进布局**，所以条高 48 与警告条那套几何（`_place_alert`）一个字都不用改。
- **「静默执行」是全局偏好，不是某台音箱的属性**，所以不塞进 picker 菜单：那会读成
  "这台的静默"。它只影响"这一条怎么发"，跟着设备选择放在面板**左下角**（参考图位置），
  半夜想安静一下不用翻两层设置。状态存 `Prefs.speaker_silent`（v10），默认**关**。
- **静默行刻意做弱**：11px 弱色文字 + 16px 勾选框（`_QuietCheck`），不复用设置页那颗
  44×24 绿色胶囊。第一版用了 `ToggleSwitch`，结果它比面板里任何一台设备都抢眼（用户
  原话"存在感很强"）——静默只是修饰语，不该和"选哪台"抢同一层注意力。关着时文字走
  `text_mute`、开着才提到正文色，颜色本身就是状态提示。

## 多键面板：转无线（2026-11-12 落地）

米家里可以把某个按键设成**「转无线」**：那一路继电器**常通**（一般是为了给智能灯一直
供电），物理按键不再切继电器，只发无线事件。面板上如果还能点它，轻则点了没反应
（写一个固件不认的 `on`），重则把给灯供电的那一路断掉。

### 判据：`switch` 服务的 `mode`，**逐路独立**

| 服务 | 属性 | 值 | 含义 |
|---|---|---|---|
| `switch`（左/中/右键各是一个服务） | `mode`(N,**2**) | 0 | 有线：继电器跟着按键 |
| | | 1 | 仅无线：继电器常通，按键不发有线事件 |

三条必须守住的：

1. **只在同一个 `switch` 服务里找 `on` 和 `mode`。** `switch-sensor` 也有个叫 `mode`
   的属性，值列表是「极速单击模式 / 多功能模式」，宽匹配（`spec.find("mode")`）会
   随机命中它，把按键手势模式当成有线无线。见 `catalog._gangs`。
2. **值不写死 1。** 各家文案不同（「无线开关」/「无线模式」/「有线和无线开关」），
   判据是**含「无线」且不含「有线」**，并且**恰好一项命中**才采信；命中两项（歧义）
   或零项（电小酷插座 USB 那个「均衡分配/C1高效模式」）一律当"没有这个能力"。
   认不准就不锁——宁可多点一下，不能把有线键锁死。见 `catalog.wireless_value`。
3. **逐路判，不按设备判。** 实测 1103 卫生间三开单控只有左键是 1（中键是排气扇、
   右键都有线），领普三键只有中键是。用"这台设备有没有 mode 属性"当判据会错得很离谱。

### 落地

- 模型：`Gang` 多了 `mode` / `wireless_value`，判据是 `Gang.is_wireless(values)`。
  `store._card_props` 把每一路的 `mode` **并入轮询**（同一次请求，每台多 1–3 个属性），
  所以设备侧改了设置界面 3 秒内跟上，不用重开。
- 卡片：那一路画**虚线框 + 右上角无线标记 + 灰字**，不填品类色（填了和"开着能关"的
  键分不清）。点它只吐一句提示、**不发写请求**，光标不变手型；`_hit` 仍然命中它，
  否则点击会落到卡片主体上变成"打开详情"。
- 详情页：行名写成「左键（转无线）」，开关置灰（`ControlRow.set_enabled(locked=True)`）。
  **不要用 `write=False`**：属性本身是可写的，是 `mode` 不让写；把 `write` 定死之后
  "设备侧改回有线"这一行就永远解不开（`verify_gang_wireless` 有这条断言）。
- 统计口径：无线路的继电器恒通是"给灯供电"，不是"这盏灯开着"。`DeviceState.power` /
  `any_on`、房间标题的「N 台开启」都跳过它，`Store.set_power_for_devices` 也不下发它。
- 副标题：有无线时换紧凑写法（`3 路 · 1 开 · 1 无线`、`3 路 · 全关 · 1 无线`）。
  原来的 `3 路 · 1 路开启 · 1 路转无线` 在 138px 宽里会被省略号切成半句（实测 136px
  才勉强放下「全部关闭」那一版）。

### 样式：「隐藏转无线」

右键「卡片样式」里的第二项（`小卡 1×1：隐藏转无线`，id `switch_wired`）：body 只画
**实际控制通断**的那几路，剩下的按键按数量重排——三键里中键转无线就摆成两键布局；
一路都不剩（单开整块转无线）就退回产品图，不再画一块点不动的内容带。

- 可见性判据是**静态能力**：面板上至少一路同时有 `mode` 和认得出的 `wireless_value`。
  不看运行时值——样式菜单不能跟着轮询变，否则设备侧改一次设置，菜单里就凭空多出或
  少掉一项。
- **读按键只有一条入口**：`DeviceCard._gangs()`（`hide_wireless` 为真时过滤）。绘制、
  命中、副标题、点击处理全部走它；别在别处再直接读 `card.gangs`——那会画出一个
  点不到的键，或者算出一个和画面矛盾的"3 路"。
- 副标题按**画出来的路数**统计（`2 路 · 1 路开启`）；剔空时写 `N 路 · 全部转无线`，
  解释这张卡为什么是产品图。
- 点击行为不变：可见的有线键照常写；转无线那几路本来就不写，只是在这个样式下
  干脆不出现。
- 全部有线的面板选它 = 标准卡，没有差别（`verify_switch_wired_style` 有断言）。

### 边界

- 没有 `on` 可写属性的服务不算一路（`_gangs` 的既有条件），所以只带 `mode` 的服务
  不会被误当成按键。
- 插座（`plug`）的 `switch` 服务也可能带同名 `mode`（优智者那只就是 1），但插座走
  电源键布局、不走 `_gangs`，不受影响。
- **未验证**：转无线那一路写 `on` 之后固件到底怎么反应。没有实测，也不打算实测——
  代价可能是断掉常通那一路。这里选择"根本不发"，而不是"发了让设备忽略"。

## 风扇卡片：两列四格（2×1，2026-11-12 落地）

风扇一天里最常碰的是「往哪儿吹」和「吹多大」，模式反而是一次性设置。2×1 的内容带
是 312×78 = 两行 36，竖着只排得下两件事，所以做**两列 × 两行**：

```
┌──────────────────────┬──────────────────────┐
│ 左右扫风      [ 开关 ]│ 模式  [自然风|直吹风] │
│ 角度      [− 60°  +] │ 风速  [0 ──●── 100]  │
└──────────────────────┴──────────────────────┘
```

### 列有语义，缺项就空着

左列永远是"往哪儿吹"（扫风开关 + 角度），右列是"吹多大"（模式 + 风速）。
`FanBody.CELLS` 就是这个契约：**某台设备缺一项时那一格空着，别的格子不挪位置**
——挪了之后换台设备用户就得重新找一遍。所以格子表按 `(列, 槽位候选)` 写死，
不按"有几项"重新排布。

左右扫风与上下扫风同时存在时**只上左右**：四个格子放不下五个控件，上下扫风留在
详情页。这一条也是"列有语义"的推论，不是随手二选一。

### 品类级 vs 型号级（最容易糊的一处）

| | 在哪 | 回答什么问题 |
|---|---|---|
| 品类级 | `catalog` 的 fan 画像（8 个控件） | 风扇**可能**有哪些功能 |
| 型号级 | `adapters/dmaker.py` 的 `speed_by_mode` | 同一功能有**两套属性**时，此刻谁说了算 |

- **品类级不做型号分支**：有没有上下扫风、有没有模式、风速是档位还是连续量，
  全由规格回答，"绑不上就跳过"。所以不需要维护"哪些风扇有上下扫风"这种名单，
  也不需要按型号前缀收窄——换一台风扇，规格一变，卡片自己跟着变。
- **型号级必须按型号**：`dmaker.fan.p5c` 的规格里 `speed-level`(8.1, 1–100) 与
  `fan-level`(2.2, 4 档) **同时存在、都可写**，`mode=0`（直吹风）认前者、
  `mode=1`（自然风）认后者。规格里看不出这层关系（两个属性没有任何关联标记），
  只能登记成 `speed_by_mode = ("mode", {0: "fan_speed", 1: "fan_level"})`。
  真机数据与三层缺口见 `docs/reference/fan-purifier-speed.md`。
- **样式可用性用 `at_least_one` 而不是 `slots`**：风扇之间的差异太大，`slots`
  会在缺一项的设备上让整条样式从菜单里消失。现在只要求"六项里至少一项绑上"，
  摆什么由规格定（`CardStyle.available()` 里 `slots` 是"全绑"、
  `at_least_one` 是"有其一个"，两个都写时是"且"）。

### 风速格：同格换形态，不换槽位

右下那格同时持有滑条（`fan_speed`，1–100）与 4 档轨道（`fan_level`），按
`speed_slot(mode_value)` 只显示一个。**换的是格子里哪个控件，不是槽位，也不是行的
显隐**——格子高度固定是 `ROW_H`(36)，两个控件各按自己的高度在格内垂直居中
（26 高的轨道 → 上下各留 5）。如果改成"两个槽位交替隐藏"，剩下那行会被 `QVBoxLayout`
的 stretch 重新居中，每切一次模式整行跳一下。

- 规则没登记、或模式值没读到、或固件加了新模式值 → `speed_slot` 返回 `None`，
  退到"**档位优先**、否则连续量"的通用顺序。宁可显示一个可能不生效的控件，
  也不因为一个未知值把风速整块藏起来（藏了就成了"这台设备没有风速"）。
- 判据只来自型号适配，`FanBody` 自己不认识 `mode` 的语义。

### 枚举放不下就换步进器（两道保险，都在控件库里）

净化器的风速是 `air-purifier-favorite` 里的**15 档枚举**。两个上限：

1. `MAX_SEGMENTS = 8`（在 `card_controls.py`，`card_templates` 只是转发）：超过
   8 段就不切轨道，改用 `CardStepper`（枚举在它内部按下标走，对外收发仍是设备值）。
   15 档切出来每段只有 20px，"26-45" 这种文案一个也放不下。
2. `fits_segments()`：段宽按**文字**分配（"140" 比 "30" 宽一半），连最小字号
   (10px) 都排不下就退步进器。判据是"会不会出现省略号"，不是"能不能画出来"。

"放不放得下"必须在**建控件时**回答（决定建哪种控件），而那时 Qt 还没给几何——
所以用尺寸档定死的标称宽 `card_controls.BODY_W = 312`。
**不能用 `self.width()`**：CardBody 刚构造完、挂在父控件上但几何还没定时，宽度是
QWidget 的默认值 100，5 段模式会被判成"放不下"而退成步进器（踩过）。

### 声明层新增的三个字段

卡片要"类型相同、语义不同"的控件，只能由声明方点名，于是 `catalog.Control` 加了：

| 字段 | 作用 | 为什么不能靠猜 |
|---|---|---|
| `widget` | `slider` / `stepper` / `seg` / `chips` / `toggle`，空 = 按类型自动挑 | 1–100 的连续风速和 16–30 的温度都是 range，自动挑都给步进器，前者要点二十下 |
| `kind` | `range` / `enum` / `bool`，空 = 不限 | `swing_h` 的候选名里既有布尔 `horizontal-swing` 又有枚举 `horizontal-swing-included-angle`，没有它绑到哪个取决于服务顺序 |
| `search_all` | 首选服务找不到时翻**所有**服务（含内部服务） | 连续风速在 `dm-service` 这个自定义服务里，而它整体被当成"内部服务"不出现在"更多功能"里 |

两个字符串字段都在 `Control.__post_init__` 里校验（`WIDGET_KINDS` / `PROP_KINDS`），
写错了 import 期就炸——它们都属于"写错了不崩、只会静默变丑"的那类。

### 模式和角度：轨道分段控件（`CardSeg`）

`CardSeg` 是"一条轨道 + 内嵌按钮"（OpenMexia 的 `.seg` 那种）。风扇的**模式**（直吹风 /
自然风）和**角度**（30/60/90/120/140）、空调的**模式**（自动/制冷/除湿/制热/送风）
都用它，而且**单选枚举现在默认就是它**（`make_control` 的按类型分支），不用逐个声明。

和 `CardChips` 的三处实际差别：

| | `CardChips`（独立胶囊） | `CardSeg`（轨道分段） |
|---|---|---|
| 选中态 | 卡片底色再混 24% 品类色 | **实心品类色 + 反色字** |
| 宽度 | 按文字各给一块 + 内边距 | 按文字给最小宽度，余量均分 |
| 溢出 | 压内边距 → 截字 → **丢弃多余项** | 降字号（12/11/10）→ 还不行就换步进器 |

**选中态换成实心是修一个真 bug**：卡片开启时底色已经染过同一个品类色
（`theme.tint`，10%），激活态若也只混 24%，在 26px 的高度上几乎看不出差别。
2026-11-12 用户报"风扇正处于直吹风，但模式里没有激活的高亮态"，量下来是
`#2B424A` vs 背景 `#222C33`——只差 18 点亮度。换成实心 `#5FB6C9` 之后差 136。
`verify_fan_card.py` 有像素断言（选中段填充色 == 品类色、与底色亮度差 ≥ 60）。

**为什么角度不搞等宽**：5 段在 134px 里等宽 = 每段 20px，装不下 "140"（三个数字）。
按文字分配后 10px 字号刚好排满，短的那几段略宽一点，看着仍是等分的轨道。

**列宽因此从 138/164 改成 168/134**：左列（扫风开关 + 角度 5 段）比右列（模式 2 段 +
风速滑条）更吃宽度。改 `COL_RATIO` 之前先跑 `verify_fan_card.py`，它有几何断言。

### 开关为什么贴着文字（`label=""` 时开关靠左）

风扇卡左上那格是「左右扫风 + 开关」。`FanBody` 把标签画在格子的左边，控件拿走剩下的
宽度（左列 168 − 标签 52 − 间隙 6 = 110）。开关原本按"有标签"的规则靠右摆，于是它
贴到了格子右端——离右列的「模式」只有 44px，看着像"开关属于模式那一格"。

修法不是加参数，而是让 `CardToggle` 认一件事：**`label=""` 意味着标签由外面的格子画**，
那它在控件左边紧挨着，开关就该从 0 开始摆（`_switch_x()`）。有标签时仍靠右（文字左、
开关右），那是卡里其它开关行的形状。

### 详情页：两行速度，按模式只留一行

详情页把两个属性都当普通行建出来，`_sync_speed_rows()` 按当前模式只显示一行
（`ControlRow.setVisible`，不是重建）。规则仍来自 `speed_by_mode`；`speed_by_mode`
为空的设备两行都留着——宁可多一行，也别把用户真能用的属性藏掉。模式值读不到
（刚打开、刚切、离线）时也两行都留，等值到了再收。

顺带修掉一个老问题：`speed-level` 原本根本没绑上，因为它在 `dm-service` 里，
被详情页的"更多功能"服务过滤挡住了——这就是 `search_all` 存在的理由。

### 详情页也用轨道（枚举行）

`ControlRow` 的 `select` 行以前是 `Combo`（下拉框）。现在**优先 `CardSeg`**，
判据是「段数 ≤ `MAX_SEGMENTS`（8）且 `sizeHint()` 不超过 `SEG_MAX_W`（260）」，
超了退回下拉。理由与卡片一致：同一个属性在两个界面上是两种控件，用户得记两套。

三个实现细节：

- **宽度要钉死**。`CardControl` 的 size policy 是 `Expanding`，交给布局分配会被左侧
  属性名挤窄（实测 254 → 159，段里的字立刻开始截）。所以 `setFixedWidth(sizeHint())`，
  让左边的 `ElidedLabel` 去省略——那是它本来就该干的事。
- **不试更小的字号**。卡片和详情页的轨道必须同字号，为了塞下而在详情页缩到 10px
  只会显得没做完；放不下就换下拉，下拉能把二十项列清楚。
- **`set_no_selection` 在轨道上是"一段都不点亮 + 挂 tooltip"**。轨道没有能放一行小字
  的地方，而下拉框靠 placeholder 表示"值不属于这个枚举"（`无` / `其他`，见「『无』
  不是一个枚举项」）。轨道上宁可空着也不保留上一次的选中——那会显示一个设备现在
  其实不在的状态。刚点完那几百毫秒由 `_mode_pending` 挡住，不会闪。

### 边界

- **2×2（六行）没做**。内容分配想过（风速 / 模式 / 左右 / 上下 / 定时 / 童锁），
  `CardBody` 本来就"绑不上就跳过"，技术上不需要新代码；没做的原因是没有一台设备
  同时有六项值得摆上卡，先不上。真要加时照 `FAN_CONTROLS` 再登记一条 `span=2,
  rows=2` 即可。
- **浴霸未测**（在共享家庭，按测试纪律不碰），它的"风速"是枚举还是 range 未知；
  两条路径都不崩，只是可能选错控件类型。
- 风扇卡片**不显示温度/湿度**：那是传感器的事，混进"吹多大"这一列会打乱列语义。

## 卡片控件库：一处决定"这块画什么"

卡片内容带里有两种布局、五种控件。**布局是形态，控件是零件**，两件事必须分开：

| | 谁负责 | 现在有几个 |
|---|---|---|
| 零件（滑条 / 步进器 / 分段轨道 / 胶囊 / 开关） | `ui/card_controls.py` + `make_control()` | 5 种，**选型只有这一份** |
| 形态（竖排一行一件 / 两列四格 / 视频 / 左图右按钮） | `CardBody` / `FanBody` / `CameraCard` / `GeekCard` | 4 种 |

以前选型写了两遍：`CardBody._pick` 一遍、`FanBody._make` 一遍。两份已经开始漂
（一处改了枚举上限、另一处没动），加第三个品类就得再抄第三遍。现在两个 body 都只调
`make_control(ctl, palette, accent, avail=…, label=…)`：

```
CardBody._pick   ─┐
                  ├─→ make_control ─→ 声明 widget 优先 → 按属性形状（bool/enum/range）
FanBody._make    ─┘                    │                    │
                                       │                    ├─ bool  → CardToggle
                                       │                    ├─ enum  → CardSeg｜CardStepper
                                       │                    └─ range → CardStepper｜CardSlider
                                       └─ 放不下 / 形状不符 → 退回按类型（不返回 None）
```

**加一个新品类时**：在 `catalog` 里写 `slots` + `widget`，body 用现成的；不需要写控件，
也不需要在两处同步阈值。**加一个新控件时**：只在 `card_controls.py` 里加类，然后在
`make_control` 的一张表里挂一行，`WIDGET_KINDS` 跟着加一个字符串。

四条约定：

1. **声明优先，但声明失败不许让控件消失**。`widget="chips"` 放不下就退回按类型挑
   （→ 步进器），而不是返回 `None`。整格不见了比换一种控件糟得多。
2. **`avail` 由调用方给**。选型要用宽度（决定轨道还是步进器），但布局才知道宽度，
   所以 body 传进来；body 自己用的是尺寸档定死的 `BODY_W = 312` / 列宽，
   **不是 `self.width()`**（构造期那是 100）。
3. **布局不许塞进控件库**。`FanBody` 的"两列四格、缺项空着"是形态，不是零件；
   往 `make_control` 里塞布局参数就会长成 OpenMexia 那种"内容决定高度"的模型。
4. **接线只有 body 那一处，控件不知道 siid/piid**。控件只发"用户把它改成了这个值"
   （`committed` 一个参数），`siid/piid` 由 body 补：
   `widget.committed.connect(lambda value, p=prop: self.value_committed.emit(p.siid, p.piid, value))`。
   2026-11-12 用户报"点风扇卡的模式，UI 切到自然风了、风扇不转，详情页同一个模式正常"：
   `FanBody` 建完控件只塞进 `self.controls`，**没接 `committed`**——而 `CardSeg` 在
   `mousePressEvent` 里先改自己的 `_current` 再 emit，所以视觉确实变了，看起来像
   "生效了"，实际一条写请求都没发出去（开关、滑条同样）。
   **验证要从 body 的信号口断言**：`verify_fan_card.py` 第 8 组点完轨道/开关/滑条，
   断言 `body.value_committed` 发出 `(siid, piid, value)`；最后一发把接线摘掉再点一次，
   确认"没有它就不发"。前面第 6/7 组直接连 `widget.committed` 测的是零件、绕过了
   这一层，所以它们全绿也没抓到——**零件能单测 ≠ 接好了**。

`CardChips`（独立胶囊）现在**没有声明方在用**，留着是因为"标签感"场景（非互斥、
带图标）将来可能需要；真要用先修它的溢出策略（它现在会**丢弃多余项**）。

### 控件矩形内的鼠标事件归控件（两道闸）

2026-11-12 用户报："点 body 里的控件，结果打开了详情页，操控不了。"

根因不在控件画错了，在**事件冒泡**：`DeviceCard.mouseReleaseEvent` 的判断是"按下、
松开都在卡片内就 `clicked.emit`"（打开详情页），而 Qt 会把**没被 accept 的 press
沿父链传上去**。控件里任何一个"没命中就 `return`"的早退——点轨道两段之间的缝、
点开关的标签、禁用态——都会让松手冒泡到卡片，于是值没写出去、详情页开了。

两道闸，缺一不可：

1. **`CardControl.mousePressEvent` / `mouseReleaseEvent` 把左键一律 accept**。
   边界是"控件矩形内的事归控件"：滑条的整行、轨道的整条、开关的整行都是它的地盘；
   点空白处不改变值，但也不该被解释成"点了一下卡片"。子类里那些早退
   （`_hit` 没命中、`isEnabled()` 为假）要走 `super()`，不能直接 `return`。
2. **`DeviceCard._control_at(pos)` 兜底**：`childAt` 拿到最深的子控件后沿父链找
   `CardControl`（`ToggleSwitch` 是 `CardToggle` 的子控件，直接判类型会漏），
   找到就把这次点击算作控件消费掉。防的是"新控件忘了 override"这类遗漏——
   操控失灵比点了没反应严重得多。

`scripts/verify_card_click.py` 用 `QTest.mouseClick(card, pos=…)` 走真实 hit-test
（直接发给控件就绕过了冒泡，那正是 bug 所在的环节），并且在最后一节**把两道闸都
拆掉**，确认"确实会误开详情页"——不然这个脚本只是个永远绿的摆设。

## 中枢网关：极客版入口（2×1 卡，2026-11-11 落地）

极客版是中枢网关自带的局域网后台（浏览器打开 `http://<网关 IP>/`），登录密码是
**6 位一次性码**。码不是网关本地生成的，而是米家云端两条 RPC 返回的——App 里
「中枢网关 → 自动化极客版」那几层菜单，本质只是替用户发这条请求。调研与实测见
`docs/reference/mijia-geek-login-code.md`。

* **入口就是卡片本身**：新增样式 `gateway_geek`（菜单里叫「宽卡 2×1：极客版入口」）。
  左半是产品图（外壳画的），右半是 `GeekButton`（`ui/geek_card.py`）。用户主动选，
  **默认仍是 1×1 标准卡**——不因为它是网关就擅自放大。
* **哪些设备有极客版：探测出来的，不是写死的型号名单**（2026-11-11 改）。判据是
  `CardStyle.ability = ABILITY_GEEK`，实现见「能力探测」小节。为什么不按型号前缀：
  这项能力**根本不在 MIoT 规格里**（中枢网关的 spec 只有网络 / 指示灯 / 虚拟事件），
  而能给出极客版地址的设备也不止一个型号——用户家里还有中控屏、带中枢的路由器，
  写死 `HUB_MODELS` 等于让人肉维护，漏一个就永远看不到入口。
  注意 `CardSpec` 为此加了 `did` 字段：判据是**这台设备**的实测结论。
* **外壳只开了两个小口子**：`DeviceCard._draws_art()`（要不要画产品图）和
  `_art_rect()`（产品图落在哪块矩形），`GeekCard` 覆写它们把右半让给按钮。
  默认实现与改之前完全一致，别的卡片类不用管这两个钩子。
* **按钮颜色走主题 `accent`，不抄参考图里的红棕**：参考图只借几何（左图右按钮），
  颜色得服从界面。第一版把 `#B5432C` 写死，结果整面墙里只有这一块红——选中态、
  焦点框、菜单高亮全是 `accent`，突然冒出的外来色只会像别人的控件。现在描边就是
  `pal.accent`（2px），悬停 / 按下分别往 accent 里掺 `BTN_HOVER` 10% / `BTN_PRESS` 20%，
  两套主题都不用另配一份颜色。
* **点一次的动作链**（`ui/wall.py:_on_geek_requested`）：取地址 → 取码 → 写剪贴板 →
  `QDesktopServices.openUrl`。顺序不能反：
  - **先取地址**（`miIO.get_autowebconfig_url`，不耗码）；地址拿不到就早退，
    不会白白烧掉一枚码；
  - 取码失败但地址拿到了，**仍然打开网页**，让用户手输——比什么都不做强；
  - 先写剪贴板再开浏览器：浏览器会抢焦点，剪贴板不受影响，切过去直接 Ctrl+V。
* **一次点击 = 一枚码**（用户实测：取新码会让旧码立即失效）。所以这里
  **没有缓存、没有重试、没有后台预取**，绝不放进轮询或窗口重建路径；往返期间
  按钮置忙且不接受点击，否则连点三下就白烧三枚。
* **连点保护靠"先置忙再发请求"，不靠冷却期**（2026-11-11 定）。`_on_geek_requested`
  第一件事就是 `card.set_busy(True)`，第二件才是 `fetch_geek_passcode`——中间没有
  任何异步步骤，所以双击的第二击必然落在忙态里、被 `_can_click()` 挡掉
  （`verify_geek.py::test_click_guard` 钉住这一点）。
  **不再加 3 秒 CD**：它挡住的只有"结果落定后 3 秒内又点一下"这一种情况，而这恰好是
  **有意重试**——按钮上就写着「重新获取并打开极客版」。真加上就变成"点了没反应"，
  而这一整块 UI 的存在意义就是省掉掏手机；冷却期挡的是唯一的正路。
  换主题/切家庭/整墙重建都不会造出可连点的新按钮，无需额外防抖。
* **离线时点不动**：云端这条 RPC 要转发给设备，网关离线必然失败；按钮跟着外壳
  一起压到 45% 不透明度（子控件不会被父控件的 `QPainter` opacity 带下去，这里
  必须自己压一次，否则离线时按钮反而成了整张卡里最实的一块）。
* **按钮上有三种结果态，不只"忙"一种**（`GeekButton._state`，2026-11-11 加）：
  - `idle`：`打开极客版` / `自动复制登录码`，描边是 `accent`；
  - `done`：`已复制 登录码` + **那串码放大到 18px** + `重新获取并打开极客版`，描边转
    `theme.ACCENT_GREEN`；
  - `failed`：`获取登录码失败` + `重新获取并打开极客版`，描边转 `theme.DANGER`。
  为什么成功态排成三行而不是用户原话的两行：按钮只有 150 宽，`已复制 登录码：123456`
  在 13px 下量出来正好卡在 `avail` 边界上，`elidedText` 会把**最要紧的数字**吃成
  `12…`。拆行之后码能放大一号，反而更醒目（`verify_geek.py` 有一条逐行量字宽的
  回归，专防以后改文案又把它挤出按钮）。失败原因不进按钮——那是居中提示的活，
  按钮只回答"成没成、下一步点什么"。
  **结果态会自己退回去**（`RESULT_MS = 30 秒`，`GeekButton._revert`）：这行字回答的是
  "刚才那一下成没成"，浏览器一关回来看到它还认得，但再久就成了常驻装饰，把按钮本该
  写的动作文案顶掉。计时器是 `QTimer(self)` 子对象——卡片随整墙重建会被 `deleteLater`，
  独立计时器会在那之后才触发、撞上已销毁的按钮。新一轮 `set_busy(True)` 会 `stop()`：
  旧结论已经被「正在取码…」盖住，不该让它在**新结果**上到点。退回常态**不动剪贴板**，
  码还在那儿，用户随时能粘贴。
* **提示条**走 `tooltip.toast_top(..., kind=TOAST_OK / TOAST_FAIL)`：屏幕中央偏上、
  跨程序停留（两条提示路的分工见「小爱音箱的文字指令」里那四条界面约定）。**不要退回
  `tooltip.toast`**——后者失焦即收，正好落在用户切到浏览器的那一刻。
* **工作线程**：`Store.fetch_geek_passcode` 走 `worker.submit`，回调
  `(entry, error, url)` 回主线程做剪贴板与浏览器，界面不等网络。
* **验证**：`scripts/verify_geek.py`（115 项，用假 api 跑完整分支，不发真实请求）；
  真机探针仍是 `scripts/probe_geek_passcode.py`，它**会消耗一枚码**，别加进自动化脚本集。

### 能力探测：程序问出来的型号白名单

`core/geek.probe()` 只发 `miIO.get_autowebconfig_url`（**不耗码**），拿到 http 地址就算
"这台有极客版"。结论按 `did` 落进 `<data>/geek_ability.json`：

```json
{"version": 1, "devices": {"<did>": {"model": "xiaomi.gateway.hub1", "ok": true, "at": 1762800000}}}
```

* **什么时候探**：`Store.scan_geek_abilities()`，在 `on_loaded` 之后（界面先铺出来）。
  每次启动最多派 `GEEK_SCAN_LIMIT = 20` 台，`geek.candidates()` 把 `gateway` /
  `router` / `screen` 排最前——设备多的家里头一批就命中中枢，不用等整轮扫完。
  每台设备**一辈子只探一次**，成本是"每台一次请求、结论永久落盘"。
* **跳过谁**：共享家庭整户跳过（那是另一户人家，不替他们发请求，见 `TODO.md` 的测试
  纪律）；离线设备跳过（云端要转发给设备，不在线只会拿到超时）；已知结论的跳过。
* **否定结论会过期**：`NEGATIVE_TTL = 7 天`。探测失败可能是当时云端抽风或设备没应答，
  把一次失败当永久结论会让用户永远看不到入口。`ok=true` 不带时效，型号变了才重探。
* **型号级复用**：同型号只要有一台探通，新来的那台直接算支持（`confirmed_models()`）
  ——换设备 / 新配对时省一轮请求。**否定结论不做型号推广**：同一型号另一台可能就在。
* **探测自己抛错**（工作线程层面）**不落盘**：当没探过，下次启动再来。
* **卡片类是固定的**：非摄像头一律 `GeekCard`（只是 `DeviceCard` 多一条"右半放大按钮"
  的支路，没有该样式时行为完全一致）。不能按能力挑类——能力是运行时才有的，而
  `apply_card_style` 只 `set_style` 不重建卡片，探出结果后再换类就得重造整面墙。
* 缓存丢了（删文件 / 换机）最多是"入口暂时不显示 + 下次启动重探一次"，不影响已取到的码。

### 样式什么时候判定（**不要挂到轮询上**）

`CardStyle.available()` 会被问三处，全是"用户或结构动了"的时刻：

1. `WallView.build()` —— 每张卡一次 `resolve_card_style()`。触发者是 `set_home()`
   （首次加载、切家庭、排序/隐藏变化）和 `rebuild_palette()`（切主题）。
   **"首次加载"是每次启动程序的首次**：`_on_loaded` 里 `first = not self.wall._cards`，
   进程刚起来时卡片字典是空的，所以每次打开程序都会把全部样式重判一遍，
   设备能力（固件升级后多了 `color_temp` 之类）不会躺着过期。
2. `WallView.apply_card_style(did)` —— 只刷一张。调用方是右键选样式，以及
   `_on_geek_ability`（探测结论落定后，且**只有偏好里已经存着 `gateway_geek`** 时才刷）。
3. `available_styles(card)` —— 右键展开「卡片样式」子菜单时算一次，纯 UI，不缓存。

**轮询一次都不碰**：`store.poll()` → `_changed(dids)`（值没变连回调都没有）→
`wall.update_cards()` → `card.refresh()`，里面只有 `_apply_geometry()` +
`_body.sync(state)` + `update()`。不进轮询不是性能问题（判一次是纯内存：prefs 字典
查询 + `geek._records()` 的内存缓存 + 槽位字典查找，微秒级），而是**语义**：亮度变了
样式不该变，判了也白判，还会让 `set_style` 每轮撞上"同一个样式"的早退分支。

代价是这个空档：**能力在运行中变了没有重判通道**，要等下一次整墙重建才追上。
典型场景是同一 `did` 重新配对换了型号、或者固件升级后属性变多——`resolve_card_style`
本来能正确回退/升级，但没人去问它。补法不需要新请求：`store` 有"spec 对象没换就复用"
的现成判据（`_text_specs`），在 `update_cards()` 里记住每张卡上次用的 `st.card` 对象
身份，`is not` 变了才调一次 `apply_card_style(did)` 即可（一次引用比较）。目前**未实现，
2026-11-11 用户决定不做**——每次启动都会整墙重判，日常够用；真要做先想清楚"卡片正在
被拖动 / 滑条正在被拖"时重解析的时序。

## 枚举文案层：云端原话 → 界面短名

**先分清两个方向。** 上一节和本节共用一张型号表和同一个 `ModelAdapter`，但改的不是
一回事，消费路径也是分开的：

| | 行为适配 | 文案适配 |
|---|---|---|
| 字段 | `extra` / `mode_active` | `text`（`TextLayer`） |
| 改什么 | 多读哪个属性、拿什么当状态判据 | 只改显示出来的文字 |
| 谁读它 | `catalog.build_card()` → `CardSpec` | `enum_text._lexicon()` → 短名 |
| 粒度 | **只能按型号** | 型号 / 类别 / 全局三层 |
| 写错的后果 | 设备拒收命令、状态错乱 | 某个选项显示不准，原文还在 tooltip |
| 失效方式 | 属性找不到就退回默认行为（不报错） | 查不到就退回云端原文（不报错） |

挂灯那条 `mode`(2,5) → `scene-mode`(3,9) 属于**行为适配**：它换的是"哪个属性说了算"
（判据），写入仍然写 `mode`，跟文字没有任何关系。文案适配**从不**改变哪个值会被写出去——
写请求用的始终是云端给的整数 `value`。所以两条路互不影响，一条型号记录里可以只写其中
一条，也可以两条都写。

米家规格里 `value-list[].comment` 是**给开发者看的**，不是给人看的。实测 49 份规格、
1850 个枚举项，原文长这样：

| 原文 | 问题 |
|---|---|
| `Quick Single Click`、`Frequent Wrong Password`、`Ac Mode With Outlet` | 英文 |
| `空场景（灯不在任何情况模式时，上报该属性值）` | 22 字整句 |
| `大电池耗尽且小电池电量低 (大电池 =0% &小电池<=20%)` | 带条件的告警 |
| `C1 CLEAR`、`Level3`、`Area 5` | 编号 / 拼装 |

而位置上只有：详情页下拉框（最宽 240px、按 10 个字算宽）和读数行右侧一个 `QLabel`。
以前是机械截到 14 个字加省略号，切出来常是"0关闭待机息屏，待…"这种没有意义的片段。

现在是一层独立的映射（`core/enum_text.py` + `core/adapters/`），**三层覆盖 + 规则 + 兜底，
认不出就不猜**：

1. **型号级**（`adapters/<厂商>.py` 的 `ModelAdapter.text`）——只有这台型号独有的词才写这里
2. **类别级**（`adapters/categories.py`）——某个品类独有的词。键是 URN 里的 `category`
   （`lock` / `washer`），不是中文品类名。门锁 `door-state` 那种状态机写法压成
   `已上锁·反锁+童锁` 就在这里
3. **全局词汇**（`ENUM_ALIAS`，251 条）——跨品类通用的：`Quick Single Click → 单击`、
   `大电池电量耗尽… → 大电池耗尽`。这一层不拆散到各品类，拆了必然漂移
4. 规则：`C1 CLEAR → C1 已解除`、`Level3 / Lever9 → 3 档`、`Area 5 → 区域5`、`Room1 → 房间1`
   （`Lever` 是云端把 `Level` 拼错了，两样都认）；位运算前缀 `（1<<4）` 先剥掉再查表
5. 兜底：按逗号/括号切一刀，再不行才截断加省略号——和加这一层之前的行为完全一致

三层每一层内部都是**先查「属性 + 原话」、再查裸词**；但**层与层之间是纯粹的层优先**，
精确度只在层内起作用。也就是说型号层写了个裸词，照样盖住全局的属性级条目——宁可让
"为一台设备专门写的规则"生效，也不让它被一条更通用的词条悄悄压掉。早期把三层摊平成
"属性级一张表 + 裸词一张表"、先查属性级，就出过一个这样的 bug：全局的
`("door-state", "Open") → 已开` 排在型号裸词前面，型号规则静默失效（现已按层保留，
`verify_enum_text` 有回归用例）。

属性名一律用 **URN 名**（`wash-mode` / `door-state`），不用云端中文 `comment`：comment 是给
开发者的描述，米家改一个字键就失效，而且失效时界面只是"突然又变英文了"，不报错。所以
`("wash-mode", "Dry") → 烘干` 对所有厂商的洗衣机都成立，`Dry` 在空调 `mode` 里仍然是
"除湿"——两个属性名不同，不会互相串。

**为什么文案可以按类别，行为不行。** 行为适配（多读属性、换判据）写错会让设备拒收命令，
所以一律按型号；文案是纯显示、认不出就退回原文、没有任何 IO，写错最坏是某台设备上一个
选项显示得不准。这是「设备特判一律按型号」的**唯一例外**，边界写在
`adapters/categories.py` 顶部；类别层优先写带属性名的条目，裸词只收该品类独有的词。

**原文一个字都没丢**：`ValueOption.label` 仍是云端原话，短名放在 `ValueOption.short`，
两者不同时把原文挂到 tooltip 上。写请求用的是 `value`（整数），文案改错也不会写坏设备。

故障码（`C1` / `E2.1` / `PA`）**故意不翻**——那是行业码，用户要拿它报修。品牌名同理
（`NFC` / `HomeKit` / `HDMI1`）。

**型号级要晚一步才能算**：规格缓存的键是 URN，URN 里的型号段是 `yeelink-lamp22`，和设备
节点上报的 `yeelink.light.lamp22` 不是一个东西——把"这台设备"的文案烤进"这个 URN"的缓存，
同 URN 的第二台设备就会串味。所以类别级在 `parse_raw` 里做（URN 自带 category），型号级由
`spec.localize(spec, model)` 在 store 里补，结果按 (URN, 型号) 记住：源规格没换就复用同一
个对象，否则 `prev.spec is not spec` 每次为真，一次拓扑刷新会把所有卡片重建一遍。

维护方式：改完跑 `scripts/verify_enum_text.py`（表自检 + 三层优先级 + 接线，92 项），
需要看真实规格还剩多少没映射时跑 `scripts/probe_enums.py`（离线读规格缓存，按品类给出
剩余英文的分布）。

## 交互约定：滚轮只滚页面

**本程序里鼠标滚轮只用来滚动页面，任何情况下都不改变设备状态或参数。**
这不是某一个控件的补丁，而是新控件也必须遵守的长期约束。

为什么：卡片墙、详情页、设置页都是可滚动页面。鼠标从卡片上划过时，滚轮应该
带用户去看下面的内容；如果它顺手把亮度从 60% 调到 61%，用户往往当场看不出来，
下次开灯才发现不对。滚轮是"浏览"手势，不是"调节"手势。

实现方式（`mihome/ui/wheel_guard.py`）：

- 自定义控件混入 `WheelSafe`，`wheelEvent` 里只做 `event.ignore()`；
  **不要** `event.accept()`，**不要**调 `super()`，否则事件到不了父级滚动区；
- 必须用 Qt 原生控件时，优先用 `SafeSlider` 这类受保护子类，或在子类里覆写
  `wheelEvent`；不要直接 `new` 原生 `QSlider` / `QSpinBox` / `QComboBox`；
- 新增控件先问一句：滚轮停在它上面时，页面还能不能滚？值有没有变？
  两者只要有一个不符合就不算完成。

明确保留滚轮的地方（它们滚的是"看哪儿"，不是"设备状态"）：

| 控件 / 区域 | 滚轮行为 | 理由 |
|---|---|---|
| 首页卡片墙、详情页 `QScrollArea` | 滚动页面 | 约定本身 |
| 设置页排序树、隐藏设备树 | 滚动列表 | 列表导航，不改任何值 |
| 左侧家庭/页签导航 | 滚动导航列表 | 同上 |
| 下拉框**展开后**的选项列表 | 滚动候选项 | 选项列表本质是列表；未展开时 `Combo` 不吃滚轮 |

目前**没有**为任何"设备参数控件"保留滚轮。如果以后要开例外（例如某个弹出式
温度面板获得焦点后允许滚轮微调），必须先在 issue / TODO 里写明理由并确认，
不能默默加回来。

## 详情页：打开就是真值（不等 600ms）

详情页的行控件过去只在构造完成后由 600ms 的定时器 `_sync()` 填值，于是**第一帧是
控件的出厂态**：滑条停在最左、轨道一段都不亮、开关默认关着，过一会儿才跳成真实值。
用户 2026-11-12 报的就是这个——"程序明明已经知道每台设备的属性，为什么进详情页
还要先空一下"。

改法：`DetailDialog.__init__` 末尾（`_build_advanced()` 之后）立刻调一次 `_sync()`。
两件事值得记住：

- `_sync()` 取的是 **`self.store.devices[did]`**，不是构造参数传进来的那个
  `state`——后者可能已经过期（详情页开着的时候 store 一直在更新同一个 did 的对象），
  顺手 `self.state = st` 换掉。
- **600ms 定时器不能删**：它管的是"打开之后设备状态又变了"、离线提示、
  "数据更新于 N 秒前"这类持续刷新，和"第一帧"是两件事。

`ControlRow.set_value(None)` 本身是安全的（直接 return），所以某属性还没读到时
不会因为首次同步而画出一个假值；「更多功能」那组未读的行仍走 `set_unknown()`。

## 交互约定：点压暗区关闭子窗口

**点一下子窗口外侧的压暗区 = 按一次 Esc，只关当前这一层。**

为什么不能直接用压暗蒙版吃点击：`DimOverlay` 是主窗口 `root` 的子控件，
而子窗口走的是 `QDialog.exec()`（应用模态）。模态期间 Qt 在**窗口系统层**就把
落到主窗口及其子控件上的鼠标事件丢掉了，`DimOverlay` 永远收不到。
（而模态弹窗**自己**的子顶层窗口不受拦截——实现就挂在这一点上。）

实现方式（`mihome/ui/chrome.py`）：

- 每个弹窗挂一个 `DimClickShield`：透明、无边框、不抢焦点的子顶层窗口，
  铺满最外层主窗口，用 `setMask` 把它自己和所有可见父弹窗的矩形挖掉；
- 点洞外 → `dialog.reject()`，和 Esc 走同一条 `done(Rejected)` 路径，
  所以标题栏关闭、详情页停播/释放观看位这些现有逻辑全部复用；
- 只关最上层：嵌套时每层各有一个 shield，最上层那个在最上面，
  `reject()` 只作用于它自己的 `dialog`；
- 不误伤：按下与松开**两端都必须在洞外**才关。窗口内部按下拖到遮罩松开，
  shield 没有 press 记录；遮罩按下拖进窗口松开，松开点命中洞内。
  滚轮事件直接 `ignore()`；视频画面自己的单击语义不受影响；
- 视觉不变：shield 不画可见内容，只填一层 alpha=1——Windows 对分层窗口是逐像素
  命中测试，alpha=0 的像素收不到鼠标（`setMask` 不会改变这一点）；压暗仍由
  `DimOverlay` 提供。

接线点是 `exec_with_dim_click(dialog)`，新加弹窗请走它而不是裸 `dialog.exec()`。

### 关掉就销毁（`deleteLater`，2026-11-12 修）

`exec_with_dim_click` 的 `finally` 里现在除了 `shield.hide()`，还会 `dialog.hide()`
+ `dialog.deleteLater()`。原因是一条真机上刷屏的报错：

```
AttributeError: 'DimClickShield' object has no attribute '_dialog'
AttributeError: 'WindowFrame' object has no attribute 'win'
```

它出现在**反复打开、关闭设置页**之后。链路是：弹窗 parent 是主窗口，只 `hide()`
不销毁时 C++ 对象被 parent 一直持有，挂在它身上的两个事件过滤器（`WindowFrame` /
`DimClickShield`）也跟着活下来；而 Python 侧这些对象只由 `dialog.__dict__`
和调用方的**局部变量**引用，函数一返回就可能被 GC。之后 Qt 继续回调它们的
`eventFilter`，访问 `self.win` / `self._dialog` 就是上面那两句——表现是终端刷红字、
主窗口的绘制/事件时序被打乱（用户看到卡片墙变空）。

两条加固，缺一不可：

1. **关掉即销毁**（`deleteLater`）：C++ 对象真没了，过滤器随子对象一起走。顺带
   解决"每次开设置都攒一个 `Qt.Dialog` 顶层窗口"——攒着反复开关会闪。
2. **Python 引用跟着被监控窗口走**：`WindowFrame` 构造时写 `window._window_frame = self`，
   `DimClickShield` 构造时写 `dialog._dim_click_shield = self`（原来只在
   `exec_with_dim_click` 里挂，别处直接 new 就没挂）。这样即使调用方不长期持有，
   wrapper 也不会先于 C++ 对象消失。

验证：`scripts/verify_dim_click.py` 第 8 组——连续开关 5 次后断言没有一个弹窗还活着、
主窗口名下不再挂着 `QDialog`、没有残留 `WindowFrame`；另有一条对照（只 `hide()`
不 `delete` 的弹窗**仍然活着**），证明这三条真能测到东西。

### 关窗那一下只许重绘一次

上一节把报错治住了，但**闪烁还在**（用户 2026-11-12 复测：主窗口闪一下，截图里
卡片全都变矮、只剩标题，body 是空的）。两个独立原因，都得修：

**① 关窗后又把主题应用了一遍（主因）。** `open_settings` 过去在 `_run_dialog`
之后无条件调 `self._apply_theme()`。而 `_apply_theme` 里有
`wall.rebuild_palette`——卡片是自绘的，换色靠**整墙重建**（56 张卡拆掉重造）。
所以"什么都没改、直接关设置页"也要重建一次，叠加在三处整窗失效之上，中间那帧
就是"父控件（卡片底色、标题）画完了、子控件（body 里的滑条/轨道）还没画"。

其实不需要：设置页里点主题时 `theme_selected` → `set_theme` 当场就应用过了。
**改主题时那次重建还在**（该有），关窗那次是纯重复。

**② 三处"整窗失效"没有合并。** 关一个子窗口会连着做三件事，每一件都让系统要求
主窗口重画整片区域：

| 事件 | 哪来的 |
|---|---|
| 弹窗销毁 | `exec_with_dim_click` 的 `finally`（`deleteLater`） |
| 点击层隐藏 | `DimClickShield.eventFilter` 收到 `Hide` |
| 压暗蒙版隐藏 | `_run_dialog` 的 `finally`（`_dim.cover(False)`） |

主窗口是 `WA_TranslucentBackground` 的（圆角要真透明角），Qt 在这种窗口上**分段
提交**（逐控件 blit），所以连着来三次就能看见"画一半"的中间态。这三件事都发生在
同一轮调用里（`done()` 里 hide、exec 的 finally 紧接、`_run_dialog` 的 finally 紧接，
中间没有回到事件循环），所以收尾统一走 `MainWindow._cover_dim(False)`：它先
`setUpdatesEnabled(False)`，撤掉压暗层，再 `setUpdatesEnabled(True)` + `update()`，
**合成一次 paint**。`_cover_dim(True)` 只是 `dim.cover(True)`，压暗不需要冻结。

约定：**关子窗口前后的收尾动作都写进 `_cover_dim(False)` 那段冻结里**。以后再加
"关窗时要恢复点什么"（比如摄像头画面还回卡片），别放在 `exec` 之后另起一段——
那会变成第二次整窗重绘。

验证：`scripts/verify_close_flash.py`——直接关窗时 `_apply_theme` / `rebuild_palette`
必须是 0 次；在设置页里改主题时恰好 1 次；关窗后 `WA_UpdatesDisabled` 必须已放开
（忘了放开就是整窗冻住，比闪烁更糟）、压暗层已撤。把 `_apply_theme()` 加回去，
这个脚本立刻 6 项红——反向证明它测的是真事。

**离屏测不到"看不看得见闪"**（离屏 QPA 不做分段提交），这里守的是根因；
视觉效果只能在真机上复测。

## 左侧导航底部的功能区（占位）

`ui/side_nav.py` 底部现在是**两组**：功能区（耗材 / 监控 / 电脑自动化三个按钮）在上，
设置在下，中间用 `FOOT_H` 上边界那条线切一刀，最上面还有一条线压在功能区上边界。
三个按钮都只是占位：点击直接 return，不切页、不发信号。

- **两条线的语义不是装饰**：房间列表 + 功能区 = 「这个家」的内容；设置 = 「这个程序」
  的配置。所以功能区上下各一条线，设置单独成一组。两条线样式必须一致
  （`pal.border` / 1px / 左右各缩 12），别给其中一条加粗换色——那会把功能区夹成第三组。
- **占位就是占位**：`mouseReleaseEvent` 里命中 `_zone_index_at_point()` 直接 `return`，
  不发信号、不切页、不弹窗；hover 仍给底色和指针光标（不然用户以为这一块没做）。
  将来接页面时在这里发 `zone_requested`，**不要**先悄悄跳一个空页面。
- **几何只有一个来源**：`BOTTOM_H = ZONE_H + FOOT_H`。房间列表的可视区
  （`_view_rect`）和滚动上限（`_max_offset`）都减 `BOTTOM_H`，不是 `FOOT_H`。
  改底部任何一块高度都要改这里，否则列表会盖住按钮。
- **`ZONE_H` 必须按 `len(ZONE_ITEMS)` 算**，别写 `* 2`：2026-11-12 加第三个
  「电脑自动化」时就漏了这一处，底部会压掉最后一条并盖住第二道分隔线。加按钮
  只需往 `ZONE_ITEMS` 里加一项 + 在 `_paint_zone_icon` 里补一个图标分支。
- 为什么先放空按钮：把这块位置**定下来**（主程序里独立页面 / 工具的入口区），
  页面的规划在 `TODO.md`「功能区与独立页面」，别在这里先做半成品页面。

## 单实例：再点一次图标只把窗口叫到前台

同一份数据目录只允许一个进程。第二个进程**不启动界面、不连云端**，只广播一句
"我来了"然后退出（退出码 0）。

**判据是数据目录，不是程序名**：`prefs.json`、`cache/`、`auth.json` 全在
`data_dir()` 下，按它算 SHA-1 前 10 位当名字。所以换 `MIHOME_DATA_DIR`（便携版、
第二个账号）可以并行开两个，而同一份数据绝不会被两个进程同时轮询。

**为什么不用 `QLocalServer`**（它是最省事的标准答案）：那要 `PySide6.QtNetwork`，
而 `dist` 里**没有 `Qt6Network.dll`**——打包清单根本没收集 Qt 的网络模块。为了
喊一声多带一个 DLL 不划算，改成只依赖 Win32 的两样东西（`core/single_instance.py`）：

- **命名互斥量** `Local\MiHomePanel-<hash>` 回答"是不是已经有人在跑"。用
  `CreateMutexW(None, False, name)`，只看 `ERROR_ALREADY_EXISTS`，**不要初始拥有者**
  （要了就在同线程重复调用时叠加计数，退出还得 `ReleaseMutex`）。内核对象随进程
  消失，主实例崩了也不会像文件锁那样留下死锁。
- **注册消息** 主实例 `RegisterWindowMessageW("MiHomePanel.Activate-<hash>")` 拿到一个
  会话内唯一的消息号，后来的实例 `PostMessageW(HWND_BROADCAST, 该号)`。字符串相同
  就得到同一个号，不必按窗口标题找窗口（标题会随家庭、设备变，靠不住）。

几个刻意的选择：

- **先抢令牌，再建 `MainWindow`**（`app.py`）。反过来的话两个进程会各刷一轮设备列表、
  各抢摄像头会话（设备侧并发上限 3 路）。
- **过滤器装在 `QApplication` 上**，不是某个窗口上：`QAbstractNativeEventFilter`
  不依赖窗口存在，主实例还在建窗口时消息也不会漏。
- 过滤器里只 `QTimer.singleShot(0, ...)` 转一道再 emit：`nativeEventFilter` 处在消息
  分发中途，直接 `show()/raise_()` 不安全。
- 广播发 **3 次**、间隔 120ms：对面可能正处在启动过程中，单发一次容易丢；总共多等
  240ms，用户点完图标就退出，无感。
- **拿不到令牌一律放行**（返回 True 继续启动）：`CreateMutexW` 失败是异常现场，
  这时最该做的是让程序起来，而不是弹一句"已经有一个实例"。
- `SetForegroundWindow` 在前台锁下会失败并返回 0，Windows 只让任务栏闪烁——不重试、
  不提示，这是系统限制不是 bug。最小化状态要先 `showNormal()`，否则 `raise_()` 只在
  任务栏闪一下。

边界：只有 Windows 实现，其它平台 `acquire()` 直接返回 True（不做检测）。
`--self-check` / `--probe-camera` 在 `main()` 里排在这段之前，所以自检不受"已有实例"
影响——它们是排障工具，必须随时能跑。

**挡下时不能再无声 `return 0`**（2026-11-11）。命令行里"什么都没发生"会让用户、尤其是
用故障注入测链路的人误判成"注入没生效"。现在 `app._report_instance_blocked()` 会明确
打印三件事：已有一个实例在运行、请从托盘菜单选择「退出」（点窗口关闭只是收进托盘）、
以及当前 `MIHOME_DEV_FAULT` 的取值与解析结果（没设 / 无效 / 有效但只对新进程生效）。
打包成 `--windowed` 时没有 stderr，这段提示自然消失——那正是系统通知与顶部横幅的用武之地。

验证：`scripts/verify_single_instance.py`，用**真子进程**占令牌（内核对象假不了），
依次验：空着能拿、第二个拿不到、广播真能到子进程窗口并 emit、子进程一死令牌立刻
能再拿、换数据目录互不影响。子进程不显示窗口，只 `WA_NativeWindow` + `createWinId()`
造一个真句柄——离屏平台没有 HWND，测不出广播。

## 开机启动：一条 HKCU 启动项，加上一个自愈

设置页「常规 → 开机启动」写的是
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 里的一个字符串值
（`core/autostart.py`）：

```
"C:\...\MiHomePanel.exe" --autostart
```

**只写 HKCU，不碰 HKLM**：不需要管理员、不弹 UAC，用户随时能在"任务管理器 → 启动"
里自己禁用。绿色版没有卸载器，可控比"装上就走不掉"重要——所以也没用计划任务
（`schtasks /sc onlogon`）：那需要管理员、残留最难清、杀软最敏感，换来的"延迟启动"
这里用不上。

**只在打包后的 exe 上开放**：源码运行得写 `pythonw.exe -m mihome` 再加工作目录，
venv 一换路径就废。开发态 `supported()` 为假，设置页把开关**藏起来**而不是置灰
——自绘开关看不出"灰"，点了没反应更像坏了；状态行直接写"源码运行时不支持"。

**`--autostart` 是给自己看的**：被系统拉起来时窗口最小化出现，不抢焦点（`present_window`）。
最小化而不是直接收进托盘：Win11 默认把**新的**托盘图标塞进折叠区里，"登录后什么都看不见"
很容易被当成没启动。设备列表照常在后台预热；用户点关闭时才按偏好进托盘。

**路径自愈**：启动项存的是绝对路径，重新打包到别的目录、`dist/` 改名之后旧值就指向
一个不存在的 exe，下次登录弹"找不到文件"。所以每次启动 `autostart.heal()` 比一次：
**只在该功能本来就开着**（`STATE_STALE`）的时候改写成当前路径，`STATE_OFF` 一律不碰
——"启动时顺手把功能打开"是最讨厌的一类自作聪明。

**状态读注册表，不信 `prefs.json`**：用户在任务管理器里禁用之后，偏好里没有任何变化，
开关必须跟着变。四种状态：`on` / `off` / `stale`（开着但指向别的 exe，仍显示为开）/
`unsupported`。写失败（注册表被策略锁住）抛 `AutostartError`，设置页把开关拨回真实
状态并把原因写在状态行里，不静默吞掉。

已知代价：用户直接把目录删掉时，启动项会残留，下次登录 Windows 自己弹"找不到文件"。
绿色版没有卸载器，这是必然的；能做的是**只写一个值、只在一个位置**，别到处撒。

验证：`scripts/verify_autostart.py`（45 项）。**全部读写指到
`HKCU\Software\MiHomePanel-selftest-<pid>\Run` 这个临时键，跑完整个删掉**，既不要
管理员，也不会把用户的"启动"页搞脏。覆盖命令格式与旧值解析、四种状态、`heal` 只在
已启用时改写、关掉后值真的消失、源码运行时抛错，以及用 `sys.frozen` + 假
`sys.executable` 模拟打包态跑一遍真路径。

## 系统托盘常驻：关窗不退出

设置页「常规 → 关闭面板时」默认选**最小化到托盘**：点关闭按钮把窗口藏起来，程序留在
通知区域继续轮询（`ui/tray.py` + `MainWindow.closeEvent`）。菜单目前只有两项：
**打开主窗口** / **退出**（中间一条分隔线）。曾经放过「常用场景」子菜单和「刷新设备」，
用户看过之后要求先去掉——托盘菜单要加什么等想清楚再加，不提前堆功能。

**菜单必须用 `ui/menu.py` 的 `Menu`，不能是裸 `QMenu`**。裸的那层是独立原生窗口，默认
带不透明实心底，QSS 的 `border-radius` 只画出圆角图案，四角外面还是方块底色——真机上
就是"圆角背后有四个黑角"。`Menu` 在构造时就设 `WA_TranslucentBackground` + 去边框 +
去系统阴影（**顺序很关键**：属性必须在原生窗口创建之前设，晚一步就按不透明建好了），
再配自己的 `menu_qss`。菜单是独立窗口，不会继承主窗口的 QSS，所以 `set_palette` 里要
显式给它换一份样式表，否则切主题后是一张白底配深色字的菜单。

**看不看得见，决定轮询多快**（`MainWindow._apply_poll_mode`）：前台 3 秒，收进托盘 /
最小化到任务栏 / 开机直接进托盘（从没 show 过）降到 `POLL_HIDDEN_MS = 15 秒`，切回
前台立刻补一轮。判据是 `isVisible() and not isMinimized()`——挂在 `showEvent` /
`hideEvent` / `changeEvent(WindowStateChange)` 三处，**不去 `hide_to_tray` 里单独调**：
收进托盘是 `hide()`、最小化是窗口状态，两种"看不见"走的是不同事件，只挂一处总会漏。

> 15 秒是折中：再降（30/60 秒）每小时只少几十次请求，但点开时第一眼更容易看到旧值
> （虽然点开就补一轮，那一轮也要几百毫秒才回来）。降频只动 `_poll_timer` 的间隔，
> 请求/失败退避那套逻辑一行没改；`setInterval` 会重新计时，正好是"从后台开始数 15 秒"。

**以后加桌面挂件 / 自动化时，这个判断要换位置**（2026-11-10 **已经换好了**）：

* **桌面挂件是另一个窗口**。主窗口收进托盘、挂件还贴在桌面上时，3 秒那一档不能停。
  一个进程里会有两个"可见性"，各自登记自己的需求才对。
* **自动化不看画面，但有最低频率**。规则要靠轮询喂值，窗口和挂件都关着也得继续跑
  （否则"门开了就锁屏"永远等不到）。它要的是"3 秒、常在"，而不是"看得见才 3 秒"。

所以形态是**需求登记**（`core/poll_demand.py`）：每个消费者报一份"我要多快"
（`(owner, interval_ms, reason)`），`PollDemandBoard` 取最严的那个统一生效，
`_apply_poll_mode` 只是其中一条输入、不再是唯一裁判。

三条容易写错的地方：

- **属性与事件各一张表**。`prop/get` 一轮要 2 个请求、`event/get` 一个请求能带几十个源，
  频率本来就该各自算；合成一张表就会出现"事件要 1 秒，结果把 130 条属性也拖到 1 秒"。
- **结果没变就不回调**。否则挂件要的 1 秒会被"窗口切到后台"那一下重置回 15 秒
  （`verify_tray` 有这条回归）。
- **`MIN_INTERVAL_MS` 是硬下限**（2026-11-12 从 1000 降到 **500**）。谁报 100 毫秒都会
  被收敛。放开的只有下限，不是常态频率：主窗口仍登记 3 秒 / 托盘 15 秒，
  500 毫秒只出现在下面那个"指令后窗口"里。

主窗口这边：`poll_demand` 的属性表登记 `("window", 3s/15s)`，`_on_poll_interval` 按表结果
设定时器；`poll_events` 已建好但 `idle_ms=None`——**没人登记就不起请求**，不凭空多一路频率。

### 发过指令之后的 5 秒：0.5 秒一轮

写入是**乐观**的：按下开关的瞬间屏幕上就是新值，可那是我们自己写的，不是设备回读的。
设备到底照做了没有，只有下一轮回读才知道——3 秒一轮意味着"按了没反应"要等 3 秒才看得见，
收在托盘里甚至要等 15 秒。所以：

```
Store.set_value / set_many / run_action / run_scene
        └─ on_write_sent  ──→  MainWindow._start_burst()
                                 ├─ poll_demand.set("burst", 500, "刚发过指令")
                                 └─ _burst_timer.start(5000)
                                        └─ 到期 _end_burst() → clear("burst")
```

- **挂在 `Store` 上，不挂在各个 UI 入口**。写入口有卡片、详情页、场景、批量、音箱指令
  好几处，逐处接线一定会漏。Store 只负责说"刚发了一条"，多快、多久由界面决定
  （它不该知道轮询频率这个数）。
- **是压在上面的一档，不是改 `window` 那条**。窗口该是 3 秒还是 15 秒仍由"看不看得见"
  决定；突发结束 `clear("burst")` 就自然回到原档，不需要记住"刚才是什么间隔"。
- **连续点几下不叠加**：窗口是"最后一次操作之后 5 秒"（`QTimer.start` 会重置），
  不是每点一下就加 5 秒。
- **代价**：0.5 秒 × 5 秒 = 最多 10 轮，一轮就是一个批量包（`DEFAULT_CHUNK = 300`）。
  对比 OpenMexia 每台设备每 5 秒一条（48 台 = 576 条/分钟），这 10 条连零头都不算。
- **失败也照样提速**：写回包失败时 `_on_written` 立刻还原乐观值并写 `st.error`，
  界面马上能看到"已还原"；随后这几轮高频回读是为了拿到设备的**真实**状态——
  批量里成功一半的情况，只看回包码说不清。

`scripts/verify_poll_demand.py` 的 `_burst()` 覆盖"前台 3s → 500 → 回 3s""托盘 15s → 500 →
回 15s""500 不被下限抬高"三组。

自动化还要挡住一个诱惑：我们手里只有 HTTP 轮询（云端那套 MQTT 推送有，但授权与许可都拿不到，
见「数据从哪来」一节），所以"更灵敏"只能靠加频率，而频率越高越像在刷接口。**局域网订阅也
已经明确排除**（按型号各写一套会话，换台设备就失效，见同节），所以别再指望"以后能到秒内"。
2026-11-10 用户决定：**第一版自动化就用现在的 3 秒 / 15 秒，不做快轮询**，只做对时间不敏感
的事；事件通道（`/miotspec/event/get`）已实测可用但先不接，将来要接也是接事件、不是把属性
轮询压到 1 秒。

开机自启（`--autostart`）默认**直接进托盘、不显示窗口**（`prefs.start_in_tray`），
设置页「常规 → 启动设置」里第二项可以关掉它，关掉后退回"最小化到任务栏"。进不去
托盘（没有托盘、或用户关了这项）也退回最小化——宁可多占一格任务栏，也不要程序在哪
都看不见。这时 `start_in_tray()` 会弹一次"已在后台运行"的气泡，顺手把
`_tray_hint_shown` 置真，免得第一次点关闭又弹一遍。

**常规页的排版**：和其它页一个格式——`_section()` 的分区标题在**卡片外面**
（"启动设置"、"关闭面板时"），卡片里只有行，没有卡内标题、没有标题图标。启动设置两行用
`ToggleSwitch`（和设置页其它页同一个开关）；关闭行为两行是「左名称 + 右圆点」
（`ui/radio_dot.py`，`QButtonGroup` 管互斥）——**不是**整行可点的勾选行，和设置页其它行
保持同一个结构。

**圆点用绿不用蓝**（`theme.select_dot`）。两套强调色分工：`accent`（蓝）= 能点 /
有焦点（链接悬停、输入框焦点、家庭标签激活、下拉框对勾），`TOGGLE_ON`（绿）= 这一项
生效了（开关打开、树里的开关列、状态点、确认按钮）。"关闭面板时"选中的那个圆点是
**结果**，和开关打开是同一件事，所以跟开关走。蓝色 `#3D7EFF` 和绿开关并排时更冷更亮，
反而会把视线从"哪一项开着"引到"哪一项没选"上。浅色主题下 `#4CC38A` 在白卡上只有
2.2:1，圆点没有轨道帮忙、会发虚，压深 8%（`#46B37F`，约 2.6:1）——**只压这一档**，
再深两处绿就会被看成两个色。

> 曾经做在卡内（`CardHeader` + `ui/settings_glyph.py` 画的线条图标），用户看过之后要求
> 改回卡外分区标题。那套代码已删，别再翻回来：`SettingsCard` 现在只接 `pad`/`spacing`，
> 页面上也不该再出现 `CardTitle`。

**关闭 ≠ 退出，是有意的语义切换**：`closeEvent` 里 `event.ignore()` 之后再 `hide()`。
接受关闭事件的话窗口对象会被销毁，而托盘图标还在，点它只会崩在"窗口已删除"上。

**"退出程序"这一项：关窗必须走 `quit_app()`，不能只 `shutdown()` + accept**。托盘挂上时
`quitOnLastWindowClosed` 是 `False`（见下），所以接受关闭事件只会**销毁窗口**——进程和
托盘图标都还在，用户看到的就是"选了退出程序，结果还是缩到托盘"，再去点那个图标又因为
窗口对象已删而毫无反应，只能去任务管理器杀。`quit_app()` 是**唯一**收尾路径：释放会话、
落盘、`tray.remove()`、`app.quit()`。两个入口都指向它——托盘菜单的「退出」，以及
`prefs.close_to_tray` 为假时的关闭按钮。

> 这个 bug 骗过了测试：断言 `_shutdown_done is True` 只证明清理跑过，而当时清理确实
> 跑完了、窗口也没了，只有进程没退。`scripts/verify_tray.py` 现在真跑一次
> `app.exec()`，用看门狗计时器验证"关窗后事件循环自己返回"，另加一条替身 `quit`
> 断言关闭路径**请求了**退出。

几条容易踩的：

- **必须先摘图标再退**。Windows 不会因为进程结束就清掉通知区域那一格，会留一个
  "幽灵"空位，鼠标划过去才消失。
- **`setQuitOnLastWindowClosed(False)`** 只在托盘真的挂上之后设。隐藏最后一个窗口
  不是"关闭"，但默认策略会在没有可见窗口时把事件循环带走——那正好是我们要避免的。
  代价是它同时也关掉了"关最后一个窗口就退出"，所以退出一律显式 `app.quit()`
  （别指望 `closeEvent` 被接受就等于退出）。
- **托盘不可用就老实退回"关窗即退出"**（`tray_available()`：`QSystemTrayIcon.
  isSystemTrayAvailable()` + `MIHOME_NO_TRAY` 开关）。硬撑一个不显示的图标，结果
  是"程序还在跑但没有任何入口"，用户只能去任务管理器杀。远程会话、精简系统、离屏
  测试都会走这一支。
- **收进托盘时释放摄像头会话**：藏起来之后画面完全不可见，继续取流等于白占一个观看位
  （设备侧上限 3 路）和一百多 KB/s。`hide_to_tray()` 里显式调 `_release_camera_sessions`，
  点开窗口再取。
- **注销 / 关机不拦**：那时 Qt 也会来要一次 `close`，`QGuiApplication.isSavingSession()`
  为真就直接真退（同样走 `quit_app`）。收进托盘会让关机卡在我们这一格上（Windows 会
  先等程序退出再强杀）。
- **几何要在 `hide()` 之前存**：`saveGeometry()` 记的是当前状态，隐藏后存下来的位置
  会是隐藏时的那份。
- **气泡只提示一次**：第一次收进托盘弹一句"还在后台运行"，之后不再弹。每次关窗都
  弹是骚扰，但第一次不说，用户真会以为关掉了。开机直接进托盘那次也会弹，并把标记
  置真（`start_in_tray`）。
- **从没显示过的窗口不落盘几何**：`MainWindow._ever_shown` 在 `showEvent` 里置真，
  `_save_settings` 只在它为真时写 `window/geometry`。开机进托盘、随后从托盘菜单退出
  时窗口没显示过，`saveGeometry()` 拿到的是默认尺寸，写下去会把用户调好的大小盖掉。
- **图标是画出来的，不是资源文件**：`tray_icon()` 按 16/20/24/32/48 各画一遍圆角方块 +
  2×2 圆点（首页那张卡片墙）。不能拿一张大图缩——缩下去圆点糊成一团。16/20px 那两个
  尺寸**关掉抗锯齿按整数像素画方块**，否则 2~3 个像素的圆点会被抹成灰边，看着像脏图。
- **菜单每次弹出前重建场景**（`aboutToShow`）：场景能在主窗口里随时改名、排序、隐藏，
  菜单持有的是快照就会过期。取数据抛错也只让"常用场景"空着，不能让菜单打不开。

`MIHOME_NO_TRAY=1` 是排障开关：怀疑"托盘里点不开 / 图标不显示"时用它把托盘整个关掉，
程序回到老行为。`scripts/shot*.py`、`--probe-camera` 都自己设了它——那些脚本自己驱动
窗口（建 → 截 → close → 退），让托盘接管 `close` 的话，关闭只会把窗口藏起来，脚本
等的是一个不会结束的事件循环。

验证：`scripts/verify_tray.py`（72 项）。离屏平台**没有真的通知区域**，所以把"能不能
用托盘"当参数传进去（`TrayController(available=True)`、`MainWindow(tray_available=True)`），
验的是判断与接线：图标多尺寸与像素、信号（单击/双击打开、右键不打开）、菜单只有两项且是
透明圆角层、关窗藏起来且没走退出清理、关掉偏好后真退出、托盘不可用时照旧退出、退出前摘
图标、轮询降频与回前台补一轮，以及**真跑一次 `app.exec()`** 确认关窗后事件循环会返回
（"进程真的退了"这事只能这么验）。**"图标真的出现在右下角、单击能把窗口叫回来、右键菜单
是圆角无黑角"只能在真机上人工看一次。**

## 轮询健康与异常提醒

**异常以前是"静默"的。** `api.Client._read_batch` 把轮询链路上的异常吞成空结果，到
`Store` 那层只剩一个空 dict，界面照旧显示旧值、用户不知道读不到了；更糟的是
`isinstance(result, Mapping)` 会把整轮失败判成成功，指数退避从来没真正生效，状态栏还会
写"已重新连接"。2026-11-11 把记账挪到**请求层**（只有那里拿得到原始错误码和异常文本），
再让界面按分级策略提示。

**记账（`core/health.py`）**

- 四类失败，对应四种完全不同的处理方式：`network`（连接 / 超时 / DNS / TLS，等一会儿
  多半自己好）、`auth`（token 过期或无效，必须重新扫码）、`server`（限流与其它服务端
  返回码）、`protocol`（JSON 解不开、响应结构不对）。
- `code` 与 `text` **原样保存**，不做二次翻译——错误码是排障第一手材料，翻成中文反而
  对不上米家文档。授权类按 `-10020 / -10030 / -704010000` 识别，限流按错误码后三位
  `992` 识别（格式是 `-70 + HTTP 状态码 + 出错位置 + 错误码`）。
- 记录连续失败次数、最近成功时间、最近错误码与原文、本次故障的起止与累计次数，以及
  `Store` 刚触发的退避区间。worker 线程记失败、主线程记退避与快照，内部用一把
  `RLock` 串起来。
- **不刷屏**：同一错误持续时只写第一行，之后每 5 分钟补一条聚合行；错误类别或错误码
  一变立刻补行；恢复正常写一行"连续失败 N 次后恢复"。正常时不写日志，只每 60 秒刷新
  一次状态快照，保住"最近成功时间"。
- 落盘 `%LOCALAPPDATA%\MiHomePanel\logs\poll_health.log`（人读）与
  `poll_health.last.json`（结构化快照）。下次启动第一件事就是把上次运行结束时到底好不好
  写进日志开头，进程被强杀也有据可查。日志单文件 1 MB，超了轮转成 `.log.1`，只留一代。

**提醒分级（`core/alerts.py`，纯逻辑、不 import Qt）**

- 授权失效、限流 / 服务端拒绝**第一次失败就报**；返回内容无法解析第 2 次；纯网络类
  连续 3 次**或**持续 ≥8 秒才报——拔一下网线、切个 Wi-Fi 不该弹窗。
- **同类只弹一次**，恢复后重置；同类系统通知之间再压 120 秒冷却，且**按类别独立计算**：
  刚弹过网络异常，不该把随后的授权失效一起压掉。
- 这里只决定"要不要显示、显示什么"，怎么显示（顶部横幅 / 系统通知）交给界面层。

**顶部警告条（`ui/alert_bar.py`）**

- **浮层覆盖、不占布局**：父控件是侧栏 + 卡片墙的 `body`，几何由 `_place_alert()` 手算，
  不进任何布局；出现 / 消失时页面内容位置完全不动。只盖卡片区，左边从侧栏右缘算起，
  左右留同样边距；`body` 一 resize 就跟着重新定位，显示时 `raise_()` 到最上层。
- 固定 48px 高，整条自绘：圆角 + 1px 状态色描边 + 状态色低浓度染底，左边状态图标，
  中间「加粗着色标题 · 正文」，右边 24×24 的 ×（命中区比图形大，悬停有圆底）。
- **没有定时器**：这条横幅的存在意义就是"不许自己消失"，收起只有两个来源——用户点 ×，
  或界面层明确 `hide()`。
- **恢复时原地变绿**：同一条浮层改成成功色，文案写"本次连续失败 N 次，持续 X"，同样
  要手动关。点 × 之后这段失败不再重复出现，恢复后解除屏蔽；恢复后再次变坏算新的一段。
- 系统通知是加强通道，不是主通道：本次运行内同类只弹一次；系统通知被用户关掉时程序
  探测不到，所以**横幅必须独立成立**。托盘不可用时没有通知，横幅照常。

**成功判据修正**

- 判据从"返回值是不是 `Mapping`"改为"这一轮是否真的读回来东西"：
  `api.Client` 在 `_record_poll` 里给出 `last_poll_ok`，`Store._apply_poll` 只看它和
  异常。整批属性都被服务端按错误码拒绝（设备集体离线 / 网关掉线）也算失败；没有可读
  属性、或全部是确认不支持的空转算成功。
- 于是 `min(6 × 连续失败次数, 30)` 的退避**真正生效**；轮询间隔本身没变（前台 3 秒 /
  托盘 15 秒），失败计数与退避另记在健康账本里，不改退避算法。

**开发用故障注入（`core/dev_fault.py`）**

- 环境变量 `MIHOME_DEV_FAULT`，取值 `network` / `auth` / `server` / `protocol`，可加
  `:轮数` 指定失败几轮后自愈（如 `auth:3`，用来观察横幅恢复变绿）；`off` 或不设即关闭。
  无法识别的取值只打一行提示并关闭，不会带着半个开关跑。
- 注入点在 `Client._read_batch` 真正发请求的那一行：异常之后走的是和真实故障完全相同的
  `classify_error → PollHealth → AlertPolicy` 链路，没有"直接显示"的捷径。
- 只作用于属性轮询（`source="poll"`）；写后补读、详情页按需读不受影响。默认零影响，
  热路径上只多一次模块变量判断。开启时主窗口标题显示「测试模式」，注入的异常文本带
  「（注入故障）」。
- 单实例挡下时（`app._report_instance_blocked`）不再静默 `return 0`：明确打印"已有一个
  实例在运行，请从托盘菜单选择退出后再重试"，并显示当前环境变量的取值与解析结果——
  否则用注入测故障时极易误判成"注入没生效"。

**验证**：`scripts/verify_poll_health.py`（31 项）覆盖四类分类、原始码保留、不刷屏与
5 分钟聚合、重启可见；`scripts/verify_alerts.py`（99 项）覆盖分级门槛、去重与冷却、
关闭后不再出现、恢复文案、警告条尺寸与关闭信号，以及"整批失败不能算成功"的判据。
两份都离线，不建真实 Client、不发网络请求。

## 排序与隐藏设备

界面顺序不是云端顺序，而是"用户排过的在前，没排过的按云端顺序追加"——这样新增的
设备 / 房间不会被埋到看不见的地方。

- 家庭、房间、设备、场景四类顺序都在「设置 → 排序」里拖，松手立即生效
- 家庭顺序同时决定顶部切换栏的排列；"上次看的是哪个家"单独记住
- **排列方式**（「设置 → 外观」）二选一：
  - `保持设定顺序`（默认）—— 位置永不变，切家庭时整排是静止的
  - `激活的排到最左` —— 当前家庭永远在第一个，切走时其余标签带 170ms 位移动画平移
  - 注意：这只影响**绘制顺序**，`prefs.json` 里存的仍是用户拖出来的那一份，
    否则切一次家庭就把排序改一次
- 隐藏设备是独立偏好：收进每个家庭末尾的「已隐藏设备」分组，卡片右键即可切换；
  隐藏只影响首页怎么排，轮询和控制都还在（点进详情页一样能用）
- **「已隐藏设备」可以整块收起**：点标题行（disclosure 三角 **紧跟在标题后面**，
  展开 ▼ / 收起 ▶，然后是常驻的「N 台」），卡片流整体隐掉，只剩 38px 的标题行——
  实测一组 21 台设备从 746px 压到 38px。
  - 三角放在标题旁边而不是分区最右边：隔着大半行空白的箭头没人会去点，
    「能点」这件事得贴着标题才看得出来。整行都可点，不要求精确命中三角
  - 台数**展开时也在**：一眼知道这一组有多少东西；不再提示「可在设置里恢复」，
    因为这组里右键就能取消隐藏，那句话只会把人往设置页支
  - 只有 `RoomView.kind == "hidden"` 的分区可折叠。普通房间的标题行保持
    `WA_TransparentForMouseEvents`，点它不会误收掉一整个房间
  - 收起态进 `prefs.hidden_collapsed`，切主题 / 切家庭 / 刷新重建墙之后仍是收起的
  - **搜索会临时展开**：命中项可能就在收起的那组里，否则"搜到了却看不见"。
    这个展开不写偏好，清空搜索后回到用户自己选的状态
- **隐藏分组内部再按房间分一层**（如「客厅 · 3 台」）：智能开关 / 音箱这类设备
  在不同房间里名字一模一样，平铺在一张流里根本认不出哪个是哪个。分组顺序沿用
  这一组自己的排序（首现顺序），只有一个房间时不分组——多一行标题纯属噪音。
  搜索时没有命中项的房间整块消失，不留孤零零的小标题。

落盘在 `<data>/prefs.json`（Windows 是 `%LOCALAPPDATA%\MiHomePanel\prefs.json`）。
删掉它等于全部恢复默认，不影响登录和缓存。

### 一处刻意不做：房间标题的批量按钮

房间标题右侧**不放**「全开 / 全关」这类批量按钮：一个房间的品类太杂（摄像头、路由器、
净化器和灯混在一起），一刀切没有意义；要一键控制走顶部的场景栏，场景的语义是用户
自己定的。这条不是"还没做"，是决定不做。

## 摄像头画面

米家摄像头没有 `stream_address`，码流走 TUTK/MISS 私有 P2P（UDP 打洞 + 帧加密），
厂商 SDK 有商业授权、不能进 GPL 发行包。2026-11-07 四轮调研的结论：账号里两台摄像头
都没有 `stream_address`，实时画面只能走 P2P；`miss_get_vendor` 已用本项目凭据实测拿到
`vendor=4`（CS2）的全套取流授权。所以这块**不自研协议栈**，把取流交给可选的
外部进程 [go2rtc](https://github.com/AlexxIT/go2rtc)（MIT）：

1. `core/camera.py` 用登录凭据（`userId` + `passToken`）生成一份只监听 `127.0.0.1`
   的配置，流源是 `xiaomi://<uid>:CN@<localip>?did=…&model=…&channel=0&subtype=0`
2. 起 go2rtc 子进程（端口从 1984 / 8554 往后找空位），等 `/api` 就绪
3. 详情页拿到 `rtsp://127.0.0.1:<port>/cam_<did>`，用 `QMediaPlayer` + `QVideoSink`
   解码，自绘控件按 cover 裁切画出来（圆角、加载态、错误态都在这一层）

### 默认不用显卡解码：显存一紧就会崩，而且接不住

Qt 的 ffmpeg 后端在 Windows 上**默认走 D3D11 硬件解码**，交给应用的帧是从显存纹理
转出来的 `NV12`。显存被别的程序（游戏）吃满时，实测两种后果都不是我们能处理的：

- 轻的：`AVHWFramesContext: Could not create the texture (8007000e)` ——
  `0x8007000e` 就是 `E_OUTOFMEMORY`，纹理建不出来，**一帧都收不到**（当时那次
  `verify_camera` 直接 18/27）
- 重的：`QVideoFrame::toImage()` 里 **access violation**。这一步就是把 GPU 帧回读成
  CPU 图像，失败时 Qt 不是返回空图而是踩空指针，Python 层连异常都看不到，
  整个面板进程直接消失（`exit=139`）

所以 `ui/camera_view.py` 在**导入期**就把硬解关掉（`QT_FFMPEG_DECODING_HW_DEVICE_TYPES
=none`，早于任何 `QMediaPlayer` 创建），帧改从内存里的 `YUV420P` 来，整条链路不碰显存。

代价实测很小，同一路 2960×1666 HEVC、同一台机器：

| | 帧格式 | 帧率 | 进程 CPU（14 秒） |
|---|---|---|---|
| 硬解（Qt 默认） | `NV12` | 20.0 fps | 4.0 s |
| 软解（现在的默认） | `YUV420P` | 19.9 fps | 5.7 s |

帧率没差别，多花约单核 12%。想换回硬解（例如 CPU 很弱、或不打游戏）设
`MIHOME_CAMERA_HW_DECODE=1`，或在环境里自己指定 `QT_FFMPEG_DECODING_HW_DEVICE_TYPES`。

定位过程留个记录，省得下次重新查：`python -X faulthandler` 拿到崩溃时的 Python 栈
（指向 `camera_view.py` 的 `toImage()`）→ 崩溃日志里翻到 `8007000e` → 对比开关硬解
前后帧的 `pixelFormat()`（`NV12` vs `YUV420P`）。排除了两个干扰项：占 10GB 内存 +
8 路 CPU 满载各跑一轮都不复现，说明不是单纯的内存/CPU 压力，而是**显存**。

### 打开页面不取流，点播放才连

首帧要 4–6 秒（官方 go2rtc 构建的实测值；装了开播补丁约 2 秒，见下），自动播等于让
用户盯着黑屏等。所以打开详情页**不建立 RTSP 会话**：只在后台把 go2rtc 和本机地址
准备好（实测 0.85 s，不占观看位、不推流），画面区停在一个播放键上。用户点下去才连
RTSP，加载态只写一句「加载中…」加一条流动的细条——**不写秒数、也不做百分比**。
链路上没有一处能给出可靠的剩余量（等 IDR 的相位完全随机），编个数字只会在某一格
上停住，看着比不写更让人以为卡死。

控件状态机在 `ui/camera_view.py`：`idle → loading → playing ⇄ paused`，另有
`released`（暂停闲置放掉连接）和 `error`。中央只在空闲/暂停/释放时放大播放键（主操作，
大一号）；右下角一排小键**共用一条规则**：有画面（播放 / 暂停）且鼠标在画面上才整排
出现，移开整排消失。首帧之前的 `QMediaPlayer` 报错会自动重连一次，不弹重试给用户。

暂停不是断开：画面停在当前帧，再点立刻续上，不会重新打洞。暂停时设备仍在推流
（实测 ~170 KB/s），所以闲置 3 分钟会主动放掉连接，把观看位腾出来。

### 首帧为什么要 5–7 秒：实测拆解

不是 P2P 打洞慢，局域网下打洞只要 0.3 秒。用
`scripts/measure_camera_startup.py` 把整条链路拆开（Xiaomi Smart Camera 3 / 069a01，
2960×1666 HEVC，局域网）：

| 阶段 | 官方构建 | 开播补丁版 | 能不能省 |
|---|---|---|---|
| go2rtc 子进程启动到 `/api` 就绪 | 0.85 s | 0.85 s | 打开详情页就在后台起，点播放时不用等 |
| 云端 `miss_get_vendor` 换票 | 0.65 s | 0.65 s | **go2rtc 每开一路都要调一次**，可以自己预取后并行 |
| MISS 握手 + `probe` 到首个 RTP 包 | 0.55 s | 0.75 s | 补丁多一次 video start，多 0.2 s |
| **等下一个 IDR** | **2.5–3.0 s** | **0** | 补丁把它消掉了，见下 |
| 177–251 KB 的 IDR 传完 + 解码出帧 | ~1.0 s | ~0.7 s | 换子码流能小一截，但画质就没了 |
| **点播放 → 出画面（实测 8 次）** | **4.8–6.3 s** | **1.85–3.15 s** | |

关键在第四行：**摄像头每 3.05 秒才出一个 IDR**（实测 `[5.25, 8.29, 11.29]`，间隔
3.04 / 3.00），而**会话起点那个 IDR 到不了消费者手里**——`pkg/xiaomi/miss/producer.go`
的 `Dial()` 是「先 `StartMedia()` 再 `probe()`」，probe 为了拿 VPS/SPS/PPS 会把开播那一包
读走，而 IDR 切片和参数集恰好在同一个 access unit 里。于是收到的最初 60 帧 POC 从 0 开始
却全是非关键帧，ffmpeg 只能一路报 `Could not find ref with POC 0/1/2…`，直到下一个 IDR
才解得出画面。也就是说**每次打开都要完整等一个 GOP**，而且随相位抖动（4.8–6.3 秒）。

不是「谁先连谁独占」的错觉：让一路先占住生产者，后面接进来的第二、三、四路只要等
**0.94 / 1.17 / 1.46 秒**（随机相位），只有**会话的第一路**固定等满 3 秒。

所以米家 App「感觉秒开」不是因为它连得快，而是它**立刻显示上次的静止画面**，再在背后
慢慢地出实时流。我们不垫旧画面（见下），那 3 秒只能从链路本身消掉——**已经消掉了**：
`scripts/patches/go2rtc-keyframe.patch` 在 probe 之后把流停掉、150 ms 后重起一次
（摄像头每次 video start 都从 IDR 开头），消费者第一包就能解码，补丁只有 12 行。

### 开播补丁（可选，首帧 2 秒）

`scripts/build_go2rtc.py` 自己编一版带补丁的 go2rtc：

```bash
.venv\Scripts\python.exe scripts\build_go2rtc.py
```

这一版同时带**云台接口**（见下一节「云台」）。两个补丁是独立的：官方构建两个都没有，
只打第一个就只有首帧优化。

- 取上游快照 `990f4de`（验证过的那个）→ `git apply` 两个补丁
  （`go2rtc-keyframe.patch` 开播、`go2rtc-ptz.patch` 云台）
  → 用 Go 1.27.3 编译（本机没有 Go 会自动下便携版到 `<data>/go/`，76 MB，只下一次）
  → 装到 `<data>/go2rtc/go2rtc.exe`
- 装之前把原来的官方构建留成 `go2rtc-official.exe`；**想回退把它改名回 `go2rtc.exe` 即可**，
  两个脚本互不干扰
- 实测 8 次：1.85 / 1.87 / 1.89 / 2.15 / 2.16 / 2.25 / 2.64 / 3.15 秒，均值 2.18；
  远程（relay）路径同样受益，端到端 2.86–3.07 秒（多出来的是 relay 握手那 0.9 秒）
- 代价：**这是一个自建二进制**。上游改了这段代码补丁会打不上，脚本会明确报错并提示手工改；
  想跟进新版本得重跑一遍（补丁与 `producer.go` 的 `Dial()` 一一对应，改动面很小）。
  上游哪天自己修了「probe 吃掉开播 IDR」，删掉补丁和这个脚本即可
- 试过但**不行**的方案记在这里免得重走：把 probe 读到的包缓存起来在 `Start()` 里补发
  （`Producer.cache`）。裸流里首包确实变成 IDR，但 Qt 端到端只到 4.7 秒且时灵时不灵——
  补发是在 RTSP 还没 PLAY 完时写的，和建流竞争；而且老包的时间戳/POC 落后于追上来的活流，
  ffmpeg 会直接跳过它继续等下一个 IDR

### 为什么不再垫上次的画面

试过把每台摄像头最后一帧缩到 960 宽存成 JPEG（`ui/snapshots.py`、`<data>/snapshots/`）
垫在画面区，让加载"看起来"秒开。但旧画面和实时的门口状态对不上，容易误导；既然改成
用户主动点播放，加载态如实说"在连"就够了（一行字 + 一条流动的细条）。这套缓存已随
`ui/snapshots.py` 一起删掉。

如果确实需要更快，只能从链路本身下手：`MIHOME_CAMERA_SUBTYPE=sd` 换子码流（IDR 从
~177 KB 降到 ~21 KB，画质明显下降，但**GOP 不会变短**），或者装 ffmpeg 让 go2rtc 转码
成短 GOP 的 H.264（依赖多 80 MB、还要吃 CPU）。

「闲置释放」那一档踩过同一个坑的变种：释放后本该是黑底 + 「闲置 N 分钟，连接已释放」。
实际却是一张**静止的旧画面**加一个播放键、一句解释都没有——先是因为详情页拿
`playbacks().release()` 收尾，而那个接口是给卡片墙用的硬重置（`stop()` +
`release_player()` → 回到空态），刚摆好的释放态被抹掉了；接着拆会话期间漏出来的
尾帧又落在空态底下（`_on_frame` 当时只挡 `paused` / `stopped`）。现在释放分支只放
所有权和 go2rtc 会话、控件外观留给自己，`_on_frame` 也改成只在 `loading` / `playing`
收帧，其余状态一律丢弃。

**没装 go2rtc 时不会静默失败**：画面区域直接写「没有找到 go2rtc」，并给出安装命令。
只装一次（7.7MB，MIT）——**官方构建，首帧 4.8–6.3 秒**：

```bash
.venv\Scripts\python.exe scripts\install_go2rtc.py
```

`install_go2rtc.py` 走 GitHub 的 **assets API**，不是
`releases/download`——后者 302 到 `objects.githubusercontent.com`，本机网络下
`github.com` 和几个常见镜像都不通，只有 `api.github.com` 可用。
（`build_go2rtc.py` 取源码用的也是 `api.github.com` 的 zipball；这条不能带
`Accept: application/octet-stream`，会回 415。）

**查找顺序**（`core/camera.py::find_binary`）：显式指定 → `MIHOME_GO2RTC` →
**程序目录**（`go2rtc/`、`tools/go2rtc/`）→ 数据目录 → `PATH`。程序目录排在前面是
为了打包版：把 go2rtc 和 exe 装在一起，它跟着程序版本走，是默认项；数据目录那份
是用户自己下载/编译的，要压过它就用环境变量。打包后 `__file__` 落在 `_internal`
里，`parents[2]` 算回仓库根这条会失效，所以 `program_dirs()` 额外加了
`sys.executable` 所在目录和 `sys._MEIPASS` 两个候选（PyInstaller onedir 把数据放
`_internal`，Nuitka 放在 exe 旁边，两者覆盖）。`verify_camera.py` 第 [13] 项会伪造
一个 frozen 布局守住这条。

**打包成 exe 时**：go2rtc 是外部进程，不会被自动收集，得摆到安装目录的
`go2rtc/go2rtc.exe`（`scripts/build_exe.py` 已经做了）。想让别人也拿到 2 秒，就得
**发补丁后的那一份**（MIT 允许再分发，但要把它的许可证一并带上，脚本会取；致谢表里
也如实登记了这处改动）；只发官方构建的话，别人装完是 4.8–6.3 秒——功能完整，只是慢。
缺件时的提示会区分两种情况：源码运行让你跑 `install_go2rtc.py`，打包版直接告诉你该
放到哪个路径（打包版没有 `scripts/` 目录）。

### 独立窗口

详情页播放中，画面右下角有一个「独立窗口」键：把同一块画面控件弹到一个约 62% 屏宽、
可四边（含右下角）缩放的无边框窗口。切换只做 `setParent` 和尺寸策略切换，
`QMediaPlayer` / `QVideoSink` / RTSP 会话都不动，所以不重连、画面不闪断；关掉独立窗口
画面回到详情页原位。观看位仍按详情页算——独立窗口不算第二路。

### 卡片 ↔ 详情页：画面跟着走，关掉再还回来

同一台摄像头在三个承载面（墙面卡片 / 详情页 / 独立窗口）之间搬，靠
`PlaybackOwnership` 单路仲裁：`claim` 开新会话、`move` 换承载面（只搬
`QMediaPlayer` / `QVideoSink` / `QAudioOutput`，不碰 RTSP）、`release` 真结束。

**去程**：双击卡片 → `wall.hand_off_active_to(dlg.camera_view, did)` →
`playbacks().move(target, "detail")`。源卡片进 `MOVED`，画面上写「画面已在其他窗口中
播放 / 关掉那个窗口即可回到这里」；墙上不再有"活动卡"，滚出视野也不会误停这条会话。

**回程**：详情页关窗时发 `about_to_stop(did)`，`MainWindow` 接到
`wall.adopt_back(did)`——卡片**还看得见**（`_card_on_screen`：可见、没被搜索过滤、
与视口相交）就 `move(card.view, "wall")` 收回去，同一个播放器、帧号连续、声音状态不变；
看不见就不收，交给 `release` 结束，绝不把一条看不见的会话留在墙上占观看位。
收回之后要调 `WallCameraController.take_back()` 重新登记成活动卡，否则"滚出视野就停"
不再管它。

两道保险，缺一条就会重现 2026-11-10 实测的那个 bug（关掉详情页，卡片永久停在提示）：

1. **会话结束要通知**。`PlaybackOwnership.on_finish` 在 `release` / `forget` 之后回调，
   卡片墙据此把还停在 `MOVED` 的卡片 `show_idle()`。MOVED 的卡片已经不是"活动卡"，
   没有任何状态推送会叫醒它，`CameraCard.refresh` 只在 store 推新状态时才跑。
2. **易主要放手**。`closeEvent` 与 `done` 各调一次 `_stop_camera`，第一次已经把会话
   还回去了，第二次看到 `_session_taken_by_other`（所有者是同 did 的另一个承载面）
   就只清本页界面直接 return。少了这一步，兜底的 `camera_service().release(did)`
   会把刚还回墙上的画面掐掉。

一个例外：详情页已经关掉的**独立窗口**再关，等于"用户不想看了"——直接结束会话，
卡片回到空闲等下一次点播放，不再还回去（要还也得重新取流，不符合"关窗就是不想看"）。

验证：`verify_camera_handback.py`（离屏，还回去 / 结束通知 / 易主判定）、
`verify_camera_card_return.py`（真机端到端：卡片播 → 双击进详情 → 关掉 → 卡片继续播）。

### 声音：go2rtc 一直在取音轨，Qt 只是没接输出设备

`xiaomi://` 的 `audio` 参数是**真参数**（`pkg/xiaomi/miss/client.go` 的 `StartMedia`
直接拼进 MISS 的 `enableaudio`），**不写默认 "1"**。所以以前局域网分支没写它——
音轨其实一直在流里，只是 `QMediaPlayer` 没配 `QAudioOutput`，Qt6 的语义就是"无声"。
跨网分支当时写死了 `&audio=0`，纯粹是因为没人听、省一点带宽。

实测（`chuangmi.camera.069a01`，局域网，`scripts/probe_camera_audio.py`）：

| 事实 | 数据 |
|---|---|
| 音轨格式 | `audio, recvonly, OPUS/48000/2`，Qt 解出来是 `48000Hz 2ch Float` |
| 能不能解 | 一路 8 秒收到 **121 个**音频 buffer（`QAudioBufferOutput` 为证） |
| `hasAudio()` 何时为真 | `LoadingMedia=False → LoadedMedia=True`，**必须挂 `mediaStatusChanged`** |
| 开音频拖不拖首帧 | 3.96s vs 3.92s，噪声级差异（`probe()` 是视频一到就返回） |
| 关掉音轨（`audio=0`） | 轨道只剩 `video, recvonly, H265`，`hasAudio()` 全程 False |

同一个 medias 里还会有一条 `audio, sendonly, OPUS/48000/2`：那是 go2rtc 默认挂上的
**对讲（backchannel）声明**，不是这台摄像头在发音频。本程序不碰它（只收），看到它
不必以为是 bug。

于是实现只有三处：

- `_ensure_player`：建 `QAudioOutput`，音量固定 1.0，`player.setAudioOutput()`
- 喇叭键：`_RoundButton` 新增喇叭图标（静音加一道斜线），显隐看 `hasAudio()`
- 禁音：`audio_out.setMuted()`，**不重建流**——关掉音轨要重建 producer、重新等一个
  GOP，点一下喇叭要等 4 秒就太蠢了

几个刻意的选择：

- **每次开播都从静音开始，而且不落盘**。点播放是为了看画面，不该先把家里/店里的
  声音放到当前环境。声音状态只属于**这一次观看**：`play()` 里重置成静音，而暂停/继续
  （`toggle`）与换承载面（`take_playback` / `adopt_playback`）都不经过 `play()`，所以
  它们保持原状。曾经把它写进偏好（`prefs.camera_muted`），用户实测后否掉了——"昨天
  点过一次喇叭"不该让今天打开就出声，重启、换设备、隔天都一样。偏好里的这个键随
  v8 一起删掉，老文件里读到直接忽略
- **喇叭键在卡片墙也有**。2×2 实时画面卡同样会出声，不给关的地方就只能去关系统音量
- **右下角整排一条显隐规则**，不给任何键开例外：`hover and state in (playing, paused)`。
  曾经让静音时的喇叭常驻、独立窗口键在有画面时常驻，结果是同一排里三个键各有各的
  出现条件——用户学到「这里的键悬停才出」，然后发现有一个不遵守，就会在别处找不到暂停；
  常驻的键还一直挡着画面。整排一起进、一起退，位置靠 `_place_buttons` 按「这套键里会
  出现哪些」算好，所以显隐不会让剩下的键横跳。键内再按语义各让一步：暂停键只在
  `playing` 出现（已暂停时中央已经是播放键），喇叭只在真有音轨时出现
- **三个小键同尺寸**（`_SIDE_BTN` / `_SIDE_BTN_COMPACT`，30 与 34）。26/30/34 混排会
  让人觉得它们权重不同，也让这一排像随手摆的；中央播放键是主操作，才故意大一号
- **`take_playback` 把 `audio_out` 一起搬**。它是独立的 QObject，不搬的话声音留在旧控件
  上，新控件按静音键改的却是自己那个没人用的设备
- 没有音轨（设备没麦克风 / `MIHOME_CAMERA_AUDIO=0`）时按钮直接不出现，不做一个
  点了没反应的按钮

**跨网音频未实测**：relay 是纯 UDP 转发（不解析负载），音频与视频走同一条通道，所以
理论上能过来；但只有离开局域网才能验。出问题时先用 `MIHOME_CAMERA_AUDIO=0` 把音轨
整条关掉，再判断是 relay 的问题还是解码的问题。

不做音量滑杆、不做对讲（go2rtc 有 `backchannel.go`，是另一件事：要麦克风权限与回声
消除）。

### 云台：规格里没有 ptz 服务，只能走 MISS 的 `0x112`

这台 `chuangmi.camera.069a01`（小米智能摄像机3 云台版）在米家 App 里能转，但
**MIoT 规格里没有任何 ptz / motor 服务**——`miotspec/spec` 列出来的服务只有摄像头、
存储卡、指示灯这些，也没有能拼出来的 action。云台指令走的是**取流那条 MISS 连接**
上的命令帧：`0x112`（上游常量 `cmdMotorReq`），载荷 `{"operation":N}`，
`N` = 1 左 / 2 右 / 3 上 / 4 下 / 5 校准。

上游 go2rtc 只定义了这个常量，没实现、也没有 API 入口。所以
`scripts/patches/go2rtc-ptz.patch` 补三样东西：

1. `Client.Motor(op)`：写一帧 `0x112`。**不等回包**——回包（`0x113` 角度）在
   读循环里会被当成媒体包读走，等它只会把发指令的时间拉长
2. **命令通道常驻读者** `drainCommands()`：CS2 的命令队列只有 **10 格**缓冲，
   没人读的话设备每回一条就少一格。连发十几条云台指令就会把队列撑满，worker
   直接关掉连接——表现是**取流突然中断**，和"观看位满了"长得一样，极难归因。
   所以登录完就起一个常驻读者把回包丢掉；取流走另一个通道，不受影响
3. `GET /api/xiaomi/ptz?name=<流名>&op=<1-5>`：**不带参数就是能力探测**，回
   `{"ok":true,"ptz":true}`；没打补丁的官方构建没有这条路由，直接 404

`scripts/build_go2rtc.py` 现在一次打两个补丁（开播 + 云台），装到
`<data>/go2rtc/go2rtc.exe`；两个补丁各自核对落点，哪个打不上都会明确报错并停下。

程序侧（`core/camera.py`）：

- `ptz_supported()` —— 只缓存**构建层面**的结论：404 记一次 False 就不再问；
  连不上（go2rtc 刚重启、端口还没起）**不缓存**，下次进页面再问
- `ptz(did, op)` —— 打本机 API，超时 2 秒。被拒（`ok:false`）不是异常：没在
  播放时那条流没有 producer，go2rtc 回的是 `stream has no ptz producer`，属于预期
- **官方构建整块退化**：路由 404 → `ptz_supported()` 为 False → 详情页连方向盘
  都不建。不给一个点了没反应的灰圆

界面（`ui/ptz_pad.py`）：画面下方一个圆，切成四块（中心孔不响应，圆外不响应），
按下哪块就往哪边转。

- **点一下 = 一条指令**。`HOLD_MS = 450` 之内松开只发按下那一条；超过它才开始连转，
  之后每 **220 ms**（`INTERVAL_MS`）补一条。两段必须分开：只有一条 220ms 节拍时，
  一次普通点击（按下到松开常常 300 ms 上下）会顺手多发一条，观感就是"点一下转两格"
- **上一条没回来不补下一条**（`_inflight`）。网络一堵就积压一串指令、松手了还在转，
  是这类控件最容易踩的坑；代价是慢网络下转速会自己降下来，这是想要的
- 松手 / 移出控件 / 关页面都停；`MAX_HOLD_S = 12` 秒兜底（收到松开事件才算停，
  收不到就最多转 12 秒）
- 按住拖到另一个方向直接换向，不用松开重按
- 可点性由承载面的 `_sync_ptz` 决定：LOADING / PLAYING / PAUSED 可点，
  IDLE / ERROR / RELEASED 置灰（没画面时发出去也只会被拒）
- **与画面的间隔 = 卡片下边距（14 px）**：圆盘外面包一层 `_ptz_host`，上边距 10，
  加上布局 spacing 4 正好 14。不能直接往布局里塞 `addSpacing`——官方构建里圆盘不建，
  那段空白会留在卡片底部；容器整体显隐，间隔跟着一起消失

**两种形态**（`PtzPad(..., overlay=)`），同一套交互、两套画法：

| | 详情页 | 独立窗口（`overlay=True`） |
|---|---|---|
| 直径 | 132（`SIZE`） | 104（`OVERLAY_SIZE`） |
| 位置 | 进布局，排在画面下方 | **叠在画面上**，贴左下角（`PTZ_MARGIN = 12`） |
| 底盘 | `bg_soft` + 1px 描边（跟着主题走） | 黑色半透明 `OVERLAY_ALPHA = 150`，悬停 +45 |
| 图形 | 主题文字色 / 强调色高亮 | 白色箭头 + 白色扇区高亮 |

- **四角必须真的透出去**：overlay 形态要 `WA_TranslucentBackground`，否则会在画面
  左下角糊出一块方底。离屏验证直接读像素（角上 alpha = 0）
- 为什么不是"和右下角那排圆钮一样的 110"：96 px + alpha 110 在真机上白色箭头会糊进
  白墙里（`scripts/out/camera_popout_ptz.png` 核对过），104 + 150 是"小而不糊"的下限
- 放**左下角**是因为右下角要留给暂停 / 喇叭 / 收回那排键；`_place_ptz` 用
  `_view.geometry()` 而不是窗口几何（上面还有一条标题栏），`resizeEvent` 后重排
- 显隐由 `CameraPopoutWindow._sync_ptz` 管：不支持（官方构建）或没画面就不露；
  关窗 / 收回详情页要 `stop()`，别让连转的定时器继续往摄像头发指令
- 探测走后台线程（`_probe_ptz`）+ `Signal` 回 UI：`ptz_supported()` 是一条 HTTP，
  没命中缓存时最长 0.8 s，开窗不能为了一个可能根本不存在的控件卡住

真机实测（2026-11-11）：

- **单条指令转多少是固件定的**：画面位移约 **10–14%**（`scripts/probe_ptz_step.py`，
  用列灰度剖面的 SAD 估水平位移），从静止起步那一条最大、之后每条约 7–8%。所以
  "点一下够不够"取决于点了几条，界面这一侧的杠杆只有"别多发"
- **固件不接受步长参数**：`{"operation":1}` 加 `step` / `duration` / `speed` / `time`
  试过四种，位移全部与基准一致（13.9% vs 14.2%）；`operation` 只有 1–5 有效，
  6–10 与 0 都无动作。**不要再去猜参数**，想改只能改交互
- 四条指令逐条下发，前后帧差异 74.6% / 74.2% / 33.5% / 35.3%（`scripts/probe_ptz.py`，
  截图在 `scripts/out/ptz_*.png`）
- 详情页端到端：方向盘排在画面下方（画面底 433 / 盘顶 448，上下两个间隔 15 / 14）、
  按住 0.75 秒只发 3 条（0 / 450 / 670 ms）全部 `ok:true`、松手后不再发
  （`scripts/verify_camera_ptz_ui.py`）
- 上下方向的画面变化比左右小（33%/35% 对 74%）：这台机器俯仰行程本来就短，
  不是指令没生效——判定"有没有转"要看成对发（左+右）之后是否回到原位
- 独立窗口端到端：方向盘在 `QRect(12, 404, 104, 104)`，画面 `QRect(0, 38, 760, 482)`
  （标题栏 38 px 被正确扣掉）；点一下只发一条、方向「上」、go2rtc 受理
  （`scripts/verify_camera_ptz_popout_ui.py`）

不做：预置位、巡航、跟随、变焦、画面拖动定位。校准（`op=5`）常量留在
`camera.PTZ_CALIBRATE` 里但界面没入口——误点会把画面拉回原点，不确定该放在哪。

### 已知边界

- 只做**实时画面 + 声音 + 云台方向**。画质切换、SD 卡回放、云存储录像已明确取消
  （理由见 TODO「摄像头二期」）
- 本程序对一台摄像头只开**一条** P2P 会话（多路观看复用 go2rtc 的 producer）；设备侧
  最多允许 **3 路并发**——实测第 4 路被设备直接掐断（go2rtc 日志 `miss: read media:
  cs2: EOF`），前三路不受影响。所以和米家 App 同看是可以的，占满 3 个观看位时后连的
  那一路才会掉
- **暂停不等于断开，也不等于让位**。实测暂停 4 秒内设备仍以 ~170 KB/s 向本机推流，
  控件只冻结在 1 帧：详情页开着（就绪 / 暂停 / 播放）就一直占着 3 个观看位之一，
  也一直走摄像头的上行带宽。离开详情页才会真正断开
- 所以**闲置 3 分钟会自动释放连接**（就绪和暂停都算闲置，播放不算）：画面变成
  「闲置 3 分钟，连接已释放」，点播放重新取流（局域网一次约 4.8–5.2 秒；远程另加
  2–4 秒握手）。阈值见
  `camera_view.IDLE_RELEASE_SECONDS`，测试可用 `MIHOME_CAMERA_IDLE_SECONDS` 调小
- **崩了不会一直占着位**。实测强杀程序后，设备侧的观看位在停止推流后立刻可用
  （新会话 0 秒内就能连上）；但 Windows 不会跟着结束子进程，会留一个 go2rtc 占住
  1984 / 8554。启动时会按 `<data>/go2rtc/runtime.json` 把它清掉——三样都对上才动手：
  pid 还活着、映像名是 `go2rtc.exe`、命令行里有本程序的配置路径，所以不会误杀用户
  自己跑的 go2rtc
- 流被掐断时能分辨原因：go2rtc 日志里 20 秒内出现 `cs2: EOF` / `read media` 就写
  「画面中断：观看位可能已满（最多 3 路）」，否则还是通用文案
- 点播放后才连 RTSP（打开页面只预启动 go2rtc，不建立会话、不占观看位），局域网首帧
  实测 **4.8–5.2 秒**：约 0.3 秒打洞 + 等一个完整 GOP（摄像头 3 秒才出一个 IDR）+ 解码
- **支持跨网**：同一局域网仍走直连（更快、更省摄像头上行带宽）；局域网不可达时自动
  回落到小米 relay，用户不用手动切。实现是 `core/relay.py` 的旁路代理——把 relay
  会话伪装成 `127.0.0.1` 上的"设备"交给 go2rtc，媒体仍是 MISS 加密负载，程序只搬
  传输层，没有改 go2rtc 源码
  - 直连失败（首帧前连不上 / 等不到 IDR）会自动切远程重试一次，画面区写
    「局域网直连不可用，正在尝试远程中继…」；只自动试一次，避免来回重连
  - 远程要先向云端要授权（`miss_get_vendor`），再做分阶段的无应答 UDP 握手
    （`LIST_REQ1` → `RLY_HELLO` → `RLY_PORT` → `RLY_REQ`），一次通常 2–4 秒，
    网络差时更久；加上等 GOP，**远程首帧通常在 6–10 秒**
  - 远程会话同样占一个观看位。只在真正播放时建立；关闭详情页或闲置释放会主动断开，
    不在后台占位。同一时刻只保留一条远程会话，切摄像头时先收旧再建新
  - 失败原因会分开写：没有局域网地址、relay 没有响应、relay 拒绝注册、
    relay 没分配端口、摄像头没有加入（多半是观看位已满或设备离线）、授权到期
  - **必须真实外网才能验证**：relay 的 `25000/UDP` 要能从当前网络出去，
    `api.mijia.tech` 要能访问。对称 NAT 下走 relay 是设计预期，但不同运营商 / 企业
    防火墙的 UDP 行为可能不同。代码只做了协议函数与离线路径校验，**没有在真实异地
    网络下回归过**
  - 设置 → 外观 → 摄像头 可选「局域网优先」（默认）或「始终远程」。异地常驻建议
    后者，省掉一次注定失败的局域网等待
- go2rtc 自身仍然只有"往设备局域网 IP 的 32108/UDP 发 LAN search"这一条路
  （`pkg/xiaomi/miss/cs2/conn.go`），跨网完全靠上面那层旁路
- 画面是 2960×1666 的 HEVC，解码靠 Qt 的 FFmpeg 后端。控制台里那几类行都不是故障：
  - `qt.multimedia.playbackengine.codec: "No HW decoder found"` —— 我们主动关了硬解
    （见上文），Qt 例行提示一次。已在 `camera_view.py` 导入期把**这一个类别**关掉
  - `[av1_mf] / [h264_mf] / [hevc_mf] … could not find any MFT` —— ffmpeg 在枚举
    Windows 的 MediaFoundation 编解码器，4 行，一次性
  - `Could not find ref with POC` / `Skipping invalid undecodable NALU` —— 从 GOP 中间
    开始解码的必然结果，每次打开约 60 行，**出画即停**。它和「首帧等 3 秒」是同一个
    原因的两面：那 60 帧本来就解不出来
- 摄像头自带的时间水印会一起显示（那是画面的一部分，去不掉）

## 打包成 exe 的实现

```bash
.venv\Scripts\python.exe scripts\build_exe.py
```

产物是 `dist\MiHomePanel\`（80 MB / 132 个文件，zip 后约 45 MB），**整个目录一起发**，
不是只发那个 exe：

```
dist\MiHomePanel\
  MiHomePanel.exe
  _internal\            Qt / Python 运行时（PyInstaller 收集后裁掉了用不到的部分）
  go2rtc\               摄像头取流组件（外部进程，PyInstaller 不会自动带）
    go2rtc.exe          打补丁的那份 → 别人装完也是首帧约 2 秒
    BUILD.txt           构建记录（自检靠它区分 2 秒 / 5 秒）
    LICENSE             go2rtc 的 MIT 原文（再分发要求）
  LICENSE  NOTICE.txt   本项目 GPL-3.0 + 第三方组件说明
```

脚本结尾会**在产物上**跑两项检查，都过才算打完：

1. `MiHomePanel.exe --self-check`：找得到 go2rtc、`go2rtc -v` 跑得起来、Qt 的 HEVC
   解得了。结果同时落在 `<data>\logs\self-check.txt`（`--windowed` 的 exe 没有可读的
   stdout，看文件）。
2. **窗口冒烟**：按"双击"的方式（`DETACHED_PROCESS`，不带任何标准句柄）再拉一次，
   然后看两件事：窗口标题里有没有 `Unhandled exception`、`<data>\logs\crash.log`
   有没有被重新写出来。任一命中就判失败。**这一步不能省**——自检是带管道跑的，
   stdout 反而是有效句柄，见下面第 3 个坑。

`--console` 打带控制台的版本排障，`--onefile` 打单文件（启动慢，go2rtc 仍要放旁边），
`--skip-check` / `--skip-smoke` 跳过对应检查，`--force-clean` 让 PyInstaller 清缓存
再编（有些环境会拦批量删除）。

上面两项都**不碰摄像头**，所以还得手动真播一次——打包产物里的 Python 是嵌进去的，
外部脚本驱动不了它，所以做成了 exe 自带的开关：

```
dist\MiHomePanel\MiHomePanel.exe --probe-camera            # 跑一次
dist\MiHomePanel\MiHomePanel.exe --probe-camera --rounds 3 # 冷启动三次看区间
```

它起完整界面、找到那台在线摄像头、打开详情页、**点一下播放**，等到画面真的上屏才
停表，报告写 `<data>\logs\probe-camera.txt`（含分辨率，能顺带证明不是黑屏）。`--lane
lan|remote` 只改内存里的通道偏好，不动用户设置。这一步过了才算"别人装完能看到画面"。

本机实测（2026-11-09，`chuangmi.camera.069a01`、补丁版 go2rtc、局域网）：产物上
`3.97 s / 1.98 s（2960×1666）`，源码模式 `3.46 / 1.97 / 0.89`。第一次总是慢一点，
因为 go2rtc 进程要冷启动。

四个只在打包后才暴露的坑，脚本已经兜住，但改打包方式时要留意：

- **go2rtc 不会被自动带上**。缺了它摄像头**完全不可用**（不是慢）——`find_binary()`
  会去 exe 旁边找，找不到就明确报路径。
- **Qt 多媒体后端是插件**。漏收集时程序能启动、日志干净，只有点播放才黑屏；
  `--self-check` 查的就是它。
- **`--windowed` 下 `sys.stdout` 是 `None`**（不是"没输出"，是对象不存在）。任何库在
  导入期碰一下 `sys.stdout.isatty()` 就会让程序在 `import` 阶段崩掉，连窗口都建不起来
  ——mijiaAPI 的彩色日志正好这么干。`mihome/_stdio.py` 在包初始化时给 stdout/stderr
  兜一个 devnull，`ensure_streams()`，别删。
  这个坑很阴：**从终端跑没问题**（Windows 把控制台句柄继承给子进程），只有双击才崩。
  崩溃时 PyInstaller 只弹一句英文 "Unhandled exception in script"，所以打包入口
  （`scripts/build_exe.py` 生成的 `_launcher.py`）另外接住了异常，写
  `<data>\logs\crash.log` 并弹一个中文提示框。
- **子进程的标准输入句柄无效**。窗口化进程没有控制台，`subprocess` 继承到的是空句柄
  （典型症状 `OSError: [WinError 6] 句柄无效`），所以所有 `subprocess.run/Popen` 都显式
  传 `stdin=subprocess.DEVNULL`。

### 体积：119 → 79 MB（2026-11-09）

PySide6 的 PyInstaller hook 是"宁多勿少"：整个 QML / Quick / PDF / 虚拟键盘都会收进来，
哪怕程序一行都没 import。全量 119 MB / 888 个文件，zip 后约 60 MB。

`build_exe.py` 打完会按 `_TRIM` 清单删一遍，实测 **119 → 79 MB / 132 个文件**，zip 45 MB。
（2026-11-11 带云台重测：80 MB / 132 个文件 / zip 45 MB，多出的 1 MB 是云台与叠加控件。）
逐项（按省得多排）：

| 删掉 | 省 | 依据 |
|---|---|---|
| QML / Quick / OpenGL 六个 DLL | 14.7 MB | 只用 Widgets；`Qt6Multimedia` 的静态依赖是 Core / Gui / Network，这一组只互相引用 |
| Qt 翻译只留中文 + 英文 | 6.9 MB | 128 个 `.qm` 里用得上的只有 4 个（程序目前没接 `QTranslator`） |
| `opengl32sw.dll` | 5.3 MB | 软件 OpenGL 后备；默认删，见下面的兼容性说明 |
| `Qt6Pdf.dll` + `qpdf` 图片插件 | 4.4 MB | 只有彼此引用 |
| PIL 的 avif / webp / cms / tk 扩展 | 2.0 MB | 只用来存设备图标 PNG，AVIF 一个就 1.8 MB |
| tiff / webp / icns / tga / wbmp 图片插件 | 1.6 MB | 图标是 PNG/JPEG，PNG 解码内建于 Qt6Gui |
| direct2d / minimal / offscreen 平台插件 | 1.2 MB | 只用 `qwindows`（offscreen 只有开发机截图脚本会设） |
| Qt 的 TLS 插件 | 0.6 MB | 云端走 Python `requests`，Qt 只连本机 go2rtc |
| `tzdata` | 0.5 MB | Windows 上 `tzlocal` 走系统时区 API，不读 zoneinfo 数据 |
| 虚拟键盘 + 输入法插件、TUIO | 0.5 MB | 物理键盘 |

判据不是"看着没用"，是 `scripts/pe_imports.py --who <名字>` 扫一遍产物里所有
`.dll` / `.pyd`，确认**没有任何 PE 静态引用它**：

```
.venv\Scripts\python.exe scripts/pe_imports.py --who Qt6Qml.dll dist\MiHomePanel\_internal
```

换成新版 PySide6 后要重跑一遍：上游合并或拆模块是常事，旧结论会过期。三条边界：

- **插件和它指向的 DLL 要成对删**。Qt 插件是运行时 `LoadLibrary` 按名字找的，导入表里
  看不出"谁要它"——`Qt6Pdf` 能删，是因为唯一引用它的 `qpdf.dll` 一起删了。只删插件会
  留一个 4.4 MB 的死文件，只删 DLL 会让那个插件加载失败。
- **`opengl32sw.dll` 是兼容性保险，不是垃圾**。显卡驱动正常的机器永远用不到它，
  虚拟机 / 远程桌面 / 老驱动才会回退到它。默认删（省 5.3 MB），`--keep-sw-opengl` 保留；
  **要发到那种环境请务必加上**，否则表现是没画面而不是报错。
- **`--no-slim` 是完全不裁的对照版**。怀疑"装完和别人不一样"时用它重打一份二分。

裁剪发生在自检与窗口冒烟**之前**，所以删过头当场就会 FAIL，不会拖到用户机器上。

`go2rtc.exe` 那 21 MB **不要 UPX**。实测：压到 6.1 MB，但冷启动从 80 ms 变成 486 ms
（每次开播都吃这一下），而且 Go 二进制 + UPX 是杀软的高误报组合；更要紧的是分发包
几乎没省——原版 20.6 MB zip 后 8.0 MB，UPX 版 6.1 MB 已经压不动，只差 1.9 MB。

## 踩坑清单

这些是实测确认、写进代码注释的：

- **"关窗时顺手再应用一次主题"就是闪烁**。`_apply_theme` 里有 `wall.rebuild_palette`
  （整墙 56 张卡拆了重造），叠加在"弹窗销毁 + 点击层隐藏 + 压暗层隐藏"三处整窗
  失效上；主窗口是 `WA_TranslucentBackground`，Qt 在这种窗口上逐控件分段提交，
  于是看得见"卡片变矮、body 全空"的中间帧。主题只在**真的变了**的时候应用，
  收尾动作统一冻在 `_run_dialog` 的 `setUpdatesEnabled(False)` 里合成一次重绘。

- **子设备 did 不可用**。多键面板派生的 `1087931746.s3` 对它发请求要拖到 6 秒才返回
  `-704083036`。云端只认父 did + 该路 siid。`.sN` 的 N 就是 siid。
- **"规格里有"不等于"设备认"**。红外空调的 `ir-mode`、部分门锁的 `lock-action` 回读
  一律 `-704002000`。所以有一层能力学习账本，把确认不支持的记下来，之后跳过而不是每
  3 秒重试一次。**但离线/超时绝不能记为不支持**，否则设备掉线一次就永久失去控制。
- **错误码要看后三位**。格式是 `-70 + HTTP 状态码 + 出错位置 + 错误码`，
  `013` = 属性不可读、`043` = 属性值错误、`011` = 设备离线。硬编码整个码值会漏。
- **`prop/action` 的参数键是 `in`，不是 `value`。** 这是本项目真机翻过车的一处：
  顶栏指令条发「现在几点了」回 `-704220025`（Action 参数个数不匹配），型号、`siid`、
  `aiid` 全对，错在把参数塞进了 `value`——`value` 是**属性**（`prop/set`）的键，
  action 上云端只认 `in`，于是它认为"一个参数都没给"，而这个动作要 2 个。
  正确形状：`{"did","siid","aiid","in":["现在几点了", false]}`（虚拟事件
  `siid 4 / aiid 1` 用 `in:["事件名"]` 实测 `code 0`，是同一条规矩的现成证据）。
  排障第一步永远是 `probe_speaker.py ... --dry`——把 body 原样打出来，不碰设备。
  `-704220025` 的释义来自上游 `mijiaAPI/errors.py`（注释给了 ha_xiaomi_home 的 i18n 出处）；
  我们在 `core/api.py` 的 `_CODE_TEXT` 里只收常用几条，`explain(code)` 翻成人话并**保留原始码**。
- **`updateTime` 不随读取推进**。从没变过状态的插座会显示"3 天前"，所以它只能表示
  "多久没变过"，不能拿来判断数据新鲜度。（现状：用来做「读数陈旧」提示，措辞是
  "未更新"而不是"未变化"，见 `core/freshness.py`。）
  它是**每个属性各自**一份的：`scripts/probe_staleness.py` 采样 320 个读点，绝大多数
  不随读取推进（75/85），少数"每次上报"的量会刷新、那类永远判不出陈旧——属于保守方向；
  32/234 个静态元数据没有这个字段。阈值定 3 天有分布依据。
- **控件的视觉自更新 ≠ 写请求发出去了**。`CardSeg` / `CardToggle` / `CardSlider` 都是
  "先改自己的状态、再 emit `committed`"——接线漏了的话，UI 照样跟着手变，看着像生效了，
  设备一动不动（`FanBody` 就这么漏了一整个版本，见「卡片控件库」第 4 条约定）。
  凡是 body，验证要从 `body.value_committed` 那头断言，**直接连 `widget.committed`
  测的是零件，绕过的正是出事的那一层**。
- **多键面板的按键不能一律用胶囊网格**。2–3 路的按键条只有 28px 宽，竖排文字会被压成
  一条缝，所以 1 路给一整块、2–3 路并排成竖条（标签一个字一行竖排），4 路以上才退回
  胶囊网格。
- **`run.bat` 必须保存为 CRLF 换行 + GBK 编码**。cmd.exe 解析批处理的括号块时要求
  CRLF，用 LF 会把 `(...)` 里的每一行拆成独立命令，报 "'...' 不是内部或外部命令" 和
  "'errorlevel' 不是内部或外部命令"。仓库里靠 `.gitattributes` 的
  `run.bat text eol=crlf` 兜住换行，**但编码靠编辑器自律**——改脚本时别让它存成
  UTF-8，否则中文提示会变乱码。
- **人体传感器大多没有 `occupancy` 属性**，只有 `motion-detected` 事件，属性轮询拿不到。
- **QSS 里的 8 位十六进制是 `#AARRGGBB`**，不是 `#RRGGBBAA`。写 `#9CA3AF66` 想要
  "灰色 40% 透明"，实际得到的是一块橄榄绿。要透明度就用 `rgba()`。
- **系统深色模式会漏进界面**。QSS 只画写了规则的控件，普通容器背景仍来自 QPalette；
  只在 QSS 里写 `QDialog{background:...}` 时，设置页正文会是一块系统深灰。所以
  `theme.qpalette()` 会显式把调色板也设一遍。
- **"取色板里那一档"是个陷阱**。同一支 `card`（深色 #1B1D22）压在设置窗口底
  `surface_bg`（#191A1D）上只差 2–5 个明度档，肉眼看就是一块；浅色主题下反而差 23 档
  白得干净。所以凡是要"浮起来"的容器，都得相对**它所在的那一层背景**推一档——
  `nav_bg` / `rail_bg` / `panel_bg` 三支分开写，谁也别想着复用谁的数值。
  反向也成立：面板比 `card` 亮之后，行悬停 / 选中（`panel_row_hover` /
  `panel_row_selected`）必须重新基于面板底算，否则深色下会变成"挖洞"。
- **没有父控件的 `QWidget` 就是一个顶层窗口**。`QLabel("说明")` 这种写法在
  `setVisible(True)` 的那一刻会真的弹出一个几十像素的窗口（屏幕左上角，一闪而过）。
  设置页十几行一起建，用户看到的就是"点设置有个小窗闪一下 / 许多小窗快速闪现才打开
  设置页"。**把 `setVisible` 挪到 `addWidget` 之后并不能解决**——那时布局本身还没挂到
  任何 widget 上，父控件仍然是 `None`（`SettingsRow.sub` 就踩过这个，见
  `settings_rows.py` 里两个 `QLabel(..., self)`）。凡是"先建再按需显示"的控件，
  构造时一律显式传 parent。验收方式：在 `QApplication` 上装一个拦 `QEvent.Show` 的
  过滤器，断言 `isWindow()` 的命中为空（`verify_autostart.py` 的 `_ShowSpy`）。
- **`QLineEdit` 的长度限制要挂在 `textChanged`，不能只重载 `insert()`**。
  键盘输入、`paste()`、输入法上屏都走 QWidgetLineControl 的内部实现，Python 里覆盖
  `insert()` 只对"自己调 `input.insert(...)`"有效，真实粘贴照样超长。而且 `setMaxLength`
  是静默截断，用户不知道少了什么。做法：`textChanged` 里判长度、就地截断（`blockSignals`
  围住，免得递归）再弹一条 toast。
- **QSS 里写 `qproperty-alignment: AlignRight | AlignVCenter;` 会炸掉整张样式表**。
  Qt 的解析器读到这种带 `|` 的枚举值就停，**后面所有规则一起失效**——表现是卡片
  底色、圆角统统没生效，看着像 objectName 写错了。对齐这类属性老老实实在 Python
  里 `setAlignment()`。
- **`addWidget()` 一旦带 alignment，布局就按 sizeHint 摆放而不铺满单元格**。
  `ElidedLabel` 的 sizeHint 被 `Ignored` 策略压成十几像素，于是"凭据文件"那行的值
  整块消失。要铺满就别传 alignment，把右对齐交给控件自己的对齐属性。
- **无边框窗口的"前后层"要自己造**。系统窗口自带阴影和边框，`FramelessWindowHint` 之后
  就只剩两块同色方块。现在靠三件事区分：子窗口底色离开主窗口一档（浅色更深、深色更浅）、
  外圈 1px 描边、弹出时主窗口整体压暗。`QGraphicsDropShadowEffect` 对顶层窗口无效，
  真要做投影得开 `WA_TranslucentBackground` 自己画。
- **QSS 的 `border` 不会自动让出内容区**。给 `QDialog` 写完 `border:1px` 之后，布局
  margins 还是 0，子控件会正好盖住那一圈，看起来像没生效。要 `setContentsMargins(1,1,1,1)`。
- **圆角只能靠遮罩**。无边框窗口没有系统帮忙裁圆角，`QSS border-radius` 也不会裁子控件。
  现在用 `setMask(圆角区域)`（逻辑像素，Qt 自己按 DPI 换算），代价是边缘没有抗锯齿
  （1 物理像素台阶，1.75 倍缩放下基本看不出）。两个必须记住的点：**最大化要 `clearMask()`**，
  否则四角会露出桌面；**每次 resize 都要重算遮罩**，不然窗口拉大后角又变回直角。
- **浮层（菜单 / 提示 / 下拉列表）的圆角是另一套，不是遮罩**。它们都是独立的顶层
  窗口，平台先铺一层不透明的方底，QSS 的 `border-radius` 只画在方底上，四角外
  仍然是方的。三处统一用 `FramelessWindowHint + NoDropShadowWindowHint +
  WA_TranslucentBackground` 让窗口自己透明（见 `menu.py` / `tooltip.py` /
  `combo.py`）。列表行改自绘 delegate，免得 QStyle 再画当前项的方框和
  `palette.highlight()` 方底。
- **`WA_TranslucentBackground` 必须在窗口创建前设，事后补是假透明**。`QMenu` 在
  构造函数里设，Windows 平台就给它 `WS_EX_LAYERED` + 8bit alpha；下拉框的
  `QComboBoxPrivateContainer` 却是 `showPopup()` 内部懒创建并**立刻显示**的，
  等拿到它再补属性，原生窗口已经按不透明建好（`alphaBufferSize() == -1`），
  四角的"透明像素"在屏幕上合成成纯黑方块。离屏 `QWidget.grab()` 只抓控件自己的
  backing store，四角 `alpha=0` 一片绿——**这类问题必须查原生窗口属性**。
  `Combo._make_layered()` 第一次展开时 hide → 设属性 → 把 `QWindow.format()`
  改成 8bit alpha → `destroy()` 旧 HWND → `setWindowFlags` 重建 → show；
  `verify_combo.py --native` 就是拿 `WS_EX_LAYERED` / alpha 做断言，离屏那套
  和真机这套**都要跑**。
- **浮层底色不能照抄承载它的卡片**。四角黑块没修之前，边界其实一直是黑块在提供；
  修好之后弹出层和设置页分区卡同为 `panel_bg`，整张菜单直接隐身。现在底色走
  `theme.popup_bg()`（深色比卡片亮、浅色比卡片略暗），边界再补一条**自绘**
  抗锯齿圆角描边 `theme.popup_border()`——绝不能写进 QSS 的 `border`，否则
  `QFrame` 会在圆角外又画一圈带斜接的方角框。
- **`QComboBox::showPopup()` 会把当前项对齐到控件本身**，列表正好盖住控件，用户看不到
  自己选的是什么。`Combo._place_below()` 改成右边缘对齐、控件下方留 8px，
  下方放不下才翻到上方，控件和 `^` 箭头全程可见。
- **下拉列表里的 `State_Selected` 不是"已选值"，是"鼠标/键盘临时停在哪"**。
  Qt 的 `QComboBoxPrivateContainer` 每次鼠标划过都会 `view->setCurrentIndex()`，
  那块跟着跑的高亮只是光标位置；真正的值在 `combo.currentIndex()`，弹出期间不变。
  以前把两者混为一谈，用户一移到别的选项就忘了原本选的是哪项。现在
  `PopupDelegate` 按 `currentIndex()` 给那一行画稳定的选中底 + 一支自绘的
  accent 色 ✓（不用字体，中文黑体缺这个字形会渲染成豆腐块），临时高亮只用
  `theme.popup_row_hover()` 的淡中性底；**每一行都预留同一个右侧勾槽**，否则文字的
  elide 边界会随鼠标忽长忽短。悬停色必须相对 `popup_bg()` 算，沿用相对分区卡的
  `panel_row_hover()` 会在深色下挖出一块暗洞。
- **`QComboBox` 默认吃滚轮**：鼠标停在下拉框上想滚页面，会顺手把设备属性改掉。
  `Combo.wheelEvent` 整个 ignore（键盘上下键保留，那是明确的输入），未接受的
  滚轮事件留给父级滚动区。设置页和设备详情页共用同一个 `Combo`，样式只在
  `combo_qss()` 里写一份。这条已经上升为全局规则，见
  [交互约定：滚轮只滚页面](#交互约定滚轮只滚页面)——卡片滑条 / 步进器同样不吃滚轮。
- **自绘标签行的盒模型必须所有项一致**。胶囊档曾给每个 rect 都算上左右
  `PILL_PAD`，却只把激活项文字居中、其余左对齐——激活项平白多出 14px 左偏移，
  看起来"明显偏右"，切换家庭时文字还会在居中/左对齐之间来回跳。改成所有项统一
  居中后间距均匀、文字不动。但整排会因此右移 14px，父容器得抵消：
  **Qt 会把负的 `setContentsMargins` 静默换成样式默认值**（实测 `-14` → `9`/`11`），
  所以顶栏改用正边距扣减（`24 - inset`），设置页预览把标签控件当作子控件
  `move(-inset, 0)`（Qt 不裁剪子 widget 的绘制，卡片本身还有 16px 内边距兜底）。
  `HomeTabs.content_inset` 是这个缩进的唯一来源，切样式后必须重新读取。
- **自绘滑条的 thumb 圆心要按半径内缩，轨道不用内缩**。`CardSlider` 原来让轨道和
  圆心共用一组 `x0/x1`：轨道贴边画（详情页 compact 直接是 `x=1`），thumb 圆心也落在
  `x0`，半径 7 的圆有 6px 画到控件外面。`QWidget` 不会裁剪子控件，但**会裁自己的
  `paintEvent`**，所以最左端（`0 分钟` 这种很常见的初值）圆点被切掉一块，看着像被
  遮罩挡了。现在分成两套坐标：`_span()` 返回**圆心**可用范围（左右各内缩
  `_THUMB_R`，含拖动时那 1px 放大），`_track_span()` 再外扩回贴边位置给轨道用；
  填充仍按「轨道宽 × 比例」算，满值时不会在右端留缺口。卡片 body 的滑条同样受益：
  圆心变成贴轨道左端，而不是压在左侧标签区上。
- **截图脚本里 `grab()` 出来的 QImage 带着 1.75 的 `devicePixelRatio`**。直接拿它当
  画布、又按物理像素坐标 `drawImage`，会被再缩放一次，图层缩小甚至跑出画布。
  拼板前先把所有图层的 DPR 抹成 1（`shot_ui.py` 里的 `step_combo()`）。
  同理，**直接 `grab()` 一张自绘圆角卡片，四角外会被填成不透明黑**：按圆角裁剪
  叠上去，抗锯齿边缘已经和黑色混过，浅色底上会留一圈暗描边。正确做法是给它套一层
  填了 `pal.bg` 的父容器再 `grab(容器)`，让边缘和真实界面一样与背景混合。
- **截图脚本的定时回调链会吞异常**：`shot_ui.py` 全靠 `QTimer.singleShot` 串联，
  PySide6 对回调里的异常默认只把 traceback 打到 stderr 然后**继续跑事件循环**，
  脚本就挂在那里等一个永远不会来的 `done()`——不设外层 timeout 会永久卡死，设了
  也只是 `124`，和「图漏截了但正常退出」一样看不出原因。现在装了 `sys.excepthook`
  统一收尾（还原 prefs → 退出循环 → `main()` 返回 1），**只看 exit code 就能判断
  这轮截图是否完整**。这也是上次那批图少几张、却只能靠文件时间戳发现的原因。
  同理，**等 30 秒仍拿不到设备数据也算失败**（`failed=True`）：这时截出来只是一面
  空墙，脚本会直接提示「先运行 run.bat 登录」而不是生成一堆空白图。这条降级路径
  原来直接 `app.quit()` 跳过了 `done()`，会把测试改过的家庭/主题和 `prefs.json`
  留在日常配置里。
- **收起一个装着 `FlowLayout` 的分区，父 `QVBoxLayout` 不会自己收高度**。`_body` 是
  带 `heightForWidth` 的布局宿主，`setVisible(False)` 之后分区仍旧保持展开时的
  高度（实测 746px 纹丝不动，只是卡片不画了，下面多出一大片空白）。`invalidate()`
  也不够，必须 `invalidate()` + `activate()` 显式重排（`WallView._relayout()`）。
  反过来，`apply_card_style()` 里**只** `invalidate()` 不做 activate：那里换的是卡片
  自身宽度，`FlowLayout` 会自己重排，立刻重算根布局反而让滚动位置跟着跳一下
  （`verify_card_style.py` 的「局部刷新自己就会重排」就是盯这件事的）。
- **嵌套的 `FlowLayout` 要显式把 `heightForWidth` 传上去**。「已隐藏设备」按房间分层后，
  卡片流不再直接挂在 `_body` 上，而是各有一层宿主 `QWidget`。宿主必须
  `setSizePolicy(...)` 且 `policy.setHeightForWidth(True)`，否则父 `QVBoxLayout`
  按 `sizeHint` 给高度，分组后卡片被压成一条或撑出空白。
- **`wall.grab()` 是透明的**：墙的底色由主窗口铺，单独抓这个控件只得到一张全透明图
  （`alpha=0`，看着像"全白/全黑"，很容易误判成没渲染）。截图要么抓整个窗口，要么先
  把主题底色铺上去再 `drawPixmap`。
- **小图标要按像素判断，不能用平滑放大**。顶栏刷新图标只有 ~19px，放大 6 倍看
  "还行"的三个候选，换成 `Qt.FastTransformation`（最近邻）一放大全是糊的。另外
  1.7–2.0px 的**描边弧**在这么小的尺寸上会被抗锯齿摊成灰圈，箭头根本读不出来。
- **小尺寸的箭头别自己拿三角拼**。三角箭头的底边是沿**半径**方向的，缩到 20px 后
  那条 6–7px 的底边会读成"环上鼓起一根竖刺"，而它真正指的方向反而看不见——两次
  自绘都是这个毛病（第一版是 290° 弧 + 一根斜线）。改成 Material `refresh` 字形的
  **方头箭头**（一整块实心色块，缩小后仍是一个色块）才读得出来，路径见
  `main_window._refresh_path` 与「开源致谢」里的 Material Icons 一行。教训是：
  这个尺寸下要判断"缩小后还剩几个可辨识的色块"，而不是"放大后线条好不好看"。
- **浅色主题的卡片底色要守一条下限**。`bg #F1F2F4` 只比白卡暗 13，开启态再混 10%
  品类色就只剩 1–3；电视、摄像头这类深灰品类混完**比背景还暗**，卡片整个糊进背景
  （用户报的「电脑」就是这个）。`theme.tint(..., min_gap=6)` 会把染色强度往小收到
  刚好够看为止——亮度是强度的线性函数，解方程即可，不用二分。
- **卡片模板的 body 必须是真实 `QWidget`，不是 `QPainter` 手绘**。拖动捕获、
  移出控件后的追踪、「点空白开详情 / 点滑条调亮度」的事件分流都是白送的。代价是
  三条要自己兜：鼠标移到子控件时**父卡片也会收到 `leaveEvent`**（用
  `QCursor.pos()` 判断光标是否还在卡片 rect 内，别让悬停底色闪一下）；子控件默认
  `ignore()` 的 `ContextMenu` 要在 body 上接住转发给卡片；切主题时子控件不会跟着
  外壳重绘，得显式 `apply_theme()`。
- **右键菜单的子菜单是另一层原生窗口**。`parent.addMenu("标题")` 让 Qt 自己建的那一层
  既没有 `WA_TranslucentBackground` 也没去边框，圆角背后又会冒出方块底——和主菜单
  当初一模一样。用 `menu.submenu()` 显式建同一个 `Menu` 类；勾选也别用
  `QAction.setCheckable(True)`（系统 check indicator 带方底），改成自绘 `QPainterPath` ✓，
  未选项放一枚同尺寸透明图标占位，文字左边缘才齐。
- **悬停提示只在卡片标题带触发**。`tooltip.watch()` 默认把整个控件矩形算命中区，
  可 2×1 灯具的亮度/色温滑条是真实子控件，气泡从光标右下 16px 展开会压住轨道。
  现在 `watch(..., hit_test=...)` 让卡片只认「名称 + 状态文字」那一条（右上电源键
  也扣掉）；Enter / Leave / 定时到点 / MouseMove 四处共用 `_still_inside()` 这一份
  判据——**卡片内部从标题移到内容带只有 MouseMove**，不补这一条提示不会收。
- **提示文字里的 `\n` 必须在测量阶段吃掉**。`TipBubble._wrap()` 是按字宽逐字断行的，
  整串丢进去时 `\n` 会被当成一个普通字符塞进某行中间；可 `drawText` 见到 `\n` 照样
  换行，而每行给的矩形只有 `fm.height()` 高——第二行溢出矩形、和下一行叠在一起，
  看起来就是文字挤成一团（2026-11-11 用户实测截图）。现在先按 `\n` 分段、段内再折行，
  空段保留成空行。provider 里写换行是"作者意图"，别指望折行逻辑替你保留。
- **卡片「大小」和「模板」曾是两份偏好，其实不独立**：模板的 `min_span` 会悄悄
  把用户设的 1×1 撑成 2×1，宽度变成只在切回标准时才复活的影子状态；而
  `2×1 + 标准` 只是把 76px 产品图放进一张更宽的空卡，`1×1 + 双滑块` 根本不可达。
  现在宽度写进样式（`standard` 1×1 / `light_dual` 2×1 / `light_bright` 2×1），
  `prefs.card_styles` 一条记录就是一个 `did → style_id` 字符串。v3 的
  `{span,template}` 在读取时迁移：`template` 沿用为样式 id，只设过 span 的记录
  回默认小卡。默认样式由品类声明（多数设备是 1×1 标准，存在传感器是状态卡），
  菜单第一项就是当前默认（点它会删掉偏好记录），
  所以「恢复默认样式」也删了。改样式仍走 `WallView.apply_card_style(did)` 局部刷新
  ——重建整面墙会连滚动位置、其它卡上的悬停、正在拖动的滑条一起丢掉。
  菜单文字的格式统一成 **`宽卡 2×1：亮度 + 色温`**：尺寸是「占多大格子」的硬信息，
  放在冒号前先读到；同尺寸的项前缀完全一致，纵向扫一眼就能分组，不用逐条读内容。
- **合并的是"用户那一次选择"，不是数据模型里的两个维度**。尺寸（`span`）是**全品类
  通用**的：只有 1×1 / 2×1，定义在 `SIZES` 表里，菜单前段完全由它生成；内容
  （`label` + `slots`）跟品类走，灯是「亮度 + 色温」，空调是「温度控制」。
  `CardStyle.label` **只准写内容名**，写了尺寸会在 `__post_init__` 直接报错——否则
  同一段尺寸就有 `span` 和字符串两个来源。`span` 也必须在 `SIZES` 里（写 3 会在
  import 时报错，而不是菜单上显示成"宽卡 3×1"）。加一个品类的模板只需声明
  `CardStyle(id=..., label="温度控制", span=2, category="ac", slots=...)`，
  尺寸文案、菜单前缀、几何宽度都不用碰。
- **同一内容可以出现在多个尺寸上，靠 id 区分、label 不用加后缀**：两条记录
  `id` 不同、`label` 相同、`span` 不同，菜单自然读成「小卡 1×1：温度」/
  「宽卡 2×1：温度」。**同名判重按"单台设备可见的集合"来做**：两个样式的
  `category` 相同、或任一方是通用的 `None`，它们才可能同时出现在一张菜单里，
  这时 `(label, span)` 撞车必须拒；品类不同的两条（灯的「亮度」和浴霸的
  「亮度」）永不同框，放行。id 若重复会静默覆盖偏好，同样拦掉。
- **`standard` 不是某品类的模板，是所有设备的兜底外壳**：`category=None`、
  `slots=()`，含义是"不挂内容带，产品图 / 多键面板由外壳自绘"。任何品类里
  看到「小卡 1×1：标准」都是同一件事——**回到产品图外观**。
- **「默认」和「标准」不是一回事**。品类可以在 `catalog` 的 `CategoryProfile`
  上声明 `default_style`（存在传感器 → `presence_state`、空调 → `temp_control`），
  表示"没有偏好时用
  哪个样式"，`resolve_card_style()` 三道兜底（没设过 / id 不认识 / 能力不够）
  都落到 `default_style(card)`，而不是硬编码标准。所以：
  - `prefs.card_style(did)` 对"没设过"必须返回 **`None`**，不能预填 `standard`
    ——两者混成一个值，品类默认永远轮不到；
  - 菜单里默认项排第一（排序键 `(不是默认, span)`），且"点默认项"= 删记录；
  - 在默认≠标准的设备上点「标准」是一条**真实偏好**，必须落盘（`set_card_style`
    带 `default_id` 参数），否则用户点完又回到状态卡，菜单像失灵。
  - `catalog` 是 core、样式表在 ui，两处只能靠 id 字面量对齐；
    `validate_profile_defaults()` 在 import 时校验拼写，拼错会当场报错而不是静默
    退回标准。
- **body 不只有滑条**（`CardStyle.body`）：`sliders` 建 `CardSlider`，
  `readout` 建 `CardReadout`（只读大字），`controls` 则**按属性类型各配一种控件**
  （布尔 → 开关行、枚举 → 分段轨道（2026-11-12 前是胶囊组）、数值 → 步进器）；
  空调「温度控制」是第一个用户：2×1 里一行「− 26°C +」加一行五个模式
  （模式那行现在是轨道，见「模式和角度：轨道分段控件」）。**减号在数字左侧**是刻意的：
  卡片 body 有 312 宽，两个按钮都挤在右边时手指要在同一处分辨减/加；
  数字两边各一枚和空调遥控器一致，左边调低、右边调高。详情页那一行左侧还要
  放属性名，仍是「数值 …… − +」。存在传感器的卡片正中一个「有人」，
  副标题仍然是「有人 · 49%」——**不为了去重去动副标题**：`skip` 需要知道 body
  实际建出了哪些控件（声明了但没绑上的槽位会被 body 丢掉），而副标题和 body 是
  两条独立的渲染路径，耦合后详情页（`DeviceState.subtitle`）那份还得另算一遍。
  让副标题只认 `card.metrics`，换样式时它一个字都不变，代价只是重读一次状态。
  两种 body 的可用性判据不同：滑条要求 `value_range`（没刻度映射不了轨道像素），
  读数只要属性存在。槽位查的是 `CardSpec.bound()`（**先控件后读数**），
  所以样式可以引用 `occupancy` 这种登记在 `metrics` 里的只读指标，不必知道
  它当初登记在哪一边。
- **2×1 宽卡的 body 要主动用掉宽度**。卡片内容带是 312×78，而「数字 + 两个按钮」
  只有 ~130 宽：按详情页那套「数字靠左、按钮贴右」排，中间会空出 200px，看着像
  少画了一块。所以给 `CardStepper` 加了 `centered`（整组居中）、给 `CardChips`
  加了 `spread`（余宽均分给每一项，变成等宽分段控件），两个开关**只在卡片 body
  里打开**，详情页那套默认行为一个字没动。温度用步进器不用滑条，是因为它是个
  精确的小整数（16–32），拖拽反而选不准——这也是米家的做法。
- **可见性只有一条链路**：`CardStyle.available()` 先卡 `category`（`None` = 通用），
  再按 body 类型要求 `slots` 里每个槽位都真绑上属性。`catalog.build_card()`
  会把没绑上的槽位直接丢掉（只对 `critical` 的记进 `missing`），所以卫生间那种
  只能调亮度的平板灯 `card.bound("color_temp")` 返回 `None`，菜单里就没有
  「亮度 + 色温」，只剩「标准」和「亮度」；如果它以前存过双滑块，`resolve_card_style()`
  会兜回默认样式，不会留一张空卡。
- **`QMediaPlayer` 重播同一个 RTSP 地址必须先 `stop()`**。直接 `setSource(同一 URL)`
  会被判定成「源没变」而不重连；表现是点重试毫无反应、画面一直停在错误态。
- **Qt 的 RTSP 第一次 `SETUP` 会收到 `461 Unsupported transport`**，然后自己回退 TCP。
  日志里那行不是错误，别照着它去改传输方式。
- **`QGuiApplication` 下建 `QWidget` 会直接把进程带走**：退出码 127、没有任何 traceback。
  截图 / 验证脚本只要碰控件就必须用 `QApplication`，哪怕平台是 `offscreen`。
- **go2rtc 的 `frame.jpeg` 每帧都要调 ffmpeg 转码**（实测 700ms/帧），适合「抓一张图」，
  不适合当视频源。实时播放走 RTSP 直通，解码交给 Qt 自带的 FFmpeg 后端。
- **go2rtc 的 API 比协议模块先就绪**。`xiaomi` 排在 `main.go` 的 `modules` 列表最后，
  `GET /api` 已经 200 的时候它可能还没 `HandleFunc("xiaomi")`；此时发来的第一条 RTSP
  请求会报 `unsupported scheme: xiaomi://…`，而且这个错误会被 stream 缓存下来，后面
  再连也一直失败。所以 `start()` 在 API 就绪后要再等 300ms，控件首帧前的报错也自动
  重连一次。症状很怪：同一个配置手动跑必成功、从程序里跑约 1/3 失败。
- **Windows 上不能用 `SO_REUSEADDR` 探测端口空闲**。它允许 `bind` 到别人已经 `listen`
  的端口（Linux 不允许），于是「端口占用检测」永远返回空闲，新 go2rtc 抢不到 8554 却
  以为起来了，Qt 连上旧实例、错误还对不上。要用 `SO_EXCLUSIVEADDRUSE`。顺带把就绪
  探测从 `/api` 换成 `/api/streams` 并核对流名，避免连到别人的实例还以为是自己。
- **`offscreen` 平台下 Qt 的字体库是空的**，`QFont("Microsoft YaHei UI")` 拿不到字形，
  `draw_text` 画的中文全是方块（`QFontInfo().family()` 返回空串）。离屏脚本的截图
  只能用来看布局，核对文字得用 `shot_camera.py` 这种真实窗口。
- **"返回值是 `Mapping`"不能当成功判据**。整轮网络失败时 `Client.read()` 返回的是空
  dict——那也是 `Mapping`，于是失败被记成成功，指数退避 `min(6 × 次数, 30)` 永远不生效，
  状态栏还会白写一句"已重新连接"。现在由请求层的 `Client.last_poll_ok` 回答"这轮到底
  读回来东西没有"，`Store` 只看它；没有可读属性、全部确认不支持的空转仍算正常。
- **轮询异常在 `api.py` 就被吞掉了**，到 `Store` 只剩空结果，分不清"没属性可读"和
  "请求挂了"。所以健康记账（原始错误码 / 异常文本 / 分类）必须放在请求层，`Store`
  只补一句"触发了多少秒退避"。
- **MQTT 订阅不能通配**。`device/{did}/…` 用通配符会被 `SUBACK 135 Not authorized`
  拒绝，只能按设备白名单逐台订阅；实投 QoS 0（申请 2）、`retain=false`，不能当可靠
  队列。`state` 主题实测零消息，**上下线拿不到**。
- **`expires_in=259200` 是 access_token 的 3 天，不是 refresh_token 的有效期**。
  refresh_token 单次使用、每次刷新强制换发，持续运行才是永续滚动链；官方 HA 集成按
  `now + expires_in × 0.7` 提前刷新，刷新失败必须重新认证。
- **小爱音箱的 `execute-text-directive` 不能写死 siid/aiid**：`lx06` 是 5/5，
  `oh2p` / `x6a` 是 7/4，入参固定为 `[文本, 是否静默]`，只能按 `spec_type` 解析
  （详见「规格解析与型号适配」一节）。
- **自绘 `Qt.Popup` 面板要自己管生命周期**。它不像 `QMenu.exec()` 会替你跑完再返回，
  `hide()` 之后对象还在；每次点开就新建一块的话，不处理就会一直挂在指令条底下。
  现在的收口是 `hideEvent` 里 `deleteLater()`——选设备、点外面、按 Esc 三条路都会走到
  它。另外**整行可点的开关**要确认子控件吃掉了自己的点击：`ToggleSwitch` 处理鼠标后
  不调 `super()`，所以行级 `mouseReleaseEvent` 不会和它双重切换。
