## 0. 一句话

**他们做的是「米家 App 的桌面移植」**：把 App 里那些"管理"功能（房间、场景、定时、
消息、设备信息、插件文案）搬到 PC，UI 由 MIoT spec **自动生成**，所以覆盖面广、每台
设备长得一样。
**我们做的是「桌面控制台」**：按品类手写卡片与详情页，外加手机上没有的东西（摄像头
多路 / 云台、桌面挂件、耗材、电脑自动化、极客版取码）。两边重合的只有"列设备 + 开关"。

## 4. 值得抄的四条（按价值排）

### 4.1 插件文案 / 故障码运行时拉取（我们目前是手写映射）

他们首次启动后台拉插件包，把 `i18n` 与故障码解出来给 UI 用；**包不随发行版分发**，
只缓存在本地 `data/`。我们 `core/enum_text.py` 是三层人工短名表（型号 → 品类 → 全局），
覆盖的是自己那几十台设备，遇到没见过的型号只能显示英文原话。

抄法（不引他们的代码）：按 `model` 取插件包 → 解出 `value-list` 文案与 `fault` 表 →
落到 `<data>/cache/plugin/<model>.json`，UI 查表时优先用它、查不到再退人工短名。
**注意**：体积为零（运行时数据）、但网络多一次后台请求，且文案质量取决于云端给不给包。

### 4.2 可用性矩阵（把"点了会失败"的控件先置灰）

他们用探测器在真机跑一遍，记录每个属性/动作的返回码，生成"可用性矩阵"，UI 按矩阵
置灰。我们现在只有 `advanced`（没绑定的收进"更多功能"）与型号适配层，点了失败的还是
会弹错误。**低成本版**：把每次写失败（`-70401xxxx` / 不支持）记进设备档案，下次打开
这类属性自动灰掉；不用专门跑探测器。

### 4.3 局域网 TCP 探测补在线判定

他们在线判定 = 云端 `isOnline` + 局域网 TCP 探测，能区分"设备关机"与"家里断网"。
我们只认云端 `isOnline`（每 15 s 重读设备清单），断网时会显示"全部离线"却说不清是谁
的问题。补法：设备档案里存 `ip`（`api.py` 的列表里就有），偶发一轮 TCP connect 到
`ip:54321`；失败且云端也说离线 → 离线；云端离线但端口通 → 标"局域网在线"。

### 4.4 云端写接口的可行性结论（省我们一轮逆向）

- **房间 / 设备搬家**：能做，接口已通（他们做了新建、改名、删除、搬家）。
- **场景 / 定时新建**：**要先在账号里有一条同类对象当模板**，服务端校验 `sc_id` 与动作
  信封；空账号只能给降级提示。所以"从零建场景"这条**不要立项**。
- **自动化任意触发**：**做不到**。设备事件触发要 spec-scene 的 `sc_id`，这张表不在
  miot-spec、不在插件包、不在 `GetSceneList`，手拼与复制均被
  `-998 CheckTriggerConditionSrcKey…` 拒。我们做的是"电脑触发 → 米家动作"（反向），
  正好绕开了这条；将来若想做"米家事件 → 电脑"，先读这条。
- **房间排序**：**服务端不支持**。`set_union_order` 的 `room_order` id 与真实房间 id
  对不上，写回 `-8 invalid homeid`。我们的房间顺序是本地偏好，不受影响。

### 4.5 消息中心：走 `/v2/message/v2/*`，和"设备事件"是两条完全不同的路

米家 App 的消息中心（洗衣完成、滤芯过期、场景执行失败）是**账号级通知流**；我们
`poll_events` 留着的 `/miotspec/event/get` 是**单台设备的事件最近一次**。两者不是一套数据：

| | 消息中心 `/v2/message/v2/*` | 设备事件 `/miotspec/event/get` |
| --- | --- | --- |
| 归属 | 账号（跨设备、跨家庭） | 单台设备（`did` + `siid/aiid`） |
| 返回 | 有正文 / 时间 / 未读标记的**一条条记录** | **最近一次**事件参数 + `updateTime` |
| 用途 | 看"发生过什么" | 做触发（"门铃刚刚按下"） |
| 能否回看 / 计数 | 有 `msg_id`，可列可删 | **不能**，只有一条，下次覆盖 |

（`event/get` 这条结论是我们自己实测的，见
[mijia-automation-events.md](mijia-automation-events.md) §3.3「最大的限制：只留最近一次」。）

**五个接口**（都在 `/v2/message/v2/` 下，POST JSON）：

| 路径 | body | 说明 |
| --- | --- | --- |
| `typelist` | `{timestamp: 毫秒, limit: 30}` | 列表页。**不是完整历史**，按类型各给最新若干条 |
| `list` | `{did, type: 6, timestamp, limit: 20, force_read: false}` | 单台设备的记录 |
| `check_new_msg` | `{begin_at: unix 秒}` | 之后有没有新消息（布尔） |
| `batch_read_msg` | `{homes: [{dids: [...], home_id, home_owner}]}` | 按**设备**标已读，不是按 `msg_id` |
| `delete` | `{msg_ids: [int], type, did}` | 删单条，`type` / `did` 要照抄那条记录 |

实测到的类型：`6` = 设备消息、`11` = 设备离线、`13` = 场景通知；未知类型他们保留数字不猜。

**三个坑**（都是对方真机踩出来的，我们不用再踩）：

1. `list` 的 `timestamp` 传"现在"返回**空数组**，传 `0` 才给最新那批 → **翻页拿不到**，
   每台设备只能看最新 20 条（前端只展示 5 条）。所以它视频里"设备历史消息"其实是
   "最近 N 条"，不是可回溯的历史。
2. `batch_read_msg` 按 `did` 分组，**没有 `did` 的消息（纯场景通知）没法这样标**，
   会一直显示未读——他们会如实写进限制，不会假装成功。
3. `typelist` 没有游标，列表条数上限就是 `limit`，更早的消息看不到。

**我们自己实测（2026-11-23，本机账号只读探针，未写任何账号数据）**——三条都给死了：

- `typelist`：不管传什么都是**同样的 6 条**（5 条 `type=6` 设备消息 + 1 条 `type=13`
  场景通知）。`limit`（5 / 30 / 100）、`type`、`home_id`、`timestamp`（0 / 现在 / 最早一条
  的 `ctime`）、`offset` **全部无效**——参数收下但不参与筛选，也没有游标。所以"每类只显示
  最新一条"是接口本身的行为，不是 App 前端截的。
- `list`（单设备）：`timestamp=0` 给该设备**最近一批** 6 条、跨 5.5 天，`limit=20` 与
  `limit=50` 返回一模一样；`timestamp=now` 或 `timestamp=最早那条的 ctime` 一律**空数组**
  → **没有向后翻页这回事**，和上面第 1 坑一致。
- 每条记录都带 `home_id`（还有 `home_owner` / `uid` / `sender_uid` / 整数 `msg_id` /
  `type` / `title` / `content` / `img_url` / `params` / `is_new` / `status` / `ctime`(unix 秒) /
  `last_modify`），但**顶层那个 `home_id` 恒为 0**（6 条全是），拿它比对等于不过滤——
  我们第一版就栽在这，用户实测"两个家庭都能看到全部消息"。真正的家庭 id 在
  **`params.body.home_id`**（15 位整数；5 条设备消息各带一个，两个家庭两个值，都在账号的
  家庭列表里）→ 按家庭过滤改读它即可。**场景通知（`type=13`）的 `params` 是空 dict**，
  归属判断不了，那种记录只能照旧显示（我们选择"宁可多一条别家的，不藏自己家的"）。
- 单设备 `list` 的 **`type` 是必填**（不传 → `-8 invalid param`）；`6` 设备消息、`11` 设备
  离线两种各问一次再合并，没有的类型只回空数组。
- App 里的「智能日志」（场景历史）**拿不到**：插件 SDK 只暴露原生宿主方法
  `loadScenesHistoryForDevice(did, timestamp=-1, limit≤50)`（SDK 10010 起），**JS 源码里
  没有对应的 URL**；照着命名猜的 `GetSceneHistory` / `GetSceneLog` / `GetSceneHistoryList` /
  `GetSceneRecordList` 四个路径全是 **HTTP 404 `Not Found`**（要用裸 `session.post` 才看得见
  ——过 mijiaAPI 的解密包装会变成 `BadGzipFile`，容易误判成"接口存在但解不开"）。
  点设备消息进的那一页本质就是上面的 `list`。

所以真要"历史"，只能做"单设备最近一批"，做不出"按类型往回翻"或"场景日志"。

**要接的话**：别塞进 `poll_events`——那是"单台设备最近一次事件"的语义，
`PollDemandBoard` 的假设对不上。新开一块 `poll_messages`（`idle_ms=None`，只在打开消息页 /
侧栏角标需要时登记），45 s 一档就够（对方就是这么做的，且页面不可见时跳过）。
另：标记已读与删除是**写账号数据**，按项目规矩要先问用户再动。

## 5. 明确不借

- **Win7 兼容线**：他们为了 Win7 把 Python 锁在 3.8、浏览器锁在 Chromium 109，整条代码
  被语法约束绑住。我们是 Qt 6（Win10+），没有这个包袱，也不该为它降级。
- **浏览器 `--app=` 当窗口**：省体积的代价是"界面观感 = 用户浏览器版本"，没有原生托盘/
  菜单/输入法行为，也没有我们挂件那种窗口层级能力。摄像头更是完全走不了。
- **spec 自动生成 UI 当主路径**：`core/catalog.py` 开头已经写过为什么不做——通用面板会
  把洗衣机 70 个属性、门锁 117 个属性全铺出来，且卡片没有"这一品类该看什么"的说法。
  他们的 README 也承认这是取舍（换来"新设备零代码"）。

## 6. 两边都没做的（写下来，别再当新发现）

添加设备（扫码配网留给手机）、固件 OTA、真正的推送（都要常驻长连接）、多账号、
设备列表分页（**两边都是 `limit=200` 单页**；我们的注释写"64 条远小于 200，不翻页"，
他们的已知限制写"超 200 台静默缺失"——同一条坑，谁都没解）。
