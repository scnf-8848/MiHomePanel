# 米家 App 自动化 / 事件通道 / 中枢网关「虚拟事件」：可行性调研

> 2026-11-10 调研，用用户自己的账号做了只读探测 + 两次网关动作调用（事件名随机、
> 不会命中任何自动化）。主程序代码未改，只加了探针 `scripts/probe_automations.py`。
> 关联待办：`TODO.md` →「核心特性：把电脑接进全屋智能」。
> 索引：`docs/reference/README.md`（本页状态 = **待排期**，接口已通、功能未接）。
>
> **一句话结论**：三条都拿到了，而且**都不需要局域网**。
>
> - 自动化列表：`GetSceneList` 一次读全家，触发/条件/动作/启用状态全在
> - 事件通道：`/miotspec/event/get` 能拉「某个事件最近一次发生」，带时间和参数
> - 虚拟事件：不是私有协议，是中枢网关规格里的普通服务
>   （`siid 4 / aiid 1` 产生、`siid 4 / eiid 1` 上报）→ 一次 `prop/action` 就能发

## 1. 三条结论对应的接口

| 能力 | 接口 | 请求体要点 | 实测 |
| --- | --- | --- | --- |
| 读全家自动化 | `POST /appgateway/miot/appsceneservice/AppSceneService/GetSceneList` | `home_id`、`owner_uid`、`app_version:12`、`get_type:2` | 38 条（11 条可手动执行 + 27 条自动化），83 KB |
| 读事件最近一次 | `POST /miotspec/event/get` | **必须** `{"params":[{did,siid,eiid}, ...]}` | 一次请求 7 个事件源，约 110 ms |
| 发虚拟事件 | `POST /miotspec/action` | `{"did":<中枢 did>,"siid":4,"aiid":1,"in":["事件名"]}` | 往返 253 ms，`exe_time 52 ms`，`code 0` |

三者都用**现有账号凭据**（`Client.raw()._request()` / `.run_action()` 就行），
不抓包、不补额外头。自动化属于「家庭」而不是「设备」，所以**同一账号在任何机器上
登录看到的都是同一份**——这正是用户问的"换设备登录 APP 里自动化互通"的机制。

## 2. 自动化列表（`GetSceneList`）

### 2.1 参数：两个容易踩的坑

- **`app_version` / `get_type` 不能省**：只传 `home_id` + `owner_uid` 时，手上这份数据
  少给 4 条手动场景（6 条 vs 10 条）。自动化条数不受影响，所以只数自动化会以为没问题。
- `type` 字段**不能**当"手动 / 自动化"的判据。实测 `type` 为 0 和 1 的两组里，
  都既有 `user.click` 触发（可手动点）、也有设备属性和定时触发：

  ```
  (0, 手动, ('user.user',))     -> 2
  (1, 手动, ('user.user',))     -> 9
  (0, 设备属性/事件/定时)        -> 8
  (1, 设备属性/事件/定时)        -> 19
  ```

  **可靠判据**：触发器里出现 `key == "user.click"` 就是"能在智能页手动执行"的，
  这类**按 `scene_id` 逐条对上** `GetSimpleSceneList` 返回的那一批（本项目首页胶囊用的就是
  后者；实测两边都是 11 条、`scene_id` 集合完全相同）。

  但**别按名字对**：同一个 `scene_id` 两个接口给的 `name` 可能不一样——本机实测有一条
  这里叫「强-晚安」，`SimpleSceneList` 里叫「晚安」（另一条同理）。用名字做键会凭空多出两条。

### 2.2 单条的字段结构（截断示例，已脱敏）

```jsonc
{
  "scene_id": "…", "name": "…", "enable": true,
  "type": 1,                       // 见上：不是手动/自动的判据
  "local_dev": "<中枢网关 did>",    // 非空 = 这条挂在网关名下（疑似"下沉本地执行"，未验证）
  "scene_trigger": {
    "express": 1,                  // 1 = 任一条件；0 = 全部条件
    "triggers": [{
      "src": "device",             // device / timer / user
      "key": "event.5.1012",       // prop.S.P / event.S.E / timer.crontab / user.click
      "name": "单击",              // 云端给的中文短名
      "extra_json": {"did": "…", "device_name": "…", "model": "…"}
    }]
  },
  "scene_condition": {"express": 0, "conditions": []},
  "scene_action": {"mode": 1, "actions": [{
    "type": 0,
    "payload_json": {
      "command": "set_properties",          // 或 action / tts
      "did": "…", "device_name": "…",
      "value": [{"siid": 2, "piid": 1, "value": false}]
    }
  }]},
  "scene_else_action": null
}
```

动作里的虚拟事件长这样（从用户自己的自动化里抄出来的，就是"标准动作"）：

```jsonc
{"command": "action", "did": "<中枢>", "device_name": "Xiaomi 中枢网关",
 "value": {"siid": 4, "aiid": 1,
           "in": [{"siid": 0, "piid": 1, "value": "阶段关灯判定"}]}}
```

注意 `in` 里那个 `siid: 0` 是 App 自己的写法（动作的入参用 0 表示"服务自身"），
真正调 `prop/action` 时传扁平字符串即可：`"in": ["阶段关灯判定"]`（已实测 `code 0`）。

### 2.3 能不能写

社区资料里有 `AppSceneService/Edit`（改场景）、`RunScene` / `NewRunScene`（跑场景，
本项目已在用后者）。**本次没有验证 Edit，也不建议做**：替用户改自动化，改错了
没有任何回滚手段。要"让米家做事"，正确做法是让用户建一条由虚拟事件触发的自动化，
我们只负责发那个事件（见第 4 节）。

## 3. 事件通道（`/miotspec/event/get`）

### 3.1 请求体只有一个正确形状

```jsonc
{"params": [{"did": "…", "siid": 2, "eiid": 1020}, {"did": "…", "siid": 4, "eiid": 1}]}
```

其它写法都会被拒（都实测过）：

| 写法 | 返回 |
| --- | --- |
| `{"did":…,"siid":…,"eiid":…}`（不套 params） | `code -8, params is invalid` |
| `[{"did":…}]`（顶层数组） | `code -8, data type not valid` |
| `{"params":[...]}` ✅ | 数组，每条带 `value` 与 `updateTime` |

### 3.2 返回的是「这个事件的最近一次」

```jsonc
[{"did": "…", "siid": 2, "eiid": 1020, "code": 0,
  "value": "[{\"piid\":1,\"value\":3},{\"piid\":2,\"value\":12}]",
  "updateTime": 1794228873}]
```

- `value` 是**字符串**，里面是 JSON 数组 `[{piid, value}]`，参数含义看规格。
- `updateTime` 是这次事件发生的云端时间戳（秒），去重就靠它。
- `code -9` = 这个事件没有记录（或从未发生）；`code -704220043` = 读属性时"不可读"，
  两者不要混着当失败处理。

覆盖范围实测（同一个账号，一次请求全取回）：门锁开锁（带 5 个参数）、门铃、
人体传感器移动、无线开关单击、中枢网关虚拟事件。**蓝牙设备（`blt.*` did）也能查到**。

### 3.3 最大的限制：只留最近一次

接口给的是"最后一次发生"，不是历史。所以：

- 轮询间隔就是事件的时间分辨率，两次之间连发两次只会看到后一次；
- 适合"触发型"用途（开锁了 → 锁屏），不适合"计数型"（今天开了几次门）；
- 想要历史，得看有没有别的接口（**未找到**，也没必要为它做）。

### 3.4 按键类事件按 `(did, siid, eiid)` 各自独立（**实测，2026-11-10**）

同一个家庭一次批量读了 **48 个按键事件源**（`switch-sensor` / `switch-sensor-for-ble`
服务下的单击 / 双击 / 长按），全部返回各自的"最近一次"，互不覆盖：

```
小米无线开关（蓝牙版）摄像头  blt.3.1en5qu3q4k400  3.1012 单击   code=0   2 分钟前
小米无线开关（蓝牙版）洗衣机  blt.3.1fuatqc28k800  3.1012 单击   code=0   0.5 天前
领普单火三键                2044955685          6.1    单击   code=0   0.4 天前
小米智能开关（单开）          2044220766          3.1    单击   code=0   0.3 天前
小米智能多模网关2            499323841           4.1    单击   code=-9  无记录
```

三条可用的结论：

- **BLE 设备（`blt.*`）的按键事件上云，能读**。不必因为"蓝牙设备"就以为拿不到。
- **`code == -9` 表示"从没发生过"**，不是错误，当"没有"处理即可。
- **不同按键、不同动作各有各的槽位**：三键开关的左/中/右单击是 `5.1` / `6.1` / `7.1`，
  双击/长按是另外的 eiid。所以"哪个键、什么动作"天然可区分，
  **比虚拟事件更适合当触发源**（虚拟事件只有一个槽，见 4.3.1）。

代价：每个事件源都只留最近一次（3.3 的限制没变），所以还是"轮询 + 去重时间戳"。

## 4. 中枢网关「虚拟事件」

### 4.1 它不是私有协议，是规格里的普通服务

`xiaomi.gateway.hub1` 的**设备列表里那个 `spec_type`（版本 3）**里有第四个服务：

```jsonc
{"iid": 4, "type": "urn:miot-spec-v2:service:virtual-service:000078E0:xiaomi-hub1:3",
 "properties": [{"iid": 1, "type": "…property:virtual-param:00000259…",
                 "format": "string", "access": [], "comment": "事件名称"}],
 "actions":    [{"iid": 1, "type": "…action:emit-virtual-event:000028A1…",
                 "in": [1], "comment": "产生虚拟事件"}],
 "events":     [{"iid": 1, "type": "…event:virtual-event:00005069…",
                 "arguments": [1], "comment": "虚拟事件发生"}]}
```

**陷阱**：`miot-spec.org` 上 `urn:…:xiaomi-hub1:1`（版本 1）**没有** `virtual-service`，
只有 `:3` 才有。所以判断"这台网关支不支持虚拟事件"，**必须用设备列表里的 `spec_type`**，
不能自己按型号拼一个版本号——拼错会得出"不支持"的错误结论。

### 4.2 发：一次 `prop/action`

```
POST /miotspec/action  {"did":"<中枢>","siid":4,"aiid":1,"in":["事件名"]}
→ {"code":0,"message":"成功","exe_time":52,"net_cost":42,"ot_cost":16,…}
```

实测往返 253 ms（另一次 256 ms）。事件名**精确匹配**：没有任何自动化监听这个名字，
就什么都不会发生（探针用随机名，安全）。

### 4.3 收：用第 3 节的事件接口

虚拟事件就是 `siid 4 / eiid 1` 上的一个事件，`value` 里是
`[{"piid":1,"value":"事件名"}]`。所以"收到虚拟事件"= 轮询这一个事件。

实测（探针 `latency` 子命令）：

```
发出「mihome-probe-…」：成功，动作往返 256ms
云端可见：发出后 356ms（查询间隔 0.20s，所以真实值在两者之间）
```

### 4.3.1 陷阱：`4.1` 是**全局唯一**的槽，会被别的虚拟事件覆盖（实测）

虚拟事件服务只有一个事件 `eiid 1`，任何名字的虚拟事件都写这一个槽。所以当链路里
**有两个虚拟事件**时，只能看到最后那个。

实测现场（用户家里真实链路）：

```
按无线开关 → 极客版规则发「极客版按键自动化申请」(虚拟事件1)
           → App 自动化「app自动化控制极客版」触发 event.4.1，再发「极客版按键自动化执行」(虚拟事件2)
           → 极客版规则收到虚拟事件2 → 音箱播报「按键测试」
```

盯 `4.1` 跑 120 秒、按了 7 次，**7 次变化读到的值全是虚拟事件2**：

```
   7.33s  变化  Xiaomi 中枢网关 / 极客版按键自动化申请  → 1='极客版按键自动化执行'   云端戳 +1.42s   往返 171ms
  10.61s  变化  …                                      → 1='极客版按键自动化执行'   云端戳 +1.70s   往返 151ms
  13.87s  变化  …                                      → 1='极客版按键自动化执行'   云端戳 +1.96s   往返 151ms
  17.80s  变化  …                                      → 1='极客版按键自动化执行'   云端戳 +1.89s   往返 155ms
  31.54s  变化  …                                      → 1='极客版按键自动化执行'   云端戳 +1.63s   往返 153ms
  43.31s  变化  …                                      → 1='极客版按键自动化执行'   云端戳 +2.40s   往返 151ms
  67.13s  变化  …                                      → 1='极客版按键自动化执行'   云端戳 +1.22s   往返 151ms
```

虚拟事件1 被 1 秒内的虚拟事件2 覆盖，0.5 秒的轮询一次都没抓到中间态。

**设计后果（必须记住）**：

- 用虚拟事件**收**信号不安全：用户随便新建一条"A → 发虚拟事件 X"的自动化，
  就会把你的信号冲掉，你读到的是别人的名字。
- 用虚拟事件**发**信号没问题：名字精确匹配，只影响监听它的自动化。
- **"米家 → 电脑"的触发源应该优先选设备事件**（按键 / 开锁 / 门铃 / 人体…），
  它们是各自独立的槽（3.4）；虚拟事件只在"用户主动想给电脑发一个自定义信号"时用。

### 4.4 它在米家自己体系里的位置

米家 App 的自动化和「极客版」（网关本地规则）之间，官方就是用虚拟事件搭桥：
App 里配"设备 → 中枢网关 → 产生虚拟事件"，极客版里配"虚拟事件发生 → 做一堆事"。
社区讨论里把它叫"虚拟总线 / 逻辑中间件"，本质一样。

**我们等于拿到了这条桥的外部入口**：不用极客版、不用登录码、不用局域网，
在电脑上发一个名字，就能让米家里任何一条监听该名字的自动化跑起来。

## 5. 端到端延迟（实测，不是估算）

| 段 | 实测 | 说明 |
| --- | --- | --- |
| 发虚拟事件（云端 action 往返） | 253 / 256 ms | `exe_time` 52 ms 是网关执行时间 |
| 发出 → 云端 `event/get` 可见 | 356 ms（查询间隔 200 ms） | 真实值在 256–356 ms 之间 |
| 一次 `event/get` 批量读 7 个事件源 | ~110 ms | 与属性轮询同量级 |
| 一次 `event/get` 批量读 48 个按键事件源 | ~150 ms | 上限没探到，48 个仍是一个请求 |
| 事件本身的云端戳 | 与发出时刻同秒 | `updateTime` 可用来去重 |
| 真实链路（按键→自动化→虚拟事件2）从发生到读到 | **1.2 – 2.4 s** | 见下，含整秒截断误差 |

**关于最后一行别读错**：`updateTime` 是**整秒**（`int`），所以"云端戳距今"这个数
天然被高估 0–1 秒；再叠上 0.5 秒的轮询等待，1.22 秒的真实含义是 0.22–1.22 秒。
上表 7 次的 1.2–2.4 秒里，**属于链路的开销主要在"按键→自动化→再发一个虚拟事件"
这一跳**，不是我们读得慢（往返一直稳定在 150 ms）。

要精确切分"按键上云"与"虚拟事件2 上云"的差值，得把无线开关的 `3.1012` 和网关的
`4.1` 放进同一次轮询里一起看——**还没做**，见第 9 节。

对比：属性轮询一轮（130 条）约 400 ms，3 秒一轮 → 最坏 3 秒才看到变化。
**事件通道把"米家→电脑"从 3 秒压到"轮询间隔 + 0.4 秒"**，1 秒轮询下约 1.4 秒。

## 6. 对自动化功能的意义

### 6.1 两个方向都有了落点

| 方向 | 做法 | 延迟 |
| --- | --- | --- |
| 电脑 → 米家 | 发虚拟事件，命中用户建好的自动化；或直接 `prop/set` 设属性 | 0.25 s + 自动化自身耗时 |
| 米家 → 电脑 | `event/get` 轮询事件（虚拟事件、门锁、门铃、按键、人体…） | 轮询间隔 + 0.4 s |

这比"把每条规则都用属性轮询拼出来"干净得多：属性轮询只能看"现在是什么状态"，
看不到"刚刚发生了一次单击/开锁"，而事件是瞬时的。

### 6.2 与「局域网 miIO 已排除」的关系（**重要，别混为一谈**）

这次找到的三条**都不是局域网直连**：

- 走的是米家云端接口，用账号凭据，和现在的读写属性是同一条链路；
- 不需要设备 token、不需要按型号写会话、不需要网关登录码；
- 换到别人家里，只要他的账号里有中枢网关、自动化就能用；没有网关也只是
  "发不出虚拟事件"，其余能力（读自动化、读事件）照旧。

所以**不违反** `TODO.md`「已作废」里"局域网直连明确排除"那条决定。
真正被排除的是"用 miIO UDP 54321 在局域网里直连设备"。

### 6.3 轮询归属：别再加第二个 timer

事件轮询要并进「需求登记」那套（见 `docs/DEVELOPMENT.md`「系统托盘常驻」末段）：
自动化常驻时它就是一份"要 1 秒"的需求，窗口/挂件各报自己的，
取最严的间隔统一跑，**不要**在自动化模块里另起一个 timer 各轮一遍。

## 7. 风险与边界

- **私有接口**：`GetSceneList` / `event/get` 都没有公开文档，App 版本参数
  （`app_version:12, get_type:2`）随时可能变。实现时要有"读不到就当没有"的降级，
  不能让自动化功能因为一次接口变动就整体崩掉。
- **事件只保最近一次**：见 3.3。用它做触发是够的，别当账本。
- **频控未知**：`event/get` 1 秒一次是 3600 次/小时，量级和属性轮询同档，
  但米家对非官方客户端没有公开保证；先按"用户显式开启自动化才启用"来设计。
- **写操作只有一个**：虚拟事件 `action`。名字精确匹配、天然幂等（连发两次就是两次事件，
  但不会留下状态）；除它之外不要替用户改自动化、改场景。
- **网关离线**：`action` 会失败（云端转发不过去），`event/get` 会停在旧时间戳。
  两者都要能被用户看懂，而不是静默失败。
- **中枢可能是路由器 / 屏幕 / 音箱内置的**：`did` 不能只按型号过滤，
  名字含「中枢网关」或 `model == xiaomi.gateway.hub1` 只是覆盖常见情况，
  真找不到时让用户指定 `did`（探针已支持 `--did`）。
