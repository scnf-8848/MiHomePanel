> 提出：2026-11-25（用户）。**结论已研判，代码未动**。2026-11-26 用户定**搁置**——
> 现有 9 个样式用着没问题，没有非改不可的理由。落点见 `TODO.md` B 段

>
> 命题：卡片样式不再决定内容、只决定**大小**（所以改名「卡片大小」）；卡片内部是
> 一个容器，程序预设若干「小格样式」，用户自己把控件放进去（需要编辑页）。基础的
> 属性原子 = 「属性名：属性值」占 2×1 格，功能开关 = 「功能名：开关」占 2×1 格；
> 非通用组件（温度控制、模式控制、风扇「模式 + 风速」）另做。**先要能把现有样式
> 全部转换过去**。

## 1. 格子几何（本机实测，2026-11-25）

`CARD_H=168 / CARD_MIN_W=166 / CARD_GAP=8 / PAD=14 / BODY_TOP=76`：

| 尺寸 | 卡片 | 内容带 | 可用列 | 可用行 | 小格 |
|---|---|---|---|---|---|
| 1×1 | 166×168 | 138×78 | 2 列（67） | 2 行（36） | 4 格 |
| 2×1 | 340×168 | 312×78 | 4 列（75） | 2 行（36） | 8 格 |
| 2×2 | 340×344 | 312×254 | 4 列（75） | **6 行**（36） | 24 格 |

三条结论：

- **行高能统一（`ROW_H=36`），列宽不能**：1×1 的一列 67、2×1/2×2 的一列 75。所以
  原子必须**宽度自适应**，不许写死像素。`make_control(avail=…)` 已经收这个参数，
  这一点天然兼容（它本来就要按"留多少宽"决定滑条 / 轨道 / 步进器）。
- **2×2 不是 4×4**：它不是"四张小卡拼起来"，而是一条标题带 + 一整块 254 高的内容带
  → 4 列 × **6 行**。想让 2×2 变成 4×4 只能把行高改到 56 左右，代价是"同一个原子"
  在不同尺寸里长得不一样（同一个风扇组在 2×1 是 36 高、在 2×2 是 56 高），不建议。
- **1×1 的硬上限是两件**：只有 2 行，而"属性显示 / 功能开关"各要占整行宽（2×1 格）。
  编辑页在空卡时就得说清这件事，否则用户会以为能塞四件。

## 2. 现有 9 个样式能不能表达成原子

| 样式 | 能不能 | 需要什么 |
|---|---|---|
| `standard`（产品图） | 能 | 一个「整块」原子（无行分割，占满 4×2） |
| `light_dual` / `light_bright`（全宽滑条） | 能 | 属性原子支持 `span=4`（跨整行） |
| `presence_state`（大字读数） | 能 | 「整块」原子（读数） |
| `temp_control`（温度 + 模式） | 能 | 两个属性原子；模式胶囊要 4 列宽（8 段轨道） |
| `fan_controls`（两列四格） | **勉强** | 见下，有三件原子表达不了的东西 |
| `camera_live`（实时画面） | 能 | 「整块」原子（视频，占 4×6） |
| `gateway_geek` / `_small` | 能 | 「整块」原子（按钮，一次云端 RPC，不是属性） |
| `switch_wired` / 多键面板 | 能，但只能整块 | 它不是控件，是整块自绘面板，见 §3.5 |

`fan_controls` 是照妖镜——`FanBody` 里有三件纯"格子摆控件"表达不了的行为：

1. **列有语义**：左列永远是"往哪吹"、右列是"吹多大"，缺一项的那格空着、别的不挪位；
2. **双选格**：右下那格按当前模式在"0–100 滑条"和"档位胶囊"之间切换（型号级
   `speed_by_mode`），同一格换控件、布局不动；
3. **标签让位**：第二行的标签搬到副标题（`summary_slots` / `_hide_label`），让出
   30px 给五段角度轨道（每段 26 → 33px）。

所以原子系统最低要支持三类：**属性原子**（span 1–4 × 1 行，内部按属性形状选控件）/
**整块原子**（span = 全部，产品图 / 视频 / 极客按钮 / 多键面板 / 大字读数）/
**复合原子**（自带参数的组件：温度控制、模式控制、风扇组）。第 2、3 条要靠原子的
可选参数（`switch_by` / `label_moved_to_summary`）保住，否则风扇卡一定变难看。

## 3. 六个必须先定的口径

不定这些，"原子化"落地后会出现"用户排好的卡片换台型号变成一堆洞"。

1. **原子能引用哪些属性？** 建议只允许 `card.controls / metrics / extra` 里已登记的
   槽位（`card.bound(slot)`），**不支持"设备任意属性"**。理由：轮询集合
   `poll_refs` 就是从这三张表算出来的，让布局能引用任意属性 = 布局一变就要重建轮询
   表，而"布局与轮询解耦"是 3 秒轮询这套的地基。代价：可选属性比手机米家里少。
   先例：耗材页 11-24 就是"卡片声明了、轮询没登记"→ 卡片永远停在「—」。
2. **引用的属性换型号后绑不上怎么办？** 建议**保留格子、显示「不可用」占位**，另给
   一次「清理失效格」。直接删格子会让用户排的其余格子整体位移，比留个洞更难接受。
3. **编辑后的卡片怎么存？** 建议 `prefs` 新增 `card_layouts: did → {size, atoms[]}`，
   与现有 `card_styles`（预设 id）并存：没编辑过 = 走预设（**老数据零迁移**），编辑过 =
   走 layout。预设表本身改写成"一组原子摆放"的模板，右键菜单从「卡片样式」变成
   「卡片大小 / 编辑内容…」。`resolve_card_style` 加一层：自定义 layout > 预设 > 默认。
4. **双选格 / 标签让位**：做成两个可选参数，只给风扇组用，不强求通用（§2）。
5. **多键面板算不算原子？** 算「整块复合原子」，参数是"选哪几路"。**别拆成 N 个按键
   原子**：竖排文字、转无线路过滤（`Gang.is_wireless`）、点按热区与"点空白开详情"的
   分流全部要重写，换不来更好的效果。
6. **2×2 的行数**：按 4×6（§1），不按用户设想的 4×4。

## 4. 编辑页（真正的大头）

要素：左侧该设备的可选原子清单 / 右侧网格画布 / 原子的参数面板 / 尺寸切换 / 真实
状态预览 / 还原预设。难点：

- **拖放不能复用 `ui/dnd.py`**：`grid_drop_index` 是**卡片级**的（行带 + 行内中线），
  格子级要另写一份吸附 + 越界回弹。
- **撤销 / 重做**：画布式编辑没有这个基本不可用（表单式可以没有）。这是本项目第一次
  需要这个机制。
- **实时冲突提示**：span 超过剩余列、1×1 放第三件、原子不支持该属性——都要当场拦，
  而不是保存时弹一句。
- **预览必须用真状态**：假数据看不出"关机置灰""标签让位""不可用占位"这些真实行为。

## 5. 回归面与"等价性测试"

现有卡片相关断言约 420 处（`verify_card_style` 167 / `verify_geek` 123 /
`verify_fan_card` 66 / `verify_card_controls` 33 / `verify_card_layout` 26 /
`verify_combo` 6 / `verify_card_click` 5）。

建议的验收方式：**同一台假设备 + 同一个预设，老渲染器与新渲染器产出的每个控件矩形
必须逐像素相同**。9 个预设全过一遍，再动编辑页——这条能防"原子化顺手把风扇卡画歪"，
而肉眼看截图是看不出 2px 偏移的。

## 6. 建议的推进顺序（仅排序，不执行）

1. 抽 `CardLayout` 数据结构 + 渲染器（只支持属性原子 / 整块原子），**9 个预设全部
   改写成模板、视觉零变化**，靠 §5 的等价性测试把关。这一步用户完全无感。
2. `prefs.card_layouts` + 右键菜单「卡片大小 / 编辑内容…」入口。
3. 编辑页（画布 + 撤销 + 冲突提示 + 真状态预览）。
4. 复合原子逐个迁移（温度控制 → 模式控制 → 风扇组）。
5. 多键面板 / 视频 / 极客按钮作为整块原子并入。

## 7. 明确不建议做的

- **任意属性可排**（§3.1）——会破掉布局与轮询的解耦；
- **2×2 改 4×4**（§1）——行高不一致，原子会随尺寸变形；
- **拆多键面板**（§3.5）——重写热区与转无线判据，收益为负；
- **半格 / 像素级自由摆放**——只允许整格 `span`，否则 `ROW_H` 基线对齐整套作废。
