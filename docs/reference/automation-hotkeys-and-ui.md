## 1. 热键冲突：系统到底怎么裁决

用户的疑问是「多个程序都响应，还是按某个优先级只响应一个」。**都不是优先级排序**：
对走 `RegisterHotKey` 的程序，同一组合在会话内**排他**，先注册者持有，后注册者
`RegisterHotKey` 返回 `FALSE`、`GetLastError()` 为 `ERROR_HOTKEY_ALREADY_REGISTERED`；
按键时系统只把 `WM_HOTKEY` 投给持有者。失败是**静默**的——多数程序不检查返回值，
表现为「按了没反应，设置里还显示一切正常」。

但不同实现机制的表现不一样，这正是日常看到两种矛盾现象的原因：

| 路径 | 是否排他 | 冲突时的表现 |
| --- | --- | --- |
| `RegisterHotKey`（本项目走这条） | **排他，先到先得** | 只有持有者收到 `WM_HOTKEY`；后来者注册失败。**没有优先级概念** |
| 系统保留键（`Win+L`、`Ctrl+Alt+Del` 等） | 最高，普通程序注册不到 | 直接失败；`F12` 官方明说保留给调试器，别注册；`Win+字母`、`Alt+F4`、`Alt+Tab`、`Ctrl+Esc`、`Ctrl+Shift+Esc` 大多被占 |
| 系统预置默认热键（如 `PrintScreen` → 截图工具） | 例外 | 官方说明：当应用窗口位于前台时，**可能被应用的热键覆盖** |
| 应用内快捷键（窗口前台监听 `WM_KEYDOWN`） | 最低 | 全局热键命中时，组合被吃掉，应用内那条根本收不到 |
| `WH_KEYBOARD_LL` 低级键盘钩子（输入法 / 翻译 / 截图 / PowerToys / 宏工具） | **不在热键表里** | 按键先过钩子链：钩子放行 → 钩子程序和热键持有者**两个都响应**；钩子返回非零吞掉 → 热键持有者**完全收不到** |

所以「两个程序都动了」不是热键表失效，而是其中至少一个用的是钩子。钩子还要求安装线程
有消息循环，且处理超时会被系统静默摘钩（`LowLevelHooksTimeout`，Win10 1709+ 上限 1 s），
这也是它行为飘忽的原因。

> 网上有「高优先级进程 / 管理员权限可以抢占热键」的说法，微软 `RegisterHotKey` 官方文档
> 没有这条。按**先到先得**实现和排查，别指望提升权限能抢回来。

### 1.1 本程序大概率会遇到，而且比一般程序更容易

- 托盘常驻 + 开机自启 → **长期持有一批组合**，等于长期占位；
- 裸单键（如 `F7`）和 `Ctrl/Alt/Shift` 组合正是输入法、截图录屏、显卡面板、远程控制、
  IDE 的高发区；
- **开机自启顺序不定** → 同一个组合可能「昨天能用、今天不行」，看起来像随机故障；
- 注册失败本来就是静默的，我们若不检查返回值，用户只会以为规则没生效。

`MOD_NOREPEAT`（1.4 节那层）**不参与冲突判定**，只影响自动重复。

### 1.2 实现约束（写进验收清单）

- **每次注册都检查返回值**；失败在规则页标红「该组合已被其它程序占用，请换一个」，
  并说明「Windows 不告诉是谁占的」，别猜占用者、别弹一个假的程序名。
- 录制时就拦系统保留键与常见冲突组合，给「建议 `Ctrl+Alt+…` 或 `F13`–`F24`」的提示
  （后一个来自同 build 实测：`F13`–`F24` 可单独使用，普通 `F12` 基本被占）。
- **一个物理组合只注册一次**，多条规则共用同一个 id，由内存索引分发（见第 2 节）。
- 停用规则 = `UnregisterHotKey` 释放；改键 = 先注销再注册；页面显示每条规则的
  「已注册 / 被占用 / 已停用」状态。
- 启动后可延迟重试**一次**（应对自启顺序），被长期占用时不要无限重试、不要刷日志。
- 注册 id 用 `0x0000`–`0xBFFF` 范围（官方文档要求；`0xC000`–`0xFFFF` 留给 DLL）。

## 2. 热键存哪：用户的判断是对的

**Windows 不需要任何文件来注册热键。** `RegisterHotKey` 是**进程运行时** API，注册信息
在会话的 USER 热键表里；进程退出 / 崩溃自动释放，重启不保留，注册表里也查不到绝大多数
全局热键（能查到的只是少数 `AppKey` 之类的固定绑定）。所以不存在「单独一个文件去给
系统注册」这回事。

**撤回上一轮推荐的 `hotkeys.json`**：那是 11-10 旧草案「一级 = 一张
`[(快捷键, 事件名)]` 小映射表」的遗留思路。既然已定三段式规则，键位就该是规则自身的
字段 `trigger.keys`，跟 `condition` / `actions` / `cooldown_ms` 一起存在 `rules.json`
的每条规则里。再放一份 `hotkeys.json` 或塞进 `prefs.json` 都会变成**第二份真相**，
改规则时极易不同步。

真正需要的是**内存索引**，不是文件：

```
启动 / 改规则 → 遍历 enabled 规则的 trigger.keys
              → 去重：一个组合分配一个 hotkey id
              → RegisterHotKey(id, modifiers|MOD_NOREPEAT, vk)
              → 建 id → [rule_id, ...]
WM_HOTKEY(id) → 查表分发给该组合下所有规则
              → 每条规则各自求值条件、各自走自己的冷静期
```

**同一组合绑多条规则不是冲突**（系统层面只注册一次，分发在我们这边）。反过来说，
同一个热键在多个规则里各自独立冷却，符合 1.4 节「冷却挂在规则上」的定义。

将来若要做「全局热键黑白名单 / 冲突诊断记录」，那也只是一份**配置**，不是注册表。

## 4. 规则编辑器：三段式 vs 图形化画布

极客版网页的公开形态是**节点式画布**：左侧功能卡面板按类分组、右侧画布，拖卡片到画布、
用触点连线表达执行顺序，支持串行 / 并行、分支、变量、循环（本会话**没有极客版网页截图**，
以下按公开描述评估；真要评估视觉细节请补一张图）。

| | **A · 仿米家 App 三段式（推荐）** | **B · 仿极客版节点画布** |
| --- | --- | --- |
| 形态 | 三块分区卡（触发 / 条件 / 动作），块内行列表 + 添加按钮，动作行可上下拖拽调序 | 左卡片库 + 右 `QGraphicsView` 画布、节点端口、贝塞尔连线 |
| 项目现成底座 | `settings_rows.py` 直接可用；`ui/dnd.py` 的 `DragGesture` / `move_in_list` 能做列表排序；`WindowFrame` 已有 | **全仓零处** `QGraphicsView` / `QGraphicsScene` / `QUndoStack`，要从零建 |
| 工作量 | 低~中：表单控件 + 校验 + 落盘 + 触发日志 | 高：场景视图、节点与端口命中、连线合法性、拖拽增删、缩放平移、图 ↔ JSON 双向序列化、撤销重做、自动布局 |
| 与 v1 规则匹配 | **完全匹配**：1 类触发、6 类条件、2 类动作，严格线性「触发 → 条件 → 动作按序执行」，没有分支 / 并行 / 回路 | **不匹配**：画布上只会画成一条直线，用户还得手动连线，纯增负担 |
| 视觉参照 | `mihome-app/31_create_automation.jpg`（本地已 gitignore） | 极客版网页（缺截图） |

**结论（2026-11-13 01:37 用户拍板 = A，已定不再待确认）：能仿，就仿 A。** 三段式几乎就是照着 `settings_rows.py` 的形状长出来的：
触发块 = 按键录制控件 + 「已注册 / 被占用」状态；条件块 = `全部 / 任一` 切换胶囊 +
条件行（类型 + 比较符 + 参数）+ 空状态；动作块 = 可拖拽排序的动作行（**11-14 起是
「设备 + 功能 + 参数」与「延迟」交替**，见 §6.2 里的 v4 说明）+ 块间画一条竖向连线
保留「流程感」。这些都复用现有自绘控件，不引入新的渲染体系。

B 留到将来真出现「条件分支 / 并行 / 多触发组合」时再评估——那时画布才有表达价值。
另外本轮已定**一期只做电脑 → 米家单向**，画布的并行分支更用不上。

## 7. 动作执行的时延与"发出去就不等回执"（2026-11-14 晚调研，**已落地**）

**用户实测**：③ 里「音箱-唤醒」→「中枢-发虚拟事件」，后者有明显延迟，像是"在等唤醒
的某个回应"。**他没说错**，但根因不在引擎。

**结论（按证据强弱排）**

1. **`jobs.SerialWorker` 只有一条线程**——这是硬瓶颈。第一条 HTTP 不返回，第二条连
   `connect` 都发不出去。所以只把引擎改成"不等"没有用，必须让"发"这一步本身不阻塞。
   （`core/jobs.py` 的 `_loop` 是单 `worker` 线程串行取任务。）
2. **`http.client` 的 `request()` 只写不读**：`putrequest → putheader → endheaders →
   send`，写完 socket 就返回，`getresponse()` 才是阻塞点。这就是"只发不等"的天然实现，
   不需要自己造协议。
3. **不能用 `requests` 的 `timeout` 实现这件事**：`read timeout` 触发会关闭连接，
   回执就永久丢了（而且我们无权重发——那是设备的动作）。要"发完继续等回执"必须自己
   持有连接，把 `getresponse()` 交给别的线程。
4. **`connect timeout` 与 `read timeout` 必须分开**：前者失败 = **一个字都没发出去**
   （该立刻告警）；后者失败 = **发出去了没等到回执**（命令已在云端，播报 / 唤醒这类
   设备压根不回执，报失败就是一堆假警报）。代码里是 `FAILED=-2` / `UNCONFIRMED=-3`。
5. **回执可能是密文**：云端对 `miot-accept-encoding: GZIP` 的响应是 RC4 密文，
   `decrypt(ssecurity, nonce, text)` 要用**同一个 nonce** → nonce 得跟着连接一起交给
   读线程。`/miotspec/action` 的成功码还藏在 `result` 里
   （`{"code":0,"result":{"code":-704040005}}`），两层都看。

**落点**：`mihome/core/channel.py`（1 条发送线程 + 4 条读线程 + 结果队列 + 主线程
16 ms drain）；`engine._step` 改成"提交即下一步、失败不拦后续"；`Feature.refreshes`
决定要不要跑 1/2.5/4 秒全量回读（只有 `execute-text-directive` 是）。细节见
`docs/DEVELOPMENT.md`「发送链路」。

### 7.1 真机第一跳就踩到的坑：请求体必须包 `params`（2026-11-14 21:xx）

用户实测：③ 里「唤醒 → 发虚拟事件」，**两个动作不论谁先谁后**，按下热键立刻弹
「…未成功（…）：**invalid request**」。两个动作都错、换顺序也一样 = 错的不是动作，
是**请求外壳**。

**根因**：`/miotspec/*` 的请求体形状是 `{"params": <单条|列表>}`。上游
`mijiaAPI/apis.py` 里每个入口都是 `self._request(uri, {"params": param})`
（`run_action` / `get_prop` / `prop/set` 全一样）。`Channel` 上线时把
`{"did","siid","aiid"}` 直接当请求体发了，少一层壳 → 云端 `-6 invalid request`。

**离线也验过**：同样的 uri + data，`urlencode` 出来的字节与
`requests.Request(...).prepare().body` **逐字节相同**（只有 `bytes` / `str` 的类型差），
所以编码层没问题，差的只是那层字典包装。**这说明"逐字节对齐上游"这类校验必须覆盖
请求体的完整形状，只对齐签名参数是不够的。**

**真机探针（不碰任何设备）**：拿一个不存在的 `did`（`000000000`）对比两种外壳——

| 请求体 | 云端回 |
| --- | --- |
| `{"params": {"did": "000000000", "siid": 2, "aiid": 1}}` | `-8 get udid error=000000000`（认了外壳，只是找不到设备） |
| `{"did": "000000000", "siid": 2, "aiid": 1}` | `-6 invalid request`（**就是用户看到的那个**） |

这条探针顺手证明了 `Channel` 的签名、Cookie、`Connection: close`、回执解析在真云端
**都是通的**（回执是明文 JSON，直接 `json.loads` 成功）。以后验"请求形状"类改动都可以
照这个办法：**用不存在的 did 打一发，看错误码是不是"设备级"而不是"请求级"**——比让
用户去按热键快得多，也不会动到任何设备。

**还没定论的**

> 下面四条**只针对 B 通道**（`core/channel.py`）。11-14 22:0x 定案后 B **默认不启用**
> （自动化动作走原名单线程机制），所以这些都不阻塞发布；哪天要切 B 再逐条过。

- `Connection: close` 会不会被云端提前丢（探针里没掉，但只跑了两次）。
- 20 秒读超时对"唤醒"够不够（唤醒要等音箱进聆听，云端一直挂着连接）。
- 并发 4 条读线程会不会触发频控（本程序动作串很短，风险低但没实测）。
- 鉴权过期不自动重登（`Client` 本身也不做），云端回 `-704010000` 之类就原样进日志。

**已定论的一条（11-14 实测，推翻原假设）**：`wake-up` 之后的"明显延迟"**不是**收发排队，
而是唤醒让音箱进入**聆听态**，之后到音箱的指令要等聆听结束才执行——设备侧顺序，换哪条
通道都一样。所以在编排上该绕开：**把唤醒放到动作串的最后一步**，或改用别的动作。

## 8. 触发日志落盘（2026-11-14 23:xx 定，已落地）

**用户要求**：日志原来只活内存、重启清空，要落盘；并自己指出"加了 run 批次号，落盘后
这个也要改吧，是不是按自动化 id + 时间戳更好"。**两点都对**，按这个做：

1. **`LogEntry.run` 从整数换成字符串** `规则id@触发毫秒-序号`。整数是内存计数器，
   重启就归零——文件里昨天的第 3 次和今天的第 3 次会折进同一行。这个键必须**写在文件里**
   而不能靠读回时按"下一个 FIRED 另起一组"重算：两条规则的触发会交错，重算就串组。
2. **存储格式 JSONL**（`<data>/automation_log.jsonl`，一行一条）而不是 JSON 数组：
   日志只增不改，追加一行只要一次 `open(..., "a")`；数组要整份读改写，每来一条重写全量。
3. **每条 append 都开关文件**：强杀 / 断电最多丢最后一行；攒内存批量落盘丢一整段。
   坏行（半行 JSON）在 `load()` 里跳过，**先解析再截尾**——否则末尾几行坏行会把要留的
   好行挤出窗口（这条是测试抓出来的）。
4. **上限只留一个数** `MAX_ENTRIES = 500`：内存 `max_log`、文件、表格 `MAX_ROWS` 同源。
   文件攒到 **两倍**（1000 条）才裁一次，平均 500 条写一次盘；所以文件里实际 500~1000 条。
5. **写失败不抛不提示**：磁盘满 / 没权限不该中断规则执行，界面上那条日志照常出现，
   只是重启后翻不到。
6. **展开状态不记忆**（同一条需求里用户另提）：删掉按批次恢复的那套；记住的展开态会在
   新日志插到顶部、行号整体下移之后挂到别的行上，看着像串行。

**落点**：`core/automation/logstore.py`（`LogStore`）、`engine.restore_log()` /
`_new_run()`、`AutomationService.logstore` / `log_path` / `clear_log()`、
`ui/automation_log.py`（状态条 + 「日志文件」按钮）。细节见 `docs/DEVELOPMENT.md`
「独立日志窗」。
