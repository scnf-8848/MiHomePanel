## 1. 热键冲突：系统到底怎么裁决

用户的疑问是「多个程序都响应，还是按某个优先级只响应一个」。**都不是优先级排序**：
对走 `RegisterHotKey` 的程序，同一组合在会话内**排他**，先注册者持有，后注册者
`RegisterHotKey` 返回 `FALSE`、`GetLastError()` 为 `ERROR_HOTKEY_ALREADY_REGISTERED`；
按键时系统只把 `WM_HOTKEY` 投给持有者。失败是**静默**的——多数程序不检查返回值，
表现为「按了没反应，设置里还显示一切正常」。

但不同实现机制的表现不一样，这正是日常看到两种矛盾现象的原因：

| 路径 | 是否排他 | 冲突时的表现 |
| --- | --- | --- |
| `RegisterHotKey`（本项目走这条） | **排他，先到先得** | 只有持有者收到 `WM_HOTKEY`；后来者注册失败。**没有优先级概念** |
| 系统保留键（`Win+L`、`Ctrl+Alt+Del` 等） | 最高，普通程序注册不到 | 直接失败；`F12` 官方明说保留给调试器，别注册；`Win+字母`、`Alt+F4`、`Alt+Tab`、`Ctrl+Esc`、`Ctrl+Shift+Esc` 大多被占 |
| 系统预置默认热键（如 `PrintScreen` → 截图工具） | 例外 | 官方说明：当应用窗口位于前台时，**可能被应用的热键覆盖** |
| 应用内快捷键（窗口前台监听 `WM_KEYDOWN`） | 最低 | 全局热键命中时，组合被吃掉，应用内那条根本收不到 |
| `WH_KEYBOARD_LL` 低级键盘钩子（输入法 / 翻译 / 截图 / PowerToys / 宏工具） | **不在热键表里** | 按键先过钩子链：钩子放行 → 钩子程序和热键持有者**两个都响应**；钩子返回非零吞掉 → 热键持有者**完全收不到** |

所以「两个程序都动了」不是热键表失效，而是其中至少一个用的是钩子。钩子还要求安装线程
有消息循环，且处理超时会被系统静默摘钩（`LowLevelHooksTimeout`，Win10 1709+ 上限 1 s），
这也是它行为飘忽的原因。

> 网上有「高优先级进程 / 管理员权限可以抢占热键」的说法，微软 `RegisterHotKey` 官方文档
> 没有这条。按**先到先得**实现和排查，别指望提升权限能抢回来。

### 1.1 本程序大概率会遇到，而且比一般程序更容易

- 托盘常驻 + 开机自启 → **长期持有一批组合**，等于长期占位；
- 裸单键（如 `F7`）和 `Ctrl/Alt/Shift` 组合正是输入法、截图录屏、显卡面板、远程控制、
  IDE 的高发区；
- **开机自启顺序不定** → 同一个组合可能「昨天能用、今天不行」，看起来像随机故障；
- 注册失败本来就是静默的，我们若不检查返回值，用户只会以为规则没生效。

`MOD_NOREPEAT`（1.4 节那层）**不参与冲突判定**，只影响自动重复。

### 1.2 实现约束（写进验收清单）

- **每次注册都检查返回值**；失败在规则页标红「该组合已被其它程序占用，请换一个」，
  并说明「Windows 不告诉是谁占的」，别猜占用者、别弹一个假的程序名。
- 录制时就拦系统保留键与常见冲突组合，给「建议 `Ctrl+Alt+…` 或 `F13`–`F24`」的提示
  （后一个来自同 build 实测：`F13`–`F24` 可单独使用，普通 `F12` 基本被占）。
- **一个物理组合只注册一次**，多条规则共用同一个 id，由内存索引分发（见第 2 节）。
- 停用规则 = `UnregisterHotKey` 释放；改键 = 先注销再注册；页面显示每条规则的
  「已注册 / 被占用 / 已停用」状态。
- 启动后可延迟重试**一次**（应对自启顺序），被长期占用时不要无限重试、不要刷日志。
- 注册 id 用 `0x0000`–`0xBFFF` 范围（官方文档要求；`0xC000`–`0xFFFF` 留给 DLL）。

### 1.3 自己的热键会挡住自己的「按键录制」（2026-11-17 实测，已落地）

用户报的现象：进某条规则的编辑页，点键帽想重输它**正在用的**那个组合（`Ctrl+1`），
按键进不了界面，反而听到音箱播报 —— 规则被自己的热键触发了一次。

真因不在录制代码：`WM_HOTKEY` 是**系统层**投递的，消息根本不下发到窗口，对话框的
`keyPressEvent` 永远等不到那次按键。这跟「热键优先级」无关（1 节：排他、先到先得，
持有者是我们自己），所以**唯一解法是编辑期间先把自己那条规则注册的组合退掉**。

落地方案（契约级，改之前先读 `docs/dev/automation.md` 那一节）：

- 进编辑页 `AutomationService.suspend_hotkeys(rule_id)`：只 `UnregisterHotKey`，
  **不动 `enabled`**，也不落盘；关掉编辑页（保存 / 取消 / 关窗都算）
  `resume_hotkeys(rule_id)` 按当前启用状态重算注册。**恢复只能写在 `done()`**，
  `closeEvent` 补一次（它不经过 `reject`）。
- 同一组合还被**别的**启用规则用着时，注册必须留着（那本来就该触发别的规则）；
  分发层再由 `engine.trigger(keys, skip_ids=...)` 挡掉编辑中的那条，否则编辑页开着、
  按一下两条一起响。
- 状态下不要说成「未注册」：编辑页里显示「编辑中已暂停，关闭后恢复」，否则用户会
  以为键坏了。判据是**按组合算**（同一个键还有别人在用 → 仍报「已注册」）。

真机探针（`build/probe_hotkey_pause.py`，一次性，未提交）确认了这条路径成立：
注册 `Ctrl+Alt+Shift+F12` 后别的窗口抢不到；`sync([], paused=[...])` 之后能抢到；
恢复注册后又抢不到 —— 说明「暂停」是真的把系统热键还给了别人，不是只改了界面文案。

### 1.4 同键多条规则：排他按「组合」，不按「规则」（2026-11-17 实测）

用户问「调试时建几条同快捷键、不同动作的规则会怎样，两条都启用呢」。实测（离线，
fake `user32` + 真 `AutomationService`）：

| 情况 | 结果 |
| --- | --- |
| 编辑页里输入**另一条未启用**规则的键 | **能输入**。停用的规则不注册热键（`enabled_keys` 只取 `enabled` 且 `home` 非空），系统层没有占位，按键照常进对话框 |
| 两条同键规则**都启用** | 系统层按组合去重、**只注册一份**（不会互相抢失败）；按一次 `rules_for` 返回两条 → **两条都执行**，各自冷静期 / 重入锁 / 日志批次（日志窗两行）。**11-17 起界面已经存不进这种规则了**（见 1.5，键全局唯一），只剩旧数据 / 手改 `rules.json` 会是这个状态 |
| 一条启用、一条停用 | 只跑启用的那条 |
| 编辑页里输入**另一条启用**规则的键 | 仍被截走（那条的注册还在），并会执行它 —— 用户 11-17 明确「这是用户自己的选择」，**不加自动停用全表的机制**：那会让本来该响的规则失效 |

配套的文案：编辑页里的「未注册」不再直接显示 —— 换成「保存后注册」（本条启用，
保存才注册）或「规则已停用，启用后注册」（本条停用，永远不会注册），免得调试时
刚改完键就看到"未注册"以为键坏了。

### 1.5 一个键只分配给一条规则（2026-11-17 **当日落地**）

用户 11-17 在看完 1.4 之后提的："已有某个规则用了一个快捷键，不管它是否启用，
程序都不支持另一条规则设为相同快捷键。"随后补一句**"停用的规则当然算占坑"**，
并为此把校验放宽（见 1.6）。

**关键判断：这个方案比"只拦两条同时启用"实现更省事** —— 约束越早，运行时越简单：

| 层 | 改之前 | 改之后 |
| --- | --- | --- |
| 保存时 | 只校验本条内部（两个触发行撞键） | 多一次 `key_owner` 查询 |
| 启用时 | 无检查 | **没动**：键已唯一，撞不了 |
| 注册表 | 一个组合可能被多条规则共用 | 一个组合只有一条 |
| `rules_for()` | 可能返回多条 | 最多一条 |
| 日志 | 一次按键多行、多个批次号 | 一次一条 |

对比方案"只在两条同时启用时拒绝"要改 `set_enabled()`，还得处理 `ToggleSwitch`
回弹 —— 而启停那个信号栈本身就有坑（`RuleSet` 回调从 `toggled` 里同步发出）。
**唯一性把约束前移到保存时，运行时那一层一行没碰**，这是它成本上的真正优势。

实现上占到一个便宜：`TriggerRow.error_text()` 本来就在保存时被逐行调用、自动亮
红字、自动滚进视野，所以"这个键存不进去"是白拿的，`_save` 里没有另开一道检查。
行只差一个"按 `self._draft.id` 排除自己"的回调（`_owner_note`）。

顺带修的坑：`set_keys()` 之前只改键帽文字，**不刷行内红字和注册状态** —— 录制完
一个被别人占着的键，界面上什么都不变，直到点保存才知道存不进去。现在键一变就刷。

**编辑页那一格改成只回答"能不能存"，与启停无关**（用户 11-17 当天第二次要求）。
原来它是「注册状态：已注册 / 未注册」，再配「保存后注册」「规则已停用，启用后注册」
两种解释——这些在键位全局唯一之后都没有意义了：编辑期间本条规则的热键必然被暂停
（所以"未注册"永远成立），停用的规则本来就从不注册也不能作为理由（它也占着键）。

现在只有三类结论（外加本规则内撞键一条）：

| 结论 | 颜色 | 能存 |
| --- | --- | --- |
| 可以注册 | 绿 | ✓ |
| 与「X」的快捷键冲突（**停用的也算**） | 红 | ✗ |
| 这条规则里已经用了同一个键 | 红 | ✗ |
| 系统保留 / 被**其它程序**占用 | 红 | ✗ |

红线那两条是**硬拦**：判据就是 `TriggerRow.error_text()`，`_save` 逐行调它。

"被其它程序占着"只能靠**真的试注册一次**（`HotkeyRegistry.probe()`）：Windows 不
告诉你是谁占的，而 `_status` 缓存里新录的键根本没有记录。探测成功立刻注销、不写
`_status` / `_ids` / `_by_id`，用固定 id 不消耗分配池；数字主键两份里任意一份能注册
就算可用。结果按组合缓存在行上（改一次键只碰一次系统 API），代价是"占用程序关掉后
缓存不会自己变，得改一下键"。

**缓存的作用域要说清**：`_probed` 挂在 `TriggerRow` 上，而编辑页每次打开都重建行，
所以**每次进编辑页本来就是重新探测的**。上面那句"不会自己变"只指同一个编辑页开着
的期间。

### 1.5.1 被别的程序抢走：显示与自愈（2026-11-17 第三轮）

键位唯一管的是"你别设成别人的键"，管不了"别人先占了这个键" —— `RegisterHotKey`
先到先得，开机时谁先跑谁赢。三种情况的实际后果：

| 情况 | 结果 |
| --- | --- |
| 规则**已启用**，别的程序后来抢 | 抢不走（本程序持有，对方注册失败），无影响 |
| 规则当时**停用**（从未注册），别的程序抢了，之后启用 | 注册失败，**界面上看不出来** |
| 开机时对方先注册 | 本程序启动失败 → `retry_once` 3 秒后重试**一次**，对方还在就仍失败 |
| 对方**中途退出** | 不会自动发现，要等下一次 `sync()` |

`sync()` 本身会重试所有"本该注册却没注册"的组合，所以不是"永远好不了"，而是
"靠用户碰巧动一下"。补两处：

1. **卡片红标**：`automation_list.hotkey_note()` 判失败（白名单式：`已注册…` /
   `未注册` / `编辑中已暂停` 都不报），卡片挂「热键没注册上」，tooltip 给完整原因。
   同时把 `service.status_changed` 接到列表页刷新，重试成功后红标自己消失。
2. **进页面就重试**：`AutomationPage.showEvent` 先 `service.sync()` 再重画；编辑页
   打开时 `suspend_hotkeys()` 内部已经 sync 一次（新建规则走 `else` 分支手动 sync）。
   用户"进去看一眼"的那一刻就是重试时刻，显示的也是这一次的真实结果。

**不做**定时轮询：每隔几秒调 `RegisterHotKey` 只为看状态，噪音大于收益。

### 1.5.2 还原：一律停用，撞键只提示两行（2026-11-17 第四轮）

`restore()` 早先只清触发行、不动 `enabled`（= 恢复删除前的状态）。用户 11-17 改成
**一律停用**：还原的是一条规则，不该顺带恢复它的**运行**——它可能已经删了一阵，
键早被别人拿走了。停用态下用户先看一眼再手动启用，那一步才做注册检查。

这条和上一节配合成一条链：

1. 还原 → 停用，不检查系统占用（**用户明确要它不提示**，也省得还原要等一次探测）；
2. 用户点开关启用 → `_on_toggle` 查 `status_for` → 失败就弹
   「规则已启用，但快捷键没注册上」+ 原因；
3. 卡片上同时有红标兜底（不是每个人都看弹窗）。

撞**别的规则**的键仍然在还原时处理（清掉那条触发），提示从原来那段"快捷键是全局
唯一的…"缩成两行：

```
本规则的快捷键 F10 已被「新规则」使用
已删除本规则的快捷键，请重新编辑
```

"为什么"不在这里讲——编辑页那一格红字会说清。

**三条边界，实现就是这个样子**：

1. **回收站不算占用**：删了还要能再建。撞车放在 `restore()` 里处理——**清掉那条
   触发、把键和占用者带回界面弹提示**，不阻止还原。用户要的是那条规则，不是一个键。
2. **已有重复数据不能让程序打不开**：`rules.json` 能手改、GPL 之后别人可能带着老
   数据。`load()` 只记 warning，不删不改；等用户下次编辑那条规则时才要求解决。
   （本机 11-17 实测：5 条规则全停用、无同键重复 → 迁移成本为零。）
3. **唯一性查询放 `RuleSet.key_owner(keys, exclude_id=)`**，不进
   `validate_rule()`：后者是纯函数、被 20 多处测试直接调，加必填参数会全红，
   而且它拿不到规则集。

**代价（当时跟用户复述过的）**：

- **"把 `Ctrl+1` 从 A 挪到 B"要改两次**（先改掉 A 或删掉 A）。这是唯一会天天碰到
  的摩擦。
- **调试场景没了**：1.4 里"建几条同键不同动作、只启用一条去测"建不出来。
- **跨家庭也唯一**（家庭 A 和 B 的 `Ctrl+1` 不能共存）。热键是操作系统级的，
  不分家庭，判断为对。

**同样不做**：保存时"把键从别人那里抢过来"的一键夺权 —— 要处理撤销、还要处理被
抢那条以后怎么办，不值。

### 1.6 允许"没有触发"的规则，以及触发源怎么扩展（2026-11-17）

全局唯一带来一个新问题：**从回收站还原一条规则时，它的键可能已经被别人拿走了**。
用户给的答案是——不要拦，把键清空就行。于是 `validate_rule` 必须允许
`triggers == []`：

- 这种规则**存得下、能启用，只是不会被任何事件唤起**。不是错误状态。
- **空档行 ≠ 没有触发**：空档（`type` 为空）是"填了一半"仍然拦；`triggers == []`
  是"故意不要"放过。混起来的话，编辑页加一行没选类型就保存会静默丢掉它。
- 卡片显示「未设置触发」（原来那句「未设置快捷键」说得不准）。

用户还提了个前瞻要求：**别让这套检测逻辑只能认键盘**——TODO 里排着"本程序启动
时"，以后还会有别的。做法是把类型规格化：

```python
TRIGGER_SPECS: dict[str, TriggerSpec] = {"keyboard": TriggerSpec("键盘快捷键")}
# 加一种：TRIGGER_SPECS["app_start"] = TriggerSpec("本程序启动时", needs_keys=False)
```

两个读取入口 `trigger_keys(trig)` / `trigger_label(trig)` 取代原先散在 6 处的
`t.type == "keyboard"`（`Rule.keys`、`enabled_keys`、`rules_for`、编辑页冲突提示、
卡片摘要、卡片 tooltip）。`needs_keys=False` 的类型不要求键、不占键位、不注册热键。

**这条是被测过的，不是嘴上说的**：`verify_automation_rules.py` 里临时注入一个
`app_start`，断言"校验不报缺键 / `enabled_keys` 为空 / 卡片文案是类型名 / 能存进
`rules.json` 再读回 / 和键盘触发混排时只注册键盘那个"，跑完再 `pop` 掉。

`TRIGGER_TYPES`（`type → 中文名`）保留，但由 `TRIGGER_SPECS` 推导，**不要往里加**。

**第一个真类型就是「本程序启动时」（11-17 当天落地）**：`rules.py` 加一行规格，
UI 一行没改——下拉多一项、键帽自动藏起来、卡片自动写"本程序启动时"、校验自动不要求
键。真正要新写的只有"谁来叫它"：`MainWindow._on_loaded` → `fire_start_rules()`，
内部 `_start_fired` 保证一个进程只跑一次，再延 2 秒避开首屏轮询；日志来源写
「程序启动触发」，`keys` 留空（日志窗显示 `—`）。

顺手修了一个拦路 bug：`TriggerRow.block_reason()` 对空键会走 `reserved_reason("")`，
返回"快捷键格式不对"——**任何一种不带键的触发行都会被它判成存不进去**。现在空键在
那个函数开头就早退。

### 1.6.1 一条规则挂多个触发时，前面那些机制怎么作用（2026-11-17 用户追问）

| 问题 | 答案 |
| --- | --- |
| 还原时清空**所有**触发，还是只清冲突的？ | **只清冲突的那几条**。`F9 / F10` 里只有 `F10` 被占，还原后留 `F9`；`dropped` 只记 `F10` |
| 不带键的触发（"本程序启动时"）会被清吗？ | 不会。`trigger_keys()` 对它返回空串，`key_owner` 查不到，原样保留 |
| 一个键被别的程序占，其它触发还能用吗？ | **能**。注册是按**组合**做的，不是按规则：`F7` 成功、`F8` 失败 → 按下 `F7` 照样 `rules_for("F7")` 到这条规则、照样执行 |
| 那卡片/提示会漏报吗？ | 会——如果只看 `rule.keys`（第一个有键的触发）。所以 `hotkey_failures()` **遍历所有触发**，`_on_toggle` 的提示逐条列失败项，并在还有成功键时补一句"其余快捷键照常可用" |

这条是 11-17 补的一个真 bug：`hotkey_note()` 原先只查 `rule.keys`，多键规则里
第二个键哑了却显示正常。现在拆成 `hotkey_failures()`（列表）+
`hotkey_note()`（给 tooltip 的多行文本）。

`retry_once()` 只挑 `_status` 里失败的那些重注册，成功的键（在 `_ids` 里）不碰。

## 2. 热键存哪：用户的判断是对的

**Windows 不需要任何文件来注册热键。** `RegisterHotKey` 是**进程运行时** API，注册信息
在会话的 USER 热键表里；进程退出 / 崩溃自动释放，重启不保留，注册表里也查不到绝大多数
全局热键（能查到的只是少数 `AppKey` 之类的固定绑定）。所以不存在「单独一个文件去给
系统注册」这回事。

**撤回上一轮推荐的 `hotkeys.json`**：那是 11-10 旧草案「一级 = 一张
`[(快捷键, 事件名)]` 小映射表」的遗留思路。既然已定三段式规则，键位就该是规则自身的
字段 `trigger.keys`，跟 `condition` / `actions` / `cooldown_ms` 一起存在 `rules.json`
的每条规则里。再放一份 `hotkeys.json` 或塞进 `prefs.json` 都会变成**第二份真相**，
改规则时极易不同步。

真正需要的是**内存索引**，不是文件：

```
启动 / 改规则 → 遍历 enabled 规则的 trigger.keys
              → 去重：一个组合分配一个 hotkey id
              → RegisterHotKey(id, modifiers|MOD_NOREPEAT, vk)
              → 建 id → [rule_id, ...]
WM_HOTKEY(id) → 查表分发给该组合下所有规则
              → 每条规则各自求值条件、各自走自己的冷静期
```

**同一组合绑多条规则不是冲突**（系统层面只注册一次，分发在我们这边）。反过来说，
同一个热键在多个规则里各自独立冷却，符合 1.4 节「冷却挂在规则上」的定义。

将来若要做「全局热键黑白名单 / 冲突诊断记录」，那也只是一份**配置**，不是注册表。

## 7. 动作执行的时延与"发出去就不等回执"（2026-11-14 晚调研，**已落地**）

**用户实测**：③ 里「音箱-唤醒」→「中枢-发虚拟事件」，后者有明显延迟，像是"在等唤醒
的某个回应"。**他没说错**，但根因不在引擎。

**结论（按证据强弱排）**

1. **`jobs.SerialWorker` 只有一条线程**——这是硬瓶颈。第一条 HTTP 不返回，第二条连
   `connect` 都发不出去。所以只把引擎改成"不等"没有用，必须让"发"这一步本身不阻塞。
   （`core/jobs.py` 的 `_loop` 是单 `worker` 线程串行取任务。）
2. **`http.client` 的 `request()` 只写不读**：`putrequest → putheader → endheaders →
   send`，写完 socket 就返回，`getresponse()` 才是阻塞点。这就是"只发不等"的天然实现，
   不需要自己造协议。
3. **不能用 `requests` 的 `timeout` 实现这件事**：`read timeout` 触发会关闭连接，
   回执就永久丢了（而且我们无权重发——那是设备的动作）。要"发完继续等回执"必须自己
   持有连接，把 `getresponse()` 交给别的线程。
4. **`connect timeout` 与 `read timeout` 必须分开**：前者失败 = **一个字都没发出去**
   （该立刻告警）；后者失败 = **发出去了没等到回执**（命令已在云端，播报 / 唤醒这类
   设备压根不回执，报失败就是一堆假警报）。代码里是 `FAILED=-2` / `UNCONFIRMED=-3`。
5. **回执可能是密文**：云端对 `miot-accept-encoding: GZIP` 的响应是 RC4 密文，
   `decrypt(ssecurity, nonce, text)` 要用**同一个 nonce** → nonce 得跟着连接一起交给
   读线程。`/miotspec/action` 的成功码还藏在 `result` 里
   （`{"code":0,"result":{"code":-704040005}}`），两层都看。

**落点**：`mihome/core/channel.py`（1 条发送线程 + 4 条读线程 + 结果队列 + 主线程
16 ms drain）；`engine._step` 改成"提交即下一步、失败不拦后续"；`Feature.refreshes`
决定要不要跑 1/2.5/4 秒全量回读（只有 `execute-text-directive` 是）。细节见
`docs/dev/automation.md`「发送链路：设备动作怎么发」。

### 7.1 真机第一跳就踩到的坑：请求体必须包 `params`（2026-11-14 21:xx）

用户实测：③ 里「唤醒 → 发虚拟事件」，**两个动作不论谁先谁后**，按下热键立刻弹
「…未成功（…）：**invalid request**」。两个动作都错、换顺序也一样 = 错的不是动作，
是**请求外壳**。

**根因**：`/miotspec/*` 的请求体形状是 `{"params": <单条|列表>}`。上游
`mijiaAPI/apis.py` 里每个入口都是 `self._request(uri, {"params": param})`
（`run_action` / `get_prop` / `prop/set` 全一样）。`Channel` 上线时把
`{"did","siid","aiid"}` 直接当请求体发了，少一层壳 → 云端 `-6 invalid request`。

**离线也验过**：同样的 uri + data，`urlencode` 出来的字节与
`requests.Request(...).prepare().body` **逐字节相同**（只有 `bytes` / `str` 的类型差），
所以编码层没问题，差的只是那层字典包装。**这说明"逐字节对齐上游"这类校验必须覆盖
请求体的完整形状，只对齐签名参数是不够的。**

**真机探针（不碰任何设备）**：拿一个不存在的 `did`（`000000000`）对比两种外壳——

| 请求体 | 云端回 |
| --- | --- |
| `{"params": {"did": "000000000", "siid": 2, "aiid": 1}}` | `-8 get udid error=000000000`（认了外壳，只是找不到设备） |
| `{"did": "000000000", "siid": 2, "aiid": 1}` | `-6 invalid request`（**就是用户看到的那个**） |

这条探针顺手证明了 `Channel` 的签名、Cookie、`Connection: close`、回执解析在真云端
**都是通的**（回执是明文 JSON，直接 `json.loads` 成功）。以后验"请求形状"类改动都可以
照这个办法：**用不存在的 did 打一发，看错误码是不是"设备级"而不是"请求级"**——比让
用户去按热键快得多，也不会动到任何设备。

**还没定论的**

> 下面四条**只针对 B 通道**（`core/channel.py`）。11-14 22:0x 定案后 B **默认不启用**
> （自动化动作走原名单线程机制），所以这些都不阻塞发布；哪天要切 B 再逐条过。

- `Connection: close` 会不会被云端提前丢（探针里没掉，但只跑了两次）。
- 20 秒读超时对"唤醒"够不够（唤醒要等音箱进聆听，云端一直挂着连接）。
- 并发 4 条读线程会不会触发频控（本程序动作串很短，风险低但没实测）。
- 鉴权过期不自动重登（`Client` 本身也不做），云端回 `-704010000` 之类就原样进日志。

**已定论的一条（11-14 实测，推翻原假设）**：`wake-up` 之后的"明显延迟"**不是**收发排队，
而是唤醒让音箱进入**聆听态**，之后到音箱的指令要等聆听结束才执行——设备侧顺序，换哪条
通道都一样。所以在编排上该绕开：**把唤醒放到动作串的最后一步**，或改用别的动作。

## 8. 触发日志落盘（2026-11-14 23:xx 定，已落地）

**用户要求**：日志原来只活内存、重启清空，要落盘；并自己指出"加了 run 批次号，落盘后
这个也要改吧，是不是按自动化 id + 时间戳更好"。**两点都对**，按这个做：

1. **`LogEntry.run` 从整数换成字符串** `规则id@触发毫秒-序号`。整数是内存计数器，
   重启就归零——文件里昨天的第 3 次和今天的第 3 次会折进同一行。这个键必须**写在文件里**
   而不能靠读回时按"下一个 FIRED 另起一组"重算：两条规则的触发会交错，重算就串组。
2. **存储格式 JSONL**（`<data>/automation_log.jsonl`，一行一条）而不是 JSON 数组：
   日志只增不改，追加一行只要一次 `open(..., "a")`；数组要整份读改写，每来一条重写全量。
3. **每条 append 都开关文件**：强杀 / 断电最多丢最后一行；攒内存批量落盘丢一整段。
   坏行（半行 JSON）在 `load()` 里跳过，**先解析再截尾**——否则末尾几行坏行会把要留的
   好行挤出窗口（这条是测试抓出来的）。
4. **上限只留一个数** `MAX_ENTRIES = 500`：内存 `max_log`、文件、表格 `MAX_ROWS` 同源。
   文件攒到 **两倍**（1000 条）才裁一次，平均 500 条写一次盘；所以文件里实际 500~1000 条。
5. **写失败不抛不提示**：磁盘满 / 没权限不该中断规则执行，界面上那条日志照常出现，
   只是重启后翻不到。
6. **展开状态不记忆**（同一条需求里用户另提）：删掉按批次恢复的那套；记住的展开态会在
   新日志插到顶部、行号整体下移之后挂到别的行上，看着像串行。

**落点**：`core/automation/logstore.py`（`LogStore`）、`engine.restore_log()` /
`_new_run()`、`AutomationService.logstore` / `log_path` / `clear_log()`、
`ui/automation_log.py`（状态条 + 「日志文件」按钮）。细节见 `docs/dev/automation.md`
「独立日志窗」。
