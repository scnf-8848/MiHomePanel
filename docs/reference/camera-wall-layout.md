## 1. 参考对象：DD_Monitor_CE（LGPL-2.1）

[Lanpropro/DD_Monitor_CE](https://github.com/Lanpropro/DD_Monitor_CE) 是多窗口直播
监控工具（PySide6 + mpv，本体最多 16 路）。用户 2026-11-19 点名参考它，并限定范围：
**只取多画面布局，不要 16 路、不要它那套自由划格**。

取的三条设计：

1. 左侧一列所有画面的缩略图，拖到右边某个窗口决定那格放哪一路；
2. "一主 + 5 / 2 小"的布局；
3. 最基础的单窗口、左右两分、四宫格。

明确不取：

| 它的能力 | 为什么不取 |
|---|---|
| 最多 16 路 | 我们每路是 2960×1666 HEVC 软解，实测一路约 40% 单核；6 路已经 ~2.4 核 |
| 拖动格子边界自由划格 | 存储要记几何（x/y/w/h），窗口一缩就要重算比例；预设用"跨行跨列"就能表达主+小，代码少一个数量级 |
| 每路独立弹幕 / 录制 / 逐路画质 | 与摄像头无关（直播场景），`camera.md` 已明确不做画质切换与回放 |

许可：**LGPL-2.1，只学交互与布局，没有抄任何代码**；本项目是 GPL-3.0-or-later，
但同行依赖/复用清单里不出现它（没引入）。

## 2. 本机的硬约束（实测，不是估算）

| 约束 | 数字 | 出处 |
|---|---|---|
| 每台设备的并发观看位 | **3 路**，第 4 路被设备掐断 | `camera.md`「已知边界」 |
| 我们每台设备开几条 P2P | **1 条**（go2rtc 的 producer 复用） | 同上 |
| 软解一路的 CPU | 约 **40% 单核**（14 秒 5.7 s，2960×1666 HEVC） | `camera.md`「默认不用显卡解码」 |
| 点播放到出画面 | 局域网 **4.8–6.3 秒**；带开播补丁 **1.85–3.15 秒** | 同上 |
| 同时开多路，第一路要等整个 GOP | 后面接进来的路只等 0.94–1.46 秒 | 同上 |

推论：**6 路（1+5）= 6 条独立的 P2P 会话**（6 台不同设备各 1 条），每台都只占 1 个
观看位，**不会**撞 3 路上限；真正的瓶颈是 CPU 与首次全亮要等 5–7 秒。

## 3. 关键实测：go2rtc 能不能一次挂多台、不消费时会不会拨号

**能挂多个源，且不消费就不拨号**（2026-11-19，官方构建，`go2rtc.exe` 起一个临时实例）：

配置里挂 3 个 `xiaomi://` 假源，启动后 `GET /api/streams`：

```json
{"cam_a": {"producers": [{...}], "consumers": null},
 "cam_b": {"producers": [{...}], "consumers": null},
 "cam_c": {"producers": [{...}], "consumers": null}}
```

`consumers: null`，且日志里 `miss` / `dial` 命中 **0 行**——producer 是**按需拨号**
的。所以进监控页时把全家的摄像头源一次性写进配置，**零成本、不占观看位、不耗上行**。

**但改配置要重启进程**：`CameraService._open` 在"这台不在配置里"时分两路——同源复用，
否则 `runtime.restart(sources)`。而 `restart()` 是 `stop()` + `start()`，**会把所有正在
播的流一起掐断**。所以不能"每格播的时候各加一条源"：那样第二格一开就把第一格掐了。
→ 新增 `CameraService.prepare(client, nodes)`：进页面时一次登记全量，之后每格
`open()` 都命中 `_same_source`，不重启。

（运行时用 `POST /api/streams` 热加源这条路没走通：参数格式试错返回 400。既然预置
已经能解决问题，不再深挖；`/api/streams` 只用来读状态。）

## 4. 远程多路：relay 从"进程内一条"改成"按设备各一条"

原来 `CameraService._relay` 是单槽，注释写着"同一时刻只保留一条 relay 会话"。多路同屏
下这是死结：开第二路远程会把第一路的会话关掉。

改法（`core/camera.py`）：

- `_relays: dict[did, RelaySession]`；
- `_ensure_relay(client, did)` 只查这台自己的那条，不从别的设备抢；
- `open()` 的局域网分支只 `_close_relay(did)`（原来是全关，会顺手关掉别人的远程）；
- 切源时"删除别的设备的远程源"那条也删了——每台各自留着；
- 端口由 `relay._bind_udp` 从 32108 往后找空位，多条会话天然不撞。

**没在真实异地网络下验证过**：本地只能测"两条会话都能建起来、端口不冲突"。
异地多路（6 条 relay 同时）要等有环境时实测，见 `TODO.md`。

## 5. 缩略图：播过的那一帧，模糊，不取流

左侧列表如果也走实时画面，6 路同屏就变成 12 路解码，且每台多占一个观看位。

做法（`ui/thumbs.py`）：

- `CameraView.snapshot` 信号：播放中每 **2 秒**给一张当前帧（不是每帧——接收方要
  降采样 + 落盘）；
- 降采样到 1/8 再平滑放大回去当模糊（`BLUR_DIVISOR = 8`）。不用
  `QGraphicsBlurEffect`：为一张静帧引入整套 `QGraphicsScene` 不值；
- 存 `<data>/cache/thumbs/<did>.jpg`（质量 70，实测一张约 1 KB 起、典型 6–10 KB），
  重启后仍能认出是哪路；
- 没有缓存的设备画镜头剪影。

模糊是用户 2026-11-19 定的：2960×1666 缩到 168×94 满屏锯齿，看起来像画质坏了。
当天晚些时候同一张图又兼作监控页格子的空态封面，所以**存档尺寸改成 480×270**
（`POSTER_W/H`），列表里画的时候再缩到 168×94，一份存档两处用；播放中每 10 秒刷新，
停播 / 换布局 / 离页前存最后一帧。

## 6. 还没验证的

**作者手上摄像头数量少于 `1+5` 的格数（`2x2` 都铺不满），多路相关的真机数据一律没有**
（2026-11-19 用户明确：没设备可测，文档里要写明这一点，不要当成已验收）。已在
`README.md`「已知限制」、`docs/dev/camera.md`「多路同屏」、`docs/dev/ui.md`「监控页」
三处标注，`TODO.md` D 段从待办改成「已知局限」。

- **6 路真机并发**：CPU 实际占用、首次全亮的总时长、6 路同时首帧时 go2rtc 的表现。
  代码路径与上限（6）已定；"每路 40% 单核"是**单路**测的，6 路是外推。
- **首帧等待**：预热地址这一段已回填——等预热完成后点播放，出画约 3 s → 2 s
  （用户体感，没掐表）。
- **远程多路**：需要异地网络（`25000/UDP` 能出去）。本地只验了协议与端口。
- **设备侧 3 路观看位**：我们每台只开 1 路，理论上不撞；但"米家 App 同时看同一台"
  时会不会把我们那路挤掉，没测。
