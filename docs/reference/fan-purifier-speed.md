## 1. 风扇 `dmaker.fan.p5c`（米家智能直流变频落地扇 1X）

规格 `urn:miot-spec-v2:device:fan:0000A005:dmaker-p5c:1`，只列和卡片有关的：

| 方法号 | 属性 | 形状 |
|---|---|---|
| 2.1 | `on` | bool，可写 |
| 2.2 | `fan-level` | **enum 4 项**：1=1挡 / 2=2挡 / 3=3挡 / 4=4挡 |
| 2.3 | `mode` | enum 2 项：0=直吹风 / 1=自然风 |
| 2.4 | `horizontal-swing` | bool |
| 2.5 | `horizontal-swing-included-angle` | **enum 5 项**：30 / 60 / 90 / 120 / 140 |
| 7.1 | `physical-controls-locked` | bool（童锁） |
| 3.1 | `off-delay-time` | range 0~480 分钟 |
| 8.1 | `speed-level` | **range 1~100 step 1**（在 `dm-service` 自定义服务里） |

探测当刻的读数（只读）：`on=True`、`fan-level=4`、`mode=0`（直吹风）、
`speed-level=100`、`swing=True`、角度 `60`、童锁 `False`、定时 `0`。

### 关于「直吹风 0~1100」

云端 spec 里这条是 **1~100**，而且 4 挡（最高档）时读到的正是 **100**——两者吻合。
用户记忆里的 `0~1100` 应该是**设备端/蓝牙协议的刻度**，云端已经归一化过一次；
按 1100 写进去会越界（**未实测，不拿它当代价**）。

所以卡片上该按 **1–100** 设计：滑条满格 = 4 挡，刻度点可以落在 25/50/75/100。

## 2. 净化器 `zhimi.airp.rma2`（米家空气净化器 4 Lite）

| 方法号 | 属性 | 形状 |
|---|---|---|
| 2.1 | `on` | bool |
| 2.4 | `mode` | enum 3 项：0=自动 / 1=睡眠 / 2=最爱 |
| **11.1** | `fan-level` | **enum 15 项**，0–14，在 `air-purifier-favorite` 服务里 |
| 8.1 | `moto-speed-rpm` | range 0~2500，**只读** |
| 4.1 | `filter-life-level` | range 0~100（滤芯） |

15 项的 `description` 是数字 `"0"…"14"`，`comment` 是 **m/s 风速区间**
（`"3-6"`、`"4-7"`、`"6-10"` … `"26-45"`）。也就是说这 15 项是"最爱模式下的档位"，
名字落在"区间"上，不是给人读的档位名。

### 为什么这条不能直接上卡片

`CardChips` 的溢出策略是"先压内边距 → 再截字 → **最后丢弃多余项**"。312px 宽的
2×1 内容带放 15 项，每项约 20px，结果是只画出三四个、其余**点不到**——不是难看，
是坏。这条必须走"多档枚举不铺胶囊"的分支。

## 3. 结论：三个品类三种形状

| 设备 | 速度属性 | 卡片该怎么办 |
|---|---|---|
| 风扇 | 连续 `speed-level`(1–100) **和** 档位 `fan-level`(4 项)，由 `mode` 决定用哪个 | 同一格内换控件（滑条 ↔ 胶囊），见第 4 节第 3 条 |
| 净化器 | 只有档位（15 项），没有连续量 | 不能用胶囊；滑条（15 个停靠点）或下拉 |
| 浴霸 | **未测**（共享家庭） | 待测 |

## 4. 卡片层缺的三件事（按代价从低到高）

> **2026-11-12 三件全做完了**，落地位置与两处调整见本节末尾。

1. **显式控件提示**：给 `catalog.Control` 加 `widget`（`slider` / `stepper` / `chips`，
   空 = 按属性类型）。现在 `CardBody._pick()` 只看 `prop.kind`，有 range 一律步进器，
   1–100 会变成「− 45 +」。这一步只改选型，不动布局。
2. **枚举基数上限**：超过 N 项（建议 6）就不铺胶囊。净化器 15 档必须走这条，
   否则是"看得见点不到"。
3. **同一个控件换形态**（不是改布局）：这台风扇 `speed-level` 与 `fan-level` 都存在，
   所以两个属性可以**同时静态绑定**，缺的只是"按 `mode` 决定此刻谁说了算"。
   形态定为 `CardSpeed`：内部同时持有滑条与胶囊，按 `mode` 显示其一；
   对外仍是单槽单行，`CardStyle.slots` / `build_card` / `CardBody` 一行不动
   （`CardBody` 是 `QVBoxLayout`，本来就会重排居中）。
   不采用"两个槽位交替显示"，因为隐藏一行后剩下那行会被 stretch 重新居中，
   切模式时整行上下跳一次。

**落地结果（2026-11-12）**

- `Control.widget` / `Control.kind` / `Control.search_all` 三个声明字段进
  `core/catalog.py`，`__post_init__` 校验取值，import 期就炸。
- `MAX_CHIPS = 6` 进 `ui/card_templates.py`，`CardBody._pick()` 与 `FanBody._make()`
  都吃它；后者另有 `_fits()` 判"会不会截字"（半张卡放不下四个 "1挡"）。
- 第 3 条**形态改了**：没做 `CardSpeed`，做的是 `ui/fan_body.py` 的 `FanBody`——
  风扇 2×1 本来就要分两列摆四件事，右下那格自己持有两个控件、按 `mode` 点亮一个
  （`_Cell.pick`）。与 `CardSpeed` 等效（同格、位置不动、对外仍是单槽），
  但不需要一个新控件分发两种子控件的信号。
- 型号规则落 `core/adapters/dmaker.py` 的 `speed_by_mode`；没有这条规则的设备
  退"档位优先"，不猜、也不藏。
- 验证 `scripts/verify_fan_card.py`；开发侧说明见 `docs/dev/ui.md`
  「风扇卡片：两列四格」。

## 5. 所以"能不能在 body 里做"——能，已经做了

三条缺口里前两条是**选型**问题（`widget` 字段、枚举上限），第三条是**同一格换控件**。
都不是"不可能"，也都**不需要改固定格子或布局模型**——这是 2026-11-12 更正的说法，
之前写"归适配层、样式系统不管"是错的：风扇不是"同一功能两个属性"的偶发特例，
而是米家风扇的通用形状（`mode` + 两套速度）。

克制的地方在别处：这套只在"有 `mode` 且有两条速度属性"时生效（`speed_by_mode`
为空就走单控件），**没把条件逻辑做成样式系统的通用能力**。
`FanBody` 也只服务风扇品类，净水器 / 加湿器要类似的布局时另登记 body，
别往 `CardBody` 里塞横向容器（那是 OpenMexia 那条"内容决定高度"的路）。
