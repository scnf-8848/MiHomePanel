# 灯跟随屏幕亮度：读得到亮度吗、读到了还要改哪

> 2026-11-13 06:15 用户提的场景：**电脑亮度变化 → 延迟 n 秒（等稳定）→ 读电脑当前亮度
> → 给指定灯具发指定亮度**。本页记**能力实测 + 改造清单 + 备选方案**。
> 探针 `scripts/probe_screen_brightness.py`（纯标准库 ctypes + PowerShell，只读、不设置
> 任何亮度、不发米家请求）。
>
> **一句话结论**：这台机器上**读不到屏幕亮度**——WMI 类不存在、DDC/CI 的 I2C 通路不通、
> 电源方案那个 75% 是死值。所以「做不做得到」的第一道关不是代码，是**有没有输入源**；
> 即使读得到，代码侧还有 5 处结构性改造（触发类型 / 轮询稳定窗口 / 动作传值 /
> 设备写入通道 / 频控），都不难但都不小。
>
> 索引状态 = **搁置（2026-11-13 用户定不做）**。原本写的是"待排期（前置条件未满足）"：
> 换笔记本或打开显示器 DDC/CI 后重测、有 `[OK]` 才能动手。现在两条都放下——**本页留作
> 资料**，别当成待办。真要重启，先只做「设置某台灯的亮度」这个不依赖亮度源的动作。

## 1. 把用户的话翻译成机制

| 用户表述 | 实际需要的机制 | 为什么 |
| --- | --- | --- |
| 电脑亮度**变化时** | 轮询 + 变化检测（**没有**系统级的"亮度变了"事件） | 见 3.2 |
| **延迟 n 秒**（等稳定） | **触发侧防抖**：最后一次变化后再等 n 秒才动作 | 见 3.3，照字面做成"动作延迟"会出错 |
| 获取电脑**当前**亮度 | 防抖窗口结束时**现读一次**（不是触发时的值） | 拖滑块过程中读到的都是中间值 |
| 给指定灯具发指定亮度 | 写设备属性（`store.set_value`）+ 限制写入频率 | 见 3.5 |

**注意第 2 行**：用户说的"延迟 n 秒"直觉上是③里的「延迟」动作，但语义不同——
动作延迟是"每触发一次就等 n 秒"，而需求是"等你停手 n 秒后**只做一次**"。

## 2. 实测：本机三条路全断（2026-11-13 06:2x）

机器：`PCSystemType=1`（台式机）、电池 0 块、`RTX 4070 Ti` + **Mi Monitor**
（`DISPLAY\XMI27B3`，3840×2160，`VideoOutputTechnology=5` 即 **HDMI**），
另外装了 `Todesk Virtual Display Adapter`（虚拟显示器驱动，当前未启用）。

| 通道 | API | 本机结果 |
| --- | --- | --- |
| WMI（笔记本内置屏） | `root\wmi:WmiMonitorBrightness` | **`[--]` 类不支持**：`HRESULT 0x8004100C`（"不支持"）。台式机 / 纯外接屏常见整个类都不存在 |
| DDC/CI（外接屏） | `dxva2.GetMonitorCapabilities` / `GetVCPFeatureAndVCPFeatureReply(0x10)` | **`[!!]` `0xC0262582`**：I2C 传输失败。连**能力查询**都失败，说明不是"亮度这个值不支持"（那会是 `0xC0262584`），是整条 DDC 通路没通 |
| 电源方案 | `powrprof.PowerReadACValueIndex`（`SUB_VIDEO` / `VIDEONORMALLEVEL`） | **`[OK]` 75%**（0–100，交流/直流同值）——但**这个值不可信**，见下 |

### 2.1 为什么"电源方案 75%"不能当亮度用

这一项存的是**系统设置里的亮度**，笔记本上会跟着亮度键走。但这台是台式机、屏幕是
外接的：用显示器 OSD 拨亮度**不会**写回这个值，所以它多半停在默认 75% 不动。

探针带 `--watch`：调一下亮度再看 10 秒采样，值不动就是死值。**`[OK]` 不等于可用**，
"读得到"和"值会跟着调"是两件事。

### 2.2 想让它变得可用，三条路

1. **显示器 OSD 里打开 DDC/CI**（小米/Redmi 显示器多数有这个开关，出厂状态不一）。
   打开后重跑探针，`GetVCPFeature 0x10` 应该能返回当前值。
2. **换直连线**：不经扩展坞 / KVM / HDMI 转接（这些常把 DDC 通道砍掉）。
   本机已经是 HDMI 直连，所以更可能是 OSD 开关没开。
3. **换笔记本测 WMI**：内置屏走 ACPI 背光，`WmiMonitorBrightness` 通常有，且
   `WmiSetBrightness` 可写。**本项目没有笔记本可测，这条是"应该有"，不是已验**。

## 3. 就算读得到亮度，还有这些难点

### 3.1 触发侧：规则现在只认热键

`Rule.keys` 是触发键，`validate_rule()` 里写死 `快捷键无效` 就报错；`HotkeyRegistry`
的发信号直接接 `engine.trigger(keys)`。要加"屏幕亮度变化"这种触发源，得：

- `rules.json` 加 `trigger: {type: "hotkey" | "screen_brightness"}`（**schema v2**，
  旧规则没有这个键就按 `hotkey` 读，和 `Action.unit` 一样的宽容策略）；
- `keys` 在非热键触发时允许为空 → `validate_rule` 的两条硬要求都要按类型放宽
  （另一条是"动作里至少要有一条发虚拟事件"，跟随亮度场景里根本没有虚拟事件）；
- ①触发块 UI 重排：现在是「键盘快捷键」一行 + 折叠的手动选键，要变成"触发方式"下拉；
- `EnabledKeys` / `rules_for(keys)` 这套按 `keys` 索引的路径要能跳过非热键规则，
  否则同一组合会被非热键规则"占"一份。

### 3.2 没有"亮度变化"事件，只能轮询

Windows 没有可靠的"屏幕亮度变了"通知（`WM_SETTINGCHANGE`、`GUID_MONITOR_POWER_ON`
都不带亮度值）。所以只能定时读：

| 通道 | 单次耗时（量级） | 能不能在主线程轮询 |
| --- | --- | --- |
| WMI | 10–30 ms（COM + 查询） | 不能，必须进 `SerialWorker` |
| DDC/CI | 一次 I2C 往返，慢的屏可到几十 ms | 不能，同上 |
| 电源方案 | <1 ms（纯 API） | 可以，但这个值不一定有效（见 2.1） |

轮询间隔建议 **700 ms–1 s**：再密没有意义（人眼调亮度是连续的），还会拖慢云端请求队列
（项目红线：新增轮询先算请求数——这里是本地调用，不占米家配额，但占 CPU/主线程）。

### 3.3 触发风暴：这才是最容易踩的坑

拖一次亮度滑块 = **几十次**变化（100 → 30 会发生 ~70 次）。照字面实现会怎样：

- 每次变化触发一次规则 → 70 次"延迟 n 秒 → 读 → 写"排队；
- 引擎的 **L2 重入保护**（`engine._running`）会丢弃除第一次外的全部触发，日志里刷
  70 条"上一串动作还没跑完，本次触发已丢弃"；
- 第一次的延迟结束后读到的是**最终值**（这部分歪打正着是对的），但灯会先闪一下中间值，
  而且延迟期间用户再调亮度**不会**被跟进。

正确做法是**触发侧三道闸**，动作里**不需要**再放延迟：

1. **防抖（debounce）**：每次检测到变化就重置计时器，静默 n 秒才算"一次触发"；
2. **阈值**：变化 ≤1–2% 忽略（避免自动亮度、HDR 切换的抖动）；
3. **最小写入间隔**：两次写设备至少隔 1.5–2 s，防止拖动过程中把云端请求打满
   （米家的 `prop/set` 有频控，项目红线里"不做频率压测"就是怕这个）。

改成防抖之后，用户描述里的"延迟 n 秒"就落在第 1 条上，**编辑页里那一行延迟动作也就不需要了**。

### 3.4 动作模型没有"传值"

现在 `Action` 只有 `{type, name, ms, unit}`，`engine._step()` 也没有上下文——
"读到的亮度"没地方放，下一个动作拿不到。两条路：

- **复合动作**（推荐）：`type: "follow_brightness"`，字段是目标设备 + 偏移/上下限，
  引擎内部"读一次 → 映射 → clamp → 写一次"。不引入变量系统，UI 只有一个动作行，
  日志能写"读到 42% → 写入 40%"。
- **变量系统**：`read_brightness` 产出 `$brightness`，`set_device` 的值支持 `$brightness`。
  灵活（能写进条件、能做换算），但要改 `Action` schema、引擎上下文、UI 引用选择器、
  校验器，工作量是前者的两三倍。

### 3.5 写设备：通道、属性、失败语义

好消息是底层已经有了：`store.set_value(did, (siid, piid), value)` 是乐观写入 + worker
提交 + 回调 + 失败回滚；灯的亮度槽在 `catalog` 里是 `Control(slot="brightness")`，
`store.devices[did].keys` 能拿到对应的 `(siid, piid)`。

要补的：

- **注入一个写通道**：引擎现在只有 `emit(name, done)`；要加 `write(did, key, value, done)`，
  由 `AutomationService` 接到 `store.set_value`（再把回调转成 `done(error)`）。
- **设备选择 UI**：③动作行要能选"哪台灯"——`did` + 名称 + 房间的下拉（设备多时要有搜索）。
- **属性发现**：不是所有灯都有 `brightness`（开关/插座没有），选完设备要能判断"这台不支持调亮度"
  并当场提示，别等运行时失败。
- **范围 clamp**：灯亮度多为 1–100（最低 1，写 0 有的固件当关灯、有的直接拒绝），
  以 `PropertySpec` 的 min/max 为准。
- **失败语义**：设备离线 / 云端拒绝 / 超时 → 按引擎现有语义"记失败并停止队列"。
- **灯关着时写亮度会不会自动亮**：各家固件不同，**必须真机试**（本项目红线：写设备要先申请）。

### 3.6 映射与边界

- **曲线不是线性的**：屏幕 0–100 是背光百分比，灯 1–100 是 PWM 占空比（还常有 gamma
  校正），一对一映射观感会"屏幕暗一点、灯就暗很多"。v1 给"偏移 + 上下限"就够，
  别急着做曲线编辑。
- **0 值要特殊对待**：显示器休眠/关闭时读数会变 0 或直接读失败，绝不能把灯写成 1。
  建议：读失败 → 跳过（记一条日志）；读 0 → 视作"屏幕关了"，可选"关灯"或"保持"。
- **锁屏 / 息屏会改亮度**：Windows 在熄屏、切换电源方案时会动亮度，会误触发。
  `PcState` 的 `locked` 快照已经能判断，触发前挡一下。
- **多显示器**：读哪块？v1 建议只跟主显示器；多屏一起跟需要"取最小/最大/各自映射"的策略。
- **自动亮度**（环境光传感器）会持续微调 → 靠 3.3 的阈值 + 最小间隔压住。

## 4. 备选方案（不依赖"读背光"）

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 画面平均亮度跟随** | `BitBlt` 把屏幕缩到 32×18 → 算平均亮度 | **纯软件，任何机器都能跑**；灯跟着"画面亮不亮"走，其实比背光更贴合观感 | 每秒截一帧（几 ms，可接受）；隐私要声明"只在内存算平均值"；DRM 保护窗口截出来是黑的，要丢弃该帧 |
| **B. 不做跟随** | 按时段 / 日出日落 / 电脑条件（空闲、供电）调灯 | 零新依赖，现有条件块就能配 | 不"跟手" |
| **C. 一键降亮** | 快捷键触发一条"设置设备亮度"的动作 | 最小改动（只加动作，不加触发源） | 手动 |

**A 值得单独评估**：它把"读不到背光"这个前置条件整个绕开了，而且用户要的"灯跟着电脑亮度"
在观感上本来就是"灯跟着屏幕亮不亮"，不是"跟着背光设置值"。剩下要解决的只有触发频率和
隐私声明——比 3.1 + 3.2 那套改造轻得多。

## 5. 如果排期，建议的顺序

> **本节不生效**：2026-11-13 用户定搁置。留着是因为真要重启时这是唯一靠谱的落法——
> 尤其是"第 1 步先测、测不到就别动 schema"这条，能省掉一轮白改。

1. **先测**：目标机跑 `probe_screen_brightness.py --watch`，三条路至少一条 `[OK]` 且会变；
   或者改做方案 A，跳过这一步。
2. **schema v2**：`Rule.trigger`（默认 `hotkey`），`validate_rule` 按类型放宽；旧
   `rules.json` 零变化。这一步单独提交、单独验证（`verify_automation_rules.py`）。
3. **触发源**：`BrightnessWatcher`（QTimer 轮询 + 防抖 + 阈值 + 最小间隔），产出
   `engine.fire(rule, source="屏幕亮度")`；日志写"亮度 82% → 78%"。
4. **动作**：`follow_brightness`（目标设备 + 偏移 + 上下限），内部读 → 映射 → clamp → 写；
   日志写"读到 78% → 写入 74%"。
5. **频控 + 失败日志**，再跑一遍全套验证。
6. 之后才考虑拆成通用动作（`read_*` + `set_device` + 变量系统）。
