## 0. 是什么 / 代码在哪

Electron + TypeScript 的米家桌面端，主窗口是常驻置顶的窄面板，功能接近"米家 App 的
Windows 版"。整个仓库 38 个文件，真正值得看的只有 5 个：

| 文件 | 行数 | 看什么 |
| --- | --- | --- |
| `src/devices.ts` | 996 | 数据源：轮询、在线判定、局域网/云端双通道读写 |
| `src/local-api.ts` | 778 | 本机 HTTP 联动接口 + 中文一句话解析 |
| `src/mijia-login.ts` | 1152 | 扫码 / 密码两种登录、会话落盘、验证码与二次验证 |
| `src/miot-spec.ts` | 300 | miot-spec 解析：属性名 → 语义字段的通用映射 |
| `main.ts` | 1304 | 窗口 / 托盘 / 置顶 / 多屏，Electron 专用，参考价值低 |

技术栈和我们完全不同（TS/Electron vs Python/Qt），**能借的是判断，不是代码**。

## 1. 在线状态由探测结果回写（2026-11-11 记；2026-11-13 已修，方案与他们不同）

> **2026-11-13 结论**：我们最终没有走"属性读成功/失败计数"这条路，而是每 15 秒重读一次
> 设备清单的 `isOnline`，挂在已有的轮询 tick 上（`Client.device_online()`）。原因见下：
> 云端对离线设备照样回 `code=0` + 缓存旧值，"读成功"不能证明在线；`datasource=2` 虽能
> 判离线，但全量一轮 1.17 秒，挂不进 3 秒轮询。下面保留当时的现状描述与他们的做法，
> 供以后换方案时对照。

### 当时的现状（2026-11-11）

`online` 只在**拓扑加载那一刻**从云端设备列表的 `isOnline` 读一次
（`core/api.py:505` → `core/tree.py:94`），此后**再也没有任何地方改它**
（2026-11-11 时 `grep "\.online = "` 全仓库只有构造设备树那一处；2026-11-13 起
`Store.refresh_online()` 也写它）。带来两个后果，方向相反：

- **掉线的设备一直显示在线**：它的属性每轮都被读，云端一直回离线错误码，
  白花请求额度；`counts()` 报的离线数（顶栏在用）也跟着错。
- **启动时就离线的设备永远回不来**：`Store.poll_refs` 里
  `if not st.online: continue`（`store.py:592`），它从此不被轮询，
  哪怕人已经把设备插上电，界面仍然灰着，只有手动刷新 / 重启能救。

### 他们怎么做（`devices.ts:14-15`、`630-703`）

```ts
const POLL_FAILURES_BEFORE_OFFLINE = 3;   // 轮询 5 秒一轮，约 15 秒
_markOnline(dev)            // 探测成功 → online = true，失败计数清零
_markPollFailure(dev, offline)
  offline === true          // 云端"明确"判离线（3040 / -2 / -704042011 / 文案含离线）→ 立即离线
  否则                       // 超时、会话异常这类不确定的失败 → 累计 3 次才离线
```

三条要一起搬：

1. **成功一条就回在线**，不等整轮。批量读里只要有一台设备的属性
   `code == 0`，这台就活了。
2. **失败分两种**：明确离线（我们已经有释义表：`api.py:143` 的
   `-704042011`、尾部 `11`）一次即判；超时 / 网络 / 未知码要累计。
   他们的注释说得很准："设备真断网几天不会一直显示在线，偶发抖动也不会误判"。
3. **判离线后不再轮询它**——我们本来就这么做，只是缺"什么时候变回在线"。

### 一个必须注意的坑（`devices.ts:685-691`、`788-796`）

> 云端对**离线设备会回放缓存的旧值**（`code=0`），所以"读成功"不等于"在线"；
> 二维码会话的批量结果里 `-704042011` 常与若干 `code=0` 并存，
> **必须先判离线码，否则会因为"存在 code=0"把离线设备当成在线**。

我们现在的 `_record_poll` 是"有一条好的就算这轮成功"（对轮询健康是对的），
如果照这个逻辑推在线状态就会踩同一个坑。**在线判定要按 did 汇总，且离线码优先**。

### 落地建议

判据放 `Client.read`（它本来就是唯一能看到每台设备每个属性 code 的地方），
不在 `Store` 里重新拼：`read` 返回 `ReadValue` 已有 `code`，按 `ref.did` 聚合即可。
`DeviceNode.online` 变成可写，`Store._apply_poll` 收到后只对**变了**的设备
发一次 `on_changed`（现在是"值变了才回调"，别让它把整墙刷一遍）。
验证脚本可以完全离线：假 api 连续返回离线码 / 正常码，断言第 1 次不判、第 3 次判、
第 4 次成功立刻回在线。

## 2. 本机 HTTP 联动接口（→ 待排期，`TODO.md` 第 7 步）

TODO 里这条只写了一行"给其他程序 / 脚本调用"。他们补上了**最难的那一半：
别的程序怎么找到我**（`local-api.ts:1-18`、`659-778`）：

| 做法 | 细节 | 为什么这么做 |
| --- | --- | --- |
| 只监听回环 | `server.listen(0, '127.0.0.1')` | 不触发防火墙规则，外网无从访问 |
| 端口随机 | 交给系统分配 | 固定端口会被别的程序占、被写死在脚本里 |
| 启动令牌 | `crypto.randomBytes(24).toString('hex')`，每次启动换 | 端口猜到了也没用 |
| 发现文件 | `<data>/mote-deck.json` 写 `{host, port, token, pid, appVersion}`，**退出时删掉** | 调用方读文件即知怎么连；进程没了文件也没了 |
| 原子写 | 先写 `.tmp` 再 `rename` | 避免调用方读到写了一半的 JSON |
| 鉴权 | 每个请求 `Authorization: Bearer <token>` | 没有就 401 |

端点就四个，语义很省：`GET /v1/status`（协议版本 + 设备数）、`GET /v1/devices`
（设备 + 可控项清单）、`POST /v1/action`（`{device, op}`，一次动作）、
`POST /v1/say`（`{text}`，一句话）。body 上限 8 KB，错误一律
`{ok:false, error:"中文原因"}` + HTTP 状态码（404 找不到设备 / 409 离线 / 501 不支持）。

对我们的意义：这套模式可以原样照搬设计（协议设计不受版权约束），落到
`core/local_api.py` + `<data>/local-api.json`。而且它顺带解决了一个我们已有的矛盾
——**凭据只在自己手里**：调用方（AutoHotkey、Stream Deck、手机快捷指令、用户脚本）
只调我们的接口，永远碰不到 `auth.json`。设备寻址直接复用 `Store.devices` 的 did，
不需要他们那套 `room:` / `#field` 虚拟 id（我们的多键按键本来就是独立条目）。

另有一处值得抄的小心思：`/v1/devices` 里每台设备带 `controls: [{op,label}]`
——**能做什么由我们自己算出来**，调用方不用懂 MIoT。等价物我们已经有
（`spec.controls` / `catalog`），直接暴露就行。

## 3. 中文一句话 → 设备动作（→ 待排期，ASR 不归我们）

`local-api.ts:368-619` 是一段**纯规则**的中文解析，没有模型、没有分词库，
约 250 行。链条是：

1. `normalizeCommand`：去掉空格与标点（`·` 也去，它是"设备名 · 按键名"的分隔符）；
2. **先找"设备名 + 按键名"的完整匹配**，找不到才当整台设备处理
   （否则"书房双开右键"会先命中"书房双开"，只开左键——这是他们踩过的顺序坑）；
3. `findDevice`：命中多个设备名时**取名字最长的**；没点名就用"灯 / 风扇 / 空调"
   这类类型词，该类型只有一台就用它，多台再看句子里有没有房间名；
4. `findRoomTargets`：句子里有房间名 + "所有 / 全部 / 都"，且凑够两台 → 整屋批量；
5. `matchNumeric`：`亮度 50` / `色温 3600` / `温度 26 度`，数字靠 `numberNear`
   取"关键词后面的第一个数"，找不到再看前面 6 个字——**防止把设备名里的数字当目标值**；
6. `matchOp`：最后才是一张动作词表（`关 / 关掉 / 关灯` → 关机），
   且**只保留这台设备真有的操作**（`controlsFor` 里查过）。

中文数字（`三十五` → 35）自己写了个 40 行的转换器，含 `万` 与 `十/百/千` 的量级处理。

我们的处境比他们好：控制项已经结构化（`spec.controls`、枚举短名、型号 `extra`），
不需要"猜字段名"。但"修好一半"的事得说清：**他们能说会道是因为 ASR 在别人家**
（同作者的 MoteDeck 做离线识别，把文字 POST 进来）。本项目 2026-11-11 放弃
「按住说话」的理由（ASR 是成本主体）**不因这个项目改变**。
可做的形态是"文本入口"而不是"语音入口"：托盘 / 指令条 / 本机接口接受一句话，
声音由 Windows 自带语音输入、手机输入法或第三方工具转成文字。

## 4. 局域网直连：他们的完整实现 = 我们「明确排除」的证据

他们真的做了（`node-mihome` + 登录时抓到的 `ip` / `token`），代码里全是补丁，
每一条都对应一个真实故障：

| 补丁 | 位置 | 说明 |
| --- | --- | --- |
| 只在**同网段**才试局域网 | `devices.ts:660`、`870-873` | 跨网段必然超时，白等 |
| Yeelight 要走传统协议 | `devices.ts:502-506` | 吸顶灯（`yeelink.light.ceiling22`）走 MIoT-spec **读必 2 秒超时、写必 4 秒超时**，表现为"卡且控制不了" |
| BLE 设备不能走 `/home/rpc` | `devices.ts:802-806` | 云端直接回 `bluetooth device does not support sending rpc`，得换 `/miotspec/prop/get` |
| 虚拟子设备必须发父 did | `devices.ts:23` | 发子 did 会被拒绝，**且延迟约 6 秒** |
| Zigbee / BLE 只能云端 | `devices.ts:44-46` | 没有本地入口，恒回退 |

结论**不改**：覆盖率不成立。
但要把措辞改准——我们文档里如果有"拿不到 token"这类说法是不对的：
`api.py:509-510` 早就在读 `localip` / `token`（摄像头取流用），**能拿到，只是不划算**。
这条现在是"有实现可比对的排除"，比当初"估个数"硬。

## 5. 明确不取

- **密码登录链路**（`mijia-login.ts` 里约 700 行）：GUI 图形验证码 + 二次安全验证 +
  验证码刷新 + 会话落盘。小米风控一变就废，而扫码登录（`mijiaAPI` 自带的）已经够用。
  他们保留它是因为要"跨网段也能云端回退"——我们不跨网段取流时用不着。
- **属性名通用映射**（`miot-spec.ts:85-119` 的 `FIELD_ALIASES`）：按 `on` /
  `brightness` / `color-temperature` 这些**属性名**自动绑定字段，号称"型号不写死"。
  但同一份代码里就出现了必须按型号打补丁的地方（Yeelight 三件套、
  `filter-filter-life-level` 这种 miot-spec 去重后加服务名前缀的怪名）。
  这正是本项目 2026-11-09 定下的"**行为按型号、文案按类别**"要躲的坑。
- **虚拟子设备折叠**：`tree.py` 已经做得更深（折叠成"多键开关的按键"，
  而他们只是把父设备藏掉、每个子 did 单独一张卡）。
- **Electron 窗口特性**（小组件模式 / 始终置顶 / 一键发到副屏 / 覆盖全屏）：
  代码不可移植。唯一值得考虑的是"始终置顶"——如果墙面副屏常驻，这个开关有用；
  优先级很低，且 `main_window` 已有几何记忆，加一行 `setWindowFlag` 的成本能接受，
  但**没有证据表明用户需要**，先不做。
- **Mock 数据源**（`MockProvider`，没登录就能跑 UI）：本项目有 `MIHOME_DEV_FAULT`
  故障注入和一批离屏渲染脚本，够用。

## 7. 卡片 body 设计对照：哪些能抄，哪些是布局模型的产物

（2026-11-11 追加。起因：用户看他们的风扇卡，问"多种 body 能不能作为我们适配设备的参考"。）

### 7.1 先分清一件事：他们的高度是内容算出来的，我们的高度是格子定的

- 他们的卡没有固定尺寸：`.card{align-self:start}`（`style.css:482-484`），
  `relayoutSpans()`（`app.ts:1779`）用 `offsetHeight` 反算
  `grid-row-end: span n` 写回去。收折靠 `.card-extra{max-height:800px→0}` 过渡（`style.css:500-516`）。
- 代价全在这三处，而且**只因为高度是内容驱动的才存在**：
  - `equalizeCollapsed()`（`app.ts:1710-1745`）：多列模式下默认态要等高，于是把每张卡
    `cloneNode(true)` 到离屏 `.measure-host`、加 `.measuring` 隐藏可收折区、
    `getBoundingClientRect().height` 量高、取 max、**扣子像素噪声**（`Math.ceil(t-0.01)`）、
    再**吸附到行距整数倍**（`Math.ceil((t+rgap)/rpitch)*rpitch-rgap`，否则瀑布流会多占一行留缝），
    最后逐卡写 `min-height`。
  - `trackSpans(420)`（`app.ts:1753-1770`）：收折动画 420ms 里要用 rAF 每帧重算跨度，
    否则下方卡片会在动画结束那一瞬跳一下。
  - `makeMeasureClone` 要逐条清掉内联的 `minHeight / gridColumn / gridRowEnd / transform / position`，
    注释里明写"绝不触碰活卡片的 display，否则会重置 transition 掐断动画"。
- **结论**：自适应高度的终点是"大家都一样高"（`min-height` 统一到最大值），
  只是把"谁高"从设计期推到了运行时。我们的 `166×168` 单位格 + `span/rows`
  （`ui/theme.py:379-385`、`ui/card_grid.py`）是同一件事的静态版本，省掉上面整段测量代码。
  天花板是"卡片不会随内容长高"——但这正是用户右键选 1×1 / 2×1 / 2×2 那一下在做的事：
  **尺寸档 = 收折/展开的静态替代**，选一次就固定，之后墙不会因为设备状态变化而跳动。

### 7.3 尺寸 = 内容预算，不是放大倍数

我们的内容带尺寸（`PAD=14`、`BODY_TOP=76`，见 `ui/device_card.py:49-57`）：

| 卡片 | 外形 | 内容带 | 能放什么（行高：滑条/开关 36、胶囊 26、间距 4） |
|---|---|---|---|
| 1×1 | 166×168 | 138×78 | 两行 36（36+4+36=76） |
| 2×1 | 340×168 | 312×78 | 同上，多了 174px **宽度**，不是高度 |
| 2×2 | 340×344 | 312×254 | 6 行 36（236）；或 读数 78 + 4 行 36（238） |

**宽度是 2×1 换来的唯一资源**——所以灯的"亮度 + 色温"两条滑条横向拉长才不挤；
竖向永远是两行。据此风扇的内容分配：

- **2×1 = 风速 + 摇头**。两行正好 76。风速若是枚举（1–4 档）走胶囊 26 高，
  26+4+36=66，上下各留 6px，反而更松。
- **2×2 = 六项**：风速 / 模式 / 左右摇头 / 上下摇头 / 定时 / 童锁。`CardBody` 本来就
  "绑不上就跳过"，有什么显示什么，剩下的空间自动居中——**2×2 这一档不需要任何新代码**。
- 想在 2×2 里放 hero（大号风速）：78 + 4 行 = 238，装得下。这是 2×2 才有的奢侈，
  2×1 里 hero 会吃掉整条内容带。**不建议**——hero 和风速滑条说的是同一个数，
  他们那张卡上就重复了一次（hero 的 value 由 `applySpeedReadout` 同时喂给两处）。

### 7.4 两处结构缺口：一处不补，一处改判

1. **一行放两件**（他们的 `ctrl-row` 天生是"标签 + 右侧控件"，`makeSwing` 还在一行里
   塞了 chip + 角度 seg）。我们的 `CardBody` 是"一个槽位一行，竖向堆"（`card_templates.py:521-539`）。
   要补得给 `CardBody` 加一个横向容器 + 让 `slots` 能表达 `("mode","swing_h")` 这种组。
   **先不补**：风扇 2×1 两行就够了，一行两件只在"2×2 还想再塞一项"时才需要，
   而 2×2 有六行余量。
2. **风速随模式换属性**（直吹风走 0–100 连续、自然风走档位，量程和写入目标都跟着
   `mode` 变）。**2026-11-12 改判：能做，之前的"不做"是错的。** 真机证明这台风扇
   *同时*有 `speed-level`(1–100) 和 `fan-level`(4 档) 两个可写属性（见
   [fan-purifier-speed.md](fan-purifier-speed.md)），所以不需要"条件绑定"这种危险
   东西——两个属性都能静态绑上，缺的是"哪一个此刻说了算"。
   正确形态是**一个控件内部换形态**：`CardSpeed` 自己持有滑条与胶囊，按 `mode`
   显示其一、隐藏另一个，对外仍是单槽单行。这样 `CardStyle.slots`、`catalog.build_card`
   的绑定时机、`CardBody` 的布局都不用动（`CardBody` 是 `QVBoxLayout`，
   `setVisible(False)` 本来就会重排居中）。
   **为什么不写成"两个槽位交替显示"**：隐藏一行后剩下那行会被 stretch 重新居中，
   切模式时整行上下跳一次；一个控件内部换形态则位置不动。代价是新控件要自己
   处理两种子控件的信号与 `set_value` 分发——比改布局模型小得多。
   **落地时又改了一次形态（2026-11-12）**：没做 `CardSpeed`，做的是
   `ui/fan_body.py` 的 `FanBody` —— 风扇 2×1 要摆四件事，本来就得分两列，
   于是右下那格自己持有两个控件、按模式点亮一个（`_Cell.pick`）。效果与
   `CardSpeed` 相同（同一格、位置不动、对外仍是单槽），但**不需要**一个新控件去
   分发两种子控件的信号——格子只管显隐，控件各管自己。详见
   `docs/DEVELOPMENT.md`「风扇卡片：两列四格」。

### 7.5 一个真缺口：数值属性一律走步进器

`CardBody._pick()`（`card_templates.py:578-601`）只看 `prop.kind`：enum → 胶囊、
bool → 开关、有 range → **步进器**。步进器的语义是"精确的小整数"（温度 ±1），
所以空调对。但风速若是 1–100 的 range，卡片上会出现「− 45 +」，点二十下才到头——错的。

可选修法（**2026-11-12 已落地**）：给 `catalog.Control` 加一个 `widget` 字段
（`"slider" / "stepper" / "chips" / "toggle"`，空 = 按类型），显式胜过猜量纲。
`fan_level` 在 `SLOTS` 里有四个候选名
（`fan-level` / `fan-speed` / `fan-percent` / `speed-level`），**不同型号落到不同属性、
形状也不同**，所以这件事必须看真机，不能按品类一刀切。

**2026-11-12 补：真机看过了，三种形状都齐了** —— 见
[fan-purifier-speed.md](fan-purifier-speed.md)。风扇是 `speed-level` 1–100（range，
会踩上面这个坑）+ `fan-level` 4 档（enum，按 `mode` 切换）；净化器只有 15 档 enum
（铺胶囊会丢弃多余项，另一种坏）。所以这条从"可选修法"升级成**动手前必做**。

**落地时多出两道保险**（原计划只想到 `widget`）：

- `MAX_CHIPS = 6`：枚举项超过 6 个就不铺胶囊，改步进器。净化器 15 档靠这条——
  `CardChips` 溢出时是"**丢弃多余项**"，312px 上只剩三四个可点，用户看得见点不到。
- `FanBody._fits()`：半张卡（≈130px）铺四个 "1挡" 要 162px，硬铺每个字被截成 "1…"。
  这里**复现** `CardChips._layout` 的两步挤压再判"会不会截字"，放不下同样换步进器。
  判据是"会不会出现省略号"，不是"能不能画出来"。

另外两个绑定层字段是被真机逼出来的，原计划里没写：`Control.kind`
（`swing_h` 的候选名里既有布尔 `horizontal-swing` 又有枚举
`horizontal-swing-included-angle`，不写 kind 就取决于服务顺序）和
`Control.search_all`（连续风速在 `dm-service` 这个自定义服务里，被"内部服务"
过滤挡住，详情页原本根本看不到它）。

## 8. 轮询频率与协议边界（2026-11-12 追加）

（起因：用户问"它也要和小米云轮询吧，频率多少？BLE / ZigBee 怎么对话，用电脑蓝牙吗？"）

### 8.1 频率：**每台设备一条请求，5 秒一轮**，没有前后台之分

- `pollMs = 5000`（`devices.ts:367`，硬编码，没有设置项）。`start()`
  （`devices.ts:526-527`）先立即 `tick()` 一次再挂 `setInterval`。
- `tick()`（`devices.ts:620-627`）对**全部设备** `Promise.all` 并发，每台一条请求；
  `_pollDevice`（`devices.ts:651`）把这台设备的所有 `reads` 拼成一个
  `get_properties` 批量，所以"一条请求 = 一台设备的全部属性"。
- 没有并发上限、没有分批：48 台设备就是 48 条并发请求 / 5 秒。
- **没有前后台降频**：`main.ts` 只在切换 provider 时 `stop()`/`start()`（`main.ts:902-905`），
  窗口收进托盘照旧 5 秒一轮。
- `MockProvider` 的 `3000`（`devices.ts:238`）是假数据源，跟真机无关，别拿它当轮询频率。

### 8.2 请求量：差的不是 5s vs 3s，是"每条请求管几台设备"

| | 他们 | 我们 |
|---|---|---|
| 间隔 | 5 秒（固定） | 3 秒（前台）/ 15 秒（托盘、最小化） |
| 一个请求包含 | **一台设备**的全部属性 | **最多 300 个属性**（≈ 全部在线设备） |
| 每分钟请求数 | **设备数 × 12** | **20 / 4**（与设备数无关） |

按 48 台设备算：他们 576 次/分钟，我们 20 次/分钟。差额不在秒数上，
在"每台设备各问一遍"这个模型上。

**这不是谁更勤快的问题**：他们大部分读走**局域网 miIO**（不走云），只有跨网段的
Wi-Fi 设备和 BLE / ZigBee 子设备才回云端；走云的那部分才是"云频率"。
我们全部走云，所以只能用"一轮一个批量包"来抵。

### 8.3 BLE / ZigBee：**电脑的蓝牙完全没有参与**

- `package.json` 的依赖只有 `@zythum02/mijia-api`、`node-mihome`、`qrcode`——
  **没有** `noble` / `node-ble` 之类的蓝牙栈，全仓库没有扫描或连接外设的代码。
- 文件头自己写清了边界（`devices.ts:44-46`）：
  "Wi-Fi 设备可局域网直连；ZigBee 子设备需经网关、BLE 设备不支持局域网，
  这两类会自动回退到云端。"
- 具体分叉在 `_cloudGet`（`devices.ts:802`）：`did` 形如 `blt.*` 的走
  **`/miotspec/prop/get`**，因为 `/home/rpc` 对蓝牙设备直接回
  "bluetooth device does not support sending rpc"；其余设备走 `/home/rpc/<did>`。
  ZigBee 子设备在云端/网关侧本来就是"父 did + 子 siid"，调用方不用区分。

**所以"距离太远连不上"这件事跟电脑无关**：BLE Mesh 是设备 → 网关（中枢/音箱/
多模网关）→ 云端 → 我们。电脑插不插蓝牙、离设备多远，都不影响；真正有距离约束的是
**设备到网关**那一段，超出就是云端回 `-704042011` 这类离线码，我们也只能显示离线。
这也解释了为什么我们的轮询里 BLE 设备只能走云：本地无路可走。
