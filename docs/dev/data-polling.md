## 在线状态：每 15 秒重读设备清单（2026-11-13）

2026-11-13 之前 `online` 只在拓扑加载那一刻写一次，之后**没有任何地方回写**：设备掉线
仍显示在线、每轮照读白花请求；启动时就离线的设备永远回不来（`poll_refs` 直接跳过它）。
修法是每 15 秒重读一次设备清单，**挂在已有的轮询 tick 上**，不新起定时器：

```
_poll()（3s / 托盘 15s 的 tick）
   └─ 距上次 online 刷新 ≥ ONLINE_MS(15s)?
        └─ Client.device_online()  → /home/home_device_list（每家庭 1 条）
             └─ Store.refresh_online()：只对**真正变了**的 did 写 node.online 并回调
```

- 离线设备随即从 `poll_refs()` 剔除；回线设备下一轮自动重新纳入，不用重启。
- 5 分钟的拓扑重拉本来就会带 `isOnline`，所以它也是一次在线刷新（两条路径都会打清单，
  紧挨着发生时有一次重复读，未做合并）。
- **为什么不用属性读判在线**：实测 `datasource=1` 对离线设备照样回 `code=0` + 缓存旧值
  （离线 144 天的插座也如此），"读成功"不能证明在线；`datasource=2` 才会回
  `-704042011`，但全量 151 条要 1.17 秒（ds=1 的 9 倍），挂不进 3 秒轮询。
- **清单本身的可靠性**（2026-11-13 交叉验证）：清单标离线的 8 台里 6 台用 `ds=2` 确认
  真离线（3/3 回 `-704042011`），手环与 ES5 判不出；清单标在线的 48 台里 `ds=2` 判在线
  36 台、判不出 12 台、**没有一台反证为离线**。
- 刷新失败只打日志、保留旧状态，15 秒后自然重试；它不进属性轮询的健康账本。

## 写入确认：mute 到期后单台读 5 次

写入是**乐观**的：按下开关的瞬间屏幕上就是新值，可那是我们自己写的，不是设备回读的。
设备到底照做了没有，只有回读才知道。2026-11-13 之前这里靠"写后 3 秒把全局轮询压到
0.5 秒"（burst），但实测证明它无效：被写属性有 `DEFAULT_MUTE = 3s` 的静默期，而静默期
从**回包时刻**起算，所以整个 3 秒窗口里该属性根本不会出现在读请求里。改成只盯被写的那台：

```
Store.set_value / set_many → 回包成功 → on_write_done(did, 期望值, mute 秒)
Store.run_action（code=0）  → 回包成功 → on_write_done(did, {}, None)
        └─ MainWindow._start_confirm()
             ├─ 同一台设备：只保留一个序列，重新计时（期望值按 (siid,piid) 合并）
             ├─ 跟踪超过 4 台：丢弃最早的那台
             └─ timer.start(mute×1000 + 200)
                  └─ _confirm_tick → store.confirm_read(did, 卡片属性)
                       ├─ 期望值全部读到 → 停
                       ├─ 没读到 → 0.5 秒后再读，最多 5 次
                       └─ 读失败 → 只打一行日志，不动全局退避账本
```

- **挂在 `Store` 上，不挂在各个 UI 入口**。写入口有卡片、详情页、批量、动作好几处，
  逐处接线一定会漏。Store 只负责在回包成功后说"这台写完了、期望值是什么"，
  等多久、读几次由界面决定（它不该知道确认节奏这个数）。
- **参数**：起点 `mute 到期 + 200ms`；间隔 `500ms`；上限 `5` 次；早停判据 = 这台设备
  **全部**被写属性的回读值都等于写入值（只比被写的 key，不看同批其它属性）。
  **第 5 次改成全量读**（在线设备的卡片属性），顺带覆盖联动改到的其它设备；这一轮
  无论命中与否都收工。
- **为什么从 mute 到期才开始**：`Client.write` 在拿到回包之后才给该属性打静默期，
  静默期内它会被 `Client.read` 直接跳过。实测（强 / 客厅 5 台设备、19 个样本）云端在
  回包后 **P50 0.65s、P90 2.49s、最慢 4.05s** 才出现新值；3 秒 mute + 0.2 秒起读，
  5 次覆盖到约 5.2 秒，把最慢的 4.05 秒也包住。降 mute 会让 28% 的样本读到旧值，
  所以 `DEFAULT_MUTE` 保持 3.0。
- **为什么不再全局提速**：全局提速对"被写属性"无效（被 mute 挡住），只对托盘场景和
  联动副作用有意义，代价却是每次点击多打 6 个**全量**批量包。定向读一次只有 1 台
  设备的卡片属性（通常 1–3 条），失败也不影响轮询。
- **同设备不叠加**：连续写同一台只保留一个序列，`timer.start` 重新计时，期望值按
  `(siid, piid)` 合并（后写覆盖先写）；同时最多跟踪 4 台，超出丢弃最早的那台。
- **动作**（`run_action`）：没有目标值、也没有 mute 条目，所以期望值为空、不早停，
  从回包后 **1.0 秒**起跑满 5 次（1.0 / 1.5 / 2.0 / 2.5 / 3.0 秒）。1.0 秒的依据是
  实测 P50 0.65s、P90 2.49s：等 1 秒能跳过最短的那段滞后，5 次跑到 3 秒覆盖大多数。
- **失败也照样还原**：写回包失败时 `_on_written` 立刻还原乐观值并写 `st.error`，
  界面马上能看到"已还原"；**失败不启动确认**（没有"新值"可等）。
- **没有目标设备的写**（场景、音箱文本指令）：回包后 **1.0 / 2.5 / 4.0 秒**各做一次
  全量读，最多 3 次，**固定跑满、不做早停**（不做"有值变化即停"：签名覆盖全部设备，
  烤箱腔体温度、温湿度、PM2.5、人体存在都在持续上报，"有变化"必然为真，早停会退化成
  1 秒后就结束，2.5 / 4 秒两轮永远不跑）。新指令直接重置这一条序列，不叠加。
  **自动化里的「执行文本指令」动作也走这条**（`Feature.refreshes` → `store.schedule_confirm()`），
  只是它的"回包"现在是**回执到达**而不是 HTTP 返回（那条请求发完就不等了）；唤醒 / 播报 /
  发虚拟事件的 `refreshes` 是 `False`，一条都不排队。
- **与 3 秒 tick 完全解耦**：这些全量读只是一串一次性 job——不改 `_poll_timer` 的间隔、
  不重置它的相位、也不取消它。**距上一轮全量读（tick 或确认读）不足 1 秒就跳过这一次**
  （`FULL_READ_MIN_GAP`），避免和刚跑过的 tick 读同一批。
- **全量读的范围不变**：只读在线设备、`mute` 中的属性照样跳过，沿用 `poll_refs()`。
- **两处都不进健康账本**：定向确认与全量确认失败都不加 `_fail_streak`、也不清零，
  只打一行 `[confirm]` 日志。否则一次确认失败会把全局轮询推进退避，或者把正在退避
  的整体状态误判成"已恢复"。
- **它只活在内存里，不落盘**（2026-11-12 问过：那几秒内崩了，下次启动会不会变成默认？不会。）
  链路上没有任何一处能把它存下来：确认参数全部在内存里，`PollDemandBoard` 每次启动
  都新造一张，`idle_ms=POLL_MS`，需求表初始是**空的**；`set()` 只改内存里的
  `dict[owner]`，整个 `core/poll_demand.py` 里没有一处文件写入；唯一的偏好文件
  `prefs.json` 是固定键白名单（`Prefs.save`），既没有轮询键也没有配置界面能改。
  崩溃 = 进程没了 = 那条需求和那个定时器一起没了，下次启动还是 3 秒 / 托盘 15 秒。
  **要改节奏只能改常量**（频率属于频控风险，不该由"上次运行"决定）。

## 为什么删掉 burst 和 `reraise()`（2026-11-13）

这两样都是 2026-11-12 为"点完尽快看到结果"加的，2026-11-13 实测后删掉。结论变了，
理由留在这里，免得以后有人再往回加。

**burst（写后 3 秒把全局轮询压到 0.5 秒）为什么删**

- 它的 6 轮**全部落在 `DEFAULT_MUTE` 的 3 秒静默期内**，而静默期从**回包时刻**起算：
  被写的那个属性在这段时间里被 `Client.read` 直接跳过，所以 burst 对"确认自己写的
  属性有没有生效"作用为 0——六轮全是空跑。
- 实测（强 / 客厅 5 台设备，n=18 个"距回包"样本）云端要在回包后 **0.26–4.05 秒**
  才出现新值：P50 0.65 秒、P90 2.49 秒、最慢 4.05 秒。3 秒窗口本来也覆盖不全，
  最慢的那批一定漏。
- 它原本还能服务到的两件事——托盘里（15 秒 → 0.5 秒）和联动改到的设备——已由
  新的写入确认序列接管（目标写第 5 次全量读；场景 / 音箱 1 / 2.5 / 4 秒三次全量读），
  而且只读该读的东西，不用把全量轮询提速。

**`reraise()` 为什么被取代**

- 它在 action 回包后 **t≈0** 立刻读一次卡片属性；可实测新值最早也要回包后 **0.26 秒**
  才出现（Mesh 灯），绝大多数设备 0.5–4 秒。这次读几乎必然落在旧值期，读回来的就是
  动作前的状态——用户看到的"刷新了"其实是假的。
- 副作用还有两条：它绕过了 `poll()` 的退避闸门（退避期间也照发），又走
  `_on_polled` 计入健康账本——**单台读成功会把整体的失败 streak 清零**，把"全局正在
  失败"误判成"已恢复"。
- 取代它的是写入确认：动作没有目标值，就在回包后 1.0 秒起读 5 次，读到设备真实状态；
  且不进健康账本。

`scripts/verify_poll_demand.py` 的 `_confirm()` 验两条序列：目标写（mute 3.0 → 3.2s 起点、
mute 2.0 → 2.2s 起点、同设备重算顺延不叠加、4 台上限淘汰最早、动作 1.0s 起点、
第 5 次走全量读）与无目标写（1 / 2.5 / 4 秒时点、固定跑满 3 次、中途有变化也不早停）、
不足 1 秒去重、确认读不进退避账本、不动 `_poll_timer`、`reraise` 已不存在；
`_no_persist()` 证明需求表不落盘。共 69 项。

自动化还要挡住一个诱惑：我们手里只有 HTTP 轮询（云端那套 MQTT 推送的授权已实测可通
（refresh 滚动链），但许可不可用、上下线拿不到，见「数据从哪来」一节），
所以"更灵敏"只能靠加频率，而频率越高越像在刷接口。**局域网订阅也
已经明确排除**（按型号各写一套会话，换台设备就失效，见同节），所以别再指望"以后能到秒内"。
2026-11-10 用户决定：**第一版自动化就用现在的 3 秒 / 15 秒，不做快轮询**，只做对时间不敏感
的事；事件通道（`/miotspec/event/get`）已实测可用但先不接，将来要接也是接事件、不是把属性
轮询压到 1 秒。

开机自启（`--autostart`）默认**直接进托盘、不显示窗口**（`prefs.start_in_tray`），
设置页「常规 → 启动设置」里第二项可以关掉它，关掉后退回"最小化到任务栏"。进不去
托盘（没有托盘、或用户关了这项）也退回最小化——宁可多占一格任务栏，也不要程序在哪
都看不见。这时 `start_in_tray()` 会弹一次"已在后台运行"的气泡，顺手把
`_tray_hint_shown` 置真，免得第一次点关闭又弹一遍。

**常规页的排版**：和其它页一个格式——`_section()` 的分区标题在**卡片外面**
（"启动设置"、"关闭面板时"），卡片里只有行，没有卡内标题、没有标题图标。启动设置两行用
`ToggleSwitch`（和设置页其它页同一个开关）；关闭行为两行是「左名称 + 右圆点」
（`ui/radio_dot.py`，`QButtonGroup` 管互斥）——**不是**整行可点的勾选行，和设置页其它行
保持同一个结构。

**圆点用绿不用蓝**（`theme.select_dot`）。两套强调色分工：`accent`（蓝）= 能点 /
有焦点（链接悬停、输入框焦点、家庭标签激活、下拉框对勾），`TOGGLE_ON`（绿）= 这一项
生效了（开关打开、树里的开关列、状态点、确认按钮）。"关闭面板时"选中的那个圆点是
**结果**，和开关打开是同一件事，所以跟开关走。蓝色 `#3D7EFF` 和绿开关并排时更冷更亮，
反而会把视线从"哪一项开着"引到"哪一项没选"上。浅色主题下 `#4CC38A` 在白卡上只有
2.2:1，圆点没有轨道帮忙、会发虚，压深 8%（`#46B37F`，约 2.6:1）——**只压这一档**，
再深两处绿就会被看成两个色。

> 曾经做在卡内（`CardHeader` + `ui/settings_glyph.py` 画的线条图标），用户看过之后要求
> 改回卡外分区标题。那套代码已删，别再翻回来：`SettingsCard` 现在只接 `pad`/`spacing`，
> 页面上也不该再出现 `CardTitle`。

**关闭 ≠ 退出，是有意的语义切换**：`closeEvent` 里 `event.ignore()` 之后再 `hide()`。
接受关闭事件的话窗口对象会被销毁，而托盘图标还在，点它只会崩在"窗口已删除"上。

**"退出程序"这一项：关窗必须走 `quit_app()`，不能只 `shutdown()` + accept**。托盘挂上时
`quitOnLastWindowClosed` 是 `False`（见下），所以接受关闭事件只会**销毁窗口**——进程和
托盘图标都还在，用户看到的就是"选了退出程序，结果还是缩到托盘"，再去点那个图标又因为
窗口对象已删而毫无反应，只能去任务管理器杀。`quit_app()` 是**唯一**收尾路径：释放会话、
落盘、`tray.remove()`、`app.quit()`。两个入口都指向它——托盘菜单的「退出」，以及
`prefs.close_to_tray` 为假时的关闭按钮。

> 这个 bug 骗过了测试：断言 `_shutdown_done is True` 只证明清理跑过，而当时清理确实
> 跑完了、窗口也没了，只有进程没退。`scripts/verify_tray.py` 现在真跑一次
> `app.exec()`，用看门狗计时器验证"关窗后事件循环自己返回"，另加一条替身 `quit`
> 断言关闭路径**请求了**退出。

几条容易踩的：

- **必须先摘图标再退**。Windows 不会因为进程结束就清掉通知区域那一格，会留一个
  "幽灵"空位，鼠标划过去才消失。
- **`setQuitOnLastWindowClosed(False)`** 只在托盘真的挂上之后设。隐藏最后一个窗口
  不是"关闭"，但默认策略会在没有可见窗口时把事件循环带走——那正好是我们要避免的。
  代价是它同时也关掉了"关最后一个窗口就退出"，所以退出一律显式 `app.quit()`
  （别指望 `closeEvent` 被接受就等于退出）。
- **托盘不可用就老实退回"关窗即退出"**（`tray_available()`：`QSystemTrayIcon.
  isSystemTrayAvailable()` + `MIHOME_NO_TRAY` 开关）。硬撑一个不显示的图标，结果
  是"程序还在跑但没有任何入口"，用户只能去任务管理器杀。远程会话、精简系统、离屏
  测试都会走这一支。
- **收进托盘时释放摄像头会话**：藏起来之后画面完全不可见，继续取流等于白占一个观看位
  （设备侧上限 3 路）和一百多 KB/s。`hide_to_tray()` 里显式调 `_release_camera_sessions`，
  点开窗口再取。
- **注销 / 关机不拦**：那时 Qt 也会来要一次 `close`，`QGuiApplication.isSavingSession()`
  为真就直接真退（同样走 `quit_app`）。收进托盘会让关机卡在我们这一格上（Windows 会
  先等程序退出再强杀）。
- **几何要在 `hide()` 之前存**：`saveGeometry()` 记的是当前状态，隐藏后存下来的位置
  会是隐藏时的那份。
- **气泡只提示一次**：第一次收进托盘弹一句"还在后台运行"，之后不再弹。每次关窗都
  弹是骚扰，但第一次不说，用户真会以为关掉了。开机直接进托盘那次也会弹，并把标记
  置真（`start_in_tray`）。
- **从没显示过的窗口不落盘几何**：`MainWindow._ever_shown` 在 `showEvent` 里置真，
  `_save_settings` 只在它为真时写 `window/geometry`。开机进托盘、随后从托盘菜单退出
  时窗口没显示过，`saveGeometry()` 拿到的是默认尺寸，写下去会把用户调好的大小盖掉。
- **图标是画出来的，不是资源文件**：`tray_icon()` 按 16/20/24/32/48 各画一遍圆角方块 +
  2×2 圆点（首页那张卡片墙）。不能拿一张大图缩——缩下去圆点糊成一团。16/20px 那两个
  尺寸**关掉抗锯齿按整数像素画方块**，否则 2~3 个像素的圆点会被抹成灰边，看着像脏图。
`MIHOME_NO_TRAY=1` 是排障开关：怀疑"托盘里点不开 / 图标不显示"时用它把托盘整个关掉，
程序回到老行为。`scripts/shot*.py`、`--probe-camera` 都自己设了它——那些脚本自己驱动
窗口（建 → 截 → close → 退），让托盘接管 `close` 的话，关闭只会把窗口藏起来，脚本
等的是一个不会结束的事件循环。

验证：`scripts/verify_tray.py`（77 项：74 处 `check()`，其中 3 处在明暗主题循环里各跑
两遍，71 + 3×2 = 77）。离屏平台**没有真的通知区域**，所以把"能不能
用托盘"当参数传进去（`TrayController(available=True)`、`MainWindow(tray_available=True)`），
验的是判断与接线：图标多尺寸与像素、信号（单击/双击打开、右键不打开）、菜单只有两项且是
透明圆角层、关窗藏起来且没走退出清理、关掉偏好后真退出、托盘不可用时照旧退出、退出前摘
图标、轮询降频与回前台补一轮，以及**真跑一次 `app.exec()`** 确认关窗后事件循环会返回
（"进程真的退了"这事只能这么验）。**"图标真的出现在右下角、单击能把窗口叫回来、右键菜单
是圆角无黑角"只能在真机上人工看一次。**

## 轮询健康与异常提醒

**异常以前是"静默"的。** `api.Client._read_batch` 把轮询链路上的异常吞成空结果，到
`Store` 那层只剩一个空 dict，界面照旧显示旧值、用户不知道读不到了；更糟的是
`isinstance(result, Mapping)` 会把整轮失败判成成功，指数退避从来没真正生效，状态栏还会
写"已重新连接"。2026-11-11 把记账挪到**请求层**（只有那里拿得到原始错误码和异常文本），
再让界面按分级策略提示。

**记账（`core/health.py`）**

- 四类失败，对应四种完全不同的处理方式：`network`（连接 / 超时 / DNS / TLS，等一会儿
  多半自己好）、`auth`（token 过期或无效，必须重新扫码）、`server`（限流与其它服务端
  返回码）、`protocol`（JSON 解不开、响应结构不对）。
- `code` 与 `text` **原样保存**，不做二次翻译——错误码是排障第一手材料，翻成中文反而
  对不上米家文档。授权类按 `-10020 / -10030 / -704010000` 识别，限流按错误码后三位
  `992` 识别（格式是 `-70 + HTTP 状态码 + 出错位置 + 错误码`）。
- 记录连续失败次数、最近成功时间、最近错误码与原文、本次故障的起止与累计次数，以及
  `Store` 刚触发的退避区间。worker 线程记失败、主线程记退避与快照，内部用一把
  `RLock` 串起来。
- **不刷屏**：同一错误持续时只写第一行，之后每 5 分钟补一条聚合行；错误类别或错误码
  一变立刻补行；恢复正常写一行"连续失败 N 次后恢复"。正常时不写日志，只每 60 秒刷新
  一次状态快照，保住"最近成功时间"。
- 落盘 `%LOCALAPPDATA%\MiHomePanel\logs\poll_health.log`（人读）与
  `poll_health.last.json`（结构化快照）。下次启动第一件事就是把上次运行结束时到底好不好
  写进日志开头，进程被强杀也有据可查。日志单文件 1 MB，超了轮转成 `.log.1`，只留一代。

**提醒分级（`core/alerts.py`，纯逻辑、不 import Qt）**

- 授权失效、限流 / 服务端拒绝**第一次失败就报**；返回内容无法解析第 2 次；纯网络类
  连续 3 次**或**持续 ≥8 秒才报——拔一下网线、切个 Wi-Fi 不该弹窗。
- **同类只弹一次**，恢复后重置；同类系统通知之间再压 120 秒冷却，且**按类别独立计算**：
  刚弹过网络异常，不该把随后的授权失效一起压掉。
- 这里只决定"要不要显示、显示什么"，怎么显示（顶部横幅 / 系统通知）交给界面层。

**顶部警告条（`ui/alert_bar.py`）**

- **浮层覆盖、不占布局**：父控件是侧栏 + 卡片墙的 `body`，几何由 `_place_alert()` 手算，
  不进任何布局；出现 / 消失时页面内容位置完全不动。只盖卡片区，左边从侧栏右缘算起，
  左右留同样边距；`body` 一 resize 就跟着重新定位，显示时 `raise_()` 到最上层。
- 固定 48px 高，整条自绘：圆角 + 1px 状态色描边 + 状态色低浓度染底，左边状态图标，
  中间「加粗着色标题 · 正文」，右边 24×24 的 ×（命中区比图形大，悬停有圆底）。
- **没有定时器**：这条横幅的存在意义就是"不许自己消失"，收起只有两个来源——用户点 ×，
  或界面层明确 `hide()`。
- **恢复时原地变绿**：同一条浮层改成成功色，文案写"本次连续失败 N 次，持续 X"，同样
  要手动关。点 × 之后这段失败不再重复出现，恢复后解除屏蔽；恢复后再次变坏算新的一段。
- 系统通知是加强通道，不是主通道：本次运行内同类只弹一次；系统通知被用户关掉时程序
  探测不到，所以**横幅必须独立成立**。托盘不可用时没有通知，横幅照常。

**成功判据修正**

- 判据从"返回值是不是 `Mapping`"改为"这一轮是否真的读回来东西"：
  `api.Client` 在 `_record_poll` 里给出 `last_poll_ok`，`Store._apply_poll` 只看它和
  异常。整批属性都被服务端按错误码拒绝（设备集体离线 / 网关掉线）也算失败；没有可读
  属性、或全部是确认不支持的空转算成功。
- 于是 `min(6 × 连续失败次数, 30)` 的退避**真正生效**；轮询间隔本身没变（前台 3 秒 /
  托盘 15 秒），失败计数与退避另记在健康账本里，不改退避算法。

**开发用故障注入（`core/dev_fault.py`）**

- 环境变量 `MIHOME_DEV_FAULT`，取值 `network` / `auth` / `server` / `protocol`，可加
  `:轮数` 指定失败几轮后自愈（如 `auth:3`，用来观察横幅恢复变绿）；`off` 或不设即关闭。
  无法识别的取值只打一行提示并关闭，不会带着半个开关跑。
- 注入点在 `Client._read_batch` 真正发请求的那一行：异常之后走的是和真实故障完全相同的
  `classify_error → PollHealth → AlertPolicy` 链路，没有"直接显示"的捷径。
- 只作用于属性轮询（`source="poll"`）；写入确认的定向 / 全量读、详情页按需读不受影响。
  默认零影响，热路径上只多一次模块变量判断。开启时主窗口标题显示「测试模式」，注入的异常文本带
  「（注入故障）」。
- 单实例挡下时（`app._report_instance_blocked`）不再静默 `return 0`：明确打印"已有一个
  实例在运行，请从托盘菜单选择退出后再重试"，并显示当前环境变量的取值与解析结果——
  否则用注入测故障时极易误判成"注入没生效"。

**验证**：`scripts/verify_poll_health.py`（31 项）覆盖四类分类、原始码保留、不刷屏与
5 分钟聚合、重启可见；`scripts/verify_alerts.py`（99 项）覆盖分级门槛、去重与冷却、
关闭后不再出现、恢复文案、警告条尺寸与关闭信号，以及"整批失败不能算成功"的判据。
两份都离线，不建真实 Client、不发网络请求。
