## 工程约定：参考材料不入库（2026-11-09 起，长期执行）

> 首次公开推送后发现 `docs/reference/mihome-app/` 的截图与 uiautomator dump 里
> 带着真实账号昵称、家庭名（门牌号）、房间真人名、设备清单、局域网 IP 与设备 did，
> 当天已脱敏并重写历史。随后进一步收紧：**这批采集原件不再进仓库**，
> 仓库里只留蒸馏后的规范文档（`docs/reference/*.md`）。

为什么整批不进，而不是「脱敏后继续放」：

- **版权**：截图是米家 App 的界面，属于他人作品。本项目是 GPL 仓库，把商业 App 的
  整屏截图再分发是另一类问题，与「只学思路、不抄码」的致谢口径也不一致
- **隐私是持续的**：截图必然带账号昵称、家庭名、房间真人名、设备清单；脱敏一次
  不代表下次采集时不用再脱，而漏一次就要重写历史。不入库从根上断掉这条路径
- **体积**：41 个文件 2.8 MB，占 `.git`（6.1 MB）九成以上，纯粹是历史包袱
- **本来也没人依赖**：代码只引用 `.md` 里的数值（`ui/theme.py`、`scripts/verify_theme.py`），
  没有一处读图片或 XML

约定：

- [ ] **`docs/reference/` 只提交 `.md`**：提交前跑
      `git ls-files docs/reference | grep -v '\.md$'`，输出必须为空
- [ ] 需要看图 / 量尺寸时**本地采一份**：`python scripts/grab_mihome.py grab <名字>`，
      产物落在 gitignore 覆盖的目录里；量完只把结论写进 `.md`
- [ ] **不接受「先提交、以后再处理」**：`git log` 里留一次就等于永久公开，
      清理要重写历史 + force push，且 GitHub 上旧提交按 SHA 仍能打开（只能找
      Support 清或删库重建）；提交前几分钟的检查比事后便宜得多
- [ ] 万一将来确有必须入库的图片：逐张目视脱敏（弹层截图背景里的文字 uiautomator
      **不 dump**，脚本遮不到，必须手工补遮），文字统一换成 `示例家庭` / `示例-xxx` /
      `示例自动化-NN` / `192.168.1.x` / `100000000x`，配套 `.xml` 换文字但保留 `bounds`
- [ ] 例行检查：`git grep -n -I -E "(192\.168\.|did=|userId|passToken|serviceToken)"`

### 工程约定：清理本地 git 凭据前先确认归属（2026-11-09）

Windows 凭据管理器里可能同时躺着几个客户端的 GitHub 令牌，**名字都带 github，但归属不同**：

- **Git Credential Manager**：目标名固定是 `git:<scheme>://<host>`（如 `git:https://github.com`），
  作用域通常是 `gist, repo, workflow`，等于全部仓库读写
- **GitHub Desktop**：目标名是 `<服务> - <endpoint>/<login>`（keytar 的 `<service>/<account>`
  形式，如 `GitHub - https://api.github.com/<login>`），是它自己的登录状态

2026-11-09 就因为「名字里都含 github」把 Desktop 的那条一起删了，Desktop 当场判定
「credentials can no longer be used」→ 自动登出并清空账号记录，需要重新 Sign in 一次。

- [ ] 删除前先确认归属：`cmdkey /list` 看不出创建者，只能靠命名格式区分
- [ ] 清完用 `git -c credential.interactive=false credential fill` 验证：应当报
      `unable to get password`（= 已无缓存，会重新弹登录）
- [ ] 本地删掉凭据**不会**让令牌在 GitHub 侧失效，要作废得去
      Settings → Applications → Authorized OAuth Apps 手动 Revoke

### 工程约定：文案可以按类别，行为必须按型号（2026-11-09）

适配层里有两类东西，**风险等级不同，允许的粒度也不同**，加条目时先分清：

- **行为**（`extra` / `mode_active`）——写错会让设备拒收命令或状态错乱 →
  **一律按型号**，键是 `DeviceNode.model` 的精确串，不许按品类推广
- **文案**（`TextLayer`）——纯显示，认不出就退回云端原文，没有任何 IO →
  **允许按类别**。这是「设备特判一律按型号」的**唯一例外**，理由写在
  `mihome/core/adapters/categories.py` 顶部，别把这个例外扩大到行为字段上

新增一条文案时按这个顺序问：

- [ ] 跨品类都会遇到？→ `enum_text.ENUM_ALIAS`（全局词表）
- [ ] 只有某个品类有？→ `adapters/categories.py`，键是 URN 的 `category` 段
- [ ] 只有某台型号有？→ `adapters/<厂商>.py` 的 `ModelAdapter.text`
- [ ] **属性名一律用 URN 名**（`wash-mode` / `door-state`），不用云端中文 `comment`：
      后者是给开发者的描述，改一个字键就失效且不报错。导入期会拦带中文的键
- [ ] 品类层优先写带属性名的条目（`("door-state", "已上锁(反锁：0；童锁：1)")`），
      裸词只收该品类独有的词——否则别的品类一旦也有这个词，会继承一个未必对的短名
- [ ] 改完跑 `scripts/verify_enum_text.py`；要看真实规格剩多少没映射跑
      `scripts/probe_enums.py`（它现在按品类给分布，能直接看出该落哪一层）

### 工程约定：删打包产物前先证明"没人要"（2026-11-09）

`build_exe.py` 的 `_TRIM` 会从产物里删文件。删除本身没有编译期保护——删错了不会
在开发机暴露，只在别人的机器上白屏，而且极难远程定位。所以加一条时按这个顺序：

- [ ] 先跑 `scripts/pe_imports.py --who <DLL 名> dist/MiHomePanel/_internal`，
      **输出为空才算"没有任何 PE 静态引用"**；有输出就说明还有上游
- [ ] 是 Qt 插件？插件是运行时 `LoadLibrary` 按名字找的，导入表里看不到"谁要它"，
      必须**插件和它指向的 DLL 成对删**（`Qt6Pdf` 能删是因为 `qpdf.dll` 一起删了）
- [ ] 区分"多余"和"保险"：`opengl32sw.dll`（软件 GL 后备）、`plugins/tls`（将来可能
      用 Qt 直连 https）属于后者，要么给开关（`--keep-sw-opengl`），要么别删
- [ ] 换 PySide6 版本后**重跑一遍清单**：上游合并 / 拆模块是常事，旧结论会过期
- [ ] 改完必须跑一次完整 `build_exe.py`（含自检 + 窗口冒烟），再手动
      `--probe-camera` 真播一次——自检只证明"能解 HEVC"，证明不了"画面上屏"
- [ ] 报体积变化时用**同一口径**：目录大小、文件数、zip 大小三个都报，
      只报一个容易得出"UPX 省了 15 MB"这种误导性结论（zip 后其实只差 1.9 MB）

## 工程约定：长期约定按模块分层（2026-11-13 起，长期执行）

助手侧的"项目长期约定"原来是一份 `MEMORY.md`（本地 `.workbuddy/`，不入库），一路写到
14 KB，**每次会话注入时都被截断**——被截掉的那几节等于不存在。现在按模块拆开：

- `MEMORY.md` 只放**跨模块**的规矩（文档三分、许可与提交、工具链、通用红线）+ **一张索引表**；
- 各模块的硬约定在 `modules/<模块>.md`：camera / ui-shell / cards / adapters / polling /
  mihome-api / automation / packaging。**动到哪块先读哪份**，不读也别忘它存在；
- 新增约定**写进对应模块文档**，不再往 `MEMORY.md` 里塞细节；新模块就新建一份并在索引里加行。

理由：这些约定平时是"一块一块改"的，摄像头那类已经收尾的模块没必要天天占着注入额度。
判断一个模块能不能从"核心"降级到"按需读"，看它是不是**只会被同一批文件用到**。
