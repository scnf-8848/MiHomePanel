## 副标题：没内容就留白（2026-11-18）

卡片副标题共四路来源，按顺序取第一个有结果的：离线 → 错误 → 「不支持控制」→
样式摘要 / `summary_line`（指标）→ 「已开启 / 已关闭」，最后才是"没有开关"这一路。

**最后那一路不许再画占位破折号**。网关、纯只读传感器这类设备既没有开关、指标也凑不出
一句，原来会画一个 `—`，用户读起来像"值还没同步过来"，实际是"这张卡本来就没这一句"。
现在直接返回空串（`draw_text` 对空串早退，那行就是空白，位置照旧不挪）。

判据在 `DeviceCard._subtitle()` 的 `st.power is None` 分支；`verify_card_style.py`
2e 段有用例把"没开关也没指标"和"有开关但值还没到"两种都钉住，别只改其中一种。

## 多键面板：转无线（2026-11-12 落地）

米家里可以把某个按键设成**「转无线」**：那一路继电器**常通**（一般是为了给智能灯一直
供电），物理按键不再切继电器，只发无线事件。面板上如果还能点它，轻则点了没反应
（写一个固件不认的 `on`），重则把给灯供电的那一路断掉。

### 判据：`switch` 服务的 `mode`，**逐路独立**

| 服务 | 属性 | 值 | 含义 |
|---|---|---|---|
| `switch`（左/中/右键各是一个服务） | `mode`(N,**2**) | 0 | 有线：继电器跟着按键 |
| | | 1 | 仅无线：继电器常通，按键不发有线事件 |

三条必须守住的：

1. **只在同一个 `switch` 服务里找 `on` 和 `mode`。** `switch-sensor` 也有个叫 `mode`
   的属性，值列表是「极速单击模式 / 多功能模式」，宽匹配（`spec.find("mode")`）会
   随机命中它，把按键手势模式当成有线无线。见 `catalog._gangs`。
2. **值不写死 1。** 各家文案不同（「无线开关」/「无线模式」/「有线和无线开关」），
   判据是**含「无线」且不含「有线」**，并且**恰好一项命中**才采信；命中两项（歧义）
   或零项（电小酷插座 USB 那个「均衡分配/C1高效模式」）一律当"没有这个能力"。
   认不准就不锁——宁可多点一下，不能把有线键锁死。见 `catalog.wireless_value`。
3. **逐路判，不按设备判。** 实测示例家庭的三开单控只有左键是 1（中键是排气扇、
   右键都有线），领普三键只有中键是。用"这台设备有没有 mode 属性"当判据会错得很离谱。

### 落地

- 模型：`Gang` 多了 `mode` / `wireless_value`，判据是 `Gang.is_wireless(values)`。
  `store._card_props` 把每一路的 `mode` **并入轮询**（同一次请求，每台多 1–3 个属性），
  所以设备侧改了设置界面 3 秒内跟上，不用重开。
- 卡片：那一路画**虚线框 + 右上角无线标记 + 灰字**，不填品类色（填了和"开着能关"的
  键分不清）。点它只吐一句提示、**不发写请求**，光标不变手型；`_hit` 仍然命中它，
  否则点击会落到卡片主体上变成"打开详情"。
- 详情页：行名写成「左键（转无线）」，开关置灰（`ControlRow.set_enabled(locked=True)`）。
  **不要用 `write=False`**：属性本身是可写的，是 `mode` 不让写；把 `write` 定死之后
  "设备侧改回有线"这一行就永远解不开（`verify_gang_wireless` 有这条断言）。
- 统计口径：无线路的继电器恒通是"给灯供电"，不是"这盏灯开着"。`DeviceState.power` /
  `any_on`、房间标题的「N 台开启」都跳过它，`Store.set_power_for_devices` 也不下发它。
- 副标题：有无线时换紧凑写法（`3 路 · 1 开 · 1 无线`、`3 路 · 全关 · 1 无线`）。
  原来的 `3 路 · 1 路开启 · 1 路转无线` 在 138px 宽里会被省略号切成半句（实测 136px
  才勉强放下「全部关闭」那一版）。

### 样式：「隐藏转无线」

右键「卡片样式」里的第二项（`小卡 1×1：隐藏转无线`，id `switch_wired`）：body 只画
**实际控制通断**的那几路，剩下的按键按数量重排——三键里中键转无线就摆成两键布局；
一路都不剩（单开整块转无线）就退回产品图，不再画一块点不动的内容带。

- 可见性判据是**静态能力**：面板上至少一路同时有 `mode` 和认得出的 `wireless_value`。
  不看运行时值——样式菜单不能跟着轮询变，否则设备侧改一次设置，菜单里就凭空多出或
  少掉一项。
- **读按键只有一条入口**：`DeviceCard._gangs()`（`hide_wireless` 为真时过滤）。绘制、
  命中、副标题、点击处理全部走它；别在别处再直接读 `card.gangs`——那会画出一个
  点不到的键，或者算出一个和画面矛盾的"3 路"。
- 副标题按**画出来的路数**统计（`2 路 · 1 路开启`）；剔空时写 `N 路 · 全部转无线`，
  解释这张卡为什么是产品图。
- 点击行为不变：可见的有线键照常写；转无线那几路本来就不写，只是在这个样式下
  干脆不出现。
- 全部有线的面板选它 = 标准卡，没有差别（`verify_switch_wired_style` 有断言）。

### 边界

- 没有 `on` 可写属性的服务不算一路（`_gangs` 的既有条件），所以只带 `mode` 的服务
  不会被误当成按键。
- 插座（`plug`）的 `switch` 服务也可能带同名 `mode`（优智者那只就是 1），但插座走
  电源键布局、不走 `_gangs`，不受影响。
- **未验证**：转无线那一路写 `on` 之后固件到底怎么反应。没有实测，也不打算实测——
  代价可能是断掉常通那一路。这里选择"根本不发"，而不是"发了让设备忽略"。

## 风扇卡片：两列四格（2×1，2026-11-12 落地）

风扇一天里最常碰的是「往哪儿吹」和「吹多大」，模式反而是一次性设置。2×1 的内容带
是 312×78 = 两行 36，竖着只排得下两件事，所以做**两列 × 两行**：

```
┌──────────────────────┬──────────────────────┐
│ 左右扫风      [ 开关 ]│ 模式  [自然风|直吹风] │
│ [30|60|90|120|140]   │       [0 ──●── 100]  │
└──────────────────────┴──────────────────────┘
  扫风角度 60 · 风速 45          ← 副标题（第二行的标签搬到这儿）
```

第二行两格**不画标签**，名字由副标题报（见下面「第二行的标签搬到副标题」）。

### 列有语义，缺项就空着

左列永远是"往哪儿吹"（扫风开关 + 角度），右列是"吹多大"（模式 + 风速）。
`FanBody.CELLS` 就是这个契约：**某台设备缺一项时那一格空着，别的格子不挪位置**
——挪了之后换台设备用户就得重新找一遍。所以格子表按 `(列, 槽位候选)` 写死，
不按"有几项"重新排布。

左右扫风与上下扫风同时存在时**只上左右**：四个格子放不下五个控件，上下扫风留在
详情页。这一条也是"列有语义"的推论，不是随手二选一。

### 品类级 vs 型号级（最容易糊的一处）

| | 在哪 | 回答什么问题 |
|---|---|---|
| 品类级 | `catalog` 的 fan 画像（8 个控件） | 风扇**可能**有哪些功能 |
| 型号级 | `adapters/dmaker.py` 的 `speed_by_mode` | 同一功能有**两套属性**时，此刻谁说了算 |

- **品类级不做型号分支**：有没有上下扫风、有没有模式、风速是档位还是连续量，
  全由规格回答，"绑不上就跳过"。所以不需要维护"哪些风扇有上下扫风"这种名单，
  也不需要按型号前缀收窄——换一台风扇，规格一变，卡片自己跟着变。
- **型号级必须按型号**：`dmaker.fan.p5c` 的规格里 `speed-level`(8.1, 1–100) 与
  `fan-level`(2.2, 4 档) **同时存在、都可写**，`mode=0`（直吹风）认前者、
  `mode=1`（自然风）认后者。规格里看不出这层关系（两个属性没有任何关联标记），
  只能登记成 `speed_by_mode = ("mode", {0: "fan_speed", 1: "fan_level"})`。
  真机数据与三层缺口见 `docs/reference/fan-purifier-speed.md`。
- **样式可用性用 `at_least_one` 而不是 `slots`**：风扇之间的差异太大，`slots`
  会在缺一项的设备上让整条样式从菜单里消失。现在只要求"六项里至少一项绑上"，
  摆什么由规格定（`CardStyle.available()` 里 `slots` 是"全绑"、
  `at_least_one` 是"有其一个"，两个都写时是"且"）。

### 风速格：同格换形态，不换槽位

右下那格同时持有滑条（`fan_speed`，1–100）与 4 档轨道（`fan_level`），按
`speed_slot(mode_value)` 只显示一个。**换的是格子里哪个控件，不是槽位，也不是行的
显隐**——格子高度固定是 `ROW_H`(36)，两个控件各按自己的高度在格内垂直居中
（26 高的轨道 → 上下各留 5）。如果改成"两个槽位交替隐藏"，剩下那行会被 `QVBoxLayout`
的 stretch 重新居中，每切一次模式整行跳一下。

- 规则没登记、或模式值没读到、或固件加了新模式值 → `speed_slot` 返回 `None`，
  退到"**档位优先**、否则连续量"的通用顺序。宁可显示一个可能不生效的控件，
  也不因为一个未知值把风速整块藏起来（藏了就成了"这台设备没有风速"）。
- 判据只来自型号适配，`FanBody` 自己不认识 `mode` 的语义。

### 第二行的标签搬到副标题（2026-11-12）

风扇卡的副标题原来只写「已开启 / 已关闭」，占着一整行的宽度却只说了一个字的信息，
而同一张卡的第二行正缺宽度：五段角度的轨道要跟「角度」两个字分 168px，减去标签
28 + 间距 6 只剩 134，每段 26px，字号掉到 10。用户提的办法是**把这两格的文字搬到
副标题**——副标题本来就要写一句状态，改成写「扫风角度 60 · 风速 45」照样看懂，
第二行两格不再画标签，轨道拿满整列；滑条右侧那个风速数值同理（副标题已经在报它）：

| | 让文字之前 | 让文字之后 |
|---|---|---|
| 角度轨道宽 | 134（5 段 × 26px，10px 字） | **168**（5 段 × 33px，12px 字） |
| 风速滑条 | 控件 100，其中 48 被数值占掉 → 轨道 **67** | 控件 134、轨道 **115**（数值那一格也并进来了） |

拖滑条时那个数值会临时浮回来（`CardSlider.set_show_value` → `paintEvent` 里画成
一个贴在右端的实心小药丸，松手就没）：轨道长短只能说明"大/小"，0–100 的连续量
拖动时还是得有数字。**它是浮层、不参与布局**——一旦为了它去收轨道，按下那一瞬间
轨道会缩短、拇指跟着跳一格，手就断了。

三个部件各管一段，缺一段这个效果就出不来：

| 部件 | 干什么 |
|---|---|
| `CardStyle.summary` | 一句话怎么拼（`card_templates.fan_summary`：角度 + 按模式挑出来的风速槽） |
| `CardStyle.summary_text(state)` | **写不写**（关机不写、没值不写）。判据只有这一个函数 |
| `CardStyle.summary_slots` | 副标题答应替哪些槽位报数 → body 省掉这些格子的标签 |

**判据只能有一个**。`DeviceCard._subtitle`（决定写什么）和 `FanBody._hide_label`
（决定让不让宽度）问的是同一个问题，各写一遍必然漂，所以都走 `summary_text`。

`_hide_label` 三条缺一不可：① 副标题此刻非空；② 这一格显示的槽位在 `summary_slots`
里；③ **这一格确实有值**（副标题只写读到的值，没读到就不提，那标签得留着）。三条
合起来保证"省掉的标签一定在别处看得见"。风速格是双选格，两个候选都在名单里，所以
切模式时标签同样是让出的（真实显示哪个由 `_sync_speed` 决定）。

两个容易踩的点：

- **让不让标签会影响"建哪种控件"**。建控件时按 `col_w − label_w − gap` 决定轨道
  放不放得下五段，而 `_build` 时 `labels_off` 已经知道了，所以那里就按"让出后"的
  宽度算（168）。等建完再改宽度只是缩字，形态不会变。
- **控件不重建、只改布局**。开机/关机之间不重建 body，`_layout` 每帧按
  `_hide_label` 现算标签宽：关机时副标题退回「已关闭」，标签自己回来，宽度让回去。
  不能反过来让关机状态下两格都没有名字。
- **滑条的数值也挂同一个开关**。`_layout` 里 `CardSlider.set_show_value(not hide)`
  ——"副标题正在替这一格报数"既不用画名字、也不用画数字，两个判断合用一个
  `_hide_label`，不要各写一份（写第二份的时候必然忘掉"关机要还原"这条）。
- **`summary_line`（core/catalog）没动**。它仍按 `card.metrics` 拼指标摘要（室温、
  湿度、有人），风扇没有 metrics，所以那条路在这里本来就是空的。"副标题写什么"
  因此有两条来源：样式自己的 `summary` 优先，否则退回 `summary_line`。

### 枚举放不下就换步进器（两道保险，都在控件库里）

净化器的风速是 `air-purifier-favorite` 里的**15 档枚举**。两个上限：

1. `MAX_SEGMENTS = 8`（在 `card_controls.py`，`card_templates` 只是转发）：超过
   8 段就不切轨道，改用 `CardStepper`（枚举在它内部按下标走，对外收发仍是设备值）。
   15 档切出来每段只有 20px，"26-45" 这种文案一个也放不下。
2. `fits_segments()`：段宽按**文字**分配（"140" 比 "30" 宽一半），连最小字号
   (10px) 都排不下就退步进器。判据是"会不会出现省略号"，不是"能不能画出来"。

"放不放得下"必须在**建控件时**回答（决定建哪种控件），而那时 Qt 还没给几何——
所以用尺寸档定死的标称宽 `card_controls.BODY_W = 312`。
**不能用 `self.width()`**：CardBody 刚构造完、挂在父控件上但几何还没定时，宽度是
QWidget 的默认值 100，5 段模式会被判成"放不下"而退成步进器（踩过）。

### 声明层新增的三个字段

卡片要"类型相同、语义不同"的控件，只能由声明方点名，于是 `catalog.Control` 加了：

| 字段 | 作用 | 为什么不能靠猜 |
|---|---|---|
| `widget` | `slider` / `stepper` / `seg` / `chips` / `toggle`，空 = 按类型自动挑 | 1–100 的连续风速和 16–30 的温度都是 range，自动挑都给步进器，前者要点二十下 |
| `kind` | `range` / `enum` / `bool`，空 = 不限 | `swing_h` 的候选名里既有布尔 `horizontal-swing` 又有枚举 `horizontal-swing-included-angle`，没有它绑到哪个取决于服务顺序 |
| `search_all` | 首选服务找不到时翻**所有**服务（含内部服务） | 连续风速在 `dm-service` 这个自定义服务里，而它整体被当成"内部服务"不出现在"更多功能"里 |

两个字符串字段都在 `Control.__post_init__` 里校验（`WIDGET_KINDS` / `PROP_KINDS`），
写错了 import 期就炸——它们都属于"写错了不崩、只会静默变丑"的那类。

### 模式和角度：轨道分段控件（`CardSeg`）

`CardSeg` 是"一条轨道 + 内嵌按钮"（OpenMexia 的 `.seg` 那种）。风扇的**模式**（直吹风 /
自然风）和**角度**（30/60/90/120/140）、空调的**模式**（自动/制冷/除湿/制热/送风）
都用它，而且**单选枚举现在默认就是它**（`make_control` 的按类型分支），不用逐个声明。

和 `CardChips` 的三处实际差别：

| | `CardChips`（独立胶囊） | `CardSeg`（轨道分段） |
|---|---|---|
| 选中态 | 卡片底色再混 24% 品类色 | **实心品类色 + 反色字** |
| 宽度 | 按文字各给一块 + 内边距 | 按文字给最小宽度，余量均分 |
| 溢出 | 压内边距 → 截字 → **丢弃多余项** | 降字号（12/11/10）→ 还不行就换步进器 |

**选中态换成实心是修一个真 bug**：卡片开启时底色已经染过同一个品类色
（`theme.tint`，10%），激活态若也只混 24%，在 26px 的高度上几乎看不出差别。
2026-11-12 用户报"风扇正处于直吹风，但模式里没有激活的高亮态"，量下来是
`#2B424A` vs 背景 `#222C33`——只差 18 点亮度。换成实心 `#5FB6C9` 之后差 136。
`verify_fan_card.py` 有像素断言（选中段填充色 == 品类色、与底色亮度差 ≥ 60）。

**为什么角度不搞等宽**：5 段在 134px 里等宽 = 每段 20px，装不下 "140"（三个数字）。
按文字分配后 10px 字号刚好排满，短的那几段略宽一点，看着仍是等分的轨道。

**列宽因此从 138/164 改成 168/134**：左列（扫风开关 + 角度 5 段）比右列（模式 2 段 +
风速滑条）更吃宽度。改 `COL_RATIO` 之前先跑 `verify_fan_card.py`，它有几何断言。

### 开关为什么贴着文字（`label=""` 时开关靠左）

风扇卡左上那格是「左右扫风 + 开关」。`FanBody` 把标签画在格子的左边，控件拿走剩下的
宽度（左列 168 − 标签 52 − 间隙 6 = 110）。开关原本按"有标签"的规则靠右摆，于是它
贴到了格子右端——离右列的「模式」只有 44px，看着像"开关属于模式那一格"。

修法不是加参数，而是让 `CardToggle` 认一件事：**`label=""` 意味着标签由外面的格子画**，
那它在控件左边紧挨着，开关就该从 0 开始摆（`_switch_x()`）。有标签时仍靠右（文字左、
开关右），那是卡里其它开关行的形状。

### 详情页：两行速度，按模式只留一行

详情页把两个属性都当普通行建出来，`_sync_speed_rows()` 按当前模式只显示一行
（`ControlRow.setVisible`，不是重建）。规则仍来自 `speed_by_mode`；`speed_by_mode`
为空的设备两行都留着——宁可多一行，也别把用户真能用的属性藏掉。模式值读不到
（刚打开、刚切、离线）时也两行都留，等值到了再收。

顺带修掉一个老问题：`speed-level` 原本根本没绑上，因为它在 `dm-service` 里，
被详情页的"更多功能"服务过滤挡住了——这就是 `search_all` 存在的理由。

### 详情页也用轨道（枚举行）

`ControlRow` 的 `select` 行以前是 `Combo`（下拉框）。现在**优先 `CardSeg`**，
判据是「段数 ≤ `MAX_SEGMENTS`（8）且 `sizeHint()` 不超过 `SEG_MAX_W`（238）」，
超了退回下拉。理由与卡片一致：同一个属性在两个界面上是两种控件，用户得记两套。

三个实现细节：

- **宽度要钉死**。`CardControl` 的 size policy 是 `Expanding`，交给布局分配会被左侧
  属性名挤窄（实测 254 → 159，段里的字立刻开始截）。所以 `setFixedWidth(sizeHint())`，
  让左边的 `ElidedLabel` 去省略——那是它本来就该干的事。
- **不试更小的字号**。卡片和详情页的轨道必须同字号，为了塞下而在详情页缩到 10px
  只会显得没做完；放不下就换下拉，下拉能把二十项列清楚。
- **`set_no_selection` 在轨道上是"一段都不点亮 + 挂 tooltip"**。轨道没有能放一行小字
  的地方，而下拉框靠 placeholder 表示"值不属于这个枚举"（`无` / `其他`，见「『无』
  不是一个枚举项」）。轨道上宁可空着也不保留上一次的选中——那会显示一个设备现在
  其实不在的状态。刚点完那几百毫秒由 `_mode_pending` 挡住，不会闪。

### 边界

- **2×2（六行）没做**。内容分配想过（风速 / 模式 / 左右 / 上下 / 定时 / 童锁），
  `CardBody` 本来就"绑不上就跳过"，技术上不需要新代码；没做的原因是没有一台设备
  同时有六项值得摆上卡，先不上。真要加时照 `FAN_CONTROLS` 再登记一条 `span=2,
  rows=2` 即可。
- **浴霸未测**（在共享家庭，按测试纪律不碰），它的"风速"是枚举还是 range 未知；
  两条路径都不崩，只是可能选错控件类型。
- 风扇卡片**不显示温度/湿度**：那是传感器的事，混进"吹多大"这一列会打乱列语义。

## 卡片控件库：一处决定"这块画什么"

卡片内容带里有两种布局、五种控件。**布局是形态，控件是零件**，两件事必须分开：

| | 谁负责 | 现在有几个 |
|---|---|---|
| 零件（滑条 / 步进器 / 分段轨道 / 胶囊 / 开关） | `ui/card_controls.py` + `make_control()` | 5 种，**选型只有这一份** |
| 形态（竖排一行一件 / 两列四格 / 视频 / 左图右按钮） | `CardBody` / `FanBody` / `CameraCard` / `GeekCard` | 4 种 |

以前选型写了两遍：`CardBody._pick` 一遍、`FanBody._make` 一遍。两份已经开始漂
（一处改了枚举上限、另一处没动），加第三个品类就得再抄第三遍。现在两个 body 都只调
`make_control(ctl, palette, accent, avail=…, label=…)`：

```
CardBody._pick   ─┐
                  ├─→ make_control ─→ 声明 widget 优先 → 按属性形状（bool/enum/range）
FanBody._make    ─┘                    │                    │
                                       │                    ├─ bool  → CardToggle
                                       │                    ├─ enum  → CardSeg｜CardStepper
                                       │                    └─ range → CardStepper｜CardSlider
                                       └─ 放不下 / 形状不符 → 退回按类型（不返回 None）
```

**加一个新品类时**：在 `catalog` 里写 `slots` + `widget`，body 用现成的；不需要写控件，
也不需要在两处同步阈值。**加一个新控件时**：只在 `card_controls.py` 里加类，然后在
`make_control` 的一张表里挂一行，`WIDGET_KINDS` 跟着加一个字符串。

四条约定：

1. **声明优先，但声明失败不许让控件消失**。`widget="chips"` 放不下就退回按类型挑
   （→ 步进器），而不是返回 `None`。整格不见了比换一种控件糟得多。
2. **`avail` 由调用方给**。选型要用宽度（决定轨道还是步进器），但布局才知道宽度，
   所以 body 传进来；body 自己用的是尺寸档定死的 `BODY_W = 312` / 列宽，
   **不是 `self.width()`**（构造期那是 100）。
3. **布局不许塞进控件库**。`FanBody` 的"两列四格、缺项空着"是形态，不是零件；
   往 `make_control` 里塞布局参数就会长成 OpenMexia 那种"内容决定高度"的模型。
4. **接线只有 body 那一处，控件不知道 siid/piid**。控件只发"用户把它改成了这个值"
   （`committed` 一个参数），`siid/piid` 由 body 补：
   `widget.committed.connect(lambda value, p=prop: self.value_committed.emit(p.siid, p.piid, value))`。
   2026-11-12 用户报"点风扇卡的模式，UI 切到自然风了、风扇不转，详情页同一个模式正常"：
   `FanBody` 建完控件只塞进 `self.controls`，**没接 `committed`**——而 `CardSeg` 在
   `mousePressEvent` 里先改自己的 `_current` 再 emit，所以视觉确实变了，看起来像
   "生效了"，实际一条写请求都没发出去（开关、滑条同样）。
   **验证要从 body 的信号口断言**：`verify_fan_card.py` 第 8 组点完轨道/开关/滑条，
   断言 `body.value_committed` 发出 `(siid, piid, value)`；最后一发把接线摘掉再点一次，
   确认"没有它就不发"。前面第 6/7 组直接连 `widget.committed` 测的是零件、绕过了
   这一层，所以它们全绿也没抓到——**零件能单测 ≠ 接好了**。

`CardChips`（独立胶囊）现在**没有声明方在用**，留着是因为"标签感"场景（非互斥、
带图标）将来可能需要；真要用先修它的溢出策略（它现在会**丢弃多余项**）。

### 控件矩形内的鼠标事件归控件（两道闸）

2026-11-12 用户报："点 body 里的控件，结果打开了详情页，操控不了。"

根因不在控件画错了，在**事件冒泡**：`DeviceCard.mouseReleaseEvent` 的判断是"按下、
松开都在卡片内就 `clicked.emit`"（打开详情页），而 Qt 会把**没被 accept 的 press
沿父链传上去**。控件里任何一个"没命中就 `return`"的早退——点轨道两段之间的缝、
点开关的标签、禁用态——都会让松手冒泡到卡片，于是值没写出去、详情页开了。

两道闸，缺一不可：

1. **`CardControl.mousePressEvent` / `mouseReleaseEvent` 把左键一律 accept**。
   边界是"控件矩形内的事归控件"：滑条的整行、轨道的整条、开关的整行都是它的地盘；
   点空白处不改变值，但也不该被解释成"点了一下卡片"。子类里那些早退
   （`_hit` 没命中、`isEnabled()` 为假）要走 `super()`，不能直接 `return`。
2. **`DeviceCard._control_at(pos)` 兜底**：`childAt` 拿到最深的子控件后沿父链找
   `CardControl`（`ToggleSwitch` 是 `CardToggle` 的子控件，直接判类型会漏），
   找到就把这次点击算作控件消费掉。防的是"新控件忘了 override"这类遗漏——
   操控失灵比点了没反应严重得多。

`scripts/verify_card_click.py` 用 `QTest.mouseClick(card, pos=…)` 走真实 hit-test
（直接发给控件就绕过了冒泡，那正是 bug 所在的环节），并且在最后一节**把两道闸都
拆掉**，确认"确实会误开详情页"——不然这个脚本只是个永远绿的摆设。

## 中枢网关：极客版入口（2×1 / 1×1 两种卡，2026-11-11 落地，11-16 加小卡并并入外壳）

极客版是中枢网关自带的局域网后台（浏览器打开 `http://<网关 IP>/`），登录密码是
**6 位一次性码**。码不是网关本地生成的，而是米家云端两条 RPC 返回的——App 里
「中枢网关 → 自动化极客版」那几层菜单，本质只是替用户发这条请求。调研与实测见
`docs/reference/mijia-geek-login-code.md`。

* **入口就是卡片本身**：两个样式共用同一个 body——
  `gateway_geek`（菜单里「宽卡 2×1：极客版入口」）左半产品图、右半 `GeekButton`；
  `gateway_geek_small`（「小卡 1×1：极客版入口」）不画产品图、按钮铺满整条内容带。
  两者**并存**，**小卡是网关品类的默认样式**（`catalog.PROFILES["gateway"]` 的
  `default_style`，2026-11-16 用户定）；宽卡和产品图（`standard`）在右键菜单里随时能选。
  **默认也要过能力判据**：既没有登记白名单、也没探通的网关，`default_style()`
  都会退回标准产品图；探测结论落盘后由 `wall._on_geek_ability` 重解析成小卡
  （登记过白名单的型号建卡时就是小卡，不走这条）。
* **1×1 不是另写一张卡，是同一套代码的窄落点**（2026-11-16 加）。`DeviceCard._geek_wide()`
  一处判据（内容带 `>= GEEK_SPLIT_MIN_W = 300`）同时管三件事：按钮几何、要不要画产品图、
  按钮用长文案还是短文案。1×1 的 body 只有 138 宽，左右分栏会把产品图压成 63 的竖条，
  所以整条让给按钮；文案也得缩——宽卡那句「重新获取并打开极客版」十个汉字约 120px，
  加上左右各 8 的内边距正好卡在 138 上限，`elidedText` 会悄悄吃掉最后一个字，窄卡
  因此换成「重新获取」（`GeekButton.set_compact`）。
* **按钮是内容带的一种 body，不是另一种卡片类**（2026-11-16 合并，踩过事故才改的）。
  11-11 曾单独派生 `GeekCard`（`DeviceCard` 多一条支路的超集），而墙上非摄像头一律用它
  （卡片类不能随样式重建），于是"极客窄卡不分栏"这条判据被无条件用在标准卡上：所有
  1×1 标准卡的产品图落点变成空矩形，**整面墙的产品图一起消失**，而 `_draws_art()` 仍返回
  `True`、连"没图时的淡圆占位"都不会画（`scaled(0,0)` 返回空 pixmap 而不是 `None`）。
  并进 `DeviceCard` 之后，判据只剩 `self._style.body == BODY_GEEK` 一个来源，
  `_art_rect()` / `_draws_art()` 都是"先问样式、再问宽不宽"，没有第二个类可能漏判。
  回归在 `verify_card_style.py`「产品图落点 = 整条内容带（DeviceCard 外壳）」
  与 `verify_geek.py`「小卡切回标准：产品图落点回到整条内容带」。
* **小卡不挡开详情**（用户 2026-11-16 实测）：按钮虽然铺满内容带，但按钮以外的区域
  （卡片四周 14px 内边距、标题带）仍然响应卡片自己的点击，照样能开详情页，
  操作不受影响——所以不需要为了"留一块空白可点"而牺牲按钮面积。
* **加第三种尺寸时**：`card_templates.GEEK_STYLES` 是"哪些样式属于极客版入口"的唯一
  集合，`wall._on_geek_ability` 按它判断"探测出结论后要不要重解析这张卡"。漏加这一项，
  偏好里存着新样式的卡片会一直停在标准卡上不回来（能力是异步探测的，卡片类不重建）。
* **哪些设备有极客版：型号白名单为主，探测只兜底**（2026-11-16 改判据）。判据是
  `CardStyle.ability = ABILITY_GEEK`，实现见 `core/geek.py:supports`：先查 `adapters`
  台账里的 `geek=True`（命中就**零请求**直接给入口，开机第一帧就是小卡）；没登记的
  型号才退到探测结论，而且**只探 gateway / router / screen / central-control 四类**。
  为什么不再全量探：这项能力**不在 MIoT 规格里**（中枢网关的 spec 只有网络 / 指示灯 /
  虚拟事件），只能由人确认；原来改成"每台发一条 `get_autowebconfig_url` 去问"，
  实测 43 条请求只换来 1 台设备显示入口、38 个型号判否且 7 天后重探——拿几十条请求
  去赌一个本该写死的型号事实。漏登记仍有救：探测会在中枢类设备上捡到它，而
  `scripts/list_adapters.py` 能回答"哪些型号登记过"。**新中枢设备没看到入口，先往
  台账加一行**，见 `docs/reference/model-adapters.md`。
* **外壳只开了两个小口子**：`DeviceCard._draws_art()`（要不要画产品图）和
  `_art_rect()`（产品图落在哪块矩形），极客版样式把它们收窄到左半。默认实现与
  加这个样式之前完全一致——因为**所有非摄像头卡都是这个类**，钩子里任何一处
  忘记先判 `_style.body` 都会波及其它设备。
* **按钮颜色走主题 `accent`，不抄参考图里的红棕**：参考图只借几何（左图右按钮），
  颜色得服从界面。第一版把 `#B5432C` 写死，结果整面墙里只有这一块红——选中态、
  焦点框、菜单高亮全是 `accent`，突然冒出的外来色只会像别人的控件。现在描边就是
  `pal.accent`（2px），悬停 / 按下分别往 accent 里掺 `BTN_HOVER` 10% / `BTN_PRESS` 20%，
  两套主题都不用另配一份颜色。
* **点一次的动作链**（`ui/wall.py:_on_geek_requested`）：取地址 → 取码 → 写剪贴板 →
  `QDesktopServices.openUrl`。顺序不能反：
  - **先取地址**（`miIO.get_autowebconfig_url`，不耗码）；地址拿不到就早退，
    不会白白烧掉一枚码；
  - 取码失败但地址拿到了，**仍然打开网页**，让用户手输——比什么都不做强；
  - 先写剪贴板再开浏览器：浏览器会抢焦点，剪贴板不受影响，切过去直接 Ctrl+V。
* **一次点击 = 一枚码**（用户实测：取新码会让旧码立即失效）。所以这里
  **没有缓存、没有重试、没有后台预取**，绝不放进轮询或窗口重建路径；往返期间
  按钮置忙且不接受点击，否则连点三下就白烧三枚。
* **连点保护靠"先置忙再发请求"，不靠冷却期**（2026-11-11 定）。`_on_geek_requested`
  第一件事就是 `card.set_busy(True)`，第二件才是 `fetch_geek_passcode`——中间没有
  任何异步步骤，所以双击的第二击必然落在忙态里、被 `_can_click()` 挡掉
  （`verify_geek.py::test_click_guard` 钉住这一点）。
  **不再加 3 秒 CD**：它挡住的只有"结果落定后 3 秒内又点一下"这一种情况，而这恰好是
  **有意重试**——按钮上就写着「重新获取并打开极客版」。真加上就变成"点了没反应"，
  而这一整块 UI 的存在意义就是省掉掏手机；冷却期挡的是唯一的正路。
  换主题/切家庭/整墙重建都不会造出可连点的新按钮，无需额外防抖。
* **离线时点不动**：云端这条 RPC 要转发给设备，网关离线必然失败；按钮跟着外壳
  一起压到 45% 不透明度（子控件不会被父控件的 `QPainter` opacity 带下去，这里
  必须自己压一次，否则离线时按钮反而成了整张卡里最实的一块）。
* **按钮上有三种结果态，不只"忙"一种**（`GeekButton._state`，2026-11-11 加）：
  - `idle`：`打开极客版` / `自动复制登录码`，描边是 `accent`；
  - `done`：`已复制 登录码` + **那串码放大到 18px** + `重新获取并打开极客版`，描边转
    `theme.ACCENT_GREEN`；
  - `failed`：`获取登录码失败` + `重新获取并打开极客版`，描边转 `theme.DANGER`。
  为什么成功态排成三行而不是用户原话的两行：按钮只有 150 宽，`已复制 登录码：123456`
  在 13px 下量出来正好卡在 `avail` 边界上，`elidedText` 会把**最要紧的数字**吃成
  `12…`。拆行之后码能放大一号，反而更醒目（`verify_geek.py` 有一条逐行量字宽的
  回归，专防以后改文案又把它挤出按钮）。失败原因不进按钮——那是居中提示的活，
  按钮只回答"成没成、下一步点什么"。
  **结果态会自己退回去**（`RESULT_MS = 30 秒`，`GeekButton._revert`）：这行字回答的是
  "刚才那一下成没成"，浏览器一关回来看到它还认得，但再久就成了常驻装饰，把按钮本该
  写的动作文案顶掉。计时器是 `QTimer(self)` 子对象——卡片随整墙重建会被 `deleteLater`，
  独立计时器会在那之后才触发、撞上已销毁的按钮。新一轮 `set_busy(True)` 会 `stop()`：
  旧结论已经被「正在取码…」盖住，不该让它在**新结果**上到点。退回常态**不动剪贴板**，
  码还在那儿，用户随时能粘贴。
* **提示条**走 `tooltip.toast_top(..., kind=TOAST_OK / TOAST_FAIL)`：屏幕中央偏上、
  跨程序停留（两条提示路的分工见「小爱音箱的文字指令」里那四条界面约定）。**不要改成
  窗口内浮层**——点完取码浏览器立刻抢焦点，窗口内的提示会随窗口一起被盖住。
* **工作线程**：`Store.fetch_geek_passcode` 走 `worker.submit`，回调
  `(entry, error, url)` 回主线程做剪贴板与浏览器，界面不等网络。
* **验证**：`scripts/verify_geek.py`（静态 117 处 `check()`，实跑 115 项；差值是
  循环重复与互斥分支相抵。用假 api 跑完整分支，不发真实请求）；
  真机探针仍是 `scripts/probe_geek_passcode.py`，它**会消耗一枚码**，别加进自动化脚本集。

### 能力探测：程序问出来的型号白名单

`core/geek.probe()` 只发 `miIO.get_autowebconfig_url`（**不耗码**），拿到 http 地址就算
"这台有极客版"。结论按 `did` 落进 `<data>/geek_ability.json`：

```json
{"version": 1, "devices": {"<did>": {"model": "xiaomi.gateway.hub1", "ok": true, "at": 1762800000}}}
```

* **什么时候探**：`Store.scan_geek_abilities()`，在 `on_loaded` 之后（界面先铺出来）。
  每次启动最多派 `GEEK_SCAN_LIMIT = 20` 台，`geek.candidates()` 把 `gateway` /
  `router` / `screen` 排最前——设备多的家里头一批就命中中枢，不用等整轮扫完。
  每台设备**一辈子只探一次**，成本是"每台一次请求、结论永久落盘"。
* **跳过谁**：共享家庭整户跳过（那是另一户人家，不替他们发请求，见历史快照里的测试
  纪律）；离线设备跳过（云端要转发给设备，不在线只会拿到超时）；已知结论的跳过。
* **否定结论会过期**：`NEGATIVE_TTL = 7 天`。探测失败可能是当时云端抽风或设备没应答，
  把一次失败当永久结论会让用户永远看不到入口。`ok=true` 不带时效，型号变了才重探。
* **型号级复用**：同型号只要有一台探通，新来的那台直接算支持（`confirmed_models()`）
  ——换设备 / 新配对时省一轮请求。**否定结论不做型号推广**：同一型号另一台可能就在。
* **探测自己抛错**（工作线程层面）**不落盘**：当没探过，下次启动再来。
* **卡片类是固定的**：非摄像头一律 `GeekCard`（只是 `DeviceCard` 多一条"右半放大按钮"
  的支路，没有该样式时行为完全一致）。不能按能力挑类——能力是运行时才有的，而
  `apply_card_style` 只 `set_style` 不重建卡片，探出结果后再换类就得重造整面墙。
* 缓存丢了（删文件 / 换机）最多是"入口暂时不显示 + 下次启动重探一次"，不影响已取到的码。

### 样式什么时候判定（**不要挂到轮询上**）

`CardStyle.available()` 会被问三处，全是"用户或结构动了"的时刻：

1. `WallView.build()` —— 每张卡一次 `resolve_card_style()`。触发者是 `set_home()`
   （首次加载、切家庭、排序/隐藏变化）和 `rebuild_palette()`（切主题）。
   **"首次加载"是每次启动程序的首次**：`_on_loaded` 里 `first = not self.wall._cards`，
   进程刚起来时卡片字典是空的，所以每次打开程序都会把全部样式重判一遍，
   设备能力（固件升级后多了 `color_temp` 之类）不会躺着过期。
2. `WallView.apply_card_style(did)` —— 只刷一张。调用方是右键选样式，以及
   `_on_geek_ability`（探测结论落定后，且**只有偏好里已经存着 `gateway_geek`** 时才刷）。
3. `available_styles(card)` —— 右键展开「卡片样式」子菜单时算一次，纯 UI，不缓存。

**轮询一次都不碰**：`store.poll()` → `_changed(dids)`（值没变连回调都没有）→
`wall.update_cards()` → `card.refresh()`，里面只有 `_apply_geometry()` +
`_body.sync(state)` + `update()`。不进轮询不是性能问题（判一次是纯内存：prefs 字典
查询 + `geek._records()` 的内存缓存 + 槽位字典查找，微秒级），而是**语义**：亮度变了
样式不该变，判了也白判，还会让 `set_style` 每轮撞上"同一个样式"的早退分支。

代价是这个空档：**能力在运行中变了没有重判通道**，要等下一次整墙重建才追上。
典型场景是同一 `did` 重新配对换了型号、或者固件升级后属性变多——`resolve_card_style`
本来能正确回退/升级，但没人去问它。补法不需要新请求：`store` 有"spec 对象没换就复用"
的现成判据（`_text_specs`），在 `update_cards()` 里记住每张卡上次用的 `st.card` 对象
身份，`is not` 变了才调一次 `apply_card_style(did)` 即可（一次引用比较）。目前**未实现，
2026-11-11 用户决定不做**——每次启动都会整墙重判，日常够用；真要做先想清楚"卡片正在
被拖动 / 滑条正在被拖"时重解析的时序。

## 枚举文案层：云端原话 → 界面短名

**先分清两个方向。** 上一节和本节共用一张型号表和同一个 `ModelAdapter`，但改的不是
一回事，消费路径也是分开的：

| | 行为适配 | 文案适配 |
|---|---|---|
| 字段 | `extra` / `mode_active` | `text`（`TextLayer`） |
| 改什么 | 多读哪个属性、拿什么当状态判据 | 只改显示出来的文字 |
| 谁读它 | `catalog.build_card()` → `CardSpec` | `enum_text._lexicon()` → 短名 |
| 粒度 | **只能按型号** | 型号 / 类别 / 全局三层 |
| 写错的后果 | 设备拒收命令、状态错乱 | 某个选项显示不准，原文还在 tooltip |
| 失效方式 | 属性找不到就退回默认行为（不报错） | 查不到就退回云端原文（不报错） |

挂灯那条 `mode`(2,5) → `scene-mode`(3,9) 属于**行为适配**：它换的是"哪个属性说了算"
（判据），写入仍然写 `mode`，跟文字没有任何关系。文案适配**从不**改变哪个值会被写出去——
写请求用的始终是云端给的整数 `value`。所以两条路互不影响，一条型号记录里可以只写其中
一条，也可以两条都写。

米家规格里 `value-list[].comment` 是**给开发者看的**，不是给人看的。实测 49 份规格、
1850 个枚举项，原文长这样：

| 原文 | 问题 |
|---|---|
| `Quick Single Click`、`Frequent Wrong Password`、`Ac Mode With Outlet` | 英文 |
| `空场景（灯不在任何情况模式时，上报该属性值）` | 22 字整句 |
| `大电池耗尽且小电池电量低 (大电池 =0% &小电池<=20%)` | 带条件的告警 |
| `C1 CLEAR`、`Level3`、`Area 5` | 编号 / 拼装 |

而位置上只有：详情页下拉框（最宽 240px、按 10 个字算宽）和读数行右侧一个 `QLabel`。
以前是机械截到 14 个字加省略号，切出来常是"0关闭待机息屏，待…"这种没有意义的片段。

现在是一层独立的映射（`core/enum_text.py` + `core/adapters/`），**三层覆盖 + 规则 + 兜底，
认不出就不猜**：

1. **型号级**（`adapters/<厂商>.py` 的 `ModelAdapter.text`）——只有这台型号独有的词才写这里
2. **类别级**（`adapters/categories.py`）——某个品类独有的词。键是 URN 里的 `category`
   （`lock` / `washer`），不是中文品类名。门锁 `door-state` 那种状态机写法压成
   `已上锁·反锁+童锁` 就在这里
3. **全局词汇**（`ENUM_ALIAS`，256 条）——跨品类通用的：`Quick Single Click → 单击`、
   `大电池电量耗尽… → 大电池耗尽`。这一层不拆散到各品类，拆了必然漂移
4. 规则：`C1 CLEAR → C1 已解除`、`Level3 / Lever9 → 3 档`、`Area 5 → 区域5`、`Room1 → 房间1`
   （`Lever` 是云端把 `Level` 拼错了，两样都认）；位运算前缀 `（1<<4）` 先剥掉再查表
5. 兜底：按逗号/括号切一刀，再不行才截断加省略号——和加这一层之前的行为完全一致

三层每一层内部都是**先查「属性 + 原话」、再查裸词**；但**层与层之间是纯粹的层优先**，
精确度只在层内起作用。也就是说型号层写了个裸词，照样盖住全局的属性级条目——宁可让
"为一台设备专门写的规则"生效，也不让它被一条更通用的词条悄悄压掉。早期把三层摊平成
"属性级一张表 + 裸词一张表"、先查属性级，就出过一个这样的 bug：全局的
`("door-state", "Open") → 已开` 排在型号裸词前面，型号规则静默失效（现已按层保留，
`verify_enum_text` 有回归用例）。

属性名一律用 **URN 名**（`wash-mode` / `door-state`），不用云端中文 `comment`：comment 是给
开发者的描述，米家改一个字键就失效，而且失效时界面只是"突然又变英文了"，不报错。所以
`("wash-mode", "Dry") → 烘干` 对所有厂商的洗衣机都成立，`Dry` 在空调 `mode` 里仍然是
"除湿"——两个属性名不同，不会互相串。

**为什么文案可以按类别，行为不行。** 行为适配（多读属性、换判据）写错会让设备拒收命令，
所以一律按型号；文案是纯显示、认不出就退回原文、没有任何 IO，写错最坏是某台设备上一个
选项显示得不准。这是「设备特判一律按型号」的**唯一例外**，边界写在
`adapters/categories.py` 顶部；类别层优先写带属性名的条目，裸词只收该品类独有的词。

**原文一个字都没丢**：`ValueOption.label` 仍是云端原话，短名放在 `ValueOption.short`，
两者不同时把原文挂到 tooltip 上。写请求用的是 `value`（整数），文案改错也不会写坏设备。

故障码（`C1` / `E2.1` / `PA`）**故意不翻**——那是行业码，用户要拿它报修。品牌名同理
（`NFC` / `HomeKit` / `HDMI1`）。

**型号级要晚一步才能算**：规格缓存的键是 URN，URN 里的型号段是 `yeelink-lamp22`，和设备
节点上报的 `yeelink.light.lamp22` 不是一个东西——把"这台设备"的文案烤进"这个 URN"的缓存，
同 URN 的第二台设备就会串味。所以类别级在 `parse_raw` 里做（URN 自带 category），型号级由
`spec.localize(spec, model)` 在 store 里补，结果按 (URN, 型号) 记住：源规格没换就复用同一
个对象，否则 `prev.spec is not spec` 每次为真，一次拓扑刷新会把所有卡片重建一遍。

维护方式：改完跑 `scripts/verify_enum_text.py`（表自检 + 三层优先级 + 接线，92 项），
需要看真实规格还剩多少没映射时跑 `scripts/probe_enums.py`（离线读规格缓存，按品类给出
剩余英文的分布）。

## 交互约定：滚轮只滚页面

**本程序里鼠标滚轮只用来滚动页面，任何情况下都不改变设备状态或参数。**
这不是某一个控件的补丁，而是新控件也必须遵守的长期约束。

为什么：卡片墙、详情页、设置页都是可滚动页面。鼠标从卡片上划过时，滚轮应该
带用户去看下面的内容；如果它顺手把亮度从 60% 调到 61%，用户往往当场看不出来，
下次开灯才发现不对。滚轮是"浏览"手势，不是"调节"手势。

实现方式（`mihome/ui/wheel_guard.py`）：

- 自定义控件混入 `WheelSafe`，`wheelEvent` 里只做 `event.ignore()`；
  **不要** `event.accept()`，**不要**调 `super()`，否则事件到不了父级滚动区；
- 必须用 Qt 原生控件时，优先用 `SafeSlider` 这类受保护子类，或在子类里覆写
  `wheelEvent`；不要直接 `new` 原生 `QSlider` / `QSpinBox` / `QComboBox`；
- 新增控件先问一句：滚轮停在它上面时，页面还能不能滚？值有没有变？
  两者只要有一个不符合就不算完成。

明确保留滚轮的地方（它们滚的是"看哪儿"，不是"设备状态"）：

| 控件 / 区域 | 滚轮行为 | 理由 |
|---|---|---|
| 首页卡片墙、详情页 `QScrollArea` | 滚动页面 | 约定本身 |
| 设置页排序树（家庭 / 房间 / 场景）、隐藏页的设备 / 场景树 | 滚动列表 | 列表导航，不改任何值 |
| 左侧家庭/页签导航 | 滚动导航列表 | 同上 |
| 下拉框**展开后**的选项列表 | 滚动候选项 | 选项列表本质是列表；未展开时 `Combo` 不吃滚轮 |

目前**没有**为任何"设备参数控件"保留滚轮。如果以后要开例外（例如某个弹出式
温度面板获得焦点后允许滚轮微调），必须先在 issue / TODO 里写明理由并确认，
不能默默加回来。

## 详情页：打开就是真值（不等 600ms）

详情页的行控件过去只在构造完成后由 600ms 的定时器 `_sync()` 填值，于是**第一帧是
控件的出厂态**：滑条停在最左、轨道一段都不亮、开关默认关着，过一会儿才跳成真实值。
用户 2026-11-12 报的就是这个——"程序明明已经知道每台设备的属性，为什么进详情页
还要先空一下"。

改法：`DetailDialog.__init__` 末尾（`_build_advanced()` 之后）立刻调一次 `_sync()`。
两件事值得记住：

- `_sync()` 取的是 **`self.store.devices[did]`**，不是构造参数传进来的那个
  `state`——后者可能已经过期（详情页开着的时候 store 一直在更新同一个 did 的对象），
  顺手 `self.state = st` 换掉。
- **600ms 定时器不能删**：它管的是"打开之后设备状态又变了"、离线提示、
  "数据更新于 N 秒前"这类持续刷新，和"第一帧"是两件事。

`ControlRow.set_value(None)` 本身是安全的（直接 return），所以某属性还没读到时
不会因为首次同步而画出一个假值；「更多功能」那组未读的行仍走 `set_unknown()`。

## 主题体系：24 个背景预设 × 明暗两维（2026-11-15 起）

外观由两个**正交**的维度决定，持久化也只存这两个值（`MainWindow._load_settings` /
`_save_settings`，写在 `QSettings`）：

| 维度 | 决定什么 | 键 / 取值 |
|---|---|---|
| 明暗模式 | **整套骨架 token**：三级文字、描边、阴影浓度、强调色、状态色、`card_hover` | `ui/mode` = `light` / `dark` |
| 背景预设 | 窗口底色（纯色 / 渐变）、卡片色、卡片透明度 | `ui/background/preset` = 预设 id，未知值退回 `mono` |

设置页「外观」把它们合成一块：上面两档明暗分段按钮，下面 4 列 24 个色块——
**纯色 7 个一组、渐变 17 个一组，两组之间由 `SettingsCard` 插一条分隔线**
（`_preset_grid(presets)` 调两次，`top`/`bottom` 是给那条 1px 线让的空隙；线是布局里的
子控件、不带外边距，不留缝会贴着色块）。色块 `_PresetSwatch` 直接取 `Surface` 画，
点即生效。切主题只有 `MainWindow.set_preset` / `set_theme` 两个入口，它们做三件事：
换 `palette_ref` → 调 `_apply_theme()` → `_save_settings()`；别在别处再造第三条路。

### 三层分工（`ui/theme.py`）

- **`Surface`** —— 一种背景形态：`solid` / `gradient` + 两端颜色 + 角度 +
  卡片色 + `card_alpha`。`brush(rect)` 出 `QBrush`（`WindowFrame.background_brush`
  用的就是它），`base()` 出代表色（纯色即自身，渐变取中点）——卡片合成、标题栏、
  离屏截图都从 `base()` 取，别拿第一段颜色当"底色"。
- **`Preset`** —— 一对浅 / 深 `Surface` + id + 标签。`PRESETS` 共 **24** 项，由
  `SOLID_PRESETS`（7）+ `GRADIENT_PRESETS`（17）拼成；设置页也按这两组分两块摆，
  中间插一条分隔线（`SettingsCard` 的 divider）。
  - **纯色 7 档**：`mono` 黑白、`sand` 米黄、`mist` 浅蓝、`sage` 浅绿、`rose` 浅粉、
    `lavender` 浅紫、`slate` 灰蓝。名字一律用**直白的色相词**——用户 2026-11-17：
    「鼠尾草有点过于艺术了，直接叫深绿这样直白一点」。注意名字要跨明暗两档：
    `sage` 的浅色底是 #EBF4E0（极浅黄绿）、深色底是 #172C1B（墨绿），所以叫**浅绿**
    而不是深绿，否则和浅色档打架。旧名对照：暖沙→米黄、雾蓝→浅蓝、鼠尾草→浅绿、
    藕粉→浅粉、薰衣草→浅紫、石板→灰蓝。
  - **渐变 17 档一律用编号命名**（同一天用户定：一部分有名字一部分没有太不统一，
    全都取名又混乱）。理由很具体：具名与编号混排时"晨光 / 夜色 / 极光"和"1 / 2 / 3"
    两套指法互相打架，而这 17 套里本来就有好几对颜色很接近（两套几乎同色的浅蓝、
    "青→紫"和"紫→天蓝"两端同色），名字反而更容易指错。号码 **= 界面显示顺序**，
    由 `GRADIENT_PRESETS` 用 `replace(p, label=str(i + 1))` 统一补齐——**别在构造处
    手写数字**，删一档之后编号要能自动往前收。
  - **显示顺序只看色相**（2026-11-17 用户：「渐变色里，能不能把颜色接近的挨着放」）。
    唯一的事实源是 `_GRADIENT_ORDER`（一张 id 顺序表），`_GRADIENTS` 按它重排后
    再补编号。判据是 `theme.hue_gap()`——两档 5 个色标里**最像的那一对**差多少度；
    不取平均色相，因为 5 个色标在环上是摊开的一段弧，均值只是重心、不代表任何色标
    （3 号与 16 号重心差 117.6°，却各有一个色标落在同一处）。从橙红绕色相环一圈，
    17 号的橙端接回 1 号，**相邻两档 0.1～13.7°**，唯一的大跳在 1↔2 号（橙红 ↔ 青绿）。
    定义处（`_HANDWRITTEN` / `_NUMBERED`，带 CSS 原串和各档角度）**保持原样不动**，
    重排只动 `_GRADIENT_ORDER`——所以"第几号"和"手写还是 CSS 来的"已经不重合了，
    **别拿编号推来源**，看 `id`。
  - **`id` 不跟着编号改**：它是 `settings.json` 里的持久化键，`verify_tree` /
    `verify_dim_click` / `demo_backdrop` 也按 id 取档。改 id 会让用户已选中的预设
    失效、还要连带改一堆脚本。所以 `n1` 在界面上显示 **5**，`id` 仍是 `n1`。
  - 手写 6 套（`ember` / `dawn` / `night` / `aurora` / `dusk` / `steel`）一律 135°、
    **5 个色标**，起点在右上（`stops[0]`）、终点在左下；色标顺序按"左下 → 右上"
    设计再反转写入。11 套 `n1`–`n11` 是 2026-11-17 从网上收来的 CSS
    `linear-gradient`，**每档自己的角度**（见下节「CSS 角度怎么落到 `Surface.angle`」）。
    两组在定义处分开写，界面上按色相混排。
  - `n*` **仍是候选**：删档要同时删 `_NUMBERED` 里那行和 `_GRADIENT_ORDER` 里那条
    （只删一处会在导入时 `raise`，见 `_ALL_GRADIENTS` 下面那个断言），编号自动往前收。
- **`palette_for(preset_id, mode)`** —— 以骨架 `LIGHT` / `DARK` 为底，只替换
  `bg` / `bg_soft` / `border` / `card` / `card_alpha` / `preset` / `surface`。
  `mono` 直接返回骨架**原对象**（不少地方用 `is` 判断"没换过"），所以黑白两档
  的取值、像素都与改造前一致。

### 编号档（`n1`–`n11`）怎么从 CSS 生成（2026-11-17）

设计稿给的是一条**完整渐变**（色相、明度、饱和同时变），而本项目对背景只有一条硬
约束：浅色档明度钉在 L84、深色档钉在 L23→11 的台阶上。所以 `_grade()` 只保留设计稿
的**色相弧 + 饱和度走势**，明度全部重写：

- **色相沿相邻两个设计色的最短弧插值** —— `d = (h2 - h1 + 540) % 360 - 180`。
  直接在 RGB 空间取中点会出灰：第 4 套（`#a8edea` 薄荷 → `#fed6e3` 樱粉）的中点
  在 RGB 里是一坨灰，按弧插值才是设计意图的"青 → 蓝 → 紫 → 粉"。
- **饱和度按调用方给的走势线性插值**（`light_sat` 可给 `(起, 止)` 二元组）。明度被
  钉死之后，层次只能靠饱和度扛——"蓝 → 近白"这类设计稿的意思就落在"饱和的蓝 →
  很淡的灰蓝"上。
- **明度重写**：浅色 5 个色标全是 `_GRADE_LIGHT_L = 84`；深色按
  `_GRADE_DARK_L = (23, 20, 17, 14, 11)` 递减。
- **深色卡片不手写**，按 `blend(blend(dark[0], dark[-1], 0.5), "#FFFFFF", 0.16)` 现算
  ——与手写那 6 档的 `#46426D` / `#44635A` 同一档。

配套的 `_numbered(pid, label, src, angle, light_sat, dark_sat)` 一次算完浅 / 深 / 卡片。

**已知的取舍**：浅色档明度被钉在同一高度后，色相接近的两套稿子会撞脸——第 7 套
（`#accbee` → `#e7f0fd`）和第 8 套（`#6a85b6` → `#bac8e0`）都是 213° 蓝，浅色档
几乎一样；第 9 套饱和度只有 26–34%，浅色档偏灰。这是"统一明度换可读性"的代价，
不是 bug；真要区分，调的是各自的 `light_sat`，别去动 `_GRADE_LIGHT_L`（一压就破
`text_soft` 的下限）。

### CSS 角度怎么落到 `Surface.angle`

CSS 的 0° 指"上"、顺时针；本项目 0° 指"右"、也顺时针。差 90°，所以
**`Xdeg → (X - 90) % 360`**。`to <方位>` 的换算：

| CSS | 本项目 | | CSS | 本项目 |
|---|---|---|---|---|
| `to top` | 270 | | `to right` | 0 |
| `to bottom` | 90 | | `to left` | 180 |
| `to right top` | 315 | | `to left bottom` | 135 |

`-225deg` 等价于 `135deg` → `45`。**换算完还要按需反转色标顺序**：本项目 `stops[0]`
落在角度所指的那一端之外、即"起笔端"，写反了方向就镜像了——`aurora`（原「极光」）那档当年
就写反过一次（见 `PRESETS` 里 `aurora` 上方的注释）。

### 卡片：从「白透 / 黑透」改成「白透 + 每档自带卡色」

改造前卡片只有两支：浅色白色半透明、深色近黑 `#202329` 半透明（黑白档到现在仍是
这样）。深色引入彩色底之后，中性蓝灰卡片会和米黄 / 浅粉打架，所以非黑白预设的
深色卡片改成**从自己的底色派生**：

- 浅色：卡片色一律 `#FFFFFF`，不透明度纯色 `0.80`、渐变 `0.76`（渐变底色本身有明度
  跨度，卡片再白就把整块渐变盖平，所以压到 0.76）。
- 深色：卡片色**不再共用一支近黑**，而是每档从自己底色往白提 12%（米黄
  `#473C30`、浅蓝 `#303E50`、浅粉 `#4B353D`……），不透明度纯色 `0.90`、
  渐变 `0.88`。同色相派生之后，卡片与底色的明度差从 11～14 提到 **16～22**。
- 黑白档 `card_alpha = 1.0`（不透明），保持原样。
- **全部 17 个渐变档统一 0.42 / 0.50**（2026-11-17 用户定稿的 `aurora` 那档风格，编号档
  `_numbered` 里也照抄这两个值）。它们的背景比纯色档有更多色相跨度，0.76/0.88 会把
  背景整块盖平；压到 0.42 之后卡片是"带背景色的玻璃"，文字对比度靠 `text`/`text_soft`
  在合成色上的最差值验。6 个纯色档保持 0.80 / 0.90——它们背景是一块平色，透与不透
  看不出区别，反而会让人怀疑卡片"没画实"。

### 派生值：侧栏与弹窗都从底色走

骨架里那几支是按黑白底定的，换了彩色底必须派生，否则会"描边消失 / 侧栏脱节"：

| token | 深色 | 浅色 |
|---|---|---|
| `bg_soft`（纯色档搜索框、圆形按钮） | 底色往白 3.5% | 底色往白 55% |
| `border`（分隔线、卡片/菜单描边） | **卡片**往文字 9%（要同时压在底色和卡片上） | 底色往文字 5.5% |
| `nav_bg`（纯色档侧栏底） | 底色往白 4.5% | 底色往**黑** 6%（骨架是 6%，比弹窗那档大一档） |
| `surface_bg`（弹窗正文底） | 底色往白 4.5% | 底色往黑 4.5% |
| `rail_bg`（对话框分类栏） | `surface_bg` 再往白 7.5% | `surface_bg` 再往黑 7.5% |
| `panel_bg`（排序页分区容器） | `surface_bg` 往文字 7% | 直接给卡片白 |
| `field_bg` / `field_border`（卡内输入框） | 从 `panel_bg` 再推 | 同 |
| `window_edge`（主窗口 1px 外框） | `bg` 往文字 18% | `bg` 往文字 12% |

不派生会怎样（实测）：深色描边 `#26282E` 压在新底色上只剩 1.01～1.11:1，等于没画；
`bg_soft` 比底色还暗，搜索框和圆形按钮会变成几个黑洞。

### 渐变档专用：`bar_bg` / `nav_*` / `card_field_qss`（2026-11-17）

渐变档的背景是一条会动的彩带，上面压着的每一块"面"都得自己决定怎么透，不能沿用纯色
档那套"从底色推一档"。四组口径：

| 函数 | 作用 | 渐变档的做法 |
|---|---|---|
| `bar_bg(p)` | 标题栏 / 顶栏底板 | `blend(bg, text, 0.10)`，**往文字色混** |
| `nav_fill(p)` | 侧栏卡面 | 直接 `card_fill(pal.card, pal)` |
| `nav_row_fill(p)` / `nav_hover_fill(p)` | 侧栏选中行 / 悬停行 | 卡面上再加档（见下） |
| `nav_line(p)` | 侧栏两条分隔线 | 从卡面推，跟着一起透 |
| `card_field_qss(p)` | 压在背景上的输入框（顶栏搜索框） | `pal.card` + `card_alpha` + 一起透的描边 |

**为什么 `bar_bg` 渐变档反过来往文字色混**：纯色档是 `blend(bg, card, 0.62)`
（浅色 `#F1F2F4` → 白里带灰）。渐变档照抄会把顶栏做成一条偏白的板子，可顶栏上压着
一排白色半透明胶囊（搜索框 / 状态 / 圆形按钮），底板也偏白的话胶囊落差只剩十来个色级
（实测量过：0.42 白底带上再叠 0.42 白，搜索框几乎看不出来）。往下压一档之后胶囊有
20 级以上的落差，顶栏和内容区之间也多出一道看得见的台阶——用户 11-17 要的两件事
（"线不要突兀" + "顶栏自己成一层"）一次解决。

**侧栏三层不透明度**：`card_alpha`（0.42 / 0.50）→ 悬停 `+0.12` → 选中 `+0.26`。
`Surface.nav_opacity` 这个字段 2026-11-17 已经删掉，别再引它。

**搜索框按档分流**（`main_window._apply_theme`）：渐变档走 `card_field_qss`
（卡面，和语音指令条同一支色）；纯色档继续走 `field_qss(base=pal.bg)`。分开的原因
是纯色档顶栏是 `blend(bg, card, 0.62)` 的白里带灰浅板（L≈250），卡面也是白（0.80
不透明），叠上去只剩 5 个色级、边界全靠描边；从 `bg` 推一档的浅灰（L≈230）才有
20 级落差。

### 取色原则（这组数值为什么长这样）

- **浅色靠饱和度，不压明度**：手写色标的那些档（7 纯色 + 6 手写渐变）浅色档把饱和度
  从 30%～45% 抬到 70%～90%，明度基本不动。明度再压一档，`text_soft` 就先跌破改造前
  （实测 `#F7E6C6` 那档 soft 从 4.15 掉到 3.93），所以浅色只能"更浓的粉彩"。
- **深色靠明度 + 色相**：底色抬到 HSL 明度 12%～16%（L\* 12～16），色相才认得出来
  ——原来 `#17130E` 一带只有 7%，肉眼就是黑。代价是正文对比度从 16.5:1 降到
  13.4～14.7:1（仍 ≥ AA 的三倍），次级灰 7.5 → 6.1～6.7。
- 逐档的色相角 / 明度 / 卡片明度差记在 `theme.PRESETS` 上方的注释里；复算口径是
  WCAG 对比度 + `l255 = 255·lum^(1/2.4)` 作明度代理，渐变逐端取最差值。
- **三级文字按"能不能点"分档，不按"重不重要"**：`text` = 当前项（选中行 / 当前页签），
  `text_soft` = **可操作的普通项**（未选中的房间、功能区入口、分隔线下的耗材 /
  挂件 / 设置），
  `text_mute` = 真·次要或不可用（行尾计数、隐藏设备那种收纳箱、占位提示符）。
  侧栏底部这两组曾经用 `text_mute`，读起来像禁用（用户 2026-11-16 反映"接近隐藏设备那一档"），
  现在统一 `text_soft`、悬停提一档到 `text`。**不要再把可点的东西降到 mute**。

### 哪些面跟着背景一起透（2026-11-17）

用户的原话是"各种卡片、语音指令框、快捷指令透明度不够，显示不出背景色""左侧边栏
完全没有渐变，是一块纯色"。问题不在 `card_alpha` 本身，而在**只有卡片一个面用了它**：

| 面 | 该走 | 漏了会怎样 |
|---|---|---|
| 卡片 | `theme.card_fill(bg, pal)`（`device_card` 已在用） | 实心白压在渐变上 |
| 场景条胶囊 | `theme.card_fill(...)`（`scene_bar`） | 一排实心白胶囊 |
| 语音输入框 | `theme.card_fill(fill, pal)`（`speaker_bar`） | 整条实心白，最扎眼 |
| 状态胶囊 / 圆形按钮 | `theme.card_fill(theme.chip_bg(pal), pal)` | 两个实心白圆点 |
| 侧栏 | `theme.nav_fill(pal)`（渐变档 = 卡面） | 一条不透明的竖板，左上角没有渐变 |
| 侧栏选中行 / 功能区选中格 | `theme.nav_row_fill(pal)` / `nav_hover_fill(pal)` | 一块纯白方块 |
| 主窗口标题栏 | `theme.alpha(bar_bg(pal), pal.card_alpha)` | 顶部一条白带，正好压在渐变最亮的一端 |
| 主窗口家庭栏（`HeaderBand`） | 同上，**同一个 alpha** | 与标题栏分档，中间留一条接缝 |

**硬规矩：画"卡片面"一律走 `card_fill`，不要直接 `QColor(pal.card)`。** `pal.card`
是不透明 token（`tint` / `blend` / `field_border` 都拿它算颜色，不能带 alpha），
所以透明度只能在**下笔那一刻**加。

`HeaderBand` 的 alpha 必须跟 `card_alpha` 走（不能给个 0.22 之类的独立值）：它和
`TitleBar` 铺的是**同一支** `bar_bg`，两个 alpha 不一致，标题栏与家庭栏之间就会
显出一道明度台阶。同理，`TitleBar.paintEvent` 尾那条下边线在**主窗口 + 渐变档下
不画**——两岸本来是一条完整的窗框带，中间夹一条"从背景推的单一颜色"只会留下接缝
（`if is_dialog or not pal.surface.is_gradient()` 才画）。

顶栏搜索框（`QLineEdit`）走的是 QSS，加不进 `card_fill`，所以 `field_qss` 多了
`alpha` 参数：底色出 `rgba(...)`（经 `qss_alpha` 反解，QSS 背景会画两遍），**描边
用同一个 alpha 再加 0.22**。描边不能一起全透——0.5 的描边压在渐变上约 1.05:1，
深色下输入框直接看不见；描边全实又会把半透明胶囊重新勾成一张"贴纸"（用户
2026-11-17 的原话：「快捷语音指令框周围一圈描边有点突兀」）。`speaker_bar` 的自绘
胶囊同理。

渐变浅色档为什么不直接用深色那串原色：源串明度只有 12%～50%（`#051937` 最暗），
浅色模式的文字是 `#0E1116`，直接放上去等于黑字压黑底。所以浅色档保留 5 个色标的
**色相弧**，只把明度整体抬到 L84、饱和度给 S88。L84 是 `text_soft` 还能站住的上限：
再压到 L80，黄绿那端 soft 就从 3.04 掉到 2.71（项目基线 4.15、下限 3.83）。

深色档压暗的做法（用户 2026-11-17：「颜色过于鲜艳」）：色相不动，明度按色标从
**右上 23 递减到左下 11**、饱和度 78%。`aurora`（原「极光」）的源串右上 `#A8EB12`（L50）就是那个
"荧光黄绿"，压到 `#4E680D`（L23）之后才沉下来；明度递减而不是全档拉平，是为了
保住渐变的方向感——全拉平会变成一条同样亮的糖果彩虹。手写那 6 档卡面色从中点色往白
提 13% 派生；编号档走 `_grade`（见上节），提 16%。

### 背景抖动：不让渐变长出分界线（2026-11-16，当天返工一次）

渐变的量化台阶在平滑底色上就是**一条肉眼可见的斜线**，不是渐变本身不平滑。实测
旧「夜色」那一档深色 `#142438→#0B1521` 三通道只差 9～23 级，摊在 2380×1575 的斜线（长 2797
物理像素）上，**要 120 物理像素才跳一级**——用户 11-16 截图上那一条条"渐变带"就是它，
沿带方向颜色一模一样，因为那本来就是同一条等色线。

**第一版修法是错的，别再走回去**：叠一层白黑各半、alpha 3 的零均值噪点。它把"同色段"
从 993 px 缩到 12 px，但**均值台阶一级没少**——噪点只改变方差纹理，不动均值；眼睛一低通，
界线照旧。同一条判据下新旧画法的差距：斜带 16 px 窗均值与理想值的最大偏差
**旧 1.98 级 / 新 0.09 级**；顺带旧画法还把整块背景**整体提亮了 1.5 级**（白点比黑点有效）。

现在走**随机取整**（stochastic rounding）：每个像素先加一个 **±0.5 级（8-bit 一级）的
均匀随机偏移**再取整。一个 1 级台阶因此摊成"点密度随位置线性变化"的细点带，低通之后
是一条真正的连续斜坡。实现要点（`chrome._dithered_image` / `_backdrop_pixmap`）：

- 渐变在 135° 下**只依赖 `t = x - y`**（等色线就是斜带），所以色值是**一维**的：
  按 t 预生成 `_DITHER_CLASSES = 16` 套随机偏移的像素串，再**按行切片**拼成整图
  （同一行就是同一条斜带的平移，直接切 `bytes`）。纯 Python 也能 30 ms 出 2380×1575，
  换成逐像素 Python 循环要 10 秒级。
- **任意角度都能切片**（2026-11-17 放开。以前只支持 45°/135° 那一族，因为那时投影
  `t = x ± y` 是整数）。现在按 `abs(dx) >= abs(dy)` 选"行切片 / 列切片"：慢轴每前进
  一格，快轴起点就平移 `slow / fast` 格（< 1 格），取整误差 ≤ 半格 ≈ 0.04 色级。
  横向用 `data[y*stride:(y+1)*stride] = template[off:off+stride]`；竖向因为 `bytearray`
  的扩展切片**一次只搬一个字节**、且要求长度严格相等，必须 4 个通道各来一遍
  `data[start:start+ph*stride:stride] = col[ch::4]`（直接塞一整段会
  `ValueError: attempt to assign bytes of size 1600 to extended slice of size 400`）。
  实测全屏 2380×1575：0° 21 ms、30° 27 ms、135° 50 ms、270° 38 ms。
- **色带下标要减掉像素中心的投影**：`p00 = ((0.5 - cx)*dx + (0.5 - cy)*dy + half) / span`。
  少了这半个对角线，整条色带会整体偏移——45° / 135° 因为对称恰好互相抵消所以看不出来，
  斜角和竖直却是实打实偏色（当年就是这个 bug）。
- 生成一张**物理像素 1:1** 的 `QPixmap` 缓存起来（`_backdrop_cache`，最多留 2 张，
  一张 2380×1575 约 15 MB），之后每帧只是一次 `drawPixmap`（0.07 ms）。
  只在 resize / 换主题 / 切预设时重算；resize 拖动时每个尺寸 30–50 ms，不用加防抖定时器。
- **尺寸用 `ceil` 而不是 `round`**：宁可多出不到 1 个物理像素（被窗口/圆角裁掉），
  也不能少一列，否则右/下边漏出一条底色。
- 圆角靠 `setClipPath(rounded_path(...))` + 抗锯齿，和原来 `fillPath` 的边一样干净。
- **只对 `is_gradient()` 生成**，纯色直接 `fillRect`（纯色没有台阶）。
  `verify_backdrop_dither.py` 用"纯色背景相邻像素必须完全平坦"钉住这条。
  判断"要不要走离屏截图"的入口是 `_backdrop_shot()` 里的 `not surface.is_gradient()`
  ——以前是 `_diagonal_axis(angle) == 0`，那个函数和 `_dither_pixmap` / `_DITHER_TILE`
  / `_DITHER_ALPHA` 一起在 11-17 删掉了，别再引。
- 别删 `_DITHER_CLASSES` 的随机序列：每行换一套序列（`y % 类数`）是为了让相邻行的偏移
  互不相关；全行共用一套时噪点会沿 45° 斜向连成条纹。
- 判据写在 `scripts/verify_backdrop_dither.py`：第 1 节拿 12 种角度（0/30/45/60/90/120/
  135/150/225/270/315/330）× 四角 + 中心，判 ≤ 2 色级；第 3 节按**投影分箱**验 16 px
  窗均值（箱内采样 < 80 像素的跳过——贴角的分箱只有二三十个点，±0.5 级均匀抖动的标准误
  0.29/√n 会盖过台阶判据，几何正确性交给第 1 节），判 ≤ 0.2 级；对照组是
  `render_naive`（理想渐变直接四舍五入），要求它 > 0.35 级（判据不许永真）。
- **肉眼验收**用 `scripts/demo_backdrop.py`（真窗口 1:1，第 1 档是 30° 斜角，空格切
  新旧画法，`1` 是"蓝→红"色差放大 10 倍的特例）。数值判据只能证明"窗均值贴理想值"，
  这种问题最终得人眼看；当年就是靠这个蓝→红特例才确认旧画法的界线、新画法看不出来
  （用户 11-16 认可）。

### 顺手补的坑：frame 被 gc 后 `eventFilter` 要放手

`WindowFrame` 与窗口是**双向引用**（`frame.win` / `window._window_frame`），这对环只能靠
gc 回收。gc 清对象时 `__dict__` 先没了，C++ 那个 QObject 还挂在 window 上，Qt 照样把
事件送进来——`self.win` 于是 `AttributeError`，而 PySide 会把它包成
`SystemError: ... returned NULL without setting an exception`，**报在完全无关的调用栈上**
（2026-11-16 这次报在 `_ensure_edges` 建子控件，看起来像 QWidget 构造失败）。
现在 `eventFilter` 开头 `getattr(self, "win", None)`，拿不到直接返回 False。

**这个隐患本来就在**，只是以前 Paint 事件赶在 gc 之前处理完，没撞上；加了背景抖动后
`_paint_fill` 慢了几毫秒，事件被推到 gc 之后，`verify_window_corners.py` 才稳定复现。

### 不做的事

**卡片磨砂 / 弹窗半透明这条路线已整体废弃**（2026-11-15 用户定：不做，不是排期）：
背景只有纯色 / 渐变，模糊前后最大差 1～3/255，做出来看不见；截图 + 模糊另有结构性
缺陷。研判过程见 [card-frosted-glass.md](../reference/card-frosted-glass.md)。现在的层次靠
"卡片色从底色派生 + 描边"，不要再去接 blur / 半透明蒙版。

## 程序图标：米白底 + 绿显示器（2026-11-17 落地）

**一句话**：任务栏 / Alt-Tab / 资源管理器看到的那枚图标是 `assets/app.ico`，由
`scripts/make_icon.py --ico` 生成。**生成脚本才是源，`.ico` 是产物**——改图标先改
脚本再重导，别拿图像编辑器直接改 ico（7 档尺寸对不上就全白费）。

- 图形：米白圆角底 + 青绿**直角**显示器 + 屏内白房子 = "电脑里的米家"。绿色取自米家
  App 图标采样的 `#18CC8E` 一族，具体取值和"为什么不能再亮"写在脚本的常量注释里。
- **7 档尺寸各自绘制，不是一张大图缩的**：≥48 完整版（屏幕 + 颈 + 底座）、
  24–47 中等版（实心屏 + 放大房子）、<24 极小版（**只留房子 + 颈 + 底座，砍掉屏幕**）。
  16 px 下"屏里嵌对比色房子"必然糊成脏块。`verify_app_icon.py` 钉住这条：
  16/32 档与"256 缩版"必须差 8 级以上，同一几何的 64 档必须差 5 级以内（反向对照，
  证明判据不是永真）。
- **运行时只找不缩**：`mihome/ui/app_icon.py` 只做"找文件 + `QIcon(path)`"。路径三段
  回退（exe 旁边 → `_MEIPASS` → 源码树），照抄 `core/camera.py: search_dirs()` 的惯例；
  少一段就会"开发机正常、打包版一片空白"。
- **打包要两条腿，缺一条就有一半是空白**：`--icon` 写进 exe 的 PE 资源（资源管理器 /
  桌面快捷方式 / 开始菜单），`--add-data` 把 `assets/` 打成数据文件（运行时
  `setWindowIcon` 读它）。只做前者的话，exe 在资源管理器里有图标、任务栏和 Alt-Tab
  却是空白，这种问题极难查。`build_exe.py` 现在两样都默认做，图标默认 `assets/app.ico`。
- `setWindowIcon` 必须在**建窗口之前**调（`app.py: main()`）：晚了任务栏按钮已经用
  默认空白图标注册过，再设也不换。
- **三处必须同一枚图形，别再各画各的**（2026-11-17 统一）：任务栏 / Alt-Tab / 资源管理器
  读 `assets/app.ico`；标题栏左侧那个 20 px 的 logo（`chrome.py: _paint_logo()`）和托盘
  （`tray.py: tray_icon()`）以前各是各的——标题栏画"主色圆角块 + 白房子"，托盘画"圆角块 +
  2×2 圆点"，同一个程序三个样，用户会当成三个程序。现在两处都直接读这枚 ICO：

  - 标题栏用 `icon.pixmap(rect.size(), dpr)` 取图，**不 `scaled()` 大图**——ICO 的 16/24/32
    几何是分开画的，让 QIcon 按物理像素自己挑档才不糊。20 逻辑像素在 175% 缩放下是 35
    物理像素，Qt 挑 48 那档缩下来，细边框还留得住。
  - 托盘图标**不吃调色板**（旧签名收 `Palette`、拿 `accent` 上色，换主题托盘里就变个颜色，
    跟任务栏对不上）。这是一枚品牌标记，不是状态点，`set_palette()` 里不用重设图标。
  - 两处都留了"读不到 ICO 就退回旧画法"的兜底：标题栏空一块、托盘空一块，都比图形不对
    更难排查（托盘空了用户直接找不到程序）。`verify_tray.py` 钉住"托盘像素 == app.ico"、
    "签名不吃调色板"和兜底那条。
  - **已经跑着的实例不会自己换**：托盘图标在进程启动时注册，改完代码要退出托盘再重开才
    看得到新的。真机上验图标永远先重启。

## 系统托盘：`show()` 调过 ≠ 图标挂上了（2026-11-21 修）

**一句话**：`QSystemTrayIcon.show()` 是 void，内部那句 `Shell_NotifyIcon(NIM_ADD)`
失败时既不抛异常、也没有任何返回值。所以"图标到底挂上没"只能**反过来问系统**
（`Shell_NotifyIconGetRect`）。`tray.install()` 现在每次都问，没挂上就重试三次。

现场（2026-11-21）：用户先用「以管理员身份运行」启动，托盘里有图标；改为普通双击
（中间过了系统的「打开文件 - 安全警告」对话框）启动，程序起来了、挂件也在，**托盘里
什么都没有**。这个组合很容易被读成权限问题，实测不成立：

- 同一会话里 Medium（未提权）进程自己 `NIM_ADD` **成功**（`Shell_NotifyIconGetRect`
  拿到矩形），所以不是 UAC / UIPI 挡的；管理员那次成功、普通那次失败是**那一次
  `NIM_ADD` 失败**，不是权限差异。想复核：`scripts/out/probe_tray_register.py`。
- 失败那次的现场证据：进程里 `Qt6120TrayIconMessageWindowClass` 窗口在，但
  `Shell_NotifyIconGetRect` 返回 `E_FAIL`、`NIM_MODIFY` 说"图标不存在"——
  即 Qt 建好了宿主窗口，图标从没进过通知区域。
- 当时完全查不出来是因为**窗口化 exe 的 `sys.stderr` 是 devnull**（`mihome/_stdio.py`），
  Qt 就算 `qWarning` 也一起扔了。

### 判据：问系统，别问自己

```python
registered_with_shell() -> bool      # mihome/ui/tray.py
```

1. 在**本进程**里找类名以 `TrayIconMessageWindowClass` 结尾的窗口（Qt 每版带前缀，
   本机是 `Qt6120...`，所以按后缀匹配），没有就是没挂；
2. 按 `(hwnd, uID=0)` 调 `Shell_NotifyIconGetRect`：拿得到矩形 = 在（**缩在溢出
   面板里也算在**），`E_FAIL` = 不在。这个调用**只读**，不改图标状态。

**离屏 / 非 windows 平台一律当"在"**：`QApplication.platformName() != "windows"`
直接返回 True。50 多个验证脚本都跑在 offscreen 上，判死会把它们全带进"关窗即退出"
的分支。反过来说，这条探针只有真机上才会说"没挂上"——那正是唯一有意义的场合。

### 重试：1.2 s / 3.5 s / 9 s，每次先 `hide()`

`hide()` + `show()` 是幂等的：图标其实在时等于重新注册一遍，不在时正好把"半死"
状态清干净。间距越拉越开，前两次盖住"通知区域那一刻正忙"（`NIM_ADD` 在 shell 忙时
会以 `ERROR_TIMEOUT` 失败），最后一次盖住 explorer 短暂抽风。四次都失败才认输。
注入点：`TrayController(probe=...)`，测试用它模拟"系统里查不到"。

### 后果：`active` 是真的，藏窗才会退回退出

`_should_hide_to_tray()` 判的是 `tray.active`。以前 `install()` 里 `show()` 完直接
`_shown = True`，等于自欺——用户点关闭，窗口藏进一个**空托盘**，除了任务管理器没有
任何入口。现在 `active` 来自系统校验：挂不上就是 False，关窗直接退出，宁可少一个
"收进托盘"，也不留一个看不见的进程。重试稍后成功时 `active` 自己会翻成 True。

**另外两处顺带补的坑**：图标为空（`assets/app.ico` 丢了且兜底画法也失败）时不假装
挂上——Qt 对空图标是"`setVisible(true)` 直接返回"，连 `NIM_ADD` 都不发，和注册失败
长得一模一样；`MIHOME_NO_TRAY=1` 仍然是一刀切。

### 日志与排查顺序

- `logs/tray.log`：每次尝试一行（"已挂上" / "查不到图标，1200 ms 后重试 1/3" /
  "重试全部失败"）。**先看这个文件**，比盯通知区域快。
- `logs/qt.log`：`core/applog.py` 装的 Qt 消息处理器只收 Warning 及以上。
  `app.py: main()` 在建完 `QApplication` 后 `install_qt_handler()`。
- 用户说"没有图标"时先分清三件事：① `tray.log` 有没有"已挂上"；② 有的话是
  **Win11 把它折叠进溢出面板了**（新图标默认进 `^`，不是故障）；③ 都没有才是
  真没挂上。
- 真机复核（都在 `scripts/out/`）：`probe_tray_install_live.py`（未建时 False →
  `install()` 后 True → `remove()` 后 False，证明判据不是永真）、
  `probe_tray_retry_live.py`（前两次判据说"没挂上"→ 4.8 s 后 `active` 翻真）、
  `probe_tray_register.py`（Medium 进程自己 `NIM_ADD` 的对照实验）。

`verify_tray.py` 钉住的是机制：失败时 `install()` 返回 False、`active` 不撒谎、
排了重试、重试成功翻真、空图标不假装挂上。

### 挂不上之后：关窗收进挂件，不再"面板一关全没了"（2026-11-21 二次修）

`active` 变成真话之后冒出一个新问题：设置里选的是「最小化到托盘」，托盘却挂不上，
于是关窗走 `quit_app` —— 用户看到的是**面板一关，桌面挂件也一起消失**，读起来就是
"程序被关掉了"。

现在的判定顺序（`MainWindow.closeEvent`）：

| 条件 | 行为 |
|---|---|
| `close_to_tray` 且 `tray.active` | 收进托盘（原路径） |
| `close_to_tray` 且托盘不可用、**挂件可见** | 只 `hide()` 主窗口，进程与挂件都留着 |
| 其它（选了退出程序 / 挂件没开 / 正在退出） | `quit_app()` |

挂件不是"关不掉的死路"：头部第二个按钮是「打开主窗口」，右键菜单里有
「打开主界面…」「管理挂件…」「退出程序」——最后那条是 `active` 为假时**唯一**能
干净结束进程的入口（`quit_requested` 信号 → `MainWindow.quit_app`），没有它用户
只能去任务管理器。设置页那句说明也跟着改成"关窗后收进桌面挂件；挂件没开则退出程序"。

### 诊断落 `%TEMP%`：数据目录写不进去时，日志也一起没了

**同一轮暴露的真问题**：用户双击 exe 弹「设置无法保存」，而 `logs/prefs.log` 里
**一条失败记录都没有** —— 因为日志和数据文件在同一个目录，一起写不进去。
"落盘失败必须留痕"这条约定在这里失效了。

所以 `core/diag.py` 在每次启动时往 `%TEMP%/MiHomePanel-diag.txt` **追加**一段现场
（`app.py` 的 `_report_startup` / `_report_runtime` 各调一次，后者延时 3 秒）：

- `frozen`、Python 版本、`argv`、`cwd`；
- `LOCALAPPDATA` / `TEMP` / `MIHOME_DATA_DIR` / `MIHOME_NO_TRAY` 的实际取值；
- **进程身份**：SID、`USERNAME`、完整性级别（Low / Medium / High）、是否
  AppContainer、是否已提权 —— "写不进去"最常见的原因就在这五项里；
- `prefs_path` / `prefs_writable` / `probe_error`（带 `WinError` 与 `errno`）；
- 运行 3 秒后的 `tray=available=… active=… icon_null=… attempt=… system=…`
  与两个窗口的可见性。

坑：`GetCurrentProcess()` 不显式声明 `restype` 会按 32 位返回，`-1` 被截断，
`OpenProcessToken` 直接回 `ERROR_INVALID_HANDLE(6)` —— 第一次跑就是这么翻的。
报告里的每一行都值得先看，它比"弹窗上那句常见原因"具体得多。

### 兜底：进程本身是 Low 时，直接说"你被降权了"（2026-11-21 定位到根因后）

上面那一整套（问系统 + 重试 + 关窗退路）都是在**进程本身正常**的前提下才有意义。
真正那次报障的根因不在代码里：exe 所在的目录带 `Mandatory Label\Low`，Windows 就以
Low 完整性启动它 —— Low 进程**发不了窗口消息给 Medium 的 explorer**，`NIM_ADD` 怎么
重试都会失败；顺带连 `%LOCALAPPDATA%` 也写不了。详见
`docs/dev/packaging-release.md`「产物目录的强制完整性标签会被 exe 继承」。

所以启动时多一句判定（`app._warn_if_readonly`）：`diag.low_integrity()` 为真就弹
「程序被以低权限运行」，写清后果（存不住、托盘挂不上）、当前 exe 路径、进程身份，
并给一个「复制修复命令」按钮把 `icacls "<exe 目录>" /setintegritylevel (OI)(CI)Medium /T`
塞进剪贴板——手打那串容易错。**这条弹窗只在这种环境出现**，正常机器上永远不会看到。

## 字体渲染：引擎换成了 FreeType（2026-11-16）

**一句话**：全程序走 FreeType 字体引擎 + 灰度抗锯齿，目的是去掉 DirectWrite 的
ClearType 子像素彩边——13 px 中文笔画边上会带红蓝两色，放大看像"毛刺"。
**这不是换字体**，字形仍是微软雅黑。

- 出口只有一个：`mihome/ui/fonts.py`（`FAMILY` / `PIXEL_SIZE` / `make_font()` /
  `prepare_engine()` / `apply_to(app)`）。`app.py` 两条启动路径（正常启动、
  `--probe-camera` 冒烟探针）都走它，别再自己 `QFont(...)`。
- **顺序不能动**：`prepare_engine()` 必须在 `QApplication` 之前。平台插件只在构造时
  读一次 `QT_QPA_PLATFORM`，晚了**不生效也不报错**，只会安静地保持彩边。
- **它会跳过三种情况**：非 Windows、环境里已经写了 `fontengine=`、
  平台不是 `windows`（`offscreen` / `minimal` 原样放过——50 多个验证脚本靠这一条）。
- **回退**：启动前设 `MIHOME_FONT_ENGINE=default` 即退回 DirectWrite，不改代码。
- **QSS 不会吃掉策略**：`app_qss()` 的 `* { font-family }` 只重建字体族，
  `NoSubpixelAntialias` 仍在控件上（`scripts/verify_fonts.py` 钉住）。
- **实测口径**（别凭印象改）：顶栏标题彩边最大 **176 → 9**、平均 **15.9 → 2.0**，
  明暗两档一致；笔画最深处落差 **233（浅）/ 219（深）前后不变**——所以不是"变淡"，
  只是边缘从"彩"变"灰"；13 px 行高不变（两侧都 16），整窗 **99.65 % 像素零位移**。
- **改字号 / 换字体前**：`theme.FONT_STACK` 与 `fonts.FAMILY` 是两处，
  只改一处会出现"部分控件还是旧字体"。字形的备选方案、体积与许可见
  [font-swap.md](../reference/font-swap.md)。

## 子窗口的浮窗形态：外圈阴影 + 内缩面板（2026-11-13）

系统标题栏去掉之后，"这块是另一个窗口"这件事得自己画。最早靠三件事凑：子窗口
底色离开主窗口一档、外圈 1px 描边、弹出时主窗口压暗。**2026-11-15 起压暗归零**
（`DIM_ALPHA = 0`，见下一节），分离只剩"投影 + 描边 + 底色差"这三样明度信号，
所以投影必须自己画：

窗口四边各留 24px 透明边，把阴影画进这段留白里，可见面板缩在中间。

```
┌──────── 窗口（= 可见面板 + 24px × 2，透明底）────────┐
│   ░░░░░░░ 阴影（多层圆角扩张，半分辨率缓存）░░░░░░    │
│   ┌──────── frame.body（可见面板，圆角 18）────────┐  │
│   │ TitleBar / 内容 —— 各窗口的根布局挂这里         │  │
│   └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

### 为什么要多这一圈

`QGraphicsDropShadowEffect` **对顶层窗口无效**（文档里写了，别试），阴影只能自己
画；而"能画的地方"只有窗口自己的矩形。所以想让阴影出现在面板外面，窗口就必须
比面板大一圈。这 24px 是**结构性的**，不是随便调的边距。

代价与取舍：

- 窗口几何变大 → 修 `floating_size(w, h)` 把内容尺寸换算成窗口尺寸。各窗口
  `resize()` 写的仍是**内容**尺寸，设置页那种按最小尺寸卡死的页不会凭空少一行。
- 内容不能挂在窗口的布局上，否则子控件会画进阴影区 → 各窗口根布局改成
  `QVBoxLayout(self._frame.body)`。这是接浮窗时唯一必须逐个改的地方（七个窗口）。
- `fit_height()` 多一个 `reserve=`：总高上限不变（别顶出任务栏），扣掉两圈留白
  之后才是内容高。1080p 上编辑窗内容从 900 降到 870，离屏 800 屏上从 680 降到
  632——后者看着矮，是环境不是 bug。

### 阴影怎么画（`WindowFrame._build_shadow`）

从最外圈往里叠 24 层圆角矩形，每层 alpha 很小，越靠里累积越浓：

- **每层 alpha 必须按权重归一，不能除以层数**。第一版写成
  `peak * w / layers`，贴边累计只有 `peak` 的一半左右（曲线的平均值），
  0.24 的设定最终只暗 13%，肉眼等于没有——这是本轮唯一返工的地方。
- 曲线用 `(1 - t²)^1.6`：贴边最浓、外圈迅速淡掉，比线性斜坡像真阴影。
- **半分辨率生成再放大**（`ratio = dpr * 0.5`）：阴影本来就是糊的，24 层 `fillPath`
  的耗时与像素数成正比，砍到 1/4 后 resize 那一下从 ~3ms 降到 ~1.5ms。绘制端
  `SmoothPixmapTransform` 放大，放大 4 倍看圆角也没有方块。
- **缓存 key = 尺寸 + dpr + 半径 + 浓度 + 留白**。不动就一次 `drawImage`；窗口
  resize、切主题改浓度都换 key 重画。切主题只有设置页需要（它能在窗口开着的时候
  换主题），所以 `_apply_palette` 里补了一句 `frame.set_shadow_alpha(...)`。

数字都在 `chrome.py` 顶部：`SHADOW_PAD = 24`、`SHADOW_DY = 4`、浮窗圆角用
`theme.RADIUS_CARD`（18，不是主窗口的 12）。

**浓度 `shadow_alpha()` = 浅 0.18 / 深 0.44（2026-11-15 从 0.30 / 0.55 下调）**。
旧值是**配着压暗**定的（底色先压 12% / 24%，投影再叠一层）；压暗归零后投影变成
唯一的深度信号，旧值在浅色白卡上贴边要掉 48 个明度档，就是一圈黑晕。新值按
"贴边压暗档位"反解，两档同一条方法：

| 档 | alpha | 贴边压暗（卡片色） | 为什么是它 |
|---|---|---|---|
| 浅色 | 0.18 | 白卡 252.1 → 219.1（**32.9 档**） | 超过 ~40 档发脏，低于 ~25 档看不出浮起 |
| 深色 | 0.44 | 米黄 58.5 → 43.1（**15.4 档**）、渐变档 50.3 → 36.9（13.4 档） | 深底明度只有白卡 1/5，同 alpha 绝对差看不见，需要更大比例 |

深色最弱的一环是**投影落在比卡片更暗的底色上**：只压暗 6.6 档，此时靠描边
（对底色 1.74:1）顶上。四组背景的实测表在 `verify_dim_click.py` 第 9 节，验收带
浅 26～38 档 / 深 11～18 档，超出即判失败。

> 这里只动浓度，`SHADOW_PAD`（半径/扩散）与 `SHADOW_DY`（方向）都没动。
> 觉得"过渡太硬"改 `SHADOW_PAD`（会同步影响 `floating_size`，内容尺寸不变），
> 觉得"方向不对"才改 `SHADOW_DY`。**不要**用 alpha 去调这两个问题。

### 三处容易被漏掉的接线

1. **点击层挖洞要用面板，不是 `frameGeometry()`**。`DimClickShield._hit_rect()`
   现在返回 `frame.panel_geometry()`：阴影是透明留白，点它算"点外侧"→ 关窗；
   点面板才算"点进窗口"。`_place()` 挖洞与 `_over_dialog()` 判定必须用**同一个**
   矩形，否则会出现"点得到但不关窗"。
2. **标题栏的顶部圆角要跟窗口半径走**。`TitleBar` 现在从 `frame.radius` 取，
   写死 `WINDOW_RADIUS` 会让 18 的浮窗在标题栏处被 12 的弧盖出一个小方块。
3. **描边层、缩放热区也要内缩**。`_FrameBorder` 画在 `panel_rect()` 上；8 个
   `_ResizeEdge` 贴在面板边（阴影区不参与缩放——那块本来就不算窗口）。

### 刻意没做的

- **摄像头独立播放窗（`camera_popout`）仍是老形态**：它是贴桌面的独立窗、尺寸按
  屏幕比例算，而且画面控件是方的——加圆角阴影后会引出"方角画面盖住圆角"这个
  老问题，收益不抵风险。要改先解决画面控件的圆角裁剪。
- **主窗口不加阴影**：它贴边、能最大化，最大化时阴影无处可画（`_pad = 0`，
  详见 `WindowFrame` 的注释）。替代方案是**一圈 1px 外框**：
  `theme.window_edge(p) = blend(bg, text, 0.12 浅 / 0.18 深)`，由 `_FrameBorder`
  画在最外一圈，最大化时不画（贴着屏幕边没有"和桌面分界"这回事）。
  它跟着当前背景预设走，换色自动变，别写死色值。
- **没有打开/关闭动画**：阴影随窗口一起出现，先保证不闪（见「关窗那一下只许
  重绘一次」）。

### 验证与性能

`scripts/verify_float_window.py`（**35 项**）：面板内缩 / `shadow=0` 的老形态一行
不动 / 阴影贴边浓度接近设定值 / 外圈连续非零（不是一刀切）/ 窗口最外一圈透明 /
缓存命中与失效 / 四角透明 / 描边落在面板边 / TitleBar 半径 / 点击层洞 = 面板
（点阴影不算点进窗口）/ 七个窗口面板尺寸仍等于设计值 / `fit_height` 扣留白。

`scripts/out/shot_float_windows.py` 出浅深两套预览 + 一张"主窗口上叠详情页"的

## 交互约定：点弹窗外侧关闭子窗口（原「点压暗区」）

> 2026-11-15 起主窗口不再压暗（`DIM_ALPHA = 0`），但**可点区照旧**：这一层仍然
> 铺满主窗口、仍然是"点一下 = Esc"。**压暗与命中测试是两个独立参数**，
> 调其中一个时别顺手改另一个。

**点一下子窗口外侧 = 按一次 Esc，只关当前这一层。**

为什么不能直接用窗口内的蒙版吃点击：`DimOverlay` 是主窗口 `root` 的子控件，
而子窗口走的是 `QDialog.exec()`（应用模态）。模态期间 Qt 在**窗口系统层**就把
落到主窗口及其子控件上的鼠标事件丢掉了，`DimOverlay` 永远收不到。
（而模态弹窗**自己**的子顶层窗口不受拦截——实现就挂在这一点上。）

实现方式（`mihome/ui/chrome.py`）：

- 每个弹窗挂一个 `DimClickShield`：透明、无边框、不抢焦点的子顶层窗口，
  铺满最外层主窗口，用 `setMask` 把它自己**和它自己开的独立子窗口**的矩形挖掉；
  **父弹窗不挖**（2026-11-15 修）：父窗此刻被应用模态禁用，点上去只会被 Qt 丢掉，
  用户看到的就是"点上级窗口关不掉子窗"；留在遮罩里则等同 Esc 关掉当前这一层，
  父窗自己的 shield 还在，这一层关完再点才轮到它；
- 点洞外 → `dialog.reject()`，和 Esc 走同一条 `done(Rejected)` 路径，
  所以标题栏关闭、详情页停播/释放观看位这些现有逻辑全部复用；
- 只关最上层：嵌套时每层各有一个 shield，最上层那个在最上面，
  `reject()` 只作用于它自己的 `dialog`；
- 不误伤：按下与松开**两端都必须在洞外**才关。窗口内部按下拖到遮罩松开，
  shield 没有 press 记录；遮罩按下拖进窗口松开，松开点命中洞内。
  滚轮事件直接 `ignore()`；视频画面自己的单击语义不受影响；
- 视觉：shield 不画可见内容，只填一层 alpha=1——Windows 对分层窗口是逐像素
  命中测试，alpha=0 的像素收不到鼠标（`setMask` 不会改变这一点）。这层填充
  和压暗**无关**，`DIM_ALPHA` 归零时也必须保留；`DimOverlay` 现在强度为 0、
  `paintEvent` 直接返回（不画任何像素），只保留显隐逻辑，方便以后把常量调回去。

接线点是 `exec_with_dim_click(dialog)`，新加弹窗请走它而不是裸 `dialog.exec()`。

### 关掉就销毁（`deleteLater`，2026-11-12 修）

`exec_with_dim_click` 的 `finally` 里现在除了 `shield.hide()`，还会 `dialog.hide()`
+ `dialog.deleteLater()`。原因是一条真机上刷屏的报错：

```
AttributeError: 'DimClickShield' object has no attribute '_dialog'
AttributeError: 'WindowFrame' object has no attribute 'win'
```

它出现在**反复打开、关闭设置页**之后。链路是：弹窗 parent 是主窗口，只 `hide()`
不销毁时 C++ 对象被 parent 一直持有，挂在它身上的两个事件过滤器（`WindowFrame` /
`DimClickShield`）也跟着活下来；而 Python 侧这些对象只由 `dialog.__dict__`
和调用方的**局部变量**引用，函数一返回就可能被 GC。之后 Qt 继续回调它们的
`eventFilter`，访问 `self.win` / `self._dialog` 就是上面那两句——表现是终端刷红字、
主窗口的绘制/事件时序被打乱（用户看到卡片墙变空）。

两条加固，缺一不可：

1. **关掉即销毁**（`deleteLater`）：C++ 对象真没了，过滤器随子对象一起走。顺带
   解决"每次开设置都攒一个 `Qt.Dialog` 顶层窗口"——攒着反复开关会闪。
2. **Python 引用跟着被监控窗口走**：`WindowFrame` 构造时写 `window._window_frame = self`，
   `DimClickShield` 构造时写 `dialog._dim_click_shield = self`（原来只在
   `exec_with_dim_click` 里挂，别处直接 new 就没挂）。这样即使调用方不长期持有，
   wrapper 也不会先于 C++ 对象消失。

验证：`scripts/verify_dim_click.py` 第 8 组——连续开关 5 次后断言没有一个弹窗还活着、
主窗口名下不再挂着 `QDialog`、没有残留 `WindowFrame`；另有一条对照（只 `hide()`
不 `delete` 的弹窗**仍然活着**），证明这三条真能测到东西。

### 关窗那一下只许重绘一次

上一节把报错治住了，但**闪烁还在**（用户 2026-11-12 复测：主窗口闪一下，截图里
卡片全都变矮、只剩标题，body 是空的）。两个独立原因，都得修：

**① 关窗后又把主题应用了一遍（主因）。** `open_settings` 过去在 `_run_dialog`
之后无条件调 `self._apply_theme()`。而 `_apply_theme` 里有
`wall.rebuild_palette`——卡片是自绘的，换色靠**整墙重建**（56 张卡拆掉重造）。
所以"什么都没改、直接关设置页"也要重建一次，叠加在三处整窗失效之上，中间那帧
就是"父控件（卡片底色、标题）画完了、子控件（body 里的滑条/轨道）还没画"。

其实不需要：设置页里点主题时 `theme_selected` → `set_theme` 当场就应用过了。
**改主题时那次重建还在**（该有），关窗那次是纯重复。

**② 三处"整窗失效"没有合并。** 关一个子窗口会连着做三件事，每一件都让系统要求
主窗口重画整片区域：

| 事件 | 哪来的 |
|---|---|
| 弹窗销毁 | `exec_with_dim_click` 的 `finally`（`deleteLater`） |
| 点击层隐藏 | `DimClickShield.eventFilter` 收到 `Hide` |
| 压暗蒙版隐藏 | `_run_dialog` 的 `finally`（`_dim.cover(False)`） |

主窗口是 `WA_TranslucentBackground` 的（圆角要真透明角），Qt 在这种窗口上**分段
提交**（逐控件 blit），所以连着来三次就能看见"画一半"的中间态。这三件事都发生在
同一轮调用里（`done()` 里 hide、exec 的 finally 紧接、`_run_dialog` 的 finally 紧接，
中间没有回到事件循环），所以收尾统一走 `MainWindow._cover_dim(False)`：它先
`setUpdatesEnabled(False)`，撤掉压暗层，再 `setUpdatesEnabled(True)` + `update()`，
**合成一次 paint**。`_cover_dim(True)` 只是 `dim.cover(True)`，压暗不需要冻结。

约定：**关子窗口前后的收尾动作都写进 `_cover_dim(False)` 那段冻结里**。以后再加
"关窗时要恢复点什么"（比如摄像头画面还回卡片），别放在 `exec` 之后另起一段——
那会变成第二次整窗重绘。

验证：`scripts/verify_close_flash.py`——直接关窗时 `_apply_theme` / `rebuild_palette`
必须是 0 次；在设置页里改主题时恰好 1 次；关窗后 `WA_UpdatesDisabled` 必须已放开
（忘了放开就是整窗冻住，比闪烁更糟）、压暗层已撤。把 `_apply_theme()` 加回去，
这个脚本立刻 6 项红——反向证明它测的是真事。

**离屏测不到"看不看得见闪"**（离屏 QPA 不做分段提交），这里守的是根因；
视觉效果只能在真机上复测。

## 主界面页面宿主（2026-11-15）

中间内容区不再是固定的卡片墙，而是 `QStackedWidget`（`MainWindow.pages`）：

| 索引 | 页面 | 来源 |
|---|---|---|
| 0 | 卡片墙 `WallView` | `ui/wall.py` |
| 1 | 电脑自动化 `AutomationPage` | `ui/automation_list.py` |
| 2 | 耗材 `ConsumablesPage` | `ui/consumables_page.py` |
| 3 | 监控 `PlaceholderPage`（尚未开放） | `ui/placeholder_page.py` |

- **宿主只包卡片墙这一层**：顶部说话条（连同它那条 band）在宿主**外面**（上面），
  只在卡片墙上显示；功能区三页会整条藏掉，页面因此顶到窗口上沿，回到卡片墙再显示。
  顶部警告条仍是 `body` 上的浮层，`_place_alert` 按 `body` / `nav` 的几何算，
  和当前是哪一页无关（说话条藏起来也不影响它的落点）。轮询、写入、排序拖拽都还挂在
  常驻的 `WallView` 上，切页只是把它隐藏，不重建、不停止轮询。耗材页同样是常驻实例：
  切到它时补一次 `refresh()`（期间可能加过监控项、改过设备名 / 房间）。
- **提示浮层按右栏内容区定位**：`InlineToast` 不再锚说话条输入框，而是以**右栏**
  （含说话条与页面宿主的那一列）为基准——垂直贴右栏顶部 + `ALERT_MARGIN_TOP`（12），
  水平按右栏宽度居中、左右各留 `ALERT_MARGIN_X`（28）。右栏顶部不随横带显隐变化，
  所以功能区分页藏掉说话条时提示**完全不动**，与警告条同一落点、同一条中线
  （不是按整窗居中，否则会左移半个侧栏宽）。切页不需要重算提示位置。
- **记住上次页面 + 家庭 / 房间**：`Prefs.last_page` 在每次 `_show_page()` 时写入（含
  `"wall"`），`last_home` / `last_room` 只在**点房间**和**切家庭**时更新（都是云端 id，
  `"*"` = 全部设备）；停在功能区页面时房间记录保持不动，所以从自动化页回来还能落回
  原房间。切家庭后侧栏落在"全部设备"，记录也就是新家庭 + `"*"`。开关只决定启动时
  用不用这些记录，记录本身照常写。
- **启动落点**：`_restore_start_page()` 先按 `last_page` 切页；房间要等拓扑加载完，
  在第一次 `_on_loaded()` 里由 `_apply_start_room()` 处理：
  - 开关开：家庭用 `last_home`（仍存在时），房间用 `last_room`；`"*"` 表示全部设备。
  - 开关关：页面固定卡片墙，房间固定当前家庭**第一个普通房间**。
  - 兜底：`last_home` 不存在 → 回当前家庭；`last_room` 不在当前家庭的房间表里
    （被删 / 改名导致 id 失效）→ 第一个普通房间；一个普通房间都没有 → 全部设备。
    全程不抛错、不阻塞；托盘启动时滚动位置等窗口真正显示后再校一次。
  - 默认关（面板主视图是卡片墙，功能区与分隔线下的页面都不在常用路径上，开机落到
    那里预期更差）。坏值 / 老文件缺键退回 `"wall"` / 空 id，没有一次性迁移分支。
- **切页只换索引**：`MainWindow._show_page(index, zone)` 设当前页，并把侧栏选中态
  交给 `SideNav.set_active_zone()`。功能区 key → 索引的映射在 `_zone_pages`，
  加页时映射和 `addWidget` 顺序一起改。
- **离开卡片墙会停播**：`wall.stop_playback("切换到独立页面")`——整页盖住后画面
  不可见，继续取流只是白占一个观看位（与打开子窗口 / 收进托盘同一条理由）。
  切回卡片墙**不自动恢复播放**，仍要用户点卡片上的播放。
- **点任一房间回卡片墙**：`_on_room_selected` 先 `_show_page(0, None)` 再
  `scroll_to_room`。切换家庭后 `nav.build()` 重建的房间列表同样走这一条。
- **切家庭不离开当前页**：停在自动化页时切家庭，页面调 `refresh()` 换成新家庭的
  规则列表；侧栏选中态保持不变（`build()` 不重置 `_active_zone`）。
- **主题**：`_apply_theme` 逐个调页面的 `set_palette`；卡片墙仍走 `rebuild_palette`
  （自绘卡片），自动化页只重设页面 QSS + 开关色板。
- **页面别给空壳**：加新入口时要么接真页面，要么像早期占位页那样给一张居中卡
  （标题沿用侧栏入口名 + 一句说明），别让点进去的人以为加载失败。

## 左侧导航底部的功能区

`ui/side_nav.py` 底部现在是**两块**：功能区（监控室 / 电脑自动化两个按钮）在上，
分隔线下方是**三行**——「耗材」（页面）、「桌面挂件」（开关）、「设置」
（`FOOT_H = 114`：三行 32 + 行距 2 + 上下各 7）。**2026-11-15 起前三个入口全部接线**：
点任何一格都把中间内容区整页换成对应页面（页面清单见上一节「主界面页面宿主」），
不再有"收到即忽略"的入口。
**2026-11-20 晚起「桌面挂件」从功能区挪到分隔线下方**（用户 m02862 定）：
挂件是**跨家庭**的（切家庭它不跟着变），而功能区在语义上是"当前这个家"的功能，
放一起会误导。它仍然是**开关不是页面**：点一下弹出桌面挂件、再点一下收起。设置页里
不再有启用开关，只剩「启动时开启桌面挂件」，管的是"下次启动要不要自动出现"。
**2026-11-21 起「耗材」也挪到分隔线下方**（同理，且更彻底）：耗材页本身已经改成
按**全部家庭**统计（见「耗材页」），它不再属于"这个家"的内容。挪下去之后底部正好
三行、总高不变（`ZONE_H` 少一行、`FOOT_H` 多一行，`BOTTOM_H` 还是 193），房间列表
的可见区没变。

- **两条线的语义不是装饰**：房间列表 + 功能区 = 「这个家」的内容；分隔线下方 = 「跨
  家庭 / 程序级」（耗材、桌面挂件、设置）。所以功能区上下各一条线，底部三行在同一组里。
  两条线样式必须一致（`pal.border` / 1px / 左右各缩 12），别给其中一条加粗换色——
  那会把功能区夹成第三组。
- **接线**：`mouseReleaseEvent` 命中 `_zone_index_at_point()` 后统一
  `zone_requested.emit(ZONE_KEYS[idx])`，`MainWindow._on_zone()` 用 `_zone_pages`
  切页。`ZONE_KEYS`（长度 2）与 `ZONE_ITEMS` 顺序必须一一对应，加按钮时两处一起改。
  底部三行共用 `_foot_rect(i)`（顺序同 `FOOT_ITEMS`）：
  `foot[0]` 耗材 → `zone_requested.emit("consumables")`（页面，会设选中态）、
  `foot[1]` 挂件 → `zone_requested.emit(FOOT_WIDGET)`（开关，不动选中态）、
  `foot[2]` 设置 → `settings_requested`。
  `"widget"` 是唯一的例外：`_on_zone()` 见到它直接转 `_toggle_widget_visible()`
  就返回，不进 `_zone_pages`。收起挂件**不写** `widget_autostart`——那是"下次启动
  自动出现"的偏好，归设置页管；左栏只管当次显隐。
- **`PAGE_ZONE_KEYS` 仍是三个**（`consumables / monitor / automation`）：它定义"哪些
  key 有页面"，和"画在哪个区"是两件事，别因为耗材挪了位置就从这里删掉。
- **选中态**：当前所在的入口用与房间选中行同一套标记——`nav_row_bg` 底色、
  左侧 3px `pal.accent` 竖条、主文字色 + 半粗，图标也跟着提亮。耗材虽然画在分隔线
  下方，**选中态与功能区完全一致**（它就是个页面入口）。此时房间行**不再高亮**
  （`paintEvent` 里 `active` 条件和 `_active_zone` 互斥），一眼只有一处"当前位置"。
  点任一房间会清掉选中态、回到卡片墙，房间高亮照旧。
  「桌面挂件」那一行不参与 `_active_zone`：它的高亮由 `SideNav.set_widget_on()` 跟着
  挂件**实际是否可见**走（`DesktopWidget.visibility_changed` → 主窗口转发），所以挂着
  挂件时仍然可以停在耗材 / 监控任一页面，两处高亮互不抢占。设置行只用 `hover` 态。
  三种行的区别集中在 `_paint_foot_row()` 的一句 `emph = active and kind != FOOT_WIDGET`：
  耗材走选中态、挂件只靠圆点、设置没有持续状态。
- **挂件行的启用点**（2026-11-21 用户 m03313）：`_paint_widget_dot()` 在标签右侧画
  直径 7 的 `pal.accent` 实心点，位置按文字实际宽度算（与 badge 同一套算法）。
  不复用那两枚计数 pill——pill 的形状绑定"有 N 项提醒"，挂件没有数字，会读成
  耗材告警；这里要表达的是"这个开关此刻是开的"。
  **启用态只有这一个圆点**：不铺选中底色、不画左侧 accent 竖条、文字也不提亮加粗
  （用户 m03616 定）——那套标记属于"当前所在页面"，挂件行是开关，用上会读成"你在挂件页"。
  悬停底色保留，那是可点提示、与开关状态无关。
- **耗材的计数圆点画在耗材行**（不再在功能区）：`SideNav.set_zone_badges("consumables",
  warn, crit)`，key 就是页面 key，绘制代码与功能区那套 `_paint_zone_badges` 同一份。
- **`build()` 不重置选中态**：切家庭 / 排序变化重建房间行时，用户可能还停在同一个
  页面，选中态不该自己跳回房间。
- **几何只有一个来源**：`BOTTOM_H = ZONE_H + FOOT_H`。房间列表的可视区
  （`_view_rect`）和滚动上限（`_max_offset`）都减 `BOTTOM_H`，不是 `FOOT_H`。
  改底部任何一块高度都要改这里，否则列表会盖住按钮。
- **`ZONE_H` / `FOOT_H` 都必须按 `len(...)` 算**，别写死数字：2026-11-12 加第三个
  「电脑自动化」时就漏了这一处，底部会压掉最后一条并盖住第二道分隔线。加按钮
  只需往 `ZONE_ITEMS`（或 `FOOT_ITEMS`）里加一项 + 在 `_paint_zone_icon` 里补图标分支。
- 底部三行共用 `_paint_foot_row()`：图标、文字、选中/悬停底色和左侧 accent 竖条与
  功能区同参数，避免两套绘制漂移。图标：耗材 `battery`、挂件 `widget`（复用
  `_paint_zone_icon`）、设置 `gear`。

## 耗材页（2026-11-18）

功能区「耗材」从占位页换成真页面：**一张卡 = 一条监控项 = 一台设备的一个属性**。
同一台设备要盯两个耗材就加两张卡，卡片之间没有任何联动。

### 跨家庭：全部家庭一起看（2026-11-21）

这一页**不跟顶栏家庭**（推翻 2026-11-18 的"只显示当前家庭"）：耗材问的是"整栋房子
该换什么了"，切个家就不显示另一套房子的滤芯，等于漏报。所以：

- 卡片取 `prefs.consumables` 里的**全部**条目，不再按 `store.active_home` 过滤。
  位置靠 `Row.place_text`（`示例家庭 · 客厅`）区分、靠 `Row.place_key`
  （`(home_id, room_id)` 二元组）分组——**分组与排序认 id，显示认名字**：房间改名
  不会把分组拆散，两个家的"客厅"也不会并成一组。
- **连带效果一**：`counts()` 变成**全家庭计数**，侧栏圆点与桌面挂件右下角的角标从此
  同源（`_on_consumable_counts` 把同一份数发给两个消费者）。B 家耗材归零、用户却停在
  A 家时，圆点和角标都会动——这是改跨家庭顺带修掉的漏报（原来 B 家的条目根本没进
  `_rows`，也就没人通知）。
- **连带效果二**：切家庭不再刷新这一页（`_on_home_selected` 里那行已删）。页面顶部
  统计句写「共 N 项 · M 个家庭」，是唯一解释"为什么切家没变"的地方。
- **连带效果三**：选设备树改成**家庭 → 房间 → 设备**三层（见下节），否则会出现"页面
  显示两个家、却只能往当前这家加"的不对称。
- 「按房间分组」的序号表来自 `store.rooms()` **不传参**：它返回全部家庭，且已按
  `prefs.order_homes` + 每家的 `prefs.order_rooms` 排好，与顶栏、侧栏是同一套顺序。
  注意它只返回**有设备**的房间（且滤掉隐藏设备），所以被隐藏设备的耗材在 room 排序里
  落到末尾——既有行为，不是这次引入的。
- **设备已不存在**的条目照旧保留（这时 `place_text` 为空、分组头写「设备已不存在」），
  否则这条配置就再也删不掉了。
- **副标题宽度**：横卡 12px 放得下（「示例家庭 · 客厅 | 滤芯剩余寿命」216px / 可用
  236px）；环卡是 180 方卡（可用 148），同一句在 11px 下要 154px 会被截成
  「… | 滤…」，所以**环卡副标题用 10px**（140px）。实测脚本
  `scripts/out/measure_subtitle.py`，断言固化在 `verify_consumables.py` 第 9 组末尾；
  再长就省略，tooltip 给全（`设备｜位置｜属性`）。
- `refresh(preserve_scroll=True)` 现在只给**换卡片样式**用（圆环是方卡，尺寸一变整页
  重排）：重建前记下滚动值，先 `_grid.activate()` + `_canvas.adjustSize()`；重建那
  一刻 `maximum()` 可能还是 0，这时**保留待恢复值等下一轮事件循环**（100 ms 兜底
  丢弃），别当场 `setValue` 被 clamp 成 0 还把值清掉。加 / 删监控项、拓扑变化那些
  刷新仍回顶部（那时回到开头才对）。

### 添加流程：两步走

1. `＋ 添加设备`（页面右下角，绿色主按钮）→ **只选设备** → 墙上立刻落一张**空卡**。
2. 点空卡 → 配这一条：属性 + 名称 + 两档阈值（卡片**画法**不在这里，见下面的
   「两种样式」）。

为什么拆两步（2026-11-18 用户定）：第一步只让人回答"是哪台设备"；属性 / 阈值一起
塞进去，等于在看见卡片之前先做三个决定。空卡用**虚线框** + 「点击设置要监控的
属性」，和"暂时读不到数据"的卡（实心卡 + 「暂时读不到这个属性」）明确分开——
前者是还没开始配，后者是配好了但读不到。

空卡在数据里的形态是 `Consumable(did, siid=0, piid=0)`，id 固定为 `did:0.0`：

- **一台设备只可能有一张空卡**（id 相同 → `add_consumable` 去重，重复添加直接打开
  已有那张，不在墙上摞第二张空壳）。同一台设备的**第二条**耗材没问题——那要盯的是
  另一个属性，走"再添加一次 → 新空卡"。
- 配好属性时不是新增，而是 `Prefs.reconfigure_consumable(old_id, item)` 按旧 id
  **原地替换**：id 变了，位置不能跟着变（用户排过的顺序）。目标属性已被另一条占用时
  留在窗里报错，不顶掉别人。
- **属性配好之后仍然可改**（2026-11-18 用户改的口径）：挑错了不该让人删了重来。
  属性行一直是下拉，保存时若 id 变了就走上面那条原地替换，名称 / 阈值 / 位置都留着；
  新属性已被另一条占着时同理报错。
- 旧属性从规格里消失（规格更新 / 变成不可读）时，下拉里**保留一条**
  「`13.1`（规格里已没有这个属性）」并选中它，不静默换成第一个——那会在用户没动过的
  情况下把监控项指向另一个量。
- 空卡不判档、不进提醒计数、不进 `poll_refs`；按余量排序时垫底。

### 设备用树选，不用下拉

和设置页的排序 / 隐藏是同一个控件 `ui/tree.py`，构造时传 `draggable=False`——这里是
选一行，不是排序，不能把行拖走。下拉列几十台设备时只能一行行扫，同名设备还得靠拖在
后面的房间名区分；树把层级摊开，一次看全。

- 层级是**家庭 → 房间 → 设备**三段（2026-11-21 起，与桌面挂件管理窗的选设备树一致）。
  页面跨家庭了，树就得跟着跨；只列当前家庭会出现"页面显示两个家、却只能往当前这家加"。
  家庭节点默认展开（一共两三个家），空家庭 / 空房间整枝不出现。
- 这一步**不套「标签 + 控件」两列**：只有一个控件，96px 的标签列白占地方，树直接吃满
  弹窗宽度（`setMinimumWidth(400)`，提示文字也走整窗宽换行）。
- 只列**有可监控属性**的设备、只画**有这种设备**的房间：一棵树混着几十台配不了的
  设备，等于让人自己找哪个能点。
- 点房间行只折角，**不改变已选设备**（否则选好的设备被这一下清掉）；点到空白处则把
  选中态挪回已选设备。
- 一台能监控的都没有时给一行「没有可监控的设备」，且「下一步」置灰。
- 设备行后缀写「已离线」：离线设备照样能配，只是读数会停在最后一次。

属性清单只列 `DeviceSpec.properties` 里 **`readable` 且 `kind` 为 number / range**
的项：

- **不用 `card.advanced`**：那里只收"可写且卡片没用到的"，电量 / 滤芯寿命这类只读量
  根本不在里面（`TODO.md` 的原始规划里专门提醒过这一条）。
- **枚举 / 布尔 / 文本一律不列**：两个数字阈值套不到它们身上。真要支持，得先定义档位映射。
- **但"有值域"不等于"是余量"**（2026-11-19 查清，**决定不治**）：门锁「铃声类型」
  （`ringtone`，1–5 档、无单位、无 `value-list`）照样进清单，`fill_percent` 把它折算成
  50% 余量——取 1 时是 0%，会标红并进侧栏重提醒圆点，即**假告警**而非单纯干扰。
  49 份规格实测：无单位且跨度 ≤10 的候选全是档位 / 阈值 / 场景 id / 次数，而 `%` 里也混着
  湿度 / 亮度 / 音量——**规格里没有"这是余量"这个字段**。所以不做预过滤、也不按型号登记
  白名单（理由与"真要治怎么做"见 `TODO.md` C 段那条）：属性本来就是用户手选的，多一个
  干扰项的代价小于"某台设备该有的属性没列出来"。

### 属性重名：靠服务注释分开（2026-11-18）

小米门锁 4 Pro 的两块电池，属性名都是 `battery-level` → 界面上都叫「电池电量」，
下拉里两行一模一样，用户随手挑了一个、挑错了也看不出错在哪（当天实景）。
规则抽在 `core/spec.py` 的 `prop_labels(props)`，**弹窗下拉和卡片墙上的名字同一处
出处**：

1. 名字 + 单位都撞的，补一句服务注释 → 「电池电量 · 干电池（%）」/「· 锂电池（%）」；
2. 服务注释也撞（或压根没有）时退回 `siid.piid` → 「电池电量 · 7.1（%）」；
3. 不撞的保持原样，别让每台设备都拖一条后缀。

卡片墙上同理：没自定义名字的卡自动用这个结果，两张电池卡不会都写「电池电量」。
坐标与背景见 `docs/reference/lock-dual-battery.md`。

### 模型：阈值两档、含等于、可只开一档

`core/consumables.py` 只放纯数据与纯函数（不 import Qt）：

- `level_of(percent, warn, crit)`：`percent <= crit` → 红，`<= warn` → 橙，否则绿。
  **等于阈值就算**（写 20 就是"降到 20% 时提醒"）。
- 两档填反（warn 10 / crit 20）在 `parse()` 里自动换成"橙 20 / 红 10"——否则红色永远
  到不了。两档填同一个数时红那档作废（差值 ≤ 0 没有意义）。
- 阈值留空或 0 = 这一档不启用；两档都空 = 只显示读数，不变色也不计数。
- `fill_percent(value, span)`：有值域就按值域折算，没有就把读数当 0–100 的百分数。
  拿不到数值（None / bool / 文本）返回 `None`，卡片显示 `—` 且不参与变色。
- `KEY_UNSET = 0` 表示"还没选属性"的空卡（见上面的添加流程）；`is_configured`
  就是"两个 id 都大于 0"。`parse()` 只接受"都为 0"或"都为正"，半配置当坏数据丢掉。

### 卡片：两种样式，整页一个（2026-11-18）

`ConsumableCard` 自绘（和设备卡同一套理由：内容只有三行字 + 一条条）：

| style | 画法 |
|---|---|
| `bar`（默认） | 底部一条**轨道固定的血条**，填充按比例缩短，颜色随档位 |
| `fill` | 整张卡片当轨道：从左往右按比例染一层 16% 的档位色（裁在圆角路径里） |
| `ring` | **方形卡 + 居中大环**（11-18 用户给结构图定稿）：圆心大号百分比，12 点留开口，弧长随余量 |

**样式是整页一个**，存在 `prefs.consumable_style`（不再存在每条监控项里），入口是
耗材页右上角「卡片样式」下拉。原来的做法是每条各设一次——十张卡要重复做十次同样的
选择，而它表达的其实是"这页怎么读"，不是某条监控项的属性（2026-11-18 用户定）。
切换时 `_on_style` 分两种：横条 ↔ 整卡染色只把每行的 `Row.style` 改掉再逐卡
`update()`，**不重建页面**（这不是数据变化，重建会把滚动位置拉回顶部）；只要涉及
圆环就必须重建——它是 180×180 方卡，另两种是 268×100 横卡，`card_size(style)`
决定尺寸，只改绘制不改尺寸会把大环塞进 100px 高的卡里。重建时用
`refresh(preserve_scroll=True)`，滚动照旧保住。配置弹窗里已经去掉这一项。

三种样式共用同一套颜色（`theme.CONSUMABLE_LEVEL_COLORS`：绿 = `TOGGLE_ON`、
橙 = `WARNING`、红 = `DANGER`）——项目里每种语义色只有一个出处，别在界面里抄字面量。

**圆环卡的结构**（2026-11-18 用户给图定稿，`ui/consumables_page.py` 的 `RING_*`）：
方形卡 180×180（11-18 用户嫌 240 太大，缩到 3/4），上两行是设备名 /
`Row.subtitle`，中间一个直径 108 的粗环（线宽 12）占主体，圆心是 18px 百分比，
右下角照旧是读数时间。标题字号只从 15/12 收到 13/11，不按 0.75 缩——那样小到读不清。
**右上角不画原始读数**——结构图里
没有它，圆心百分比就是这页要读的那个数；带单位的原值仍在悬停 tooltip 里，没丢。
百分比按 `fill_percent` 折算成 0–100，和原值不是一回事（量程 0–500 的滤芯在 60% 时
原值 300）。读不到值时只画空轨道 + 圆心 `—`，不画假进度，也不再补「暂时读不到」。

两个踩过的坑，别回退：
- **开口角度基准**：Qt 的 `drawArc` 角度是**逆时针**、0° 在 3 点，所以 12 点是 `+90°`，
  写成 `-90` 会把缺口画到正下方。`span` 取负才是顺时针；`RING_GAP = 7°`、两端
  `Qt.FlatCap`——RoundCap 的圆头各外扩半个线宽，会把 14° 的缺口整个补上。
  满格也留口，`span < 360` 顺带绕开 `drawArc` 把 360° 当空弧的坑，不用 `drawEllipse`。
- **尺寸跟着样式走**：`card_size(style)` 是卡片尺寸的唯一点，`_columns()` 也用它算列数，
  别在别处写死 268。

**主副标题的分工**（2026-11-18 用户定）：第一行是**设备名**，第二行是
`Row.subtitle` = **「房间 | 属性名」**。同一台设备可能并排两张卡（门锁的两块电池），
先认出"哪台设备"再看"哪一间、哪个属性"，比反过来读着顺。房间为空（设备已不存在 /
设备没分房间）时只写属性名，别留一根孤零零的竖线。文字放不下就省略，悬停的
tooltip 给全（`_sync_tooltip`）。**横卡**的第一行右侧另有一个档位色原始读数；
圆环卡按结构图不画它。

### 页头：标题要和「监控」「电脑自动化」落在同一条线（2026-11-18）

三页共用一套外边距（左 28 / 上 8），标题都挂 `PageTitle`（20px）。但耗材页右上角多了
两个下拉：`padding: 6px` + 13px 字 → 33px 高，而 20px 标题的行高只有 26px。**标题如果
直接作为 head 的一项，会被拉伸到 33px 再垂直居中，文字比另两页低约 3.5px**（用户报
"标题位置有一点偏差"）。

做法：标题 + 统计先包一层 `QWidget`（行内 spacing 10 不变），再按 `Qt.AlignTop` 放进
head。容器高度取自身 `sizeHint`（26），贴住 8px 顶边，三页标题就落在同一条水平线上；
统计文字仍和标题在同一个容器里，两者共中线。**别改成 `setFixedHeight(26)`**：换字号或
改 QSS 时固定值不会跟着变，下次又会差几像素。

右侧下拉比标题行高是必然的（控件本身 33px），所以耗材页 head 之后的空白比另两页多
约 9px——那不算错位，别为了凑齐去压 `col.setSpacing()`，压到 3px 会让下拉贴着卡片。

`scripts/verify_consumables.py` 第 4 组钉住：标题左上角 `(28, 8)`、高度等于自身
`sizeHint`（没被下拉撑高）、统计文字与标题的中线相差 ≤1px。

### 排序：三种，只有自定义能拖

右上角两个下拉：**卡片样式**（见上一节）和**排序方式**——按余量（默认，低者优先）/
按房间分组（分房间画分组头）/ 自定义。前两种只改显示，不动 `prefs.consumables` 的顺序。

**拖动只在「自定义排序」下开放**（2026-11-18 用户改的口径，推翻原来"任意模式拖一下
就自动切自定义"的做法）：按余量 / 按房间时卡片的顺序是算出来的，搬一张没有稳定落点，
下一轮刷新还会被排序规则塞回去；所以这两种模式下**连拖动手势都不启动**，点击照常，
也不会偷偷替用户改排序方式。实现上 `ConsumableCard.set_draggable()` 由
`ConsumablesPage._reflow()` 按当前模式设置，卡片构造函数**默认 `draggable=False`**
（安全侧：将来新增调用点忘了传参只会"拖不动"，不会让按余量 / 按房间又能拖乱顺序），
页面 `_on_drag_start()` 再留一道兜底（绕过界面直接调回调也会早退）。

**三种卡片样式共用主页卡片墙那套拖动**（2026-11-18 用户定，替换原来的"松手才按
最近一张插"）。主页用 `CardGridLayout + eventFilter`，这页有房间分组头、用的是
`QGridLayout`，不能直接换布局，所以复用它的组件、自己接信号：

- `ConsumableCard` 用共享 `DragGesture`（8px 阈值，不再自己写一份）+ `set_drag_placeholder`
  画虚线框——被拖的卡留在原位当**落点提示**，网格也不塌；
- 页面层复用 `wall.py` 的 `DragGhost` + `rounded_shot`（四角透明的跟手快照），接
  `drag_moved`，贴边自动滚；
- 落点由 `dnd.grid_drop_index` 统一算（主页 `CardGridLayout.drop_index` 和这页
  `_drop_index` 都调它）：**先按行带、行内再按左右中线**——整张卡完全在探针上方就
  +1；探针落在卡的垂直范围里就只看 x，越过中线才算排在它后面；
- **拖动中只重排内存 `self._rows` + `_reflow()`，不重建、不写盘**。`_rebuild()` 会
  `deleteLater()` 掉正在拖的那张卡，幽灵和占位框当场失效；松手才
  `prefs.move_consumable()` 一次落盘。之前的 `drag_moved` 信号没接，所以没有实时
  反馈——现在必须接上。

#### 落点为什么看卡片中心，不看鼠标（2026-11-18，用户报「拖不准」）

两个原因叠在一起：

1. **旧判据对同一行的卡也用 y**。「某卡中线以下就 +1」在单行网格里意味着鼠标一旦
   越过该行中线，**整行每张卡都算"排在它后面"**，落点直接跳到队尾。用户在 3 列墙
   上拖第 1 张卡、鼠标刚过中线，占位框就从第 2 格跳到第 3 格——正是截图里"幽灵已经
   在那张卡左边，占位框却在它右边"。
2. **探针用的是鼠标点**。抓取点落在卡片哪儿是随机的：抓左下角和抓右上角，同一个
   画面位置会得出不同落点。现在探针固定为**被拖卡片的中心**（`_update_drag` 里用
   `ghost.geometry().center()` 反算到布局坐标）。

`verify_drag_sort.py` 把旧判据留在测试里当对照：同一处探针，新 0 / 旧 2。

#### 切程序后不能留下幽灵（2026-11-18，用户报「残影」）

手写拖动依赖 `MouseMove` / `MouseButtonRelease` 回到被拖的卡片。Alt+Tab、截图
快捷键、锁屏都会让窗口失活，这两个事件**永远不来**，状态机停在半路：幽灵窗 + 虚线
占位框留在画面上，下一次按下时状态还是脏的。

`dnd.DragGuard` 给两条判据，任何一条成立就发 `aborted`：应用状态变成非 Active
（覆盖切程序 / 截图工具），以及定时检查左键是否已经松开（覆盖"在窗口外松手"）。
**三处宿主**（首页卡片墙、耗材页、设置-排序页的树）都接了它，收到后一律按取消收尾
（回到按下时的位置、不写盘）——中断那一刻幽灵可能已经停在画面外，落点不可信；这条路
和 ESC 共用一套语义。耗材页还多一步：拖动中只是内存重排，取消要把 `_drag_backup`
那份顺序摆回去，并清掉卡片自己的 `_press`
（否则下一次移动会按旧按下点判阈值，一挪就"凭空"又起拖）。设置页的树只在**松手**时才
移动项（拖动中只画幽灵行和落位线），所以清理本身就是取消。

**设置页的树为什么不用改落点**：它是单列纵向列表，`_drop_target` 用
`pos.y() > 目标行中线` 判断"插在它之后"——单列下这个判据是对的，主页那个 bug 只在
"同一行并排多张卡、y 判据对整行生效"时才出现。而且它的幽灵是**纵向以指针为中心**
（`pos.y - rect.height()/2`），视觉基准和判定基准是同一点，不存在主页那种"幽灵按抓取
偏移、判定却用鼠标点"的错位。它也是手写拖动（不是 Qt 原生 InternalMove，原生拖影和
落位线跟首页那套不一致），所以中断这一条同样要接看门狗。

验证在 `verify_card_style.py`（墙）与 `verify_consumables.py` 第 5c 组（耗材页），
`DragGuard` 本身的判据在 `verify_drag_sort.py`。

验证在 `verify_consumables.py` 第 5b / 5c 组：5b 用真鼠标事件确认按余量 / 按房间
下拖过阈值也不启动手势、不建幽灵、不改排序和盘上顺序（松手会被当点击，测试里临时
摘掉编辑弹窗，否则离屏下模态框会挂住脚本）；5c 在自定义模式下以**存储顺序**为基准
验证幽灵 / 实时落点 / 松手落盘，并先确保夹具至少两张卡——只有一张时"插到最前"是
恒真的假断言。

### 提醒：只有卡片配色 + 侧栏圆点

- 卡片按档位变色；侧栏「耗材」入口文字后面画两个计数圆点：**灰 = 轻提醒**、
  **红 = 重提醒**，0 的那档不画（一排 0 是噪声）。
- 圆点由页面算、主窗口转发（`counts_changed` → `SideNav.set_zone_badges`）：
  页面不认识 `SideNav`，也不需要知道圆点画在哪。
- **顶栏警告条、托盘气泡、跨阈值只提醒一次这些都不做**（2026-11-18 用户定）：
  轻重提示就以这两个圆点为准，将来可能把它们带到桌面挂件上——那也只是多一个
  显示位置，不需要新的提醒通道。别再从"要不要弹一下"那条路往回捡。

### 离线读数：右下角标更新时间（2026-11-18）

在线设备的读数每轮都在刷新，标个"刚刚"是废话；**只在离线设备上标**，让人知道
这个数还能不能信：

- 右下角一行小字，精确到天：`今天更新` / `3 天前更新` / `2 个月前更新`。
  判据在 `core/freshness.py` 的 `read_note()`，阈值 `OFFLINE_STALE_AFTER = 一天`
  （用户定：一天没更新就算不新鲜）。
- 超过一天换 `theme.WARNING` + DemiBold；一天以内的用 `text_mute`。时间戳在未来
  （设备时钟不准）当"今天"，没有时间戳（静态元数据本来就不带 `updateTime`）
  **不写"未知"**——那会被读成"出问题了"。
- 时间戳来自云端 `updateTime`（`DeviceState.stamps`，每个属性一份）。顺带修了一处
  会导致它丢失的地方：拓扑重建时 `stamps` 原先按卡片属性筛，而耗材属性不属于卡片，
  离线后就说不出读数有多旧了；现在整份继承。
- `BAR_BOTTOM` 因此从 14 提到 20，血条上移 6px 给这行字腾位置；空卡的加号不跟
  这个常量走（它没有血条，跟着上移会浮在半空）。

### 轮询：并入现有 3 秒 / 15 秒，不另开定时器

`Store.poll_refs()` 里除卡片用到的属性，还会补上 `prefs.consumables` 订阅的那几条。
原因很实际：耗材属性常常不在任何卡片上，只按 `_card_keys` 永远读不到，页面会
一直显示 `—`。**不另开低频轮询**是用户 2026-11-18 定的口径（与历史规划里
"按周变化、别塞主轮询"相反）。代价是每轮多一条 ref——同一台设备的属性在客户端
那边合并成一次请求，不是"多一台设备的轮询"。

### 设备不在了怎么办

设备被删 / 换了家庭之后，**配置保留、卡片照画**，副标题写「设备已不存在」。
不这么做的话这条监控项既看不见也点不进去，用户永远删不掉它。点开仍然能删除。
设备没了但卡还是空壳时同理（右上角「未设置」，名字写「空卡」）——两条路都得留着
删除入口。

验证：`scripts/verify_consumables.py`（模型 / 落盘 / 轮询 / 页面 / 像素 / 侧栏圆点 /
设备树 / 空卡与按家庭 / 属性可改与重名 / 离线读数时间 十组）。

## 监控页（2026-11-19）

多路摄像头同屏。**不是"把卡片墙 2×2 放大"**：卡片墙是按房间浏览设备，一张卡一件事；
监控页是同时看几路画面，左边选源、右边画面是两种不同的交互，混在一起会把"看画面"
变成"找卡片"。取流侧的改造（`prepare` / relay 多会话 / 上限怎么定）在
[camera.md](camera.md)「多路同屏」，这里只写界面。

### 五种预设，几何只有一张表

`ui/monitor_page.py` 的 `LAYOUT_SPECS`：`1x1` 单窗口 / `1x2` 左右两分 / `2x2` 四宫格 /
`1+2` 一大两小 / `1+5` 一大五小。"主"用**跨行跨列**表达：`1+5` 就是整块切 3×3，
主窗占左上 `(0,0,2,2)`、其余五格是右上 / 右中 / 底行三格（2026-11-19 按用户要求改成
参考项目那种画法，此前是"5 行 4 列 + 右列五个窄条"，小窗太细）。

**跨列改不了列宽**：`1+2` 的主窗占左列两行，但两列默认等分，主窗只会和小窗一样宽。
要 2:1 必须给预设补 `col_stretch=(2, 1)`（`row_stretch` 同理，缺省全 1）。所以加新预设
只是往表里加一行（必要时带一对拉伸比），页面代码不用动。

**换布局 / 拖到另一格：画面接续，不重新取流。** 和卡片墙 → 详情页 → 独立窗口同一个
机制（`PlaybackOwnership.replace_view`）：把 `QMediaPlayer` 整份交给新格子，RTSP 会话
不动，下一帧直接画上去。细节与"哪些情况要真停"在 [camera.md](camera.md)「多路同屏」。

**左侧选源栏是一张卡**（`QFrame#RailCard`，`card` 底色 + 1px 描边 + `RADIUS_CARD`）。
底色别用 `bg_soft`：深色下它和页面底只差一点点，围起来也看不出来。卡片里是
`QScrollArea`，item 高度固定 138，`RAIL_W = 缩略图 168 + 内边距 16 + 边框 2 + 20`
——最后那 20 是**给滚动条留的**：摄像头多到要滚时它要占 10px，不预留就会把缩略图挤窄。
滚动是 `QScrollArea` 自带的，不用额外代码；`verify_monitor_page.py` 第 9c 组用 11 台
假设备钉住"出滚动条 / 缩略图没被挤 / 滚到底看得到最后一项"。

不做"拖格子边界自由划格"（DD_Monitor_CE 有）：那要把几何存成 x/y/w/h、窗口一缩就要
重算比例；预设已经能表达主+小，代码少一个数量级。理由与参考对象见
`docs/reference/camera-wall-layout.md`。

右上角是「布局」下拉 + 「全部停止」；标题旁一句统计（`3 台摄像头 · 2 路在播 ·
1 台离线`）。标题位置仍是 `(28, 8)`，与耗材页、自动化页同一条线。

### 左侧选源：播过的那一帧，模糊，不取流

- 每项 = 缩略图（168×94）+ 名称 + `房间`（离线时红字 `房间 · 离线`）。
- 缩略图**不是实时画面**：`CameraView.snapshot` 每 2 秒给一张，`ui/thumbs.py` 降采样
  到 1/8 再放大当模糊，存 `<data>/cache/thumbs/<did>.jpg`。6 路同屏再叠 6 路实时缩略图
  等于解码翻倍、每台还多占一个观看位；而列表只需要"认出是哪台、能拖"。
- 没播过就画镜头剪影。缓存在 `cache/` 下，删了只是回到剪影。
- 只列**当前家庭**的摄像头（`is_camera` 判品类），灯、传感器不进来；空家庭给一句
  「这个家庭没有摄像头」。

### 拖动：拖到哪格就换哪路

`SourceItem` 自己实现按下 / 移动 / 松手（阈值 6 px），**不用 Qt 原生 DnD**——和卡片墙、
耗材页的拖动排序同一套理由：无边框窗口里松手丢事件时没有兜底，所以配 `DragGuard`
（切程序 / 左键已松开就按取消收尾），幽灵是缩略图的透明快照。

- 拖到格子上：那格高亮（accent 2px 边框），松手即分配并**自动开播**。
- **单击** = 放进第一个空格（都满了替换第一格）。已经在某格里的那台，再点不会把它
  搬来搬去。
- 一台设备只占一格：拖到新格子时，原来那格自动腾空（同一个 did 两格既浪费观看位，
  画面也完全一样）。
- 每格右上角 `×` 清空（hover 才出现）；双击放大到独占整块，再双击还原。

### 播放：进页面只预热，点播放才取流

- `showEvent` → `CameraService.prepare()` 把全家的摄像头源**一次性**登记进 go2rtc，
  再把每格的 RTSP 地址在子线程里要到手（`prefetch_urls`）。不能每格各加一条源——改
  配置要重启 go2rtc，重启会把正在播的流全掐断（`camera.md`「多路同屏」）。
- **进页面不自动播**（2026-11-19 用户定）：格子里放"上次那一帧的模糊图 + 播放键"，
  点了才建立 RTSP 会话。一进页面就 6 路齐解，风扇会先响起来。
- 封面就是左侧列表那张缩略图（同一份存档，480×270 存、168×94 画）：播放中每 10 秒
  刷一次，停播 / 换布局 / 离开页面前把**最后一帧**存一次，落在 `cache/thumbs/`，
  所以重启程序后仍然有（细节在 `camera.md`「多路同屏」）。
- 拖进格子 / 点播放键都会立刻开播；地址若是预热过的那条，`_start` 直接 `claim + play`，
  不再走一遍取址。2026-11-19 用户实测（体感，没掐表）：等预热完成后点播放，出画约从
  3 秒降到 2 秒；剩下的基本是连流 + 等关键帧，预热管不到那一段。
- `hideEvent` / 离开页面 → `playbacks().release_surface("monitor")` **全停并归还
  观看位**。看不见的画面继续解码只是白烧 CPU。
- 取址在后台线程（每格一条），主线程用 80 ms 轮询收结果，与卡片墙同一个模式。
- **局域网失败只在取址阶段回落远程一次**，不做首帧后的 9 秒看门狗：6 路各自看门狗
  互相打断的复杂度不值。失败就在格子里写原因，用户点播放键重试。
- 同一台设备在详情页打开时，`PlaybackOwnership` 只腾出监控页**那一格**，其余路继续播。

### 上限与仲裁

最多 6 格（`PlaybackOwnership.MONITOR_MAX`，与 `1+5` 的格数同一个数）：每路软解约
40% 单核，6 路已经 ~2.4 核。`PlaybackOwnership` 只对 `monitor` 面开多槽，卡片墙 /
详情页 / 独立窗口仍是单槽——那些地方到处是"当前只有一路"的假设，放开会让"滚出视野
就停""暂停占着观看位"这类判断从永远成立变成偶尔不成立。

验证：`scripts/verify_monitor_page.py`（布局几何 / 落盘 / 选源 / 换布局 / 单击与清空 /
离线提示 / 放大 / 多路仲裁 / 缩略图 / 标题对齐 / 不自动播 / 停止后换布局 / 封面节流 /
预热地址 十四组）。

还没做的：逐路音量与画质（`camera.md` 已明确不做画质切换）、格子边界拖动、
圆环式的"路数总览"。远程多路只测了协议与端口，没在异地网络下实跑。

**满配 6 路没被真机验证过**（2026-11-19 定）：作者手上的摄像头不足以铺满 `2x2`，
所以"六格同时出画是什么手感"没有数据——CPU、首帧争抢、选源栏滚动是否掉帧、封面刷新的
开销，全都只在单路下量过。上面那些上限与 40%/路的数字是**推算**，不是 6 路实测。写成
这样是为了别让后来的人把推算当结论：`verify_monitor_page.py` 用假设备能铺满 6 格、
能验仲裁与搬运，**验不了真实解码负载**。详细清单在 `camera.md`「多路同屏」末段。

## 设置页：七页、滚动与分类边界（2026-11-15，11-18 加「设备」）

设置窗左侧分类栏共 **7 页**：外观 / 排序 / 隐藏 / 设备 / 账号 / 常规 / 关于，
`self.pages` 是 `QStackedWidget`，切页只换索引（`verify_tree.py` 里按索引取页面，
**加页时那份断言要跟着改**，否则测的是隔壁页）。

- **外观 / 设备 / 账号 / 常规 / 关于五页各自套 `QScrollArea`**（`_scroll_page`）：
  外观页比窗口高（明暗两档 + 24 个背景色块 + 家庭标签预览），不滚动的话
  Qt 会把卡片压到低于最小高度，主题名、排列 / 激活样式两行会和下一块叠在一起
  （2026-11-15 用户两次截图）。滚动之后控件保持原生尺寸。
- **排序 / 隐藏两页不套**：里面的树自己就滚，再套一层会变成"滚动套滚动"。
- `widgetResizable=True` + 横向滚动条关闭：内层宽度跟着视口走（换行说明才对得齐），
  高度不足时补到视口高，所以账号页那颗"贴底"的「退出登录」仍落在最底部；
  内容真超了才出现纵向滚动条。
- 滚动容器 objectName 是 `SettingsScroll`（透明底 + 自绘滚动条），
  页面里不要再写死宽度或自己套滚动。
- `setMinimumSize` 只保证分类栏和最窄几行放得下，**页面高度不再靠窗口兜底**。

### 分页边界：外观管"长什么样"，设备管"怎么连设备"（2026-11-18）

摄像头「取流方式」原来挂在外观页最后一张卡，用户看着别扭（外观页管观感，局域网还是
远程是连接策略）。现在单开 **「设备」页**，页面自述写的是"决定程序怎么跟你的米家设备
打交道，和窗口长什么样无关"。**以后的设备级偏好（轮询节奏之类）都进这一页**，别再
塞回外观；「常规」页的自述是"程序自己的行为，和你的米家设备无关"，也别往里放设备项。


## 排序与隐藏设备

界面顺序不是云端顺序，而是"用户排过的在前，没排过的按云端顺序追加"——这样新增的
设备 / 房间不会被埋到看不见的地方。

- 设备顺序在首页拖动卡片调整（只在房间内，松手只写一次盘）；家庭、房间、快捷场景的
  顺序在「设置 → 排序」里拖，松手立即生效。排序页不再渲染设备层，分成「家庭 → 房间」
  与「家庭 → 快捷场景」两个互斥 tab，各自铺满卡片高度；拖动和首页卡片一样带幽灵行、
  落位线和上下边缘自动滚。「恢复默认」会清空家庭 / 房间顺序，并一并清掉各房间的设备顺序
- 「设置 → 隐藏」沿用排序页那套骨架：顶部同样是「家庭 → 房间 → 设备」与
  「家庭 → 快捷场景」两个互斥 tab，同一时间只显示一棵树、各自铺满卡片高度。
  开关**打开 = 显示、关闭 = 隐藏**（沿用原来的语义），设备行用 did、场景行用 scene_id
  落盘；房间 / 家庭行是整组操作，部分隐藏时停在中间。「全部恢复显示」也按 tab 分开，
  在设备页不会顺手清掉场景的隐藏。两棵树常驻，切 tab 只换索引，折叠状态和滚动位置不丢
- 顺序键全部用云端 `home_id` / `room_id`（`device_order` 的键是 `home_id + \x1f + room_id`），
  值仍是设备 did；改家庭名或房间名不会影响家庭 / 房间 / 房间内设备的顺序。`prefs.json`
  版本为 11，旧版按名字存的顺序直接丢弃，不迁移
- 家庭顺序同时决定顶部切换栏的排列；"上次看的是哪个家"单独记住
- **排列方式**（「设置 → 外观」）二选一：
  - `保持设定顺序`（默认）—— 位置永不变，切家庭时整排是静止的
  - `激活的排到最左` —— 当前家庭永远在第一个，切走时其余标签带 170ms 位移动画平移
  - 注意：这只影响**绘制顺序**，`prefs.json` 里存的仍是用户拖出来的那一份，
    否则切一次家庭就把排序改一次
- 隐藏是独立偏好，设备和场景各存一份（设备用 did、场景用 scene_id）：设备收进每个
  家庭末尾的「已隐藏设备」分组，卡片右键即可切换；场景不进这个分组。隐藏只影响首页
  怎么排，轮询和控制都还在（点进详情页一样能用）
- **「已隐藏设备」可以整块收起**：点标题行（disclosure 三角 **紧跟在标题后面**，
  展开 ▼ / 收起 ▶，然后是常驻的「N 台」），卡片流整体隐掉，只剩 38px 的标题行——
  实测一组 21 台设备从 746px 压到 38px。
  - 三角放在标题旁边而不是分区最右边：隔着大半行空白的箭头没人会去点，
    「能点」这件事得贴着标题才看得出来。整行都可点，不要求精确命中三角
  - 台数**展开时也在**：一眼知道这一组有多少东西；不再提示「可在设置里恢复」，
    因为这组里右键就能取消隐藏，那句话只会把人往设置页支
  - 只有 `RoomView.kind == "hidden"` 的分区可折叠。普通房间的标题行保持
    `WA_TransparentForMouseEvents`，点它不会误收掉一整个房间
  - 收起态进 `prefs.hidden_collapsed`，切主题 / 切家庭 / 刷新重建墙之后仍是收起的
  - **搜索会临时展开**：命中项可能就在收起的那组里，否则"搜到了却看不见"。
    这个展开不写偏好，清空搜索后回到用户自己选的状态
- **隐藏分组内部再按房间分一层**（如「客厅 · 3 台」）：智能开关 / 音箱这类设备
  在不同房间里名字一模一样，平铺在一张流里根本认不出哪个是哪个。分组顺序沿用
  这一组自己的排序（首现顺序），只有一个房间时不分组——多一行标题纯属噪音。
  搜索时没有命中项的房间整块消失，不留孤零零的小标题。

落盘在 `<data>/prefs.json`（Windows 是 `%LOCALAPPDATA%\MiHomePanel\prefs.json`）。
删掉它等于全部恢复默认，不影响登录和缓存。

### 拖动快照：四角要透明，**容器也不能铺底**（2026-11-13，两轮才修对）

拖动排序时跟手的那张"幽灵卡"是卡片的一张透明快照，贴在墙上当浮层。

**第一轮（只治了一半）**：先 `card.grab()` 拿位图，再用 mask 图 + `CompositionMode_DestinationIn`
把圆角以外抠掉。四角 alpha 确实变成 0 了，验证也全绿 —— 但真机上**还是四块黑角**，
而且弧线边缘有一圈白毛边。两个原因叠在一起：

1. 快照贴在一个 `QLabel` 上。`QLabel` 是普通子控件，**绘制前 Qt 会先按调色板把它的
   矩形铺一遍**（离屏 `#EFEFEF`，深色主题下近黑）。抠掉的那几个像素露出的是这层底色，
   不是墙 —— 所以 alpha=0 一点用都没有；
2. 卡片自绘的矩形有 0.5px 内缩（`self.rect().adjusted(0.5, 0.5, -0.5, -0.5)`），
   `grab()` 时这圈是被**不透明底色**填过的；即使 mask 抠得再准，弧线上那几像素也已经是
   `卡片色×α + 底色×(1-α)`，再抠一次只会得到一圈更暗/更亮的描边加明显阶梯。

**现在的做法**（`wall.rounded_shot` + `wall.DragGhost`）：

- `rounded_shot` 不抓图，改成**先备一张透明画布、用圆角路径裁好、再让卡片往上画**：
  ```python
  painter.setClipPath(圆角路径)
  widget.render(painter, QPoint(0, 0), QRegion(),
                QWidget.RenderFlags(QWidget.DrawChildren))   # 关键：不带 DrawWindowBackground
  ```
  `DrawWindowBackground` 那面旗默认是开的，它会按调色板铺底 —— 就是白毛边的来源。
- 容器换成 `DragGhost(QWidget)`：`WA_TranslucentBackground` + `WA_NoSystemBackground`，
  `paintEvent` 里只 `drawPixmap`。四角露出的是**下面已经画好的墙**（`DragGhost.pixmap()`
  是给验证脚本读的，别按 QLabel 的接口想它）。

验证分三层（`scripts/verify_card_style.py` 第 8 组，共 16 项）：

- pixmap 本身：四角 alpha = 0、中心 255、角外 2px 也干净、弧内侧没多抠；
- **容器**：把快照铺到红底上 `render`，四角必须还是红的、中心是卡片色；同一张 pixmap
  装进 `QLabel` 反向证明四角会被铺成 `#EFEFEF`（这条才是用户看到的那个 bug）；
- 弧线上不许出现近白色（`min(r,g,b) > 200` 且 0 < alpha < 255）的毛边像素。

外加一条真实起拖的用例：`_begin_drag` 之后从 `ghost.pixmap()` 读四角，
再 `_finish_drag(commit=False)` 确认快照已销毁。

> 直接调 `wall._begin_drag()` 而不先摆好 `_drag_card / _drag_section / _drag_origin`，
> 会让 `_cancel_drag()` ↔ `_finish_drag()` 互递归（生产路径不可达，写测试要照"按下"
> 那一步摆一遍）。

### 一处刻意不做：房间标题的批量按钮

房间标题右侧**不放**「全开 / 全关」这类批量按钮：一个房间的品类太杂（摄像头、路由器、
净化器和灯混在一起），一刀切没有意义；要一键控制走顶部的场景栏，场景的语义是用户
自己定的。这条不是"还没做"，是决定不做。

## 设备配置重置：强制刷新与重置

设备卡片的右键菜单固定五项：**打开详情 / 卡片样式 / 强制刷新 / 重置设备配置 / 隐藏设备**。
两项新入口都只发信号（`capability_refresh_requested` / `device_reset_requested`），
由主窗口统一弹窗和执行——墙面不直接改偏好，也不直接发请求。

- **强制刷新**：清掉这台设备能力账本里「已确认不支持」的记录，**并立刻重查它全部
  可读属性**（不是只查卡片属性，也不等下一轮 3 秒轮询）。不改任何本地偏好，所以
  **不弹确认**；结果是**主窗口内的浮层**（`ui/inline_toast.py` 的 `InlineToast`，
  由 `speaker_bar.notice` 统一调用）。视觉**与极客版登录码那条提示（`tooltip.toast_top`）
  同一套参数**：10px 圆角、左侧 4px 圆点（成功绿 / 失败红，`theme.ACCENT_GREEN` /
  `theme.DANGER`）、13px 常规字重、18×12 内边距、最宽 460、最小高 46；配色参照
  **顶部警告条 `AlertBar`**——底色把状态色按 9%（深色 16%）混进卡面色、1px 描边按
  38%（深色 52%）混，状态色只用在圆点上；**没有图标、没有阴影、没有淡出动画**——
  极客版那条也没有，不保留多余元素。状态语义**只有 `ok` / `fail` 两档，没有 `info`**：
  `InlineToast.show_message` 与 `tooltip.toast_top` 都只认这两个值，未知值一律按
  `fail` 画红点——宁可红得显眼，也别把一条失败提示静默画成绿点。文字始终用主文字色。
  **垂直贴右栏内容区顶部 +12px、水平按右栏宽度居中**（左右各留 28px，与警告条同一
  落点、同一条中线；右栏顶部不随说话条显隐变化，功能区页面藏掉说话条时它不动）。窗口 resize 时若还在显示就
  跟着重新居中，内容区过窄时按内边距夹住、不越出窗口；
  **约 3 秒后直接消失**，不受鼠标移动 / 悬停 / 焦点影响，期间点击只收起提示、
  不穿透到底下的卡片；同一时间只有一条，后到的替换先到的并重新计时。
  **不要换回 `tooltip` 的悬停气泡**——那和悬停提示共用一个窗口，鼠标划过设备卡片
  就会把它一起收掉。也**没有 `tooltip.toast()` 这条通道了**（2026-11-15 删除），
  主窗口里只留 `InlineToast` 一条提示路径；设备卡片的悬停解释仍走
  `tooltip.watch(卡片, 文案)`，那是"指着才出现"的气泡，和这条主动提示不是一回事。
  界面文案**只说读到了多少项**：有属性读到就是「已刷新 N 项属性」，**不报没读到的
  条数，也不出现"失败 / 未读到 / 无响应"**；一项都没读到才说「设备暂时无响应，
  稍后会自动重试」，点明会自动重试、不用反复点。未读到的条数与原因只写控制台日志
  （`[caps] …`），清掉的账本条数同样只进日志。
- **重置设备配置**：清 **能力账本 + 卡片样式 + 隐藏状态 + 房间内排序**。二次确认
  逐项列出四类条数；如果这台设备当前是隐藏的，额外写明"隐藏状态清除后，该设备会
  重新出现在卡片墙原位置"。底部固定一句"不影响米家 App 里的设备、场景与自动化，
  也不影响登录状态"。完成后同样用上面那个窗口内浮层回报一句
  「已重置“设备名”的配置」，不再罗列清了哪几类。
- **已隐藏分组**：首页末尾「已隐藏设备」里的卡片和普通卡片走同一个 `_on_card_menu`，
  右键同样能到这两项；搜索态、空房间里的卡片也一样。没有"只在卡片墙生效"的分支。
- **全部重置**：入口在设置页账号页新增的「设备配置」板块（本地配置行右侧的
  「全部重置」），与单设备同一口径，确认窗额外给出"有本地配置的设备 N 台"以及
  卡片样式 / 隐藏 / 排序 / 能力缓存各自的条数。成功后按钮变「已重置」并禁用，
  直到重新打开设置页。

**不变量**：三处入口都只动本机文件（`prefs.json` / `capabilities.json`），
不写云端、不动 `auth.json`；重置隐藏状态后排序记录不存在，设备按云端顺序回到
原房间——这就是"回到卡片墙原位置"的实现方式。
