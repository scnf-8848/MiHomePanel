## 电脑自动化：四层窗口（2026-11-13 落地）

### 分层：core 里有一半是纯逻辑、一半是 Qt 适配层

| 文件 | 职责 | 能不能离线 import |
| --- | --- | --- |
| `rules.py` | `Rule` / `Condition` / `Action` / `RuleSet`，校验、`rules.json` 原子写、热键去重；**两种动作**（`device_action` / `delay`） | ✅ |
| `action_catalog.py` | 功能白名单（四功能）+ 每项入参元数据、设备可用性两道判据、参数清洗唯一入口 `clean_values()`、按家庭筛候选 | ✅ |
| `hotkeys.py` | 组合键规范串 ↔ Win32 `mods/vk`，保留键拦截，`MOD_NOREPEAT` 常量 | ✅ |
| `pc_state.py` | 纯 `ctypes` 快照 + 条件求值（6 类），**「不可用 ≠ 不成立」** | ✅ |
| `engine.py` | 纯逻辑：条件、冷静期、动作队列、重入、日志；`run` / `call_later` 外部注入；**提交即下一步、失败不拦后续** | ✅ |
| `logbook.py` | 触发日志的中文结果名、五列、全文与筛选 / 查找，以及按 `run` 批次把一次触发折成一行（`group_entries`） | ✅ |
| `hotkeys_win.py` | `RegisterHotKey` + `WM_HOTKEY` 原生事件过滤器 | ❌ 依赖 PySide6 |
| `service.py` | 常驻 `AutomationService`：串起上面全部 + `Channel` + 成员 `QTimer`；`_run` 在这里做找设备 → 查功能 → 查坐标 → 清洗 → 拼 `in` → 交给收发器 | ❌ 依赖 PySide6 |

`channel.py`（`core/` 下，不在 `automation/` 里）是**云端请求的收发口**：`post()` 发完
就返回、回执由读线程异步带回来，见下面「发送链路」。它只 import `mijiaAPI` 与标准库，
不依赖 Qt，用假连接离线验（`scripts/verify_channel.py`）。

action 名字 → `siid/aiid` 与入参顺序在 `core/miot_action.py`（`core/` 下、不在
`automation/` 里，顶栏指令条 / 中枢发送 / 动作目录三处共用），纯逻辑、可离线 import。

`core/automation/__init__.py` **只导出上面那六个纯逻辑模块**。离线验证脚本一律从包入口
import；一旦把 `service.py` / `hotkeys_win.py` 也塞进 `__init__`，`verify_automation_rules.py`
就会要求装 PySide6 才能跑，等于把纯逻辑测试绑死在 GUI 环境上。`service.py` 和
`hotkeys_win.py` 放在 `core/` 下只是因为它们不画界面，别按目录名误判成"core 无 Qt"。

### 数据与生命周期

- `<data>/rules.json` 是**唯一真相**；键位在每条规则的 `triggers[]` 里（v3），
  **没有 `hotkeys.json`**。`RuleSet` 用 `.tmp` + `os.replace` 原子写；**删除标记也
  落盘**（见「回收站：软删除」）。热键冲突、注册状态、冷静期表、触发日志
  **全只在内存**，重启不残留（日志上限 `max_log=500`）。
- 状态必须挂 `MainWindow` 上**常驻**的 `AutomationService`：`exec_with_dim_click()`
  关窗会 `deleteLater()` 销毁对话框，冷却表 / 注册表挂在 `AutomationListDialog` 上
  会随关窗蒸发。页面只持有一份「草稿」`Rule`，点「保存」才写回 `RuleSet` 并
  `service.sync()`；`sync()` 同时重算热键注册表。
- `MainWindow.start()` 调 `automation.start()` 注册热键，`shutdown()` 先
  `automation.close()`（撤注册 + 丢弃未跑完的动作队列）再停 worker。
- 关自动化页**不补** `_apply_theme()`（11-12 关窗闪烁的根因，见「交互约定：点压暗区
  关闭子窗口」）；录制态按 Esc / 点遮罩只取消录制，不走 `reject()`。

代码分支。**删掉的分支**（再遇到旧文件就按默认值处理，不做转换）：

**保留并说明原因的**：

- **旧动作不保留兼容**：本机只有一条测试规则，用一次性脚本
  `scripts/migrate_actions_v4.py` 平移（跑前把 `rules.json` 复制成 `.bak-<时间戳>`，

  留着也只是"看着能读、执行时找不到设备"。

- `autostart.py` 的注册表引号变体、`relay.py` 的旧版 API 导入回退：是 Windows /
  上游库的差异，不是本程序的数据迁移。

### 三层防重与动作队列

`MOD_NOREPEAT (0x4000)` 内置在 `RegisterHotKey` 里、不给用户配不展示；规则级
`cooldown_ms` 默认 1000 ms（`0` = 关），从「触发被接受」起算；上一串动作没跑完又来
一次 → **丢弃 + 记 `reentry` 日志**，不排队。三种拦截（`cooldown` / `reentry` / 条件不成立）
都会落一条 `LogEntry`，**绝不静默**（"按了没反应"会被当成程序坏了）。延迟用
`service` 上的**成员 `QTimer`** 串队列，`engine` 只调注入的 `call_later`。

**上面三层挡不住"同一条消息被 Qt 分发两次"（11-14 实测）**：Windows 上
`nativeEventFilter` 对**一条** `WM_HOTKEY` 会被调 **两次**（PySide6 6.12 / Win11 实测：
`wParam` 相同、两次 `eventType` 都是 `windows_generic_MSG`、间隔 < 1 ms）。不去重的话
一次按键跑两遍规则，第二遍必然撞进 1 s 冷静期 —— 日志里就是那条莫名其妙的
「冷静期阻止，剩余 1 秒」，看着像"按一下键自己触发了两次"（用户 11-14 实测反馈）。

`hotkeys_win._HotkeyFilter` 的做法是**按 hotkey id 记时间戳**的 50 ms 窗口
（`_DEDUP_SECONDS`），只认第一次：

* **不能靠 `event_type` 过滤** —— 实测两次都是同一个类型；
* **不能只记"最后一条"** —— A→B→A 时第二个 A 会漏过去，所以用 `dict[id, monotonic]`；
* 50 ms 的余量足够（两次分发 < 1 ms），又不会误伤真人连按（一次完整按下 + 抬起
  就要 60~80 ms）。

`single_instance._ActivateFilter` 有同样的双分发，但它的回调只是把窗口叫到前台，
重复执行无副作用，故未改（别再照抄它去写新的过滤器）。

**11-14 定案：动作之间是顺序关系，不是条件链。** 从前每步都要等云端完整往返才走下一步
——「唤醒」让音箱进聆听、云端要等设备回执，这一步好几秒，后面的动作全被堵着（用户实测
「唤醒 → 发虚拟事件」中间有明显延迟，而且那个延迟不是引擎在 `sleep`）。现在的语义：

* **提交即下一步**：`_step` 调完 `run(act, done)` **立刻**推进到下一条动作，`done`
  不参与推进队列，只在失败时补一条日志；
* **失败不拦后续**：某一步失败（没发出去 / 回执报错）只记 `FAILED`，后面的动作照发
  ——和米家自动化一致；
* 未知动作（不在白名单）记一条「已跳过」后**继续**，不停队列；
* 整串发完就释放 `_running`，**不等回执**。回执晚到只会再补一条 `FAILED` 日志，不动
  已经写下的那些 `DONE` 条目。

引擎只有**两个出口**，全是外部注入的回调，纯逻辑层不许知道设备长什么样：

| 出口 | 签名 | 谁实现 |
| --- | --- | --- |
| `run(action, done)` | 把一条 `device_action` 原样交给通道（did / action 名 / 清洗后的 args） | `service._run`（找设备 → 查功能 → 查坐标 → 拼 `in` → `_post`，再按 `transport` 分叉到 `_post_serial` 或 `Channel.post`） |
| `call_later(ms, fn)` | 延迟 | `service._call_later`（成员 `QTimer`） |

**一个出口就够**：从前 `emit` / `say` 两个出口逼着引擎认识"这是发事件还是念句子"，
而 `device_action` 只是"对哪台设备做什么"，引擎不必也无权判断。

`done(error)` 的语义按**什么时候被调**分两种——这正是日志文案的依据：

| 调用的时机 | 含义 | 日志 |
| --- | --- | --- |
| `run` 里**同步**调（`sent` 还没置位） | 一个字都没发出去（找不到设备 / 离线 / 没这功能 / 参数空 / 建连失败） | 「…未成功（没发出去）」 |
| 回执回来后**异步**调 | 发到了云端，云端或设备报错 | 「…未成功（回执报错）」 |
| 一直不调 | 成功，或 `UNCONFIRMED`（发出去了、设备没回执，**不算失败**） | 无 |

`run` 不注入时**明确失败**（`_no_run` → 「没有配置执行通道」）而不是静默跳过——
否则界面上看着链路"成功"，实际一件事都没做。两个出口都做了 try/except：通道抛异常
也要收尾，不然规则会永久卡在"运行中"。

### 两条云端通道：使用范围与差异（2026-11-14 定案）

程序里有**两条**发云端请求的路，不是一套。分工是**按调用方要不要拿返回值**切的，
不是按"新旧"切的——**别再往 `Channel` 上搬**，除非那个调用方真的不需要结果。

自动化动作是唯一两条都能走的调用方，**当前定案走 A（`serial`）**：11-14 22:0x 用户
实测确认，他先前报的"动作之间有明显延迟"**不是本程序内部排队**，而是 `wake-up` 让音箱
进入聆听态、之后到音箱的指令要等聆听结束——设备侧的顺序，换哪条通道都一样。B 那套
代码完整保留但**默认不启用**（实验性），切法与判据见本节末尾。

| | **A. 单线程同步**（默认，绝大多数） | **B. 收发分离**（`Channel`，实验性、仅自动化动作） |
| --- | --- | --- |
| 实现 | `jobs.SerialWorker`（**一条**线程）+ `Client._lock` + `requests.Session` | `core/channel.py`：1 条发送线程 + 4 条读线程，`http.client` 裸连接 |
| 调用形状 | `worker.submit(fn)`，结果从回调拿 | `channel.post(uri, data, on_reply=...)`，**提交立刻返回** |
| 阻塞谁 | **排在队列里**：前一条不返回，后一条连发都发不出去 | **不阻塞**：只写 socket，几毫秒一条；回执异步回来 |
| 连接 | `requests.Session` 复用（keep-alive） | 每条请求**独占一条连接** + `Connection: close`（不等响应不能复用，否则响应会串） |
| 超时 | 一次同步调用一个 `timeout`（连不上和没回执分不开） | 建连 6 s / 等回执 20 s **分开**，于是"没发出去"和"发出去了没等到"能区分 |
| 失败判据 | 抛异常 / 返回非 0 → 一律失败 | `FAILED(-2)` 立刻（没发出去）/ `UNCONFIRMED(-3)` 当成功（设备不回执）/ 云端码原样带回 |
| 顺序 | 严格 FIFO（一条队列） | 发送严格 FIFO（**一条**发送线程），回执乱序回来 |
| 走它的调用方 | 3 秒轮询读（一次 130 条属性）、写属性 `prop/set`（卡片 / 详情页 / 开关）、场景、顶栏文本指令条、摄像头跨网授权（`locked()` 借锁）、登录、**自动化动作（当前）** | 空（代码保留，改一个常量才启用） |

**为什么不全搬**（三条都是用户 11-14 拍板"只有自动化用"的依据）：

* 轮询读**要拿返回值**才能更新 130 个属性、才能算健康度；写属性要比对目标值决定
  乐观值回不回滚、失败要不要提示；指令条要把错误码当场报在气泡里。这些都是
  "同步等结果"的语义，搬到异步通道等于把回调套回调。
* 轮询是**一条请求批量读 130 条**，A 通道一次往返就够；走 B 通道会变成每条一连接，
  每 3 秒多一次 TLS 握手，纯亏。
* B 通道每条请求一次新握手（`N` 个动作约多 `N×30~80 ms`，**估算，未实测**）。
  动作数少、一次几个，这点开销换"不互相堵"划算；轮询这种高频固定节奏不划算。

**两条路不共享连接，但共享协议**：签名 / 加解密都调 `mijiaAPI.miutils` 的同一套
（`gen_nonce` / `get_signed_nonce` / `generate_enc_params` / `decrypt`），Cookie 都读
`api.session.headers` 里 `_init_session` 拼好的那串。**不要为了 B 通道另写一套签名**，
上游改了协议这里要能一起坏、一起修。

**新增一个云端调用时怎么选**：

1. 调用方需要返回值（读属性、写确认、要报错到界面）→ 走 A（`worker.submit`）。
2. 只是"发一条命令出去、失败再告诉我" → 走 B（`channel.post`）。
3. 拿不准就选 A：同步语义不会错，只是慢；B 通道的正确性依赖"调用方写了 `on_reply`
   且 `service` 的 16 ms `drain` 定时器活着"，别让新的调用方半路用它。

**实测结论：`wake-up` 的"延迟"不在收发机制里（2026-11-14 22:0x 定案）**

用户最初报的很具体：③ 两条「音箱-唤醒 → 中枢发虚拟事件」，按下热键后虚拟事件明显晚到，
"像是等了唤醒的某个回应"。当时的诊断是"引擎串行等回执 + `SerialWorker` 单线程"，
于是做了 B 通道。**但他切回 A 复测后确认：真因是 `wake-up` 这个动作本身**——它让音箱
进入**聆听态**，之后收到的指令（尤其是到音箱的）会**等到聆听结束才执行**。这条链在
设备 / 云端侧，**换哪条通道都一样**，因为通道只决定"本程序什么时候把请求发出去"。

三条推论，写下来免得以后又重新怀疑一遍收发机制：

1. **A 通道没被堵**：A 下第二条动作确实要等第一条 HTTP 完整返回才出网，复测却看不出
   明显间隔 → 说明 `wake-up` 那次 HTTP 往返本身不长（云端回的是"已下发"，不等音箱应答完）。
2. **B 通道救不了这类延迟**：`post()` 只让"发"不阻塞；音箱在聆听态时，云端照样把后续
   音箱指令排到聆听结束。**别拿 B 去治"某个动作本身慢"。**
3. **编排上该绕开它**：需要"唤醒 + 后续动作"时，要么把唤醒**放到最后一步**（反正它
   之后没有别的动作等着），要么用别的动作替代。这是编排问题，不是代码问题。

**开关（B 保留但默认关闭）**：

| 切哪条 | 怎么切 |
| --- | --- |
| 常量 | `core/automation/service.py` 的 `DEFAULT_TRANSPORT = "serial"` ↔ `"channel"` |
| 环境变量 | `MIHOME_AUTOMATION_TRANSPORT=serial` / `channel`（**优先于常量**，不用改代码） |
| 单次调用 | `AutomationService(..., transport="channel")`（只有验证脚本这么用） |

判据只有一条：`transport != "channel"` 就走 `_post_serial`（`worker.submit` +
`Client.run_action`——v3 就在用、真机验过的同步路径）；等于 `"channel"` 才走 `_post`。
`serial` 模式下 `channel` 照旧建好（5 条 daemon 线程阻塞在队列上，不发包、不占 CPU），
但 **drain 定时器不启动**——切回去只需改一个词。

**两条路的日志文案与失败语义完全一样**（done 语义 / 日志文案 / 失败分类 / `refreshes`
三轮回读），所以真要做 A/B 时可以直接看同一条规则两次运行的时间线。差别只在**第二条
真正出网的时刻**：serial 要等第一条 HTTP 返回，channel 是提交完就发。另外注意引擎这
一版**已经不等待**（`_step` 提交即下一步），所以 serial 模式下"日志里的动作间隔"和
"真正出网的间隔"是两回事——**判断 A/B 只能看设备的物理反应**。

### 发送链路：设备动作怎么发（当前 A，B 为备选）

自动化的设备动作**现在走 A**（`_post_serial` → `worker.submit` → `Client.run_action`），
下面这节讲的是 **B 通道**（`core/channel.py`）的实现——保留着，改一个常量就启用。
两边的**发送前判据完全一样**，差别只在"由谁发出、发完等不等回执"。

按 action 名从 `DeviceSpec` 里查 `siid/aiid`（`core/miot_action.py`），**不写死
`4/1`**——同一能力跨型号方法号不同；中枢网关同样按能力去探，不在型号白名单里硬编码。
请求体有两层壳，缺一层就是 `invalid request`：

* **外层固定 `{"params": ...}`**：`/miotspec/*` 全是这个形状（上游 `apis.py` 里
  `run_action` / `get_prop` 都是 `self._request(uri, {"params": param})`）。11-14 实测
  踩过：直接把 `{"did","siid","aiid"}` 当请求体发，**唤醒和虚拟事件全都**报
  `invalid request`——错的是外壳，所以跟具体动作无关，换先后顺序也一样。
  **走 A 时不用管这层**（`Client.run_action` 上游自己包）；手拼请求体的 B 通道必须包。
* **内层**：设备动作的三个键是 `did/siid/aiid`，参数键是 **`in`**（`prop/set` 才是
  `value`，混用报 `-704220025`，看着像"设备不支持"），键的顺序照 spec 的入参顺序拼；
  无参动作**不发 `in` 键**（空列表也不行：那是"我带了零个参数"）。
* 这些判据**全在发送之前**做完，所以那一类失败是同步回调的。

**B 通道要解决的是"发"被堵，不是"某个动作慢"**：`jobs.SerialWorker` **只有一条线程**，
第一条 HTTP 不返回，第二条连发都发不出去。B 的做法是让"发出"本身不阻塞：

* `http.client` 的 `conn.request()` 内部是 `putrequest → putheader → endheaders →
  send`，**只写 socket、不读响应**，写完就返回（几毫秒）；
* **一条发送线程**按提交顺序逐条 `connect + request()`，顺序严格（比开一堆线程更符合
  "按顺序执行"）；
* **N 条读线程**（默认 4）跑 `getresponse()`，谁先回谁先读——唤醒卡 3 秒不会拖住后面
  动作的回执；
* 读线程是**池子不是固定槽**：读完一条就 `close()` 再回 `_read_q` 取下一条，所以
  "第 1 条归 0 号线程"这种绑定不存在。**动作数 > N 时 N 条并发读、其余的排队，
  谁读完谁接**——A 的回执一读完，那条线程立刻去接第 N+1 条。这不影响"发"：发送线程
  照旧一条不落地全发出去，只是第 N+1 条的回执要等有人空出来才被读。**4 是"同时
  几条回执在等"的上限，不是"一次最多发几个动作"的上限。**
  等回执的超时也从"有人开始读"算起（`settimeout` 作用于阻塞调用），所以排队的回执总
  等待可能超过 20 s——无所谓，我们要的是"有没有回音"。极端情况：一串 6 个动作里有
  4 个都是唤醒这种不回执的，它们的读线程要各占满 20 s 才放，第 5、6 条的回执（以及
  文本指令的全量回读）就跟着晚——`Channel(api, readers=N)` 收这个参数，真遇到再加；
* 每条请求**独占一条连接** + `Connection: close`（不等响应就不能复用，否则响应会串）；
* 结果进队列，主线程 16 ms 的 `QTimer` 调 `drain()` 执行回调，**读线程绝不碰 UI**；
* 签名 / 加解密复用 `mijiaAPI.miutils`（`gen_nonce` / `get_signed_nonce` /
  `generate_enc_params` / `decrypt`）；Cookie 直接用 `api.session.headers` 里
  `_init_session` 拼好的那串固定值（不需要 cookie jar）；`api_base_url` 从
  `api.api_base_url` 读，`ssecurity` 从 `auth_data` 读。

四类结果（`channel.SENT` / `FAILED` / `UNCONFIRMED` / 云端原码）：

| 码 | 含义 | 什么时候知道 | `_run` 怎么处理 |
| --- | --- | --- | --- |
| `0` `SENT` | 发出去了，云端回成功 | 收到回执 | `feat.refreshes` 时 `store.schedule_confirm()` |
| `-2` `FAILED` | **没发出去**（建连 / 写 socket 失败） | 立刻 | `done(reason)`，日志「没发出去」 |
| `-3` `UNCONFIRMED` | 发出去了但没等到回执 | 读超时（20 s）后 | **当成功**，`done("")`——命令已在路上 |
| 其它 | 云端错误码原样带回，附 `explain(code)` 的人话 | 收到回执 | `done(...)`，日志「回执报错」 |

`-2` 与 `-3` 必须分开：前者请求根本没到云端（该告警），后者到了只是没等到话（播报 /
唤醒这类设备压根不回执，报失败就是一堆假警报）。建连超时 6 s、等回执 20 s，两个数分开
设（`sock.settimeout` 放在 `request()` 之后，因为 `request()` 用的是建连那个超时）。
回执解析先按明文 `json.loads`，失败再按 RC4 密文 `decrypt(ssecurity, nonce, text)`
——**必须同一个 nonce**，所以它跟着连接一起传给读线程；`/miotspec/action` 的成功码
藏在 `result` 里（`{"code":0,"result":{"code":-704040005}}`），两层都要看。

**只有"效果落在别的设备上"的动作做全量回读**（`Feature.refreshes`，目前只有
`execute-text-directive`）：它可能去开别的灯，只有全量读看得到结果。唤醒 / 播报文字 /
发送虚拟事件都不改可读属性，回读只是同一批属性白读三遍，还占着串行队列给后面的动作
添堵。回读那串 1 / 2.5 / 4 秒是**单例 + 重置**：`main_window` 的 `_cmd_timer` 每次
`start()` 就把旧的顶掉，永不重叠；`confirm_full` 自己还有 1 s 去重
（`FULL_READ_MIN_GAP`，且 `_last_full_at` 也会被 3 秒 tick 写），所以第一个点约 1/3
概率被跳过——有意的，不是丢帧。

`Channel` **只服务动作类请求**，其余全部留在 A 通道（判据与理由见上面那张表）。
鉴权过期不做自动重登（`Client` 本身也不做）：云端会回 `-704010000` 之类的码，原样
带到日志里。

### 按钮：焦点只换颜色，尺寸一动不动（2026-11-13）

用户报的两个现象其实是**同一个根因**：鼠标点一下按钮 → 按钮拿到焦点 → `:focus` 的
`border: 2px solid accent` 画上去，而且**松手后还留着**。

1. "按下再松开，按钮维持按下的样子" —— 那个框不是按下态，是焦点态；
2. "按下时文字两侧被遮挡" —— `sizeHint` 是照**没焦点**的状态算的（Qt 的
   `SE_PushButtonContents` 也不随 `State_HasFocus` 变），而 `:focus` 把边框从 0 变成
   2px，内容区当场缩 4px。「编辑」正好 26px 宽，挤到 22px 就被裁掉了。回收站「回收站」
   按钮、`#Tool` 一圈都中招，所以看起来"几乎所有按钮"都有。

两条一起改：

- **焦点规则只写 `border-color`**；没有描边的按钮（`#RuleEdit` / `#RuleDelete` /
  `#Disclosure`）在常态就留 `border: 2px solid transparent` 占住那 2px。宽度永远不变
  → 文字永远不会被裁。实心按钮（`#Primary` / `#Ghost`）没有描边可用，焦点改成
  "提亮一档"；
- **焦点策略收成 `Qt.TabFocus`**（`automation_style.tab_focus_only(root)`，
  动态创建的按钮要在自己的构造函数里再设一次）：鼠标点击不再抢焦点，Tab 键照样能到。
  这才是"点完不留任何痕迹"的正解 —— 光改颜色的话，点完那个 accent 框还在。

顺手补齐 `:pressed`：按下要有一眼可见、松手就一定消失的反馈，别让焦点框兼职。

> 验证方式见 `scripts/verify_automation_ui.py` 第 13 组：用
> `style().subElementRect(SE_PushButtonContents, opt)` 量**有焦点 / 没焦点**的内容区，
> 断言两者相等；再用一份"旧写法"的 QSS 反向证明这个方法真能抓到 4px 的缩水
> （26 → 22）。只比 `sizeHint` 是抓不到的。

### 压在卡片上的小按钮：底色要从 `panel_bg` 起算

回收站深色主题的「还原」几乎看不见，不是配色丑，是**算错了底**：
`blend(p.bg, p.text, 0.12)` = `#292A2D`，而卡片底 `panel_bg` = `#28292C`，**1.01:1**。

### 回收站：软删除，不是 `remove()`

列表点「删除」= `RuleSet.trash()` 只打 `deleted` 标记（连同 `deleted_at` 一起落盘），
**不弹二次确认**，因为可还原；只有回收站里的「彻底删除」= `purge()` 才物理移除且弹确认。
`active()` / `get()`（默认）/ `enabled_keys()` / `rules_for()` / `set_enabled()` /
`update()` 全部跳过或拒绝 `deleted` 规则 —— **少过滤一处，删掉的规则还在注册热键**，
这是软删除最容易漏的坑。`purge()` 默认 `only_deleted=True`，避免误删在用规则。
`add()` 也要连回收站里的 id 一起查重，否则还原时撞出两条。
离线验证专门覆盖「已删规则不能被热键触发 / 不能被 `engine.test()` 触发」。
「彻底删除」原先是透明红字、权重比「还原」还低，现改**红色描边幽灵按钮** + 间距 10px。

### 独立日志窗：一次触发只占一行，动作记录折在下面

`core/automation/logbook.py` 是纯逻辑：中文结果名表、表格五列、全文（**必须含 `keys`**，
不然「刚才按的是 Ctrl+K」搜不到）、`matches()` / `filter_entries()` / `group_entries()`，
以及 `outcome_tone()` 三档语义（`FAIL_OUTCOMES` 真失败 / `NEUTRAL_OUTCOMES` 被拦下 /
其余正常）。`ui/automation_log.py` 只收集条件 + 画 `QTreeWidget`，默认 `rule_id=""`
即**跨全部规则**，时间正序的 `engine.log` 在表格里倒序显示（最新的在最上）。

**折叠模型（2026-11-14 用户提，同日落地；当日又按用户意见改过三处，见下）**：按几次键
就刷满一屏时，"哪几步属于哪一次触发"根本看不出来。现在 `LogEntry.run` 是**批次号**，
同一次触发的每条日志共用；日志窗把每一批折成一行：

| 概念 | 规则 |
| --- | --- |
| 批次号 | `规则id@触发毫秒-序号`（`engine._new_run()`）。**是字符串，不是内存计数器**——日志要落盘，从 1 数起的计数器重启就归零，昨天的第 3 次会和今天的第 3 次折进同一行 |
| 父行 | 批次里第一条 `FIRED` / `ELSE`（`HEAD_OUTCOMES`），不带子项的条目自己占一行 |
| 子行 | 同批次其余条目，缩进显示，**只留时刻 / 结果 / 说明**（规则和快捷键与父行重复，是噪音） |
| 拦截类 | `COOLDOWN` / `REENTRY` / `CONDITION` 的 `run == ""`——它们本身就是结论，没有"内部动作" |
| 默认状态 | **收起，且不记忆**（用户 11-14 定）：每次打开 / 每次换筛选都全部收起。记住的展开态会在"新日志插到顶部、行号整体下移"后挂到别的行上 |
| 父行结果列 | `触发 · 2 步（1 步失败）`。`steps` **不数**「执行完毕」那条总结（否则"共 3 步"下面只有 2 个动作）；有失败时结果列直接染 `DANGER`，**收起也看得出来** |

**展开按钮自己画**（`ui/automation_log.py:_LogTree.drawBranches`）：Qt 默认那枚三角由
当前 style 画，9px 宽、`text_soft` 色，浅色下压在白底上几乎看不出能点（用户 11-14 报
「太不明显」）。现在画成 accent 淡底 + 描边的圆角方块（18px）+ 一道 chevron，展开朝下、
收起朝右，悬停再提一档底色并把光标换成手型。三条实现约束：

* `indentation` 就是分支区宽度（`INDENT = 22`），按钮画在里面才点得着；子行按同样宽度
  再缩一级，正好把"这几步属于上面那次触发"画出来。
* **点击交给 Qt**（`setItemsExpandable`）：自己再判一次会和 Qt 各 toggle 一次，变成
  "点一下展开又被收回去"。
* 命中区**必须从分支区算**（`chip_rect()` 用 `QRect(0, y, INDENT, h)`）。拿
  `visualItemRect().left()` 去算会整体右移一格——鼠标在按钮上不算热点、在文字上反倒算。
* 选中行的分支区要在 `drawBranches` 里自己补 `accent_soft` 底色，否则左边缺一块。

**列宽全部自己管**（`_sync_widths()` + `_fit_last()`，2026-11-14 三次反馈 + 11-15 两次修订
后定）：**五列都是 `QHeaderView.Fixed`**，宽度全由代码给。两种做法都不能用：
`ResizeToContents` 会把子行缩进算进列宽、还只看当前展开的行；`Stretch` 会让最后一列
在**前面几列很宽时被压成省略号**（用户 11-15 00:2x 报："长规则名那一页，说明列被…截断"）。

口径：**列宽 = 当前这一页里（父行 + 子行一起算）最长的那段文字**，与展开哪几行无关，
所以展开 / 收起不挪位。五列都按内容给，「说明」再多一条规则（`_fit_last`）：
**内容短时撑满窗口**（右边不留空白）、**内容长时不压缩**（总宽超出视口就横向滚）。
窗口尺寸变化由 `_LogTree.resizeEvent` 回调重算（带重入保护），所以拉宽窗口它会跟着长。
实现要点：

* 子行在**时刻**列的左偏移是**两级缩进 `2 × INDENT`**，不是一级：`rootIsDecorated` 让
  父行自己也占掉一级（实测父行 `rect.left() = 22`、子行 `44`）。按一级算少 22px——父行
  完整、子行显示成 `11-14 23:0…`，很容易漏（第一版就这么错的）。
* 「结果」列子行也有内容，必须把两种行一起量，否则展开时它一变宽、右边的「说明」右偏。
* **表头也算内容**：快捷键列的内容常常只有 "F3"，不把表头"快捷键"算进去，表头会被裁成
  "快捷…"（用户 11-15 报）。所以 `widths` 的初值就是五个表头的文字宽度。
* 每列在"最长文字"之外再留 `_COL_PAD = 2*8 + 12`（QSS `::item` 左右 padding 各 8px +
  12px 余量），比 Qt `sizeHintForColumn` 宽 6px，不会出现省略号。
* 增量插入只量新来的那一行（`_note_entry`），**只增不减**；父行"步数"变长时
  `_refresh_summary` 也会再量一次。
* 时刻列用 `_TIME_SAMPLE`（最宽数字）打底，这一页恰好没有某一天也不会忽宽忽窄。
* **放不下就横向滚**（`reserve_scrollbar(lock_horizontal=False)`，一直是 `AsNeeded`）：
  长规则名 / 长说明会把列撑开，总宽超过窗口时出现横向滚动条——**不许压窄任何一列**。

**分页（2026-11-15 用户提，为列宽服务）**：`PAGE_ROWS = 50` 行/页，页脚是
`‹ 第 x / y 页 ›`。分页不是为了"看着方便"，而是**列宽要量文字**——不分页的话日志攒到
几千条，每次重载都要量上千段文字，迟早卡。现在一次最多量 50 行 × 每行几步。
代价是**每页列宽可能不同**，这正是用户要的"每页独立分配"。配套规则：

* 翻页 → `_reload(top=True)`：列宽重算、滚动条回顶、选中不恢复。
* 新日志到达时：在第 1 页走增量（满了把最后一行挤到下一页，本页仍 50 行）；**在旧页上
  只更新总数 / 页数，不动表格**——否则每来一条就把正在看的那页整体挤走一行。
* 换筛选 / 清空 / 重置 → 回到第 1 页（`_on_filter_changed`）。
* 只有一页时整组翻页控件 `setVisible(False)`：不占位置，状态文案也不用为了躲它而缩写。
* 状态条只剩「共 N 条 · 本页 M 行」：范围在下拉 / 「已筛选」chip 上，落盘路径在
  **tooltip** 里——720px 最小宽度下这一行还要放翻页、清空、日志文件、已筛选 chip。
* **「清空」**：走 `AutomationService.clear_log()`（内存 + 文件一起清），**弹一次确认**
  （不可恢复，和回收站「彻底删除」同一口径）。清完服务发 `log_cleared`，窗口据此重载。

**日志落盘（2026-11-14 用户提）**：`core/automation/logstore.py` + `<data>/automation_log.jsonl`。

| 决定 | 理由 |
| --- | --- |
| **JSONL（一行一条）**，不是 JSON 数组 | 日志只增不改：追加一行只要一次 `open(..., "a")`；数组得整份读出来改完再整份写回，每来一条就重写一遍全量历史 |
| 每条 append 都开关文件 | 程序被强杀 / 断电最多丢最后一行；攒在内存里批量落盘丢的是一整段 |
| 坏行跳过（`_entry()` 返回 `None`） | 崩溃留下的半行不该让整份历史读不回来。**先解析再截尾**：反过来的话末尾几行坏行会把要留的好行挤出窗口 |
| 上限三处同一个数 `MAX_ENTRIES = 500` | 内存 `max_log` / 文件 / 表格 `MAX_ROWS`。各写一个 500 迟早对不上 |
| 文件攒到**两倍**才裁（`TRIM_RATIO = 2`） | 每来一条就整份重写 500 行没必要；攒到 1000 行裁到 500，平均 500 条写一次盘。所以文件里实际留 500~1000 条，界面只显示最近 500 条 |
| 先 `.tmp` 再 `os.replace` | 同 `rules.json` / `prefs.json`：裁到一半断电不会留下半份文件 |
| 写失败**不抛、不提示** | 磁盘满 / 没权限不该让规则执行中断；界面上那条日志照常出现，只是重启后翻不到 |

接线全在 `AutomationService`：`logstore = LogStore(log_path)` → `engine.restore_log(logstore.load())`
（**不重放 `on_log`**，界面还没建）→ `_on_log()` 里先 `append` 再 `emit`；
`clear_log()` 必须内存和文件一起清（单清内存，下次启动 `restore_log` 又读回来）。
界面：状态条写「已写入 automation_log.jsonl，重启后仍在」，右侧「日志文件」按钮
`QDesktopServices.openUrl` 打开**所在文件夹**（双击 .jsonl 会拿记事本打开，用户要的
多半是"文件在哪、多大"）。

### 编辑窗布局：`ui/automation.py`

仿米家 App「创建自动化」四段式：① 触发（**目前一种触发源：键盘快捷键**，一行 = 类型
下拉 + 键帽 + 注册状态；录制、折叠的手动选键；**可以挂多条，OR 语义**；底部按钮与冷静期
同一行）、② 条件（AND / OR、可空、增删）、③ 动作（**两枚入口**：＋ 选择设备 / ＋ 延迟；
一行 = 设备 + 功能 + 该功能的参数，增删 + ↑↓ 调序）、④ 否则执行动作（**条件不成立时**
跑的另一串，结构整套复用 ③）。头部只剩「名称」一行：**启停归列表卡片**（编辑一次不该把
停用的规则悄悄打开），**冷静期按用户要求挪到①触发块最下面**。

**④ 否则执行动作（2026-11-14 用户定）**：结构**整套复用 ③**——同一款 `ActionRow`、
同样两枚「＋ 选择设备 / ＋ 延迟」、序号各自从 1 起（两段互不串位）。三条硬约束：

- **只有"条件不成立"走 ④**。动作执行失败（云端拒了、音箱离线）**不走**——那是故障，
  照旧记 `FAILED` 日志，并由主窗口弹系统通知（同一条规则 120 秒内只弹一次，明细留在
  日志窗里）。用户定过：失败用通知，不用 else 兜。
- **冷静期共用**。冷静期针对的是"触发动作"，不区分走哪条分支：条件不成立且真的跑了
  ④ 时，同样记 `_last_fired`、同样占 `_running`。否则连按会反复执行否则队列（一句
  "还没到点"能刷十遍）。**没有 ④ 时保持原样**：只记一条「条件不成立」，不算触发被
  接受，不占冷静期。
- **② 为空时不能加 ④**（没有"不成立"可言）：按钮置灰 + tooltip 说明原因。已经存在的
  ④ 动作**不清空**——用户删条件可能只是想换一个，不是要扔掉整段；真删光了还去保存，
  `validate_rule` 会拦下来，并把两条出路都写进错误条（加条件 / 清空这一段）。

落盘只在非空时写 `else_actions` 键，旧文件形状不变。日志 outcome 新增 `else`
（标签「否则分支」，按正常流程**染绿**——它真的执行了动作；琥珀色的「条件不成立」
仍然表示"按设计没执行"，两者别混）。

**① 允许多条触发（11-13 用户第十条）**：`Rule.triggers` 是 `list[Trigger]`，每条
`{type, keys}`，语义是 **OR**——任一触发命中就执行这条规则；条件、冷静期、动作队列
都不变，冷静期仍按**规则**算（同一个规则换另一个键按也会被同一次冷静期挡住）。

- **数据模型**：v3 起 `rules.json` 只写 `triggers[]`，不再写单个 `keys`。`Rule.keys`
  退成只读属性，回第一条键盘触发的键位，只给日志 / 旧卡片文案兜底。
- **旧规则兼容**：本机 `rules.json` 已用一次性脚本从 v2 规范成 v3（`keys` 摊成一条
  `keyboard` 触发，家庭 id 原样保留）；**代码里的转换分支已删**，再遇到旧 `keys` /
  `mode` / 家庭名归属只按当前字段读，不再迁移（见「一次性迁移清理」）。
- **注册与冲突**：`RuleSet.enabled_keys()` 把各规则的触发**摊平去重**后交给注册表；
  `rules_for()` 任一触发命中就返回该规则。同一个键被两条启用规则用到时**不阻止**
  （两条都会触发，这是既有语义），编辑窗在该行注册状态后面加一句「这个键也被
  「X」使用，按下会各触发一次」；停用规则不算冲突。同一规则里两条触发用同一个键
  会被 `validate_rule` 拦下。
- **编辑窗**：点①底部那枚「＋ 添加触发」加一行 `[- v]`；类型下拉目前只有空档「-」和
  「键盘快捷键」两项，**为以后增加其它触发源留位置**。每行右侧有 × 可单独删；删到
  0 行允许（视觉上是空态），但保存会被 `validate_rule` 拦：**「至少要有一个触发方式」**
  ——0 行等于永不触发，不能当"无触发规则"存下来。切离键盘类型会清空该行的键位
  （`_collect()` 只收 `value()`，不会把看不见的旧快捷键带进保存）。录制只认被点的
  那一行（`_recording_row`），多行互不串键；手动选键也收在每行内部。

**一条动作 = 设备 + 功能 + 该功能的参数**（11-14 用户重构：动作不再按"类型"分类，而是
"对哪台设备做什么"）。`TYPE` 只剩两档 `ACTION_TYPES = ("device_action", "delay")`，
"功能"的白名单在 `core/automation/action_catalog.py`，不在 `rules.py` 里。

**绝不存 siid/aiid**：同一份能力在型号之间方法号完全不同（`wake-up` 在 lx06 是 aiid 3、
在 oh2p / x6a 是 1；`play-text` 3 vs 1；`execute-text-directive` 5 vs 4），固件升级也可能
变。存 **action 名字 + 入参名**，执行时用 `core/miot_action.py` 现查坐标与入参顺序——
`speaker.py`（顶栏指令条）、中枢发送、动作目录三处共用这一份，别再各写一遍"按名字找
action"。

**白名单只有四功能**（`action_catalog.FEATURES`）：发送虚拟事件（中枢网关）、唤醒 /
播报文字 / 执行文本指令（小爱音箱）。一台小爱音箱的 spec 里有 11 个 action
（`play` / `pause` / `radio` / `stop-alarm` / `tv-switchon` …），全列出来比从前的四档
类型下拉还乱，而且大多与自动化无关；要放开就在 `FEATURES` 里加一行，别把过滤逻辑散进 UI。

**可用性要两道都对得上**（`action_catalog.action_for`）：

- 设备**少**了任何一项入参（**包括** `required=False` 的「静默」）→ 不显示这个功能。
  `required` 只决定"值能不能为空"，不决定"这台设备有没有这个槽"；
- 设备**多**了我们不认识的入参 → 也不显示（这个功能在没见过的固件上长胖了，参数会错位）；
- 有认不出的槽（piid 在服务里找不到名字）→ 同样不用。

宁可少一个功能，也不要"看着能用、点下去报参数个数不对"（`-704220025` 那种）。

**中文名以本地表为准，不读云端 `comment`**：`xiaomi-oh2p` 的 `play-text` 叫「播放文本」、
`xiaomi-lx06` 干脆没有 comment——同一件事在两台设备上显示两个名字比没名字更糟。云端只
提供"这台设备有没有这个能力"。

**参数清洗只有一个入口** `action_catalog.clean_values()`：界面校验、存盘校验、执行前清洗
共用一份，三处各写一遍迟早出现"界面能存、执行被拒"。`truncate=False` 用于存盘（超长报
错，**不静默截短**），执行前保留截断。文本类走 `speaker.clean` 的字符白名单，**事件名不
走**（用户自定义串，可能带下划线和括号，被白名单剔掉等于静默改事件名）。

**「＋ 选择设备」先弹窗、选中才加行**（`DevicePicker`）：动作的主语是设备，没有设备就
无从谈起，先加一行空的只会留下半成品。窗里列当前家庭能做事的那几台（中枢 + 音箱），
行文本 `名称　　房间[　离线]`，离线行**点不动**；搜索框按设备名 / 房间过滤，搜不到给空态
文案。取消就什么都不加。行内那份设备名是个**按钮**，点它重开同一个窗（换设备时尽量保留
已选功能）——不另做设备下拉，两套入口迟早不一致，而且设备一多下拉里放不下房间与在线
状态。

**无参功能收掉整列**（唤醒）：留一个灰着的输入框会被当成"这里该填点什么，只是坏了"。
直接让那一列不占位置，行短一截，反而说明了"没有参数"。

**家庭筛选按 id，不比显示名**：`action_catalog.collect(states, home)` 比 `node.home_id`
（`node.home` 是显示名，改个家庭名就全对不上），没挂家庭的设备算任何家庭可见；排序
`(不在线, 房间, 名字)`，在线的在前。**执行时不按家庭过滤**（`_run` 按 `did` 全家庭找）：
家庭只决定界面上能选哪些，把音箱换到别的家庭，老规则照样能喊。

**设备不在了**（被移除 / 换了家庭）：这一行仍回显原来的名字（tooltip 说明"可能被移除或
换了家庭"），功能下拉退回整个白名单，保存**不拦**——执行时 `_run` 才报「找不到设备「X」
（可能已从家庭移除）」并停下整串。

**旧数据不留兼容**（11-14 用户定，本机只有一条测试规则）：`Action.from_dict` 只认
`device_action` / `delay`，旧的 `virtual_event` / `speaker` 那一条**读不回来**（规则本体
还在，用户重选一次）。一次性平移用 `scripts/migrate_actions_v4.py`：跑前把 `rules.json`
复制成 `.bak-<时间戳>`，认不出的动作原样留着并报出来，**不进程序**。

- **① 一枚「＋ 添加触发」、③ 两枚「＋ 选择设备 / ＋ 延迟」**（11-13 第八条 → 11-14 重构）：
  ① 的按钮以前叫「＋ 添加动作」（跟着 ③ 的旧名字），现在叫「＋ 添加触发」——它加的是
  触发，不是动作。③ 的两枚入口分别对应"对某台设备做一件事"和"等一会"，点「选择设备」
  先弹窗、点「延迟」直接加一行（默认 1 秒）。
  - ① 的触发行仍落在**空档「-」**上（`TriggerRow.kind` 第一项 `data == ""`，为以后增加
    其它触发源留位置）。**空串 = 还没选，不是"类型写错了"**：`validate_rule` 说「触发 N
    还没选触发方式」，真正写错的非空未知类型才说「触发方式未知」——两句话别混。
  - **缺失类红字点保存才亮**（`reveal_missing()`）：① 的空类型、③ 的「要先选设备 /
    要先选功能 / 要填文字」都走这条，刚点按钮就一片红等于边让人挑边骂人。**填法类**
    （超长、脏字符、整数 / 位数、超上限）例外，边打边说——用户正在敲那个值。
  - **core 层也必须拦**：`Action.to_dict()` 对空 / 未知类型会写成 `device_action`，而
    `from_dict()` 读不回来——放过去等于用户存了个空行、回来变成另一种动作。

- **② 的行内红字（11-13 用户第九条：②也改成行内红字）**：`ConditionRow` 也有
  `hint`（`QLabel#Warn`，夹在程序名与 × 之间），和 ③ 一个长相——标题下那句
  「红字长在动作行右侧」对 ② 同样成立。三条规矩：
  - **判据必须和 `rules.validate_rule` 的条件那一段逐条对齐**，顺序也一样
    （空类型 → 空参数 → 数字 / 「是」「否」/ ac|battery → 缺程序名）；漏一条就会出现
    "行内没红字、点保存却在底部报错"这种最让人困惑的组合。
  - 空档那条「要先选条件类型」和 ③ 同规矩：**点保存才亮**（`reveal_missing()`）。
    其余几条（「要填参数」等）选了类型就立刻亮——参数本来就是必填，不存在"边挑边骂"。
  - `_save` 现在把 `[*_cond_rows, *_action_rows]` 合成一张**从上到下**的表找第一处
    出错，`_reveal_row()` 调各行的 `focus_widget()`：空档给类型下拉、缺程序名给程序名
    那格、其余给输入框。别再在 `_save` 里各写一套 `getattr(row, "value_edit")`。
  - 顺手修的：比较符下拉以前**没接信号**，改「≥ / ≤」「是 / 不是」既不刷新红字也不
    标脏（关窗不提示未保存），现在接 `_on_text`。

- **延迟合并回一个选项**（11-13 用户第一条）：以前是「＋ 延迟（毫秒）」/「＋ 延迟（秒）」
  两枚按钮 + `delay_s` 伪类型，现在只有一枚（即上面那枚「＋ 添加动作」加出来再选
  「延迟」），刻度由行内第二格选。
  `ACTION_TYPES` 里就是三档（`virtual_event / delay / speaker`），**不许再出现
  `delay_s` 这种伪类型**（`verify_automation_rules.py` 钉着这条）。
  - 语义永远是 `ms`：校验、落盘、引擎执行全按毫秒；秒档只是在输入框里
    ×1000 / ÷1000（`_delay_ms` / `_delay_text`），`Action.unit` 只记「这次用哪把
    尺子」，**只有秒档落盘才写 `"unit": "s"`**——毫秒是默认值，旧 `rules.json`
    一个字节都不变，旧版本读到 `unit` 也只会忽略。
  - 秒档支持小数，但**最多 3 位**、毫秒档**只收整数**（用户 11-13 逐条问过精度）：
    执行精度就是 1 ms，`1.234` 秒 = 1234 ms 存得下，第 4 位存不下。超出**报错**，
    不做静默四舍五入——填 `1.2345` 却被存成 `1.235` 是没道理的。
  - **填法 + 范围都在 UI 层判**（`ActionRow.error_text()`），`_save` 里**排在
    `validate_rule` 之前**：core 只拿到毫秒，看不出用户敲的是 `1.5 秒` 还是
    `1500 毫秒`，混进 `validate_rule` 只会得到"要在 0–600000 毫秒之间"这种答非所问。
    顺序是先具体后笼统：填法（整数 / 位数）→ 空值 → 范围。
  - **红字长在动作行右侧，不在底部**（用户 11-13 第六条）：照①「注册状态：…」
    的样子，`hint`（`QLabel#Warn`）排在输入框与 ↑ 之间，`textChanged` 就刷，
    边打边判。命中坏行时 `_save` **不写底部 `error_label`、也不弹 notice**——
    红字已经在眼前，再在下面重复一遍是噪音；只 `_reveal_row()` 把出错行滚进
    视野、焦点交回输入框。③ 动作一多，出错那行很可能正好在滚动区外面，
    **红字是唯一提示，看不见就等于没提示**（验证脚本专门造了 9 行动作的窄窗）。
  - 红字文案是短的（「只能填整数」「最多 3 位小数」「要填延迟时间」「不能小于 0」
    「不能超过 600 秒 / 600000 毫秒」），来龙去脉挂 tooltip（`_HINT_TIPS`）：
    长句会把输入框挤窄，而行内提示的宽度是从输入框那里抢的。
  - 红字色 `_error_color(p)`：色相只认主题那支 `DANGER`（"界面里只允许一种红"），
    但同一支红在浅底 / 深底上只有 ~3.9:1，11px 小字读着吃力 → 浅色压深 16%、
    深色提亮 24%，两边都过 4.5:1（`verify_automation_ui.py` 钉着这条）。
  - **毫秒 ↔ 秒切换只换算不重置**：切档时把 `2000` 变成 `2`，不会把用户刚填的值
    打回默认；`ActionRow._kind` 记住上一档，只有「事件 ↔ 延迟」这种量纲不同的
    切换才清空。这是 `_kind_changed` 里唯一一处非对称逻辑，别顺手"统一"掉。
  - 重开编辑页要还是原来那档（否则填「30 秒」的人下次看到 `30000` 会以为值被改了），
    所以 `unit` 才值得落盘——`_fill_form` → `ActionRow.__init__` 靠它选下拉档。
  - 越界也走行内：秒档说「不能超过 600 秒」、毫秒档说「不能超过 600000 毫秒」，
    用户不用自己换算；底部那条 `0–600000 毫秒（600 秒）` 只在 `validate_rule`
    兜底时才可能出现。
- **「执行文本指令」就是米家 App 里的那个名字**（11-14 改名）：以前叫「发音箱指令」，
  是内部造词；同一件事在米家设备页叫「执行文本指令」（`execute-text-directive`），
  界面上跟着它，用户不用在两套叫法之间对照。行结构仍是
  `[设备] [执行文本指令] [静默 v] [文本输入框]`，与顶栏指令条同一套三格。
  - `Action.did` 是执行用的真相，`Action.device` 只是**显示名快照**（日志 / 回显）：
    设备改名、甚至换到别的家庭，执行仍按 `did` 找，不会因为名字变了就发不出去。
  - 静默 `boolean` 默认 `false` 时**不写进 `args`**（`{text-content}`），`from_dict`
    只认 `is True`，写「是」/`1` 一律当不静默。
  - 「至少一条设备动作」：只有延迟仍然过不了校验——「按键 → 让音箱说句话」本身是条
    完整规则（`validate_rule` 数的是 `action == "device_action"`，不再数具体类型）。
  - 文本上限 200 字符（`speaker.MAX_CHARS`，与米家「自定义指令」页一致），清洗在
    `action_catalog.clean_values` → `core/speaker.py`，编辑页只管收文本。
- **顶栏指令条与编辑页各用一份候选**（11-14 起不再共用）：顶栏只列**音箱**
  （`speaker.collect_home`，比显示名 `node.home`），编辑页要的是"能干活的设备"，
  中枢与音箱混在一列（`action_catalog.collect`，比 id `node.home_id`）。强行共用只会
  让顶栏混进中枢网关，或者让编辑页漏掉中枢。两边都**只影响界面上能选哪些**，
  执行一律按 `did` 全家庭找。
- **③动作行右侧的 ×↑↓ 曾经根本看不见（用户截图报的）**：根因是套用了
  `QPushButton#Tool`，那个样式有 `padding: 6px 14px`（左右共 28px），而按钮被压到
  26px 宽 —— 文字整个被内边距挤出可视区，深色下只剩一块和卡片近色的灰方块。
  现在统一走 `_icon_button()` → `QPushButton#IconTool`：**padding: 0**、固定 30×30、
  明显底 + 1px 描边、hover accent、disabled 变淡，且都带 `setToolTip` /
  `setAccessibleName`。条件行的 × 同样处理。
- **换功能要清掉不适用的值**（`_feature_changed`）：功能下拉一变就清空文本，否则
  「执行文本指令」切到「唤醒」再切回来，看到的还是上次那句话，像自动填的。构造期用
  `ActionRow._loading` 挡住 `setCurrentIndex` 触发的回调，否则会把刚回填的值清掉。
  单位下拉那条相反——`_unit_changed` **只换算不重置**（`2000` ⇄ `2` 是同一个量）。
- **一行的格子按「功能的参数表」显隐**（`_sync_columns()`）：不再按"三种动作类型"写死
  三套布局，而是看 `Feature.params` 里有没有 `bool` / `text` 参数：
  - 有 `bool`（静默）→ 显示静默下拉，标签取自参数元数据（`_SILENT_LABELS`），
    默认按入参名进 `Action.args`；
  - 有 `text` → 显示输入框，placeholder 按功能给（事件名 / 要念的话 / 要说的话）；
  - 一个参数都没有（唤醒）→ 输入框与静默**一起收掉**，改用占位控件顶住右半边。
  隐藏的控件在 `QHBoxLayout` 里不占位置；宽度都写死（`Combo` 定宽、输入框
  `QSizePolicy` 可伸缩），换档时整行只重排不跳高。
- **边界箭头禁用 + tooltip**：`_renumber()` 每行调 `set_move_enabled(up, down)`，
  增删 / 调序后都会重算，不再"点了没反应"。
- **文本的输入规范和顶栏那条是同一套**（用户 11-13 第三轮问「编辑页那个输入栏有
  没有做检验」）。共用 `core/speaker.py`，只有"报错时机"不同——顶栏是即时发送，编辑页
  要存盘。三条判据都**从功能元数据取数**（`param.max_chars` / `param.whitelist`），
  别再在这里写死 200：
  - **白名单**：只收中英文、数字、空格与「，。？！」。`format_error()` 里调
    `speaker.clean(text).dropped`，非空就红字「含 N 个发不出的字符」，tooltip 把**具体
    是哪几个字**列出来。不拦的话，规则存进去就是脏的，执行时服务层会悄悄清洗掉，
    用户只会发现"音箱少念了几个字"。**事件名不走白名单**（用户自定义串）。
  - **长度**：超上限报**差额**「多了 N 个字」，tooltip 写上限与当前字数。这里**故意
    不静默截断**：顶栏没有"存下来再说"的机会，截断 + toast 是对的；编辑页要落盘，
    悄悄砍掉尾巴等于替用户决定删哪一句，报差额让他自己删。
  - **空**：「要填{参数名}」。三条都拦保存（`_save` 判 `error_text()`），和延迟那几种
    同级——红字就在输入框右边，改完就能存。
  - 带数字的两句没法预置进 `_HINT_TIPS`，所以 tooltip 走 `ActionRow._hint_tip()`
    现拼；静态表里只留不带数字的条目，别把上限又抄一份进去。
- **格子窄、弹出层宽，两件事分开算**：③一行四格，单位那格 80px、静默那格 88px，
  写「毫秒」「不静默」进去控件里刚够，可 `QComboBox` 的弹出层默认跟着控件同宽，
  列表里就只能显示「…」和「不…」（用户 11-13 第二轮报）。修在 `ui/combo.py`：
  `showPopup` 里按最长一项把 container 和 view 一起 `setFixedWidth` 撑开（上限
  `POPUP_MAX_EXTRA=220`、且不出屏幕），再按新宽度对右边缘。**不能只 `resize`**——
  view 的 `minimumSizeHint` 是 `sizeHintForColumn` 算的，container 的布局随后会把
  它顶回去（超长项时能一直撑到整屏宽）；也不能只改 `minimumWidth`，container 的宽度
  是 Qt 在 `showPopup` 里直接 `setGeometry` 的，根本不问 view。
- **规则按家庭隔离**（用户 11-13 第二轮，第三轮改成 id，第四轮去掉改家庭的入口）：
  `Rule.home` 记规则归属的云端**家庭 id**，列表 / 回收站 / 日志的规则下拉都只显示
  **当前家庭**那几条——1103 家庭里看不到共享家庭建的规则。显示文案一律用
  `service.home_label(id)` 换成 `display_name`，内部匹配不再经过名字。五条不能反的
  约定：
  - **归属在创建时固定，界面上只读**（一个 `QLabel`，不是下拉）。在哪个家庭的自动化
    页面创建就属于哪个家庭，编辑时也不能改：改了家庭，③ 里已经选好的设备还留在旧
    家庭，执行逻辑不成立。要"搬"规则只能新建。
  - `home == ""` = **开发中间态**（v1 `rules.json` 按名字存的老数据）。列表里照样
    能看到，卡片标「未指定家庭 · 保存后归入当前家庭」；打开编辑窗时按**当前家庭**
    固定，保存即落盘。在那之前 `enabled_keys()` / `rules_for()` 会显式跳过它——
    **不注册热键、不触发**，不能静默按某个家庭执行。
  - `rules.json` 升到 **v2**：读到 v1（或没有版本号）时只把 `home` 置空，规则本身
    （名称 / 键位 / 条件 / 动作 / 启停 / 冷静期）全部保留；不做名字→id 映射，
    也不再有 `RuleSet.claim()` / `AutomationService.adopt_home()` 这类一次性认领。
  - **热键与引擎不按"当前家庭"过滤**（`active()` / `rules_for()` 不传 home）：**用户
    11-13 第三轮已经拍板**——"切家庭后只是自动化页面不显示原家庭的自动化，但不是
    不启用了"。热键是这台电脑的系统资源，被自动化的也是这台电脑，切到别的家庭去看
    设备不该让快捷键失灵；家庭只决定"在哪个页面能看到和改"。**别顺手给它加上按
    当前家庭过滤**：那会让"换个家庭看一眼"变成"悄悄停掉自动化"。空归属的规则是
    唯一例外（见上一条）。
  - 顶栏指令条的候选仍按**显示名**（`speaker.collect_home` 的用户可见语义）；编辑页
    那份候选（`action_catalog.collect`）一律比 id，见上面「家庭筛选按 id」。
- **不再要求"家庭有中枢网关"**（11-14 去掉了这道拦）：以前③ 里选「发虚拟事件」要看
  `Store.home_has_hub()` 的结论、没中枢就禁输入框 + 红字，`ActionRow` 还得接
  `hub_ready` / `hubs` 两个入参。现在中枢只是"选择设备窗里的一台设备"——家庭里没有
  中枢，选择设备窗里自然没有可选项，点完「＋ 选择设备」看到空态就知道缺什么，比在
  行内骂一句「该家庭缺少中枢网关」更直接。`Store.home_has_hub` 随之删除（判据留在
  极客版入口那一侧：`geek.supports` + `geek_ability.json`，不另维护型号名单）。
  - 代价是"选中枢"不再校验它**现在**还有没有极客版能力：设备支持到一半的固件升级、
    或者选了台本来就没中枢能力的网关，要到执行时才报错。这条接受——设备能力本来
    就是按 action 名现查的（`miot_action`），查不到就是「找不到这个功能」，
    界面提前拦一遍等于把同一份判断抄两处。
- **注册状态颜色**（用户 11-13 第十一条）：`已注册` 才用绿色（`#Ok`）；未注册 / 被占用 /
  不支持一律用主文字色（`#RegOff`，深色主题下就是白），不再默认绿——绿只代表"系统里
  真的注册好了"。另一个启用规则用了同一组合时仍用 `#Warn` 并附一句占用者名字。
- **底栏不再有「中枢：… 云端返回 code 0…」说明**（用户 11-13 第十二条）：`code 0` 只
  代表云端收下 action，极客版本地规则是否执行无从确认——这句写进了 `Service._emit`
  的注释；界面上只留错误条与按钮，窗口高度不变。
- **③ 的 ↑ / ↓ 永不置灰**（用户 11-13 第十二条）：第一行按 ↑、最后一行按 ↓ 顺序不变，
  三枚图标按钮在任何时候都可点、样式一致；tooltip 说明"已经是第一条 / 最后一条，按了
  也不会动"。`_move_action()` 本来就在边界 no-op。
- **归属家庭不再挂说明小字**（用户 11-13 第十三条）：只留标题 + 值，tooltip 保留
  「规则归属于创建时所在的家庭，不能修改」。
- **①块降密度**：注册状态并进「键盘快捷键」行右侧（省一行），「或手动选键」默认
  折叠成 `#Disclosure`（再省一行），段距 `col.setSpacing(12)` + 标题上下留白，
  三段用编号徽章与语义竖条分开。省下的高度正好抵消段距，③三行动作仍一屏可见。
- 标题栏副标题接 `name_edit.textChanged` 实时同步，别停在构造时的旧规则名。
- **固定底栏不能进 `QScrollArea`**；固定区要薄（`error_label` 空时隐藏），否则③动作块
  被挤掉。窗口 `860 × fit_height(900)`。
- 构造期信号早连会崩：`Combo.addItem` 会发 `currentIndexChanged`，此时同行其它
  控件还没建好。所有 `Combo` 填充一律 `QSignalBlocker`，信号连接放到**全部控件
  创建之后**；`_set_manual_from_keys()` 也要挡住回填触发的 `stateChanged`。
  `clicked` / `textChanged` / `currentIndexChanged` 接的无参槽统一写 `*_args`。
- 录制态 `reject()` 只取消录制；`dirty` 时关窗弹「保存并关闭 / 直接关闭」。
  新建草稿没点保存不会 `add` 进 `RuleSet`，直接取消不落盘。
